## 0. 对齐结论(一句话)

**BW 的五阶段方法论(闭环回流)回答「为什么做、现在在哪、健不健康」;multica 式 Issue 层回答「这件活谁接、跑到哪了」;两者经同一组真实记账(队友战绩、产物登记、技能的蒸馏与使用数)汇进同一条度量派生链——这就是有机结合,不是两个面板并排摆放。**

(十实体与度量派生链各自的代码载体,见 §10-2。)

**一套账,两个入口**(有机结合的技术核心):账目只有一套——队友战绩、产物登记、技能使用数;但有两个时刻会记账:一个**工作流运行落定**时(手动跑、到期自动跑、被活触发跑,都算),一件**活被人点「完成」**时。两个入口口径一致,并且共同遵守:同一件事绝不记两次;重复点「完成」不重计;弃掉的活不记账(弃活不能当队友表现的证据)。两个入口各记哪些字段、分别被哪条测试锁死,见 §10-2。

复利闭环:**做完的活 → 蒸馏成带正文的技能(记着来自哪件活)→ 下一次运行把正文真实带给队友 → 该技能使用数 +1**——multica 的「经验沉淀」接上了 BW 的「技能可执行」,沉淀物不是死卡片。

## 4. 分层职责(为什么两者缺一不可)

- **五阶段方法论(BW 独有)**:阶段=角色=方法论(核心问题/方法循环/完成清单/常见反模式),回答「这段该做什么性质的工作、做到什么算完、什么信号该警觉」。没有它,看板只是一张待办清单,「构建段该做什么」没有答案(multica 的空白)。
- **Issue 层(multica 借鉴)**:阶段里的实际工作拆成可指派的单元,派给真实 AI 队友,沿状态机推进。没有它,五阶段就是空转的仪表盘——「活」没有落点(BW 此前的空白)。
- **记账与派生链(BW 独有,两者的汇合点)**:干了活必留痕(战绩/产物/使用数),痕迹只进只追加的观测,信号只能从观测推导。**度量诚实是焊缝本身**:队友干活(multica 语义)必然变成证据(BW 语义),两个世界在此不可分。

## 6. 实跑纪律(「一切实跑」在本仓库的操作定义)

1. 演示数字一律从演示数据库/工作区读回,报告不代答。

## 7. 融合未补全清单(2026-07-15 复盘 · 以融合命题为尺)

> 尺子 = §0 的命题:「队友干活(multica)**必然**变成证据与信号(BW)」。逐条问:断在哪、为什么算断、补法是什么。✅=本轮已修,其余入 §8 队列。
>
> 本节的 A–H 是断链的节内编号,只在本节使用,**与 §8 的 A0-A5 队列代号无关**;各条补法的工程细节见 §10-7。

| # | 断链 | 为什么算断 | 补法(设计决定) |
|---|---|---|---|
| A | **活可指派、不可开工**——指派了队友,队友并不动工;工作流的运行与活是两个并行世界,只在记账处汇合,「指派→干活」这个正向缺失 | multica 的核心是「指派即开工」;BW 当时的「完成」靠人或外部编排推,应用内的队友从不因被指派而干活 | 新增「一键开工」命令:把活的标题与描述、该阶段角色的开场指令、最相关的蒸馏技能拼成一份完整提示词交给队友,走既有运行同一条链路;起跑推「进行中」,成功推「评审中」(**队友提议、人确认「完成」**——「做到什么算完」仍由人裁决,完成时的记账不变);失败如实留在「进行中」并发事件。演示路径先行自检,网关恢复即全真 |
| B | ~~完成→重开→再完成会记两次账~~ | 公开命令面可达(桌面只给前进,但接口/未来界面能倒退);一件活两份账=假度量 | ✅ 已修(R4:一次性入账的持久标记,见 §10-5) |
| C | **活 ↔ 运行/产物没有数据关联**——「这件活跑到哪、产出什么」在活的卡片上答不出 | multica 的活挂着执行流水与 PR;BW 的活详情无从聚合 | 运行记录与产物记录各补一个「属于哪件活」的归属;开工与点「完成」时写入;活详情 = 它的运行 + 产物 |
| D | **度量派生链吃不到活(最底层断供)**——§0 说「信号从真实结果派生」,实际点「完成」只记账不落观测,阶段信号对看板全盲 | 这是命题级违约:五阶段方法论的健康度看不见活的吞吐 | 点「完成」时给「阶段完成件数」类指标追加机器来源的观测,值变才追加;**没设目标则信号诚实「未知」**,绝不因喂数变绿 |
| E | **交棒对没做完的活视而不见**——阶段交棒时该段还有未完的活,交棒记录可以只字不提 | BW 自己的诚实纪律(带险交棒留痕)没吃到活的数据 | 交棒时统计该段未完的活:大于 0 则强制标「带险」,并在交棒记录自动写明「留 N 件未完」;不阻止交棒(人有权冒险),只不许无痕 |
| F | **状态机没有合法性守卫;「阻塞」不带原因** | 状态转移当时接受任意跳转(「已取消→已完成」也行);阻塞不记原因=不可行动 | 应用层立合法转移表(前进/重开/阻塞往返/取消,拒绝无意义跳转);转「阻塞」必填原因 |
| G | **Autopilot 缺位**(定时任务→自动建活) | multica 有此模式;BW 调度器已真,只差建活一步 | 规格已冻结在交接件(见 §10-7) |
| H | **看板交互半身**——卡片只有「前进」;不能在界面上指派、不能带原因阻塞 | 可指派工作台的「指派」动作反而要走无界面通道 | 卡片加指派下拉(五角色)+ 带原因的阻塞;**倒退/重开故意不给界面**(接口层有一次性入账兜底) |

**定位性留白(不补,防蔓延)**:Squad、多 CLI provider、云 runtime/WebSocket、甘特/泳道、Inbox——multica 的多人/分布式面,与 BW 单人桌面定位相斥(论证见 `docs/archive/iterations/V2-DESIGN.md` §2.3)。

## 8. 修订执行队列(v3 · 两轨,接棒照此走)

> v3 修订理由:v2 把 Autopilot 排在「一键开工」前——**自动建活在「活还没法真的开工」时上线,只会自动堆积待办**。执行顺序改为「先让一件活端到端跑通,再自动化创建」。条目代号(A0-A5,对齐后的执行队列编号)不变,按下面顺序执行。

**即时可全真轨**(不等任何外部),执行顺序 **A2 → A3 → A0 → A4 → A1 → A5**(逐条工程细节见 §10-8):

1. **A2 · 关联列**(小,半日):给运行与产物记录补上「属于哪件活」的归属。
2. **A3 · 「一键开工」的结构**(1-1.5 天):指派后真的动工这条正向通路 + 演示路径自检。**两个此前未定的设计点,现写死**:
   - **技能注入选择规则**:只取本项目内蒸馏出来的技能,同阶段优先、按蒸馏时间从新到旧,**上限 3 条**,经既有注入通道带给队友(超限如实截断并记事件)。
   - **人确认「完成」**:运行成功只推到「评审中」;「完成」必须由既有的显式转移命令触发(界面按钮/命令),**绝不自动**。确认者身份本轮不建模,列为留口——但「评审中→完成」必须来自命令面而非记账内部,这一点用测试锁死。
3. **A0 · 复利闭环端到端测试**(30 分钟,可与 A3 同步):蒸馏技能 → 后续运行注入给队友的提示词里真有它的正文 → 该技能使用数 +1,一条链锁死(现在就能写,不依赖 A3)。
4. **A4 · 断链 D+E 点灯**(1 天):活的观测喂入 + 交棒未完检查。**前置漏洞,现写死**:「阶段完成件数」指标此前并不存在,观测无家可归——**创建完成时起,为每阶段播种一条机器喂养的引领指标**(名称常量化;目标留空=信号诚实「未知」,用户设目标后才可能变绿);存量项目在应用启动时补种(幂等)。点「完成」时按「值变才追加」的守卫追加观测。
5. **A1 · Autopilot 自动建活**(半天,规格已冻结):此时自动建出的已是「能一键开工的活」。
6. **A5 · 断链 F+H**(1 天):转移守卫 / 阻塞必填原因 / 看板指派;项目墙卡片顺手带「开放的活」计数。

**等外部轨**(用户动作后立即接):
