MVP(V4)版本：
## 愿景：
1、规范 = 所有项目都长一样，多个项目资产更容易沉淀挖掘更多价值； 知识管理 = 项目所有知识都在项目代码仓，大模型皆可见。
2、从开发变成小项目(三个月周期)的Builder, 原型、构建、优化、维护、运营, 超级个体不仅角色从「自己写代码」换成「1 个 Builder + Agent Loop」, 也基于buddy完整项目交付质量的把控。
3、一张工作台,内嵌Open Design、Claude CLI、聊天组件等，一切按照buddy规范在一个工作台驱动复用多个成熟组件\插件完成，不仅仅提供的是Skill、Agent、workflow，也提供的是好用的工具组件。

## 项目MVP过程： 
观测项目总览 -> 更新指标 -> 制定计划，录入issue -> 执行(原型可以走open design + XXskill、构建可以走Claude Cli + grillme) ->验证闭环发版本 ->下周一继续回到项目总览

## 基于V3版本需要优化：
1、项目总览缺少信息, 我们期望能从总览观测到项目是否health。 当前仅有指标，需要完善，而完善的前提实际上依赖我们给项目带来的愿景1 规范\知识管理 是什么样子。
2、从项目MVP流程来看，指标看不到本周具体制定的计划，计划落地也就是一个个需求issue，多个issue归属于某一周，某一个版本乃至某一个里程碑节点。
3、页面元素太复杂,buddy是个高high level的项目，随着v1\v2\v3落地，但是大量的界面元素、设计当前是没有实践落地的，并且没有明确规划，可能与最新的MVP不符合，基于设计新的原型，那么需要大胆删除。
example1: 五阶段核心是agent, 界面当前好比优化、运营推广、运维都可以删掉，后续根据agent实际运用落地情况填充视图。而原型和构建也可以删掉，本质上实际上是issue用的时候用open design + xxagent +xxskill进行原型设计，有的时候是用claude cli + grillme完成需求开发，也就是说issue绑上客户端程序和agent\skill即可。
example2：侧边栏Op默认展示出来无太多价值、Hub图标不清晰等；业界buddy是项目总览、计划、issue、资产等,亦或是项目总览、计划(指标 -> 周目标 ->issue)、会话、配置(skill、agent、connector)、项目空间(规范)等,具体以最新愿景和项目MVP过程来看。
example3: 找指标和绑数据可以合二为一为更新指标；增加项目信息更新；两个issue按周定时执行

## 瞄准的组内codehub两类项目：
建木（新建）、运维看板（成熟）、benchmark（成熟）、bridge（新建）

## 其它
1、前后的对比性，也就是要回答为什么要在buddy上运作项目
2、规范是资产，是严选的，可拔插的
3、默认的skill、workflow等也是严选的，可拔插的
4、V1\V2\V3实践后，V3在组内使用收集真实诉求，现在需要出MVP版本来对外发布。
