# docs/plan/ 是什么

<!-- 30 秒导读:说明 docs/plan/ 这个目录本身的用途和文件规则,给接手看这
     个项目的人、以及任何要往这个目录读写文件的 agent 看。现在作数——这

`docs/plan/` 下一个文件对应一个 ISO 周,文件名固定 `YYYY-Www.md`(比如
`2026-W34.md`)。每一份周文件都是那一周计划的**唯一正本**——本周目标是
什么、排了哪些活、指标读数如何、运作活跑了什么,全在这一份文件里;改这份
文件就是在改这一周的计划本身,不是改一份摘要或索引。

这个目录**没有数据库索引**:周列表靠直接扫这个目录得到,不存在另一张表
专门记录"这个项目有哪些周"。要看某一周的计划,直接打开对应文件名的那一
份就是全部信息。

## 历史周与本周是同一回事

项目接入 buddy 时回填出来的历史周文件,和人手写的本周文件是**同一套格
式**,放在同一个目录里,不单独分区、不另建 `history.md` 之类的旁路文件。
两者只靠 front matter 的 `origin` 字段区分:

- `origin: human` —— 人在当周写的正常计划。
- `origin: backfill` —— 项目接入 buddy 时,从 git 历史、仓内已有文档、远
  端 issue/MR 记录里回填出来的历史周,只用来解释过去发生了什么,不代表
  当时真的按这套流程走过。

## front matter

每份周文件顶部是一段 YAML front matter:

```yaml
---
week: 2026-W34
origin: human
---
```

- `week` —— 这份文件对应的 ISO 周,必须和文件名一致。
- `origin` —— `human` 或 `backfill`,含义见上一节。

## 段落结构

一份周文件按顺序包含:周目标、业务活清单、本周指标读数、本周运作、上周
完成情况。历史回填的周文件用同一套段落结构,某一段确实没有对应内容时如
实写"未发现",不倒推、不编数据凑数。完整的字段样例见同目录的
`WEEK.md.tmpl`。
