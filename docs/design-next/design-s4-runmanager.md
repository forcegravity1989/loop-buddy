# 切片四 · 并行运行设计稿(运行管理器 + 五竞态验收,可开工粒度)

> **30 秒导读**:这份稿子给切片四的实现者和验收者看,写于 2026-08-10,现在作数。它落实 `plan/23-opc-stitching-rebuild.md` §5.2 的「运行管理器」条与 §7 切片四的验收条目:把「一件活怎么开工、怎么取消、结束怎么回写、重启后遗留怎么如实收拾」这四件事收进一个口,并用一个不依赖网关的指挥器把五个撞车场景确定性地跑出来、用 SQL 读回核对。

## 1. 编排层落点:本片立 `bw-app`

### 1.1 推荐与理由

```
bw-core     领域内核(零 IO、wasm 可编译)
   ↑                    ↑
bw-connector         bw-store        存储(SQLite;只认 bw-core 的类型)
   ↑                    ↑
   └──────  bw-app  ────┘            编排:运行管理器住这里
   
bw-engine   引擎(PTY / 采证 / 指标正本 / agentcli 层)—— **bw-app 不依赖它**
```

三条理由,按分量排:

1. **它要写库,还要判状态机**。运行管理器开工时要把活推到「进行中」(要查合法转移表)、结束时要写运行行、重启时要把遗留运行标成如实的「不知道怎么结束的」。这是编排层的活;引擎的定义是「对外能力的实现方」,让它写库等于把两层职责揉回一起,正是 plan/23 §1 要躲开的旧工程结构病。
2. **守卫脚本已经在等这个目录**。`scripts/guard-no-direct-process.sh` 的待查清单里写着 `next/crates/bw-app/src`,目录不存在时打一行「尚不存在,跳过」。这个目录一建出来,「编排层不准出现直接进程调用」这条守卫**自动生效,不用改脚本**——脚本注释里就是这么预告的。反过来说:把运行管理器放进 `bw-engine`,它落在守卫覆盖之外(引擎起进程是设计如此),这条铁律就静悄悄地失去了看守。
3. **切片三设计稿已经定过档**(§1.1 末段):「编排层(切片四建的 `bw-app`)只依赖 `bw-connector`,不依赖 `bw-engine`;它拿到的是注册表里的活体连接器,谁把 agentcli 适配器塞进去是组装处的事」。本片照办,并把那份稿子建议的清单检查真正加上(见 §8)。

### 1.2 一条必须守住的边:`bw-app` 的正式依赖里没有 `bw-engine`

这条是 PTY 那堆原生依赖渗不进编排层的唯一保障。落地形态:

- `bw-app/Cargo.toml` 的 `[dependencies]` 只有 `bw-core`(带 `idgen` 特性,编排层要生成新编号)、`bw-connector`、`bw-store`、`tokio`、`time`、`thiserror`;
- `[dev-dependencies]` 里**允许**出现 `bw-engine`——「真实并行三件」那一档要在指挥器里把真的 claude 执行连接器组装进注册表,而 dev 依赖不进入库本身的依赖图;
- 门禁脚本因此必须**只查 `[dependencies]` 那一节**,不能全文 grep,否则会把合法的 dev 依赖误判成违规(脚本形态见 §8)。

### 1.3 顺带:`bw-store` 为什么也现在立,而不是内嵌进 `bw-app`

放在 §2.1 一并说——两件事的判据是同一条。

## 2. 最小存储

### 2.1 立 crate,不内嵌

切片四的验收要用 `sqlite3` 读回「十件互不覆盖、各自只结算一次」,所以必须有一个真数据库。问题只是这段代码住哪。

推荐**独立 crate**,三条理由:

1. **crate 边界是「存储不长业务判断」唯一守得住的形态**。`bw-store` 只依赖 `bw-core`,不依赖 `bw-connector`——它因此**在编译期就看不见** `ExecState` / `ExecTicket` / 协议版本这些东西,想在存储层写一句「如果执行状态是 X 就把活推到 Y」都写不出来。内嵌进 `bw-app` 的话,这道墙就只剩纪律。
2. **迁移双守卫需要一个家**。plan/23 §5.3 的器官移植清单把「迁移双守卫模式」指向「新存储层」;不立这个 crate,这个器官没地方落。
3. **晚立的成本是搬第二次**。切片五要加观测 / 交棒 / 风险 / 决策这些事实表,那时必然要独立;现在立的成本是一份 manifest 加一行门禁。

按 plan/23 §5.1 的教训(旧工程一个 trait 九十八个方法),接口**按聚合拆**:本片只有两条 trait——管活的和管运行的。加新聚合是加第三条 trait,不是往老的上面堆方法。

### 2.2 三张表,不多不少

新库的 schema 只放本片真有写入方的东西。观测 / 交棒 / 风险 / 决策等事实表**本片不建**——没有写入方的表就是假表,建了只会在切片五被重做一遍。

```sql
-- 项目:本片只需要「有这么个项目、它的本地检出在哪」。
CREATE TABLE IF NOT EXISTS project (
    id          TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    root_path   TEXT NOT NULL DEFAULT '',      -- 本地 git 检出根;空 = 未配置
    created_at  INTEGER NOT NULL
);

-- 活:砍到只剩运行管理器真读真写的字段。
-- 砍掉的(阶段、远端编号、MR 号、描述、优先级、指派、阻塞原因、标配技能)
-- 全部留给切片五,那时用 add_column_if_missing 加回来 —— 那正好是双守卫的
-- 第一次真实使用,而不是为了演示而演示。
CREATE TABLE IF NOT EXISTS issue (
    id          TEXT PRIMARY KEY,
    project_id  TEXT NOT NULL REFERENCES project(id),
    number      INTEGER NOT NULL,              -- 项目内序号 1,2,3…
    title       TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'backlog',
    settled_at  INTEGER,                       -- 首次 …→已完成 的时刻;NULL = 从未结算
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_issue_project_number ON issue(project_id, number);

-- 运行:本片的主角。
CREATE TABLE IF NOT EXISTS run (
    id                TEXT PRIMARY KEY,
    project_id        TEXT NOT NULL REFERENCES project(id),
    issue_id          TEXT NOT NULL REFERENCES issue(id),
    -- 'delivery' | 'consultation'。降级为咨询 = 这一列翻面(见 §3.5)。
    kind              TEXT NOT NULL DEFAULT 'delivery',
    connector_name    TEXT NOT NULL,           -- 哪条执行连接器跑的
    req_id            TEXT NOT NULL,           -- 连接器那次调用的请求编号(证据链要能对上)
    upstream_session  TEXT NOT NULL DEFAULT '',-- 上游会话号;空 = 这家不能指派/还没拿到
    workspace         TEXT NOT NULL,
    branch            TEXT NOT NULL,
    -- starting | running | finished | canceled | orphaned | failed
    state             TEXT NOT NULL,
    -- process_exit | stopped_by_bw | contact_lost | canceled | start_failed
    -- NULL = 如实不知道(重启遗留的运行就是 NULL,绝不填一个猜的)
    end_kind          TEXT,
    end_detail        TEXT NOT NULL DEFAULT '',-- 上游原话或诊断原文,不放 BW 编的结论
    started_at        INTEGER NOT NULL,
    ended_at          INTEGER,                 -- BW 不再把它当活的那一刻
    settled_at        INTEGER,                 -- 这次运行的账结过了(至多一次)
    demoted_at        INTEGER                  -- 降级为咨询的时刻
);

-- 铁律进存储:一件活至多一个「还活着的交付运行」。第二个插不进去,
-- 不是被 if 拦住,是数据库根本不收。降级为咨询(kind 翻面)与结束
-- (ended_at 落值)都会让这一行退出索引谓词,名额自然释放。
CREATE UNIQUE INDEX IF NOT EXISTS uq_run_live_delivery_per_issue
    ON run(issue_id) WHERE ended_at IS NULL AND kind = 'delivery';

CREATE INDEX IF NOT EXISTS idx_run_project_started ON run(project_id, started_at DESC);
CREATE INDEX IF NOT EXISTS idx_run_open ON run(issue_id) WHERE ended_at IS NULL;
```

**`ended_at` 与 `settled_at` 为什么是两列**(看着像一件事,不是):

| 列 | 含义 | 谁会只有其中一个 |
|---|---|---|
| `ended_at` | BW 侧不再把这次运行当活的 | 重启遗留:标了 `ended_at`(不占名额了),但 `settled_at` 空——账没结,如实欠着 |
| `settled_at` | 这次运行的账已经结过一次,不会再结第二次 | 降级为咨询:结了账(照 v1 的降级记账语义),但会话还活着,`ended_at` 仍空 |

这两个「只有其中一个」的情形,就是这两列不能合并的全部理由。合并了,重启遗留会被写成「结过账」(假活),或者降级会被写成「已结束」(把还在跑的会话说成死的)。

### 2.3 「结算一次」怎么进新库:两把守卫,形态不同

plan/23 §5.3 的移植清单写的是「`settled_at` COALESCE 模式 → 运行管理器 + 存储层」。落地时要分成两处,**语义照搬、形态不同**:

**① 活的结算(`issue.settled_at`)—— 原样移植 COALESCE**

```sql
UPDATE issue SET settled_at = COALESCE(settled_at, ?) WHERE id = ?;
```

v1 `sqlite.rs` 的原文(该文件约 3161 行)。它要的只是幂等:一件活重开又重做,不能结算两次;调用方不需要知道自己是不是第一个。

**② 运行的结算(`run.settled_at`)—— 升级成比较并置**

```sql
UPDATE run SET settled_at = ? WHERE id = ? AND settled_at IS NULL;
-- 受影响行数 == 1 → 这次是第一次,该记账的记账
-- 受影响行数 == 0 → 别人先结过了,如实空转,打一行诊断,不写第二遍
```

**为什么不能也用 COALESCE**:COALESCE 永远影响 1 行,分不出输赢。而运行管理器**必须知道自己是不是第一个**——取消与完成同时到达时,得由「谁抢到」来决定谁去做后续动作(切片五的技能用量、队友战绩)。这是「移植语义、不照搬形态」的一个具体例子,也是把 v1 那个进程内的 `active_run.take()`(取消与完成谁先 take 谁赢)换成一个**能扛重启、将来多写者也成立**的形态。

同一把比较并置也用在结束回写上:

```sql
UPDATE run SET ended_at = ?, state = ?, end_kind = ?, end_detail = ?
 WHERE id = ? AND ended_at IS NULL;
```

一次运行的「关门」只发生一次,谁抢到谁写;第二个到达的是诚实空转。这是**五竞态里三条**(取消完成撞车、晚到消息、重启遗留后又冒出结果)共用的同一个机制。

### 2.4 双守卫迁移:原样移植,并且本片就真的用一次

移植 v1 的 `add_column_if_missing`(v1 `sqlite.rs` 约 410 行):先 `PRAGMA table_info(表)` 查列在不在,不在才 `ALTER TABLE … ADD COLUMN`;列不存在即 no-op,可以在每次开库时安全重复调用。规矩不变:**每加一列,必须同时改 `schema.sql` 并在开库流程里加一行守卫**,否则存量库直接崩(这是本仓库踩过的真坑)。

本片不为了演示而演示,但指挥器会**真跑一次存量库路径**(见 §5.2 第 9 项):用一份少一列的旧 schema 造一个「老库」,再用正式的开库流程打开它,`PRAGMA table_info(run)` 读回新列。这是双守卫在新库里的第一次实跑验证。

`drop_column_if_present`(v1 的对称件)本片**不搬**——新库里还没有一列需要删。要删时再搬,不预置。

### 2.5 一处如实标注的偏差:`run` 表不是只追加的

plan/23 §5.2 写「新库:范围缩小后新开 schema(观测 / 交棒 / 风险 / 决策等 append-only 表 + 双守卫迁移那套老规矩)」。`run` 表有可变的尾巴(`ended_at` / `settled_at` / `kind` / `state` 会被改),不符合只追加。

**本稿的判断**:那条老规矩管的是**事实类表**——观测是「某时刻测到某个值」,交棒是「某天带险交了棒」,风险与决策是「某天记下的一笔」;这些东西一旦发生就不该被改写,改写就是抹历史。运行是**一条生命周期记录**,它天然有开始和结束两个时刻;把它拆成一张只追加的「运行事件流」再从流里折算当前状态,是给切片四加一层它不需要的间接。而且每一次尾巴写入都由比较并置守着**只会成功一次**,「事后抹不掉」这条性质在实际效果上仍然成立。

这条判断请主控确认(列入 §11 开放问题 3)。v1 的 `workflow_run` 表也是同样形状,不是本片新开的口子。

## 3. 运行管理器的形状

### 3.1 单口 API

```rust
/// 运行管理器的把手。可克隆(克隆的是发信端,不是状态)。
#[derive(Clone)]
pub struct RunManager { /* 命令发信端 + 一个共享的收尾守卫 */ }

impl RunManager {
    /// 开库 + 起循环任务。**不自动清理遗留**——清不清、什么时候清,由调用方
    /// 显式决定(见 reap_on_restart 的文档:开机批量唤醒是 v1 明令禁止的)。
    pub async fn open(db: &Path, registry: Arc<ConnectorRegistry>, cfg: RunManagerConfig)
        -> Result<Self, RunError>;

    /// 开工。返回运行编号;活会被推到「进行中」。
    pub async fn start(&self, req: StartRun) -> Result<RunId, RunError>;

    /// 取消。幂等:已经关门的运行再取消 = Ok,不改任何字段。
    pub async fn cancel(&self, run: RunId) -> Result<(), RunError>;

    /// 降级为咨询:放开这件活的交付名额,会话不杀、工作区不清(见 §3.5)。
    /// 返回 true = 这次真降级了;false = 没什么可降的(幂等)。
    pub async fn demote_to_consultation(&self, run: RunId) -> Result<bool, RunError>;

    /// 重启后收拾遗留:库里还开着的运行,BW 这边已经没有句柄了,如实标成
    /// 「不知道怎么结束的」并放开名额。返回收拾了几条。
    pub async fn reap_on_restart(&self) -> Result<ReapReport, RunError>;

    /// 读:聚合快照(界面与指挥器用)。返回的是计数与例外,不是一百行明细。
    pub async fn snapshot(&self, p: Option<ProjectId>) -> Result<RunSnapshot, RunError>;
}
```

**`on_finished` 刻意不是公开方法**。任务书把它列进单口,本稿把它收成**内部命令**,理由是产品口径:结束不是外部能宣布的事,它只能被观测出来。留一个公开的 `on_finished` 等于给调用方一把「宣布这次跑完了」的钥匙——那正是「不假装前进」要挡的东西。它的唯一来源是每个运行自己的轮询任务,经命令队列送回循环。

`StartRun` 的形状:

```rust
pub struct StartRun {
    pub issue: IssueId,
    /// 哪条执行连接器。None 的解析规则照 registry 里 issue_ops 的先例:
    /// 恰好一条 → 用它;零条 → 如实报未连接;多条 → 如实报无法判定,
    /// **绝不「取第一条」蒙混**。
    pub connector_name: Option<String>,
    pub workspace: PathBuf,
    pub branch: String,
    pub inject: Vec<InjectBlock>,
    pub budget_usd: Option<f64>,
}
```

### 3.2 竞态串行化:单条命令队列,循环独占运行表

**取舍表**:

| 方案 | 优点 | 代价 | 判定 |
|---|---|---|---|
| **单条命令队列 + 一个循环任务独占运行表** | 全序天然成立;**压根没有锁**(表被循环按值持有),不可能出现「跨 await 持锁」那类难查的卡死;重启清理天然拿得到全局视角 | 所有状态变更排在一条队列上 | **推荐** |
| 每个运行一个小演员 | 跨运行互不阻塞 | 「同一件活一个交付运行」是跨运行的不变量,还得再来一个共享结构;重启清理要另起全局视角;组件数翻倍 | 不采 |
| 共享互斥表 + 各自加锁 | 改动最小 | 正是切片三设计稿点名警告的形态(「这条不写清楚,十件活并行时会撞出难查的卡死」) | 不采 |

**「单队列会不会成为百级并行的瓶颈」——不会,而且它不是新增的瓶颈**:数据库本来就是单写者(v1 的连接池就是 `max_connections(1)`,桌面应用一个写者,序列化访问免去锁库麻烦)。循环里的每条命令做的事只有三样:改内存表、发一次存储调用、把长活派出去。轮询回来说「还在跑」的绝大多数命令**一次存储调用都不发**。

**写进代码注释的并发纪律**(三条,缺一条就会在百级并行时表现为难查的卡死):

1. 循环里**唯一允许 await 的是存储调用**;连接器调用(开工 / 轮询 / 取消)一律 `tokio::spawn` 出去,结果经命令队列送回。开工那一下尤其要紧:连接器的写操作默认超时是 60 秒,让循环等它就是让全场停摆。
2. 运行表由循环**按值持有**,不放进共享互斥体;外部要读走 `snapshot`(也是一条命令)。
3. 命令队列**有界**(1024)。无界队列在上游卡住时会把内存吃光;1024 远大于百级并行的瞬时峰值,又不至于把背压藏起来。

### 3.3 谁轮询、多快轮询

**每个运行一个轮询任务**,不是一个全局循环遍历所有运行。理由:全局遍历会把 N 次连接器调用串起来(第 100 条要等前 99 条),这本身就是一个小 N 假设。

```rust
// 开工成功后,循环为这条运行派出一个轮询任务:
//   loop {
//       sleep(cfg.poll_interval).await;
//       match execute.poll(&cx, &ticket).await { … }   // 状态有变才发命令
//   }
// 退出条件:观测到终态 / 管理器的取消令牌被触发 / 命令队列已关(管理器没了)。
```

**节奏**:`RunManagerConfig.poll_interval`,默认 **250 毫秒**。

如实说清代价:对 agentcli 那家连接器,一次轮询是查它自己内存里那张会话表(切片三设计稿 §1.2),便宜;一百个运行 × 每秒 4 次 = 每秒四百次内存查表,可忽略。但将来若有一家连接器的轮询是每次外呼一个进程,这个节奏就贵了。**正确的长期形态是让连接器自己声明轮询节奏**,本片不做(契约要加字段就得撞协议号,为一个还没出现的连接器撞版本号不划算),登记为开放问题 1。

### 3.4 「同一件活一次只有一个交付运行」守在三层,底下那层是真的

| 层 | 形态 | 作用 |
|---|---|---|
| 内存 | 循环持有的 `by_issue: HashMap<IssueId, RunId>` | 快路径,重复请求立刻如实拒绝,不用碰数据库 |
| **存储** | **部分唯一索引**(见 §2.2) | **真正的守卫**:重启后照样成立;插不进去就是插不进去 |
| 顺序 | **先插行占名额,再外呼开工** | 消灭「查完到插入之间」的空窗——两个并发请求里,输的那个在插入时就被数据库顶回来,而不是两个都通过了检查、两个都去起会话 |

第三行是这套设计里最容易写错的一处。**必须是「先占后呼」**:

```
start(req):
  ① 查活、判状态(只有「待办池 / 待办 / 进行中」能开工——移植 v1 的入口校验;
     「进行中」是合法起点,那是诚实失败后的重试路径)
  ② 解析执行连接器(名字给了就按名字找;没给按「恰好一条」规则,零条/多条都如实报)
  ③ **插运行行**(state='starting'),占住名额
        └ 唯一索引冲突 → 如实返回「这件活已经有一个交付运行在跑」+ 那条运行的编号
  ④ 把活推到「进行中」(已经在「进行中」就跳过——状态机没有自环边)
  ⑤ 派出去调连接器的 start
        ├ 成功 → 回一条命令:state='running',记下上游会话号,起轮询任务
        └ 失败 → 回一条命令:关门(state='failed',end_kind='start_failed',
                 end_detail = 连接器的错误原文)+ 结账一次;名额随之释放
```

第 ⑤ 步失败为什么**要留行**而不是把行删掉:一次起不来的尝试是真发生过的事,删掉它,进程一死这件事就没了,而它恰恰是切片五「待人处理」要显示的那类东西。留行的代价是它占了一个运行编号——本稿认为这是对的,但把「一次没起来的尝试算不算一次运行」列进开放问题 2。

### 3.5 降级为咨询:无界面时的最小语义

v1 的原意(`demote_delivery_to_consultation`,v1 `bw-app/src/lib.rs` 约 5605 行):一件活离开「进行中」(被推到「评审中」或被人点了「完成」)时,如果它的交付运行还活着,就把这笔交付**降级为咨询**——放开交付名额让同项目别的活能跑,会话和工作区都留着不动(不杀进程、不清工作区),并且在降级这一刻把账结掉。

本片在没有界面的情况下保留这套语义,落成三件事:

1. **翻面**:`UPDATE run SET kind='consultation', demoted_at=? WHERE id=? AND kind='delivery' AND ended_at IS NULL`。比较并置,幂等。翻面后这一行退出部分唯一索引的谓词,**交付名额当场释放**。
2. **结账**:紧接着做一次运行结算(§2.3 的第二把守卫)。账在降级这一刻结,是照搬 v1 的判断——会话还会跑很久,等它结束再结账,账就晚了,而且那时已经分不清是哪一段产生的。
3. **不杀、不清、不改活的状态**:会话继续跑,工作区留着,活的状态由触发降级的那件事(推到评审中 / 人点完成)决定,降级本身一个字都不改。

它的**触发点在本片是显式调用**(`demote_to_consultation`),不是自动的——自动触发要靠「活离开进行中」这个事件,而在本片里活的状态只有两个改动方(开工推进行中、人显式转移),两处都在编排层,切片五接上 MR 巡检时再把自动触发接线。本片指挥器显式调它,证明这条语义活着。

**降级之后那条会话结束时会怎样**:它的轮询任务还在,会送回一条「结束了」的命令。这条命令走的是和「晚到消息」完全相同的路径——关门的比较并置成功(`ended_at` 本来是空的,所以这次会写上 `finished` 和真实的结束事实),结算的比较并置失败(降级时已结),**账不重结**。v1 用一个专门的 `cleanup_demoted_consultation` 分支处理这件事;新形态里它不需要专门分支,两把独立的比较并置自然就对了。这是把单槽架构换成按运行编号记账之后,顺手消掉的一处复杂度。

### 3.6 活的状态:开工时改,结束时不改

这条要写死在文档和代码注释里,否则验收会误判。

- **开工时**:推到「进行中」。这是运行管理器的合法写——开工是它发起的动作。
- **结束时**:**一个字都不改**。结束 ≠ 干成了。「推到评审中」是编排层看**远端 MR 状态**做的合成动作(v1 `poll_interactive_inreview`),它要 Issue·MR 操作连接器真调用,受网关抖动,进不了常绿门禁,而且它与运行管理器的四个口是正交的两件事。本片不做(见 §6)。
- **「完成」**:永远由人显式转移;`InReview → Done` 是合法转移表里 Done 的唯一入边,而运行管理器**根本没有**改活状态到 Done 的代码路径。

## 4. 五竞态怎么确定性地造出来

### 4.1 脚本化的 mock 执行连接器:住在指挥器里,不进库

plan/23 §6 的退役清单写明「Mock 运行路径(演示只在指挥器里,自我标注)」。照办:mock 执行连接器是 `run_races.rs` 这个指挥器文件里的一个结构体,**不进任何 crate 的正式代码**。代价是切片五要用时得再写一份;这个代价换来的是「库里没有一条能冒充真执行的路径」,值。

它的形状——**关键设计是:状态是「起跑时刻 + 脚本」的纯函数,不用定时器、不用后台任务**:

```rust
/// 【mock】脚本化执行连接器。每次轮询按「现在距起跑过了多久」在脚本里查一档,
/// 不睡不等不起任务 —— 所以它对调度抖动免疫,同样的脚本永远给同样的时间线。
struct ScriptedExec {
    /// 按活分支查脚本(bw/issue-N,每件活唯一)。
    scripts: HashMap<String, Script>,
    live: Mutex<HashMap<RequestId, Live>>,   // 起跑时刻 + 是否被取消
}

struct Script {
    /// 起跑要不要直接失败(造「单条失败不牵连」的一半)。
    start_fails: Option<ConnError>,
    /// 过了多久结束、怎么结束。None = 永不结束(造「重启遗留」)。
    finish_after: Option<(Duration, SessionEnd)>,
}
```

`poll` 的逻辑一共四行:被取消过 → `Canceled`;脚本说永不结束 → `Running`;还没到点 → `Running`;到点了 → `Finished { ended, summary: "【mock】…" }`。摘要一律带【mock】自我标注。

`cancel` 只在 `live` 里打一个取消标记并记下时刻——**不改结束脚本**。这一点很重要:取消与完成撞车那一场,靠的正是「脚本说这一刻结束」和「取消这一刻到达」两件事同时为真,由**管理器**去分出胜负,而不是由 mock 替它分。

### 4.2 六段脚本

第一段是基线(plan/23 §7 的「十件并行互不覆盖、各自只结算一次」),后五段是点名要验的五个竞态。

---

**R1 · 十件并行,互不覆盖、各自只结算一次**

- 一个项目、十件活(件数是命令行参数 `--n`,默认 10),分支各自 `bw/issue-1..10`。
- 脚本:第 N 件在 `200ms + N×30ms` 结束(彼此错开,时间线唯一),结束事实是「进程自己退出,码 0」。
- 动作:十次 `start` 并发发出(`join_all`),等全部关门。
- 断言:运行行恰好 N 条;运行编号两两不同;活编号两两不同;每条的分支 / 工作区与它自己的活对得上(**这就是「互不覆盖」的操作定义**:没有一条运行行带着别人的分支);全部 `ended_at` 非空;全部 `settled_at` 非空且**恰好** N 条结过账。

---

**R2 · 同一件活开不出第二个交付运行**

- 第 1 件活起一个长脚本(5 秒后结束,跑不到)。
- 立刻再对同一件活 `start` → 必须如实返回「这件活已经有一个交付运行在跑」,并带上那条运行的编号。
- 断言:该活的运行行仍然只有 1 条。
- **防伪断言**(证明守卫在存储不在 if):指挥器**直接对数据库**插一条同一件活的活交付运行行,断言 SQLite 抛唯一约束冲突。绕过管理器还是插不进去,才叫铁律进了存储。

---

**R3 · 取消与完成同时到达,只结算一次**

- 脚本:某件活在 T = 400 毫秒结束。
- 指挥器在 T 附近发取消。**撞车不能靠一次巧合**:循环 20 轮,每轮把取消的发出时刻在 `T−5ms … T+5ms` 之间抖动,每轮用一件新活。
- 断言(每一轮都要成立,与谁赢无关):
  - 关门恰好发生一次(`ended_at` 只有一个值,复查前后一致);
  - `settled_at` 非空且**再发一次结算命令后值不变**(逐字节比对,这是「只结算一次」最硬的读回);
  - `state` ∈ {`canceled`, `finished`}——两者都诚实,取决于谁先到;
  - 关门后再显式 `cancel` 一次返回 Ok,且不改任何字段(幂等)。
- 输出里打一行**胜负分布**(「20 轮中取消赢 N 次、完成赢 M 次」)。这行不是断言,是证据:如果 20 轮里一次撞车都没造出来(某一方全赢),说明抖动窗口没覆盖到真实的撞车区间,指挥器要如实打一行警告——**不许把「没撞上」读成「撞了也没事」**。

---

**R4 · 单条失败不牵连**

- 十件活,其中:第 3 件脚本是「结束了,但连接断了、去向不明」;第 7 件脚本是「起跑就失败(未连接)」。
- 断言:
  - 运行行仍是 10 条(第 7 件**有行**:`state='failed'`、`end_kind='start_failed'`、`end_detail` 是连接器的错误原文,结账一次——见 §3.4 的理由);
  - 第 3 件 `end_kind='contact_lost'`,**不是** `process_exit`(如实说不知道,绝不当成功);
  - 另外 8 件全部 `process_exit` 且各结账一次,一个字段都没被那两条影响;
  - 第 7 件的活可以**立刻**再开工(名额从没被占死),新起一条运行行,该活共 2 条运行、编号不同。

---

**R5 · 重启后的遗留运行如实标注,不假活**

- 「重启」在进程内怎么模拟:起 3 个**永不结束**的脚本运行,然后 **丢弃管理器 A 的所有把手**(它内部的收尾守卫会触发管理器级取消令牌,循环任务与轮询任务随之退出),再用**同一个数据库文件**新建管理器 B,调它的 `reap_on_restart()`。
  - 这是对「进程被杀」的诚实模拟:被杀的进程也没机会做任何清理,库里的行就是那样开着。
  - **如实标注模拟的边界**:进程内的「重启」只重建了管理器和它的内存表,**没有杀掉上游会话**——真进程被杀时,上游的 claude 会话往往还活着,这正是「遗留」这一档存在的理由,所以这个模拟恰好对应真实场景的那一半;另一半(真把上游进程组杀干净)由切片三-1 已经验过的按进程组真杀负责,不在本片重复。
- 断言:3 条 `state='orphaned'`;`ended_at` 非空(名额已释放);`settled_at` **为空**(账没结,如实欠着);`end_kind` **为 NULL**(不知道怎么结束的就是不知道);
- **反证断言**:这 3 件活里,`state='finished' AND end_kind='process_exit'` 的行数为 0——没有一条被写成「跑完了」。
- 再断言名额真的放开了:对其中一件活重新 `start` 成功,该活共 2 条运行、编号不同。
- 顺带证明「不批量唤醒」:`reap_on_restart` 只标注,**不重起任何会话**;断言收拾之后 mock 连接器的活票据数没有增加。

---

**R6 · 晚到的消息不错账**

- 第 1 件活起运行 A,脚本 300 毫秒结束。
- 100 毫秒时取消 A → A 以「已取消」关门。
- 300 毫秒时 mock 报告「结束了」,A 的轮询任务把这条晚到的消息送回 → **必须是诚实空转**。
- 紧接着对同一件活起运行 B(名额已释放),脚本 600 毫秒结束。
- 断言:
  - A 的 `state` 仍是 `canceled`、`end_kind='canceled'`、`ended_at` 值与关门那一刻**逐字节一致**(晚到的消息一个字段都没改动);
  - B 的 `state='finished'`、`end_kind='process_exit'`——**A 的晚到消息没有落到 B 头上**(这就是「不错账」的操作定义);
  - 全库结过账的运行数是 2,不是 3。

### 4.3 晚到消息的钥匙:运行编号,不是防重编号

这条是本片最容易搞错、错了又最难查的一处,单独立节。

**钥匙必须是运行编号**。轮询任务在派出时就把自己那条运行的编号带在身上,送回的命令带着它;循环按编号找到那一行,做比较并置;那一行如果已经关门,更新影响 0 行,如实空转 + 一行诊断。

**为什么不能用防重编号**:防重编号的格式钉死在 `issue-{活编号}/{动作}`(契约文件里写死的,不给调用方各自拼)——它**故意**在重试之间保持不变,那是它防上游重复写的本事。但正因为它不变,同一件活的两次运行长得**一模一样**;拿它当晚到消息的钥匙,运行 A 的晚到结果就会精准地落到运行 B 的账上——那正是 R6 要防的那个错账。

**顺带一条历史教训**:v1 的落后消息检查比的是「这条消息说的活是不是当前那个活」(`ar.issue.id != req.issue`),按**活**认人。它在单槽架构里勉强够用,但形态上就是本仓库记忆里那条「按名污账」的真 bug 的同族(plan/20 R1-R5 那批把 Done 边的记账从按名改成按编号,就是同一个教训)。新形态按运行编号认人,这类错账在结构上不成立。

**防重编号在切片四里一次都不用**:它的正当用途是对上游的可重试写操作(提 MR、建 Issue),那属于 Issue·MR 操作能力,是切片五的事。本片不碰。

三条硬规矩:

1. **末行 `RUN_RACES_OK` + 退出码 0** 才算过;任何一条断言失败 → stderr 打 `ASSERT FAILED: …`,末行 `RUN_RACES_FAILED`,退出码 1。
2. **数据库跑完不删,路径打出来**。指挥器自己用 SQL 读回是一回事,人能拿这个路径自己 `sqlite3` 再查一遍是另一回事——后者才是「读回为证」。指挥器打印的每一条读回都**把它真正执行的 SQL 原样打出来**,人可以逐条复制去手工核。
3. **必须含故意失败路径**(R2 的防伪插入、R4 的起跑失败、R5 的反证):照 `probe_all` 立的规矩,防伪断言比正向断言更能挡住假绿。

### 5.2 sqlite 读回清单

指挥器执行、并原样打印给人复核的九条:

```sql
-- 1 结构核验(表在不在、列全不全)
PRAGMA table_info(run);
-- 2 铁律进了存储没有(部分唯一索引真的建了吗)
SELECT name, partial FROM pragma_index_list('run');
-- 3 总量与互不覆盖
SELECT COUNT(*) FROM run;
SELECT issue_id, COUNT(*) AS n FROM run GROUP BY issue_id ORDER BY n DESC;
-- 4 结算一次(总量)
SELECT COUNT(*) FROM run WHERE settled_at IS NOT NULL;
-- 5 结算一次(值不变):对同一条运行再结一次账,前后比对
SELECT settled_at FROM run WHERE id = ?;      -- 结算前后各查一次,值必须逐字节一致
-- 6 各状态分布
SELECT state, end_kind, COUNT(*) FROM run GROUP BY state, end_kind;
-- 7 重启遗留如实标注(账没结、结束事实为空)
SELECT id, issue_id, state, end_kind, ended_at, settled_at FROM run WHERE state = 'orphaned';
-- 8 完成永远人点:跑完之后,没有一件活是「已完成」
SELECT COUNT(*) FROM issue WHERE status = 'done';
-- 9 「待人处理」推导得出来(本片不建投影,只证明数据形状够用)
SELECT id, issue_id, state FROM run WHERE ended_at IS NOT NULL AND settled_at IS NULL;
```

第 8 条后面跟一段**「完成永远人点」的显式验证**:指挥器手工把一件活置成「评审中」(并注明「本片手工置,真实来源是切片五的 MR 巡检」),显式调一次转移到「已完成」,断言成功;再对另一件「进行中」的活试转「已完成」,断言被合法转移表拒绝。两条一起才说明白:Done 有入口,而且入口只有一个。

### 5.3 真实并行三件:另一档,不进常绿

照 `agent_session` 立的先例(真跑受网关抖动,只在人手或监理脚本里跑,可安全重试):

```
cargo run -p bw-app --example run_races -- --real <git 检出根> --n 3
```

- **前置**:切片三-2 落地(真的 agent 执行连接器存在)+ `claude` 在 PATH + 给一个真的 git 检出根。指挥器在这一档里用 dev 依赖把真连接器组装进注册表。
- **工作区供给**:这一档要三个真 worktree。指挥器**自己用 git 造**(它是 example,不在 `src/` 下,不受「编排层不准直接起进程」守卫的管辖——这是有意的:指挥器在这里扮演的是「用户给的工作区」那一方,不是编排层)。这件事要在文件顶部注释里写明白,免得下一个评审者以为在绕守卫。生产路径上的工作区供给本片不落点(见 §6)。

## 11. 开放问题(拿不准的,不硬拍)

1. **轮询节奏该不该由连接器自己声明**。本片钉一个全局默认(250 毫秒),对 agentcli 那家(轮询=查内存表)完全够用;但将来若有一家的轮询是每次外呼一个进程,这个节奏就贵得离谱。正确的长期形态是契约里让连接器声明,但那要加字段、撞协议号——为一个还没出现的连接器撞版本号不划算。何时改,留给撞上的那一片。
2. **起跑就失败的尝试算不算一次「运行」**。本稿定为「算」(先插行占名额,起不来就地关门结账),理由是这件事真发生过,不留行则进程一死就没了。代价是它占一个运行编号,界面上会看见一条从没跑起来过的运行。这是产品口径,请主控确认。
3. **`run` 表不是只追加的**,与 plan/23 §5.2「新库 append-only 那套老规矩」的关系。本稿判为老规矩管的是事实类表(观测 / 交棒 / 风险 / 决策),生命周期记录不在其列,且每次尾巴写入都被比较并置守着只成功一次(§2.5)。请主控确认这个划线。
4. **要不要一个可配置的软性并发闸**。本片不设人为上限(百级并行是明确要求),真实上限是机器与上游 CLI。若将来要设,正确形态是「超了排队」而不是「超了拒绝」——但排队会引入一个新的公平性问题(谁先谁后),不想现在造。
5. **按活锁与按工作区续接是两把不同的钥匙**。交付名额按「活」锁(一件活一个交付运行),而 agentcli 层的会话续接按**工作区路径**认(上游按工作目录编码存会话)。如果两件活被指到同一个工作区,第二件活开工时会「续接」到第一件活的会话历史——名额守卫拦不住这个,因为它们是不同的活。要不要在开工时加一条「这个工作区已经有别的活的活会话」的校验?本稿倾向加(便宜、如实),但它跨了编排层与 agentcli 层的边界,谁来查要定。
6. **取消的口径**:BW 侧取消 = 让连接器杀掉进程组(切片三-1 已验)+ 关账。但上游的会话文件仍在,人可以自己 `claude --resume` 接着聊。那这算「取消了」还是「暂停了」?界面上怎么说才不骗人?这是产品口径,不该由实现定。
7. **存储接口的拆分粒度**。本片给两条 trait(管活的 / 管运行的)。切片五要加观测 / 风险 / 决策,是各加一条,还是按「事实类表」并成一条?现在定容易定错,等切片五真写时看形状。
8. **切片四能不能先于三-2 合入**。本稿倾向能(mock 档已足以证明五竞态,且它不依赖 agentcli 层的任何东西),真实并行三件那一档单独等三-2。但这会让 plan/23 的进度表出现「四已完成、三未完成」的顺序倒挂,读的人可能困惑——要不要在进度表里加一句说明。
9. **给契约类型加 derive 算不算形状变更**。本稿按切片三A 立的判例判为不算(不增删字段、不改语义,不撞协议号),切片三-2 给请求编号加 `Hash` 时已经这么做了,本片给票据加 `Clone` 照办。若主控不同意,两处一起得把协议版本撞到 3,并同步所有实现——代价不大,但要现在拍。
