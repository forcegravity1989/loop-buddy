## 1. 依赖方向与落点

### 1.1 落点:`bw-engine/src/agentcli/`,不新开 crate

```
bw-core        领域内核(零 IO,wasm 可编译)
   ↑
bw-connector   契约 + 四个能力接口 + 注册表 + gh/codehub/script 适配器
   ↑
bw-engine      采证 / 指标正本 / 终端栈 / **agentcli 层(本片)**
```

`bw-engine` 的 `Cargo.toml` 加一行 `bw-connector = { path = "../bw-connector" }`。方向单向,不循环——`bw-connector` 不依赖 `bw-engine`(切片二裁决 #1 把 git 辅助函数放在 connector 侧,就是为了避免反向边)。

**为什么不新开 `bw-agentcli` crate**(三条,按分量排):

1. **减法**。新 crate = 新 manifest + 新 feature 门 + 门禁脚本多一行 + workspace 成员多一个。换来的隔离,`bw-engine` 里一个 `agentcli/` 子模块同样给得起。
2. **PTY 依赖已经在 bw-engine**(`conpty-oxide`,Windows;将来的 Unix 后端也进这里)。把适配器放别处,依赖要跟着搬,搬完 `terminal_manager.rs` 和 `interactive_cli.rs` 也得跟着走——那就不是「加一个 crate」,是「把切片一B 刚移植好的东西再搬一次」。
3. **两处已定档指的都是这里**:切片二设计稿 §6 写明「agentcli 层在 `bw-engine` 里实现,因为 PTY 依赖重」;`contract.rs` 的模块注释也写着「agentcli 层(切片三,在 `bw-engine` 里实现)也要经由本契约挂进注册表」。换落点等于推翻两处已落地的判断,举证责任不成立。

**必须保住的一条性质**:编排层(切片四建的 `bw-app`)只依赖 `bw-connector`,**不依赖 `bw-engine`**。它拿到的是注册表里的 `Arc<dyn Connector>`,谁把 `AgentCliConnector` 塞进去是组装处(桌面壳 / 指挥器)的事。这样 PTY 那堆原生依赖永远渗不进编排层。建议切片四建 `bw-app` 时门禁加一行检查它的 manifest 里没有 `bw-engine`——本片只记这条,不代切片四动手。

**顺带记一条容易被误判的事**:`scripts/guard-no-direct-process.sh` 查的是 `bw-core` 和 `bw-app` 两个目录,`bw-engine` 不在其中。agentcli 层起 PTY 子进程是**设计如此**(它就是那个「对外能力」的实现方),不是绕过守卫。这句要写进模块注释,免得下一个评审者「顺手修」。

### 1.2 终端栈与执行适配的关系:两张表,一个适配器持有

已移植的 `TerminalManager`(210 行)管的是**字节与尺寸**:按会话身份路由输出、有界输出环(满丢最老)、resize 入队、attach 不杀邻居。它的调用方是界面。

切片二定的 `Execute`(start / poll / cancel)管的是**生命周期**。它的调用方是编排层。

这两件事的键都不一样:前者按 `ConversationId`,后者只能按 `ExecTicket` 里的请求编号。硬绑在一起会出现「界面切个卡把运行状态碰坏」这类耦合。所以:

```rust
// bw-engine/src/agentcli/connector.rs
pub struct AgentCliConnector {
    kind: ConnectorKind,            // AgentCli { cli: "claude" }
    binding: ProjectBinding,        // 项目 + 工作区根
    row: &'static TuiAgentConfig,   // 注册表那一行(§5)
    exec: Arc<dyn InteractiveExecutor>,  // 真 PTY 执行器,或自我标注的 mock
    /// 字节与尺寸(界面面向)。移植件原样用,一行不改。
    terminals: Arc<Mutex<TerminalManager>>,
    /// 生命周期与身份(编排层面向)。本片新写的唯一一张表。
    sessions: Arc<Mutex<SessionTable>>,
}
```

一张**对照表**把两边绑起来,它就是 agentcli 层的核心数据结构:

```rust
/// 一次执行 = 一行。字段全部是「能观测到的事实」,没有一个是猜出来的。
struct SessionRow {
    req: RequestId,                 // 编排层的键(ExecTicket 里的那个)
    conversation: ConversationId,   // 界面的键(TerminalManager 里的那个)
    workspace: PathBuf,             // **续接必须同路径**,这是硬事实,见 §2.2
    branch: String,
    /// 上游会话号。claude 一家可以由我们指派(`--session-id`),所以首启就有值;
    /// 不能指派的家在这里留空,如实标注「未知」,绝不填一个猜的。
    upstream_session: String,
    /// 这次注入了哪些块(标签 / 字节数 / 内容指纹)。**只记事实,不做结算**——
    /// 结算是切片四运行管理器接上存储以后的事(§6)。
    injected: Vec<InjectRecord>,
    /// 本家 CLI 是否真的接得上按次预算封顶。claude 交互式接不上,如实 false(§8)。
    budget_enforced: bool,
    state: ExecState,
}

#[derive(Default)]
struct SessionTable {
    by_req: HashMap<RequestId, SessionRow>,
    /// 「这个工作区已经有会话了吗」——续接判定唯一入口,不给第二条按名查找的路。
    by_workspace: HashMap<PathBuf, RequestId>,
}
```

**并发纪律写进注释**:`Execute` 的三个方法是 async,但这两把锁是同步锁,**任何一处都不许跨 `.await` 持有**——进锁取到要的东西就出来,真会话跑在 `tokio::spawn` 出去的任务里,不在锁里等。这条不写清楚,切片四十件活并行时会撞出难查的卡死。

`RequestId` 今天只 derive 了 `Clone/Copy/Debug/PartialEq/Eq`,**少一个 `Hash`**,当不了 map 的键。按契约冻结规矩,加 derive 不改类型形状、不改语义,不必升协议号——本片顺手加上,在同一个 commit 里说明。

## 2. 无存储前提下的会话身份

### 2.1 推荐:不落 BW 自有持久化,内存表 + 上游目录反查

判据是「切片三验收要能证明什么」。要证的是**同路径续接真的拿得到历史**,不是「BW 重启后还记得哪件活对应哪个会话」——后者要有活的存储才谈得上,而活的存储是切片四/五的事。

三条理由:

1. **上游已经存了正本**。claude 把会话落在 `~/.claude/projects/<把路径里的斜杠换成横杠的编码>/<会话号>.jsonl`(2026-08-10 本机复核仍然成立:该目录下就是一堆以 uuid 命名的 `.jsonl`)。BW 再落一份 JSON,就是给同一个事实开第二本账;plan/23 第四轮理念④说得很直白——项目仓是唯一事实源,不建第二个知识库。
2. **身份可以由我们指派,「记住」这件事因此消失了**。`claude --session-id <uuid>` 存在(2026-08-10 核 `claude --help`:「Use a specific session ID for the conversation (must be a valid UUID)」)。所以会话号不必等上游回传——首启时我们自己给一个,续接时用同一个。要「记住」的只剩「哪个工作区路径配哪个 uuid」,而这个映射从上游目录的**文件名**就能反查出来。
3. **现在落盘,切片四必删**。JSON 边车文件在存储落地那天就是一条要拆的旧路径,`CLAUDE.md`「不为向后兼容留旧路径」和 v1 §10「不造要删除的临时兼容层」两处都禁这个。

所以:

```rust
/// 反查器:某个工作区路径下,上游存了哪些会话。**只读文件名与修改时间,
/// 不解析 jsonl 内容**——上游的行格式没有公开文档,解析器会脆(v1 §13 已记)。
fn discover_sessions(workspace: &Path) -> Vec<(String /*session id*/, SystemTime)>;
```

反查器是**便利,不是命脉**:续接靠的是我们指派的那个 uuid 显式传给 `--resume`,反查只是新进程起来时的一次找回。上游哪天改了目录编码规则,反查失灵,续接照样成立。

**如实标注一处缺口**:进程重启后,BW 知道「这个路径有这些会话」,但不知道「这个会话属于哪件活」——因为本片连活都没有存储。这不是遗漏,是切片三的边界。存储落地时按 v1 `claude_conversation` 的字段清单建表(项目 / 活 / 上游会话号 / 工作区路径 / 分支 / 建立时间 / 最近打开时间,见 v1 设计 §4.1),现在不要半做。

### 2.2 硬事实:续接必须同路径,适配器要守住它

v1 已经验过的表(设计 §5.2):同路径重建 → 找得到历史;换成主工作区或换了路径 → 找不到。原因是上游按工作目录编码存会话。

`ExecSpec` 只给 `workspace` 和 `branch`,没有「这是首启还是续接」的字段——**这是好事,不要加**。续接不是一个新动词,是「在一个已经有会话的工作区上再 start 一次」的自然结果:

```
start(spec):
  ① 工作区路径必须已存在、且是 git 检出 —— 不存在就如实报「未连接」,
     **适配器不给用户造工作区**(谁给的工作区谁负责,这条边界要硬)。
  ② 当前分支必须等于 spec.branch —— 不等就如实拒绝,绝不在错分支上放 agent 干活。
  ③ 查会话表(内存)→ 查不到再查上游目录反查:
       有会话 → 走续接计划(`--resume <同一个 uuid>`,不带系统提示词、不带位置 prompt)
       没会话 → 走首启计划(指派新 uuid,注入块进系统提示词,位置 prompt 自动提交)
  ④ 起 PTY,**立刻返回票据**,不等会话结束(契约:只起不等)。
```

②③ 里的「不符就如实报错」是本片对硬事实的守法:如果路径对不上就默默起一个没有历史的新会话,界面上看起来「续接成功」,实际上上下文全丢——这正是本仓库最恨的那种「看起来做了但没做」。

## 3. 完成信号

### 3.1 先纠正一个前提

任务简报里写「orca 的 hook→本地 HTTP 是设计过未实现」——**不成立**。v1 的 `crates/bw-app/src/hook_listener.rs` 是完整实现:localhost HTTP 服务器、`SessionStart`/`Stop` 两个事件、幂等改写 `~/.claude/settings.json` 装 curl 钩子、失败开放(解析不了也回 200,永不卡住 agent)。远端 MR 轮询(`poll_interactive_inreview`)同样是实现过的。

所以本片的选择不是「设计 vs 未实现」,是三条**都已验证**的信号怎么分工。

### 3.2 推荐:本片只认进程退出

| 信号 | 它到底说明什么 | 本片处置 |
|---|---|---|
| 进程退出(PTY 读到文件尾) | 这次会话结束了 | ✅ 唯一档 |
| hook 的 `SessionStart` | 上游会话号是多少 | ❌ 不要了——我们自己指派(§2.1) |
| hook 的 `Stop` | agent 说完一轮话了,在等人 | ❌ 不进本片,它不是「干完了」 |
| 远端 MR 状态 | 活是不是真的提交了成果 | ❌ 归编排层 + 仓连接器(切片四/五) |

三条理由:

1. **`Stop` 不是完成信号**。claude 每答完一轮就发一次 `Stop`。v1 拿它当的是「该去查远端 MR 了」的触发器,判定「进评审中」的是远端 MR 状态,不是 `Stop`。把它当完成信号会让活在第一句寒暄后就「完成」。plan/23 §4 那句「hook…比等进程退出可靠」混了触发器与判定,本稿如实纠正。
2. **hook 的第一用途已经没了**。它原本不可替代的价值是捕获会话号;`--session-id` 让我们自己指派,这条价值归零。
3. **装 hook 要改用户全局配置**(`~/.claude/settings.json`)。为一个本片用不上的触发器,付一个本机全局副作用的代价,不划算。留口的正确形态是**不留空模块**——空的 hook 模块会诱导下一个会话往里填东西,这正是做减法要防的。切片四真需要更早的触发时,再决定是接 hook 还是定时查,那时它是一次完整的移植(文件自包含,只依赖 tokio 与 serde_json,搬进来很便宜)。

**如实说清一句**:进程退出 ≠ 活干完了。人敲 Ctrl-D 会退出;claude 提完 MR 常常不退出(v1 那个「合入后锁不释放」的真 bug 根因就是这个)。所以 `Finished` 只说「会话结束了、怎么结束的」,成败判定归编排层看真实证据。这直接决定了下一节。

## 4. `ExecState::Finished { ok: bool }` 重审

### 4.1 推荐:改,现在改

**理由一:`ok` 算不出来。** PTY 会话的退出码几乎不携带信息——正常退出(码 0)可能是活干完了,也可能是人关了窗口;不退出可能是干完了在等人。让适配器填一个它不知道的布尔,就是在类型上逼它猜。本仓库对这类字段已有先例:`ProbeReport.reachable` 因为恒真被删掉了,理由是「恒真字段不携带信息,删掉它比留着『以防将来』更诚实」。恒盲的布尔比恒真的布尔更糟。

**理由二:`ok` 没有正当消费者。** 按 v1 收口后的真实语义,「推评审中」由远端 MR 状态判定。留着这个布尔,切片四的运行管理器第一眼就会写出 `if ok { → 评审中 }`——一条假账,而且是那种跑起来不报错的假账。

**理由三:今天是最后一个便宜的时刻。** 全仓 `Execute` 的实现数 = 0(切片二只定型),`ExecState` 的消费者数 = 0。等切片四的运行管理器接上去再改,要动的就不止契约一处。

### 4.2 撞不撞冻结点:撞,但代价很小,规矩照守

契约注释写的冻结点是「切片二B 收编完成」,而二B 已经落在 commit `257cf56`。所以按规矩这次要 `PROTOCOL: 1 → 2`。

代价如实核过:三家适配器**没有一家覆写 `protocol()`**,全用基座默认值 `contract::PROTOCOL`;协议号不落库、不上线、没有外部消费者;注册表那条校验是 `debug_assert_eq!`。所以「+1」的实际改动就是那一个常量和它的注释。规矩要守(它防的是将来真有外部消费者时的静默不兼容),但别把它说成阻塞。

**建议单独一个 commit 做契约改动**(§10 的 A),让协议号变更在一次可读的 diff 里被看见,不要混在 PTY 那堆改动里。

### 4.3 提案形状(减法版:只加真知道的事实)

```rust
pub enum ExecState {
    Running,
    /// 会话结束了。**结束 ≠ 干成了** —— 成败看真实证据(MR 状态、工作区改动),
    /// 不看这里。最远只能推到「评审中」;这里依然**没有** Done 档。
    Finished { ended: SessionEnd, summary: String },
    Canceled,
    Orphaned,
    Unknown,
}

/// 会话是怎么结束的。三档全是**能观测到的事实**,不含判断。
#[derive(Debug, Clone, PartialEq)]
pub enum SessionEnd {
    /// 上游进程自己退出。退出码只是事实,不解释成成败。
    ProcessExit { code: Option<i32> },
    /// BW 主动停的(挂钟上限 / 预算封顶)。人点的取消不走这里,走 `Canceled`。
    StoppedByBw { reason: StopReason },
    /// 连接断了、进程去向不明 —— 如实说不知道,绝不当成功。
    ContactLost,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum StopReason { WallClock, Budget }
```

`summary` 保留,但语义收紧一句注释:**只放上游给的原话或空串,不放 BW 编的结论**(移植件里 mock 的「【mock】…」自我标注就是正确样例)。

**类型断路一个字都不松**:`ExecState` 里仍然没有 `Done`;`Finished` 的三档没有一档能被读成「已验收」。指挥器要对这条做一次穷举断言(§7.2)。

**如果主控不批准改契约**:退路是保留 `ok: bool` 并在适配器里**永远填 `false`**,同时在契约注释里写死「这个布尔算不出来,不要读」。我不推荐——恒假字段比恒真字段更容易被误读成「一直失败」。

## 5. 注册表:怎么让「加一行 = 加一家」真的成立

### 5.1 现状:今天不成立

`TuiAgentConfig` 是一张声明式表没错,但 `build_startup_plan` 的函数体里**写死了三处 claude 专属字面量**:`--append-system-prompt`、`--disallowedTools` 和它的值 `Bash(gh pr merge)`。第二家 CLI 如果注入旗标不同名,加一行是不够的。

### 5.2 推荐:包一层,把字面量提进行,不重写函数

移植优先:`build_startup_plan` / `build_resume_plan` / `build_consultation_resume_plan` / `PromptInjectionMode` / `LaunchPlan` 五件的**行为**有 v1 实跑背书,一律保留,只做「把写死的东西换成读字段」这一种改动,逐处在 commit 说明里列出。

```rust
pub struct TuiAgentConfig {
    // ── 移植件原有字段(不动)──
    pub slug: &'static str,
    pub detect_cmd: &'static str,
    pub launch_cmd: &'static str,
    pub prompt_injection_mode: PromptInjectionMode,
    pub yolo_flag: &'static str,
    pub resume_flag: &'static str,
    pub resume_id_flag: &'static str,

    // ── 本片新增:原来写死在计划构造器里的三处,搬进行 ──
    /// 系统提示词注入旗标(claude:`--append-system-prompt`,2026-08-10 核 `--help` 属实)。
    /// `None` = 这家不支持系统提示词注入 —— 复利块只能走位置 prompt,
    /// 如实降级并在运行记录里写明,绝不假装注入了。
    pub system_prompt_flag: Option<&'static str>,
    /// 由 BW 指派会话号的旗标(claude:`--session-id`,同日核对属实)。
    /// `None` = 这家不能指派,会话号只能事后发现(§2.1 的反查器兜底)。
    pub session_id_flag: Option<&'static str>,
    /// 起手就禁掉的工具。**如实口径:这是篱笆不是墙**(v1 原注释已写明:
    /// 禁得掉 `gh pr merge`,禁不掉等价的其它写法),真约束在系统提示词与状态机。
    pub deny_tools: &'static [&'static str],

    /// 原 `supported` 换个说法,语义钉死:**只有在本机真跑过 `--help`
    /// 逐项核对过参数的行才准置 true**。「登记了」≠「能跑」,与连接器那条
    /// 「装了≠连上了」同一口径。
    pub verified: bool,

```

claude 那一行照旧全填(参数今天已复核:`--append-system-prompt`、`-c/--continue`、`-r/--resume [value]`、`--session-id <uuid>`、`--dangerously-skip-permissions`、`--disallowedTools` 均在;`--max-budget-usd` 标注为仅 `--print` 模式有效,见 §8)。

### 5.3 cursor:本机没装,**不许标成已核对**

`which cursor` → 未找到(2026-08-10 本机实查)。参数没法核对,标 `verified: true` 就是假装能跑。

所以切片三对「加一行 = 加一家」的证明**改成机械证明**,并且这个改法更硬:

- 指挥器遍历注册表的每一行,各跑一次计划构造,打印装配出来的完整命令行;
- 断言 claude 那行装配出来的参数与 v1 **逐字节一致**(防止「一般化」顺手把已验证的行为改坏,这是包一层最大的风险);
- cursor 那行如实报「参数未核对,拒绝启动」,并且这条拒绝也是断言项——证明表驱动的分叉真的走通了,而不是碰巧只有一条路。

真正把 cursor 接通,留给有 cursor 的机器:一行配置 + 一次 `--help` 核对 + 把 `verified` 翻成 true。

### 5.4 注入模式枚举:不预造第二档

`PromptInjectionMode` 今天只有 `PositionalArgv` 一档。v1 已经实测过 orca 那套 `--prefill` 在 claude 里**不存在**,所以当时就把它删了而不是留成死的向前兼容。本片同理:第二档等真有一家用别的方式再加,空枚举项会诱导人往里填东西。

### 5.5 移植件里的单元测试怎么办

`interactive_cli.rs` 随迁带着 v1 的 `#[cfg(test)]` 模块(约 290 行)。本仓核心纪律是不写也不留单元测试。本片一旦给 `TuiAgentConfig` 加字段,这些测试要么改要么删。

建议:**删掉整个测试模块,但有前提**——指挥器必须先覆盖等价断言(claude 装配参数逐字节一致、续接不带系统提示词、空会话号回落 `--continue`、未核对的行如实拒绝)。先补指挥器,再删测试,不许反过来。

## 6. 复利链接线:留口不留假

### 6.1 本片的职责只有一件:忠实搬运

契约已经有 `ExecSpec.inject: Vec<InjectBlock>`(标签 + 正文)。适配器要做的是把每块按标签分节拼进系统提示词,交给注册表行指定的旗标送出去。**顺序等于调用方给的顺序,一个字不改、不截断、不重排。**

装配顺序(照 v1 收口后的既定形态):衔接层正文(项目上下文 + 通用铁律,来自已移植的 `build_bridge_system_prompt`)→ 调用方给的注入块,按序。位置 prompt 仍然是「这件活要干什么」,不是方法论——方法论住在系统提示词里,agent 才会拿方法去干需求。

### 6.2 三条硬规矩(防止把口做成假账)

1. **本片不建技能库、不建目录、不造蒸馏块。** 指挥器演示时,注入块从命令行给的**真实文件**读(`--inject <标签>=<路径>`),不是内置字符串。
2. **空就是空。** `inject` 为空时,装配出来的系统提示词只有衔接层正文,指挥器如实打印「注入 0 块(本片无技能库)」。**绝不写「使用技能 0 次」这种记账行**——假零是本仓库的红线。
3. **注入发生了什么必须留下可核对的事实。** 每块记标签、字节数、内容指纹(sha256 前 8 位),连同装配好的完整系统提示词落一份文件(`--dump-prompt <路径>`),指挥器读回比对。

```rust
/// 一块注入正文的事实记录。**这就是记账口**:切片四的运行管理器接上存储后,
/// 拿这张清单做「同一件活只记一次」的结算;本片只产事实,不结算。
struct InjectRecord {
    label: String,
    bytes: usize,
    digest8: String,   // sha256 前 8 位,够对上是不是同一块
}
```

### 6.3 续接不重注入,而且要说清楚

续接进的是已有会话,复利块首启时就已经在里面了,重注是污染。所以续接的运行记录里注入清单**为空**,并且注明「续接已有会话,复利块在首启时已进」——**不是漏注,是不该重注**。这句话必须打出来,否则读回的人会以为链断了。

### 6.4 咨询态那条路径:移植了,本片不接线

`build_consultation_resume_plan`(给已验收的活续聊时追加「新交付请另开一件活」的规则)已随迁。它要活的状态(已完成 / 评审中)才谈得上,而活的状态要存储。本片**保留移植原样、不接线**,`#[allow(dead_code)]` 豁免留到切片五复查。它不是过时路径(那种要按 `CLAUDE.md` 直接删),是还没接线的新路径——区别写进注释,免得下一个人删错。

## 7. 验收设计(不写单元测试)

指挥器:`next/crates/bw-engine/examples/agent_session.rs`,风格照已有的 `port_readback.rs`(分段打印 + 末行 `AGENT_SESSION_OK` + 退出码)。

### 7.1 四件要证的事,以及本机能证到哪一步

| 要证的 | 怎么证(读回什么) | macOS 本机 |
|---|---|---|
| **真会话起得来** | `--real` 档:在临时 git 工作区起一次真会话,读回 `~/.claude/projects/<编码路径>/<我们指派的 uuid>.jsonl` 存在且非空 | ⚠️ 补了 Unix PTY 后端才行 |
| **注入真发生** | 装配后的系统提示词落文件 → 比对每块的标签与指纹;真跑档再从 jsonl 首条记录里读回系统提示词片段 | ✅ 装配部分能证(不依赖 PTY);jsonl 读回要真跑 |
| **续接真同路径** | 同一路径删了重建 → 用同一 uuid 续接 → 断言**同一个** jsonl 在增长(行数变多),且**没有**新建第二个;再做反证:换一个路径续接,断言找不到会话 | ✅ 反证档能证(只读文件系统);正向要真跑 |
| **取消真杀进程** | 起会话记下进程号 → 取消 → 断言进程不在了,**且子孙进程也不在**(按进程组断言) | ⚠️ 要 PTY |

### 7.2 确定性断言:mock 扛,进常绿门禁

`MockInteractiveExecutor` 已随迁且自我标注,本片直接用它做主力。要断言的六条:

1. `start` 立刻返回、不阻塞(证「只起不等」);
2. `poll` 在结束前是运行中、结束后是 `Finished { ProcessExit }`;
3. 同一工作区第二次 `start` 自动走续接计划(参数里有 `--resume <同一个 uuid>`、**没有**系统提示词旗标);
4. `cancel` 幂等:对已结束的票据再取消 = 成功;
5. **类型断路**:对 `ExecState` 做一次穷举匹配,证明没有 `Done` 这一档,`Finished` 的三档也没有一档能读成「已验收」;
6. 注入清单与落盘的系统提示词一致(标签、条数、指纹三项对得上)。

再加两条**故意失败**的断言(照 `probe_all` 那条「必须含一条故意失败路径」的规矩):工作区路径不存在 → 如实报未连接;当前分支与要求的不符 → 如实拒绝。防伪证明比正向断言更能挡住假绿。

### 7.3 真实路径怎么留档(不进常绿门禁)

- `--real` 只在人手或监理脚本里跑,失败可安全重试(网关 529 抖动是已知常态);
- 每次跑落一份证据目录:装配后的系统提示词、命令行原样、jsonl 路径与行数、退出码、耗时;存本机 `verification/`,**不入仓**(与既有做法一致);
- 报告里引用证据目录路径与关键读回行,不拿截图当证据。

### 7.4 macOS 的现实约束(如实,不假装)

**今天的事实**:`run_skill_pty` 是 `#[cfg(windows)]`,非 Windows 走接口默认实现,直接返回「这个执行器不支持 PTY」。移植件里还有一条 macOS 用 `osascript` 开系统终端的老路,但它自己的注释就写明:拿不到 claude 的句柄、判定不了完成,所以如实返回「未完成」——而 v1 设计 §8 明确禁止把它当回落(会造出第二条体验不同、判定不了的路径)。

**所以**:本机不补 Unix PTY 后端,「真会话起得来 / 续接真同路径 / 取消真杀进程」三件里真跑的部分**全部证不了**,能证的只剩计划装配、注入清单、路径反证、mock 生命周期这四块。

**建议补**,这是本片唯一一处「新写」:

- 把平台分叉从函数体里提成 v1 §8 呼唤过、但一直没提取的那个接缝(v1 §13 如实记着「seam 粒度偏差,当前不提取」);
- Windows 实现 = 现有 `run_skill_pty` 函数体**整段搬进去,零逻辑改写**;
- Unix 实现 = 新写,约百行,用 `portable-pty`(成熟上游库——按「选型优先于自建」,用库不算自建;v1 当年在非 Windows 侧本来就把它留成保活依赖)。

**举证**:不补的话,切片三的核心验收在本机为零,而本仓核心纪律是一切实跑。补的成本是一个接缝加一个上游库的常规用法;不补的成本是这一整片只能靠 mock 交付。

**如果主控决定不补**:那就把切片三的验收如实降级为「计划装配 + mock 生命周期 + 路径反证」,并在计划里写明「真会话验证欠在 Windows 机器上,未验」——**不许用 mock 结果冒充真跑结论**。

**顺带一条减法**:Unix 后端补上以后,`osascript` 那条分支就是过时实现路径(永不接线、判定不了完成、取消不了),按 `CLAUDE.md`「发现过时的实现路径直接移除」删掉,不留兼容层。

## 12. 开放问题(拿不准的,不硬拍)

1. **`--session-id` 在交互式(非 `--print`)模式下是否真被接受?** 帮助文本没有像别的旗标那样标注「仅 `--print`」,但没实测。它是 §2 整条身份方案的地基。建议开工第一件事就实测(在临时目录起一次,读回同名 jsonl);不成立就退回 hook 捕获 + `--continue`,并把注册表行的 `session_id_flag` 置 `None`——设计其余部分不受影响。
2. **Unix PTY 后端补不补**(本片唯一新写项)。不补则本机验收降级到 mock 级,见 §7.4。这条要主控拍。
3. **`ExecSpec.budget_usd` 在交互式 claude 上接不上**:如实无视并大声标注,还是直接按「不支持」报错拒绝?我倾向前者(拒绝会让调用方以为存在别的路),但这是产品口径,不该我定。
4. **内建 git 辅助函数住在 `bw-connector` 里的命名将就**(切片二裁决 #1 的结果:它们不是连接器,却住在连接器 crate)。本片没被这条绊到(适配器不供给工作区),但切片四编排层要用时会正面撞上。何时抽出来、抽去哪,留给切片四。
5. **cursor 那行何时标成已核对**:需要一台装了 cursor 的机器跑一次 `--help` 逐项核对。
6. **票据不可变,上游会话号靠指派才填得上**。若将来某家 CLI 不能指派,票据里这个字段会长期为空——那时是改契约(让轮询回传身份),还是接受「身份只住在 agentcli 层内部」?本片按后者做,不预埋。

9. **移植件里的单元测试删除时机**(§5.5):先补指挥器再删,还是同一个 commit 里一起动?倾向前者,但会多一个中间态 commit。
