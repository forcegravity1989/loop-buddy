## 1. 壳发起开工:从按钮到运行管理器的最小闭环

这一节清偿台账第 19 条(壳不发起开工,因此逃生舱和嵌入终端在真实部署里永远等不到一条「自己开工的、还活着的」运行)与第 20 条(工作区根目录这个深链变量至今没人消费)。

### 1.1 用例落点:编排层的一个函数,不是命令总线上的一条命令

编排层今天的命令总线上有七条命令,**开工不在其中**——这是切片五C 的既定判断,理由写在编排层的模块文档里:开工要驱动的那个运行管理器**不属于**命令总线那个把手,两者各自独立持有一条数据库连接;把开工塞进总线,就要让总线那个把手去持有运行管理器,那条切片四钉下的边界当场就破了。

本片不推翻这条判断,而是顺着它给开工一个正经的家:

```rust
// bw-app/src/cmd/issue.rs —— 与既有的「切阶段」「状态转移」同址
pub async fn run_issue(
    store: &SqliteStore,
    manager: &RunManager,
    workspaces_root: &Path,     // 深链变量 BW_WORKSPACES 的第一个真实消费者
    issue: IssueId,
    connector_name: Option<String>,
) -> Result<RunId, AppError>;

pub async fn cancel_run(manager: &RunManager, run: RunId) -> Result<(), AppError>;
```

**为什么是自由函数而不是某个把手上的方法**:它要同时握住两个独立的持有者(存储层的那份、运行管理器的那份),谁也不该吞掉谁。自由函数把「这次开工需要哪两样东西」写在签名里,调用方(壳、指挥器)各自把自己手里的那两样递进去,不产生第三个持有者。

**这条函数的价值在于它能被 headless 指挥器直接调**——验收因此不依赖点击。壳上那个按钮的处理器只有三行:发一条本地命令、内核线程收到后调这个函数、把结果变成一条提示。

### 1.2 开工用例的六步(每一步失败都如实停在原地)

```
run_issue(issue):
  ① 读活 → 读它所属项目 → 项目没有配本地检出根 → 如实拒绝「这个项目还没有本地检出,开不了工」
  ② 造工作树:按活编号在主检出的兄弟目录造一棵、切到这件活自己的分支
       └ 造失败(不是 git 仓库 / 磁盘满 / 分支名撞了)→ 如实回原文,不重试、不换路径
  ③ 交给运行管理器开工(工作区路径 + 分支名 + 注入块 + 预算上限)
       └ 这件活已经有一个交付运行 → 如实回「已经有一个在跑」+ 那条运行的编号
       └ 这个工作区已经被别的运行占着 → 如实拒绝
       └ 连接器零条 / 多条 → 如实报,绝不「取第一条」蒙混
  ④ 运行管理器插行占名额、把活推到「进行中」、派出去起会话(这一步及之后全在它内部)
  ⑤ 返回运行编号
  ⑥ 壳收到编号 → 重建一次界面数据 → 「当前 Loop」段与逃生舱当场出现这条运行
```

第②步的工作树供给**只造不删**——这是切片五 §6.3 钉死的语义(上游按工作目录编码存会话,续接必须同路径;一次交付运行结束后它的会话很可能还活着,自动删就再也接不回来)。代价是工作树越积越多,台账第 14 条已登记;本片是它第一次在真实项目上开始真的积累,如实再记一笔。

**注入块里放什么**:本片放**空**,并如实标注。复利链(蒸馏出的技能正文、标准文件、目录块)在新工程里还没有任何一片建过,注入块里今天没有真实内容可放;造一段占位文本塞进去,就是给上游会话喂 BW 自己编的东西。空注入块 + 一句如实说明,比假内容好。

**预算上限从哪来**:沿用旧工程的老约定,从环境变量读一次;没配就是不封顶(如实,不悄悄给一个 BW 自己拍的数字)。这个值要显示在运行卡上,让人知道这次跑没跑在封顶下。

### 1.3 真实连接器从哪来:壳启动时按项目装配

今天壳给运行管理器的是一个**空**注册表(切片五E 如实注释过:本片不发起开工,空的不影响聚合快照)。本片要把它换成真的。

**推荐形态**:壳启动、读完项目清单之后,给**每一个有本地检出根的项目**装配一条执行连接器(agent 类 CLI 那一档,首家是 claude),绑定到该项目。这正是「真实并行三件」那一档指挥器已经跑通过的装配方式,不是新发明。

三条如实标注:

- **连接器登记不落库**。新库里没有连接器表,新工程至今没有一片建过它。壳里这段装配是**按约定生成**的,不是从库里读出来的——因此「换一家 CLI」「一个项目挂两条」今天做不到,要改代码。登记为缺口(§11 第 5 条)。
- **不扩项目仓那份采集连接器正本**。它的词表今天只认脚本一种(格式文档写死了:出现别的值整份文件解析失败),要把 agent 类 CLI 塞进去,就要同时改格式文档、改解析器、把解析器搬进工作区能力那一层——那是独立一件事,不塞进本片。
- **装配发生在壳里,不在编排层**。编排层的正式依赖里没有引擎(分层门禁查真实依赖图),而 agent 类 CLI 的驱动住在引擎里。壳是唯一能把两边接起来的地方,这与切片五E 已经写在 Cargo 注释里的判断一致(「壳按需组装真连接器」)。

### 1.4 开工之后界面怎么变新:给运行管理器加一条事件广播

**问题**:壳不持有时钟(门禁机器守着),界面数据只在「人发了一条命令」之后重建。点完开工,那条运行会在几秒内从「起步中」走到「在跑」,再过几分钟走到关门——但界面上那张卡会一直停在开工那一刻的样子,直到人再点一次刷新。**这看起来就是假死**,而假死比不刷新更坏:它让人以为系统卡了,或者更糟——以为事情没在发生。

**推荐**:运行管理器加一条事件广播(它已经有一条同族的广播用来送终端字节,不是新机制);状态真的变了才发一条,内容只有「哪条运行、现在什么状态」。壳的内核线程多订一条通道,收到就重建一次界面数据。

**这不违反「壳不持有时钟」**:门禁查的是壳源码里有没有定时器构造;订阅一条事件通道是「事件到达才醒」,和嵌入终端那条字节订阅完全同形(切片 5.5 已经在壳里跑通过这个形状,门禁复核零开口)。轮询仍然只发生在编排层——每个运行自己的轮询任务,一如切片四所定。

**代价**:运行管理器的公开面多一个订阅方法;广播容量满时丢最老(与终端字节那条同款语义,丢了也只是少刷新一次,下一条事件到达仍会重建)。

备选是「不加广播,界面上明说『状态不会自动刷新,点这里刷新』」——诚实但难用。列进开放问题 5。

### 1.5 失败如实显示的四种形态

界面上必须能分清这四种,不能糊成一句「开工失败」:

| 形态 | 人看到什么 | 数据上是什么 |
|---|---|---|
| 开不了工(前置不满足) | 「这个项目还没有本地检出」/「这件活已经有一个运行在跑」 | 一条运行行都没有 |
| 起不来(会话没起成) | 卡片当场变红:「起步失败」+ 上游报错原文 | 运行行留着,标成失败、结束事实是「起步失败」、账结过一次 |
| 起来了但没干成 | 卡片显示结束事实原文 + 耗时 + 上游会话号 | 运行行关门 + 结账;**活的状态一个字不改**(结束不等于干成) |
| 人点了取消 | 卡片显示「已取消」 | 结束事实是「取消」;取消是幂等的,重复点不改任何字段 |

第三行那句「活的状态一个字不改」是切片四 §3.6 的既定语义,本片原样守:运行结束**不会**把活推到评审中(那要看远端合并请求的状态,是另一条正交的巡检,新工程还没建)。因此真实使用时会看到:一次跑完了,活还停在「进行中」——**这是如实,不是漏做**,界面上要有一行说明,免得被当成 bug。

### 1.6 嵌入终端与逃生舱:真会话上的验收路径

切片 5.5 把终端组件整体移植进壳了,但如实标注过:壳不发起开工,所以真实部署的进程里永远没有一条「自己开工的、还活着的」运行,终端因此永远显示不出来。本片正是解除条件。

**验收路径(三段,缺一不可)**:

1. **字节真的流到界面**:在真实项目上点一次开工(或用 §6.2 的深链档触发),嵌入终端里出现上游 CLI 的真实输出。这一段要人眼看——截图或用户自己在屏幕上核。
2. **逃生舱的命令真能跑**:卡片上那行「到你自己的终端里续接」的命令,原样复制到另一个终端里执行,能接回同一个会话(同工作目录 + 同会话号)。这是切片三验过的硬事实,本片是它第一次在真实使用中被用上。
3. **上游会话号不是编的**:界面上显示的会话号,能在上游自己的会话文件目录里找到同名文件。找不到就如实标注找不到,**绝不因为「界面显示了」就宣称接通**。

第 1 段和第 3 段都以真会话为前提,因此都在 `--real` 那一档里(§6.3),不进常绿门禁。第 2 段的命令语法本身在切片五E 已经用深链 stderr 证过一次,本片只是第一次真的拿它去接。

## 2. 一次性导入器

### 2.1 定位:跑一次、报一次、人确认一次

计划 §5.2 的原话是「旧库不自动升级,一次性导入器,逐实体计数 + 人工确认」。本稿把它落成一条硬边界:

- **它是一个命令行程序,不进壳**。界面上没有「导入」按钮,永远没有。
- **它默认只看不写**。不给确认参数时,它只读旧库、打印计数表和差异清单,一个字节都不写新库。
- **写要显式说**。加上确认参数才真的写,而且写之前把同一份计数表再打一遍,末行打印「即将写入」。
- **它不是同步器**。跑完之后旧库与新库各过各的日子,没有任何机制会再让它们对账。旧库继续躺在原地(旧应用即使归档,库也不动),想查历史就直接查它。

### 2.2 七类实体的新旧形状对照

下面六张表逐实体列出:旧库有什么、新库要什么、怎么转、**哪些列在新库没有家**(最后一列是本节的重点——含糊过去就等于让导入器悄悄丢东西)。

#### ① 项目

| 旧库的列 | 新库 | 怎么转 |
|---|---|---|
| `id` / `name` | 同名 | 原样(编号沿用,见 §2.6) |
| `workspace_path`(真执行器目标目录) | `root_path`(本地 git 检出根) | 原样;空串 = 未配置,如实空 |
| `active_stage`(文字:prototype/build/optimize/growth/ops) | `active_stage`(数字 1..5) | 按五阶段的固定次序换算;**旧库这一列不可空、默认原型**,新库可空表示「尚未开棒」——旧库分不出这两者,导入时一律按旧值给数字,并在报告里注明「旧库没有『尚未开棒』这个状态,导入后每个项目都会有一棒」 |
| `created_at` | 同名 | 原样 |
| **没有家**:`kind`(项目类型)、`descr`、`phase`(运行中/冷启动)、`cycle`(时期)、`benchmark`(对标)、`opportunity`(机会缺口)、`allow_commands`、`remote_path`/`remote_host`/`provider`(远端身份三件套)、三个信号缓存列、`updated_at`、`rev` | | 逐条打进「未导入列清单」。其中远端身份三件套要单独说一句:新工程里「这个项目对应远端哪个仓」住在连接器的绑定里,而连接器今天不落库(§1.3),所以这三列**确实无处可去**,不是漏设计 |

#### ② 目标(北极星)

旧库把北极星做成项目表上的四个文本列;新库把它做成指标表里层级为「北极星」的**一行**(切片五 §1.3 的纠偏:北极星也是一条指标,否则它永远挂不上观测、永远是灰的)。

| 旧库 | 新库 | 怎么转 |
|---|---|---|
| `project.north_star` | 指标行的 `name` | 原样 |
| `project.ns_def` | 指标行的 `def` | 原样 |
| `project.north_star_collect_kind` / `_query` | 指标行的采集方案两列 | 原样 |
| —— | 指标行的 `target_raw` | **旧库没有北极星的目标值**,新库留空;留空 = 这条指标没有目标,派生链据此给「未知」,如实不点灯 |
| —— | 指标行的 `origin`(来自正本 / 手建) | 见下方判定规则 |

**判定规则(北极星这一行的来源怎么定)**:读这个项目本地检出根下那份指标正本文件,如果文件存在、且它的北极星一节的名字与旧库这一行**逐字相同**,就标成「来自正本」;否则标成「手建」。

这条规则不是洁癖,是防一个真会咬人的坑:指标表上「同一个项目 + 同一层 + 同一个名字」是唯一的,而正本同步器**只碰来自正本的行**。如果把一条其实来自正本的北极星导成「手建」,下一次同步会试图新建一条同名的正本行,当场撞唯一索引报错;反过来把手建的导成「来自正本」,下一次同步会因为正本里没有它而把它自动停用。两种错都会在真实使用的第一天暴露。列进开放问题 6。

### 2.4 三处硬碰撞(不含糊,逐条给处置)

**第一处:五条同名指标撞新库的身份唯一约束。**

旧库里每个项目都有五条名字完全一样的指标(「阶段完成 Issue 数」),靠「这条指标上卷到哪一阶段」那一列彼此区分;新库的指标身份是「项目 + 层级 + 名字」,那一列不存在,五条会塌成一条。真库里这一族共 15 行,底下挂着 **30 条真实观测**(aihot 29 条、个人画像 1 条)——直接塌掉就是丢掉将近一半的观测。

**处置**:导入时把阶段名接在指标名后面(例:「阶段完成 Issue 数 · 运维」),观测跟着它原来的那条走,天然对得上。两条限制写死:

- **只对「手建」的行这么干**。真库里这一族 15 行全是手建,不与任何正本冲突。
- **来自正本的行一律不许改名**。改了下一次同步就认不出它,会新建一条并把老的停用,观测从此变成孤儿。真遇上正本行撞名,整条如实拒绝并打印,让人去改正本文件——那才是它该被改的地方。

改名的每一行都要**逐行打印进差异清单**,因为这是导入器造了一个旧库里不存在的名字,人必须看见。

**第二处:产物证据无归宿。** 见 §2.2 第⑥条与开放问题 1。

**第三处:新库的正常写入面写不出历史。** 新库存储层的写入方法是给「此刻正在发生的事」设计的——建项目不收创建时刻、建活不收状态与结算时刻、记观测不收创建时刻(都由实现自己取当前时刻)。导入要写的全是历史时刻与历史状态,这些方法一个都用不上。

**处置**:存储层新开一条**导入专用的写入面**,方法收完整的行(含所有时刻与状态),全部走「撞了就跳过」的插入。两条硬约束:

1. **只在开了导入这个 cargo 特性时才编译出来**。壳的产物里不开这个特性,那些方法在壳里**根本不存在**——不是「有但不许用」。这与「观测表接口上就没有更新删除方法」是同一路数:结构约束,不是纪律。门禁加一条守卫查壳的特性集(§8)。
2. **这条写入面里不许有任何更新或删除方法**,只有插入。观测的两条数据库触发器照旧生效,导入器也绕不过。

**为什么这不算给「完成永远由人点」开后门**:导入写的是「这件活在旧库里当时就是已完成」这个历史事实,不是一次状态转移——它不经过合法转移表,因为它压根不是转移。但这个区别只有靠特性开关才立得住:开关关着,生产路径上就没有第二条能写「已完成」的路;开关开着,那是一次性导入,人在命令行上亲自确认过。这条判断要写进代码文档与提交正文,不能只写在这里。

### 2.5 形态:命令行、默认只看、计数 + 差异 + 确认门

```
cargo run -p bw-app --example import_legacy -- --from <旧库路径> --to <新库路径>
        # 默认:只读旧库,打印计数表 + 差异清单,一个字节不写

cargo run -p bw-app --example import_legacy -- --from <旧库> --to <新库> --confirm
        # 真写:先把同一份计数表再打一遍,末行 IMPORT_WROTE <各实体条数>
```

输出分四段,每段都要能被人直接看懂:

1. **计数表**:七类实体各读到多少条(§2.3 那张表的样子)。
2. **差异清单**:逐条列出「没有原样导过去的东西」——被改名的指标(逐行)、未导入的列(按实体归类)、未导入的整类实体(产物证据,如果按开放问题 1 的倾向办)、旧库有但新库放不下的状态(例:旧库没有「尚未开棒」)。
3. **拒绝清单**:撞了唯一约束又不能自动处置的(重复的活编号、来自正本的行撞名),整条不导,原因逐条打印。**只要拒绝清单非空,就一条都不写**——半截导入比不导更难收拾。
4. **末行标记**:只看档打 `IMPORT_DRYRUN_OK`,真写档打 `IMPORT_WROTE`。与仓里既有指挥器的末行标记同款惯例。

**人工确认门就是这两次运行之间的那个人**。工具不做「按 y 继续」这种交互——命令行里的确认参数就是确认动作,它留在命令历史里,比一次按键更可查。

### 2.6 幂等语义:沿用旧编号 + 撞了跳过 + 一张导入流水

**推荐:身份编号原样沿用旧库。** 项目、指标、观测、活、交棒五类的编号都是随机串,新库照单收下。这样带来三件好事:

- **重复导入天然安全**:第二次跑,主键全撞,数据库自己跳过,不产生重复行。
- **两边对得上**:新库里任何一行,拿它的编号回旧库一查就是同一条,证据链不断。
- **不需要一张编号映射表**:观测挂哪条指标、活挂哪个项目,原样搬过来就是对的。

北极星那一行是唯一的例外(它在旧库里不是一行指标,没有自己的编号),给它新的编号即可——「一个项目至多一条北极星」是数据库钉死的,第二次导入照样插不进去,幂等不靠编号也成立。

**再加一张只追加的导入流水表**,每次真写记一行:旧库路径、旧库文件指纹、各实体写入条数、时刻。它的作用不是防重复(防重复靠上面那条),而是**让第二次运行能说人话**:「这份旧库在某月某日已经导过一次,本次新增 0 条」——而不是静悄悄什么都没发生,让人以为工具坏了。

**为什么不选「拒绝二次导入」**:第一次导入如果在中途因为环境问题断了(磁盘、权限),拒绝二次就把人锁在半截状态里,只能删库重来。撞了跳过 + 如实报数,天然就是一条可重跑的路。

### 2.7 旧库只读打开,并且要证明它是只读的

旧库用只读模式打开(连接串上明确声明,不是靠自觉),而且**不带自动建库**——路径打错时应当直接报「打不开」,绝不悄悄建一个空库然后报告「导入 0 条」。

**证明方式**:导入器在跑完之后打印旧库文件的修改时刻与大小,验收时与跑之前的值比对,逐字节相同。这比「代码里写了只读」更硬——本仓库有过教训:一个本意是校验的工具因为参数位置写错,把库先删了再报成功(那次的教训是「验存量库只能用专门的迁移校验工具」)。本片再踩一次的代价是用户的真实日常库,所以这条读回是**必须项**,不是加分项。

**仓纪律再重申一遍**:真实日常库只用副本读回,绝不直接写。因此真实导入的第一次运行也要先拷一份旧库副本,对副本跑一次全流程(含真写档),确认新库长得对,再对真库原件跑只看档核对计数——真写档指向的**永远是新库**,旧库全程只读。

|---|---|---|
| ① 项目目标 | 北极星一句话来自真实正本文件,不是硬编;定义与采集方案能点开 | **真数据**。信号可以是「未知」灰——北极星在旧库里没有目标值,导进来也没有,如实不点灯 |
| ② 五角色责任 | 五张责任卡照常显示(它们与项目无关,来自内核静态元数据);当前这一棒高亮;每一棒名下的活数是真的 | **真数据**(活的阶段归属由导入带来,不需要手工补) |
| ③ 引领指标 | 三层卡片全部来自真实指标行;至少有一条卡片**不是**灰的(有观测、有目标、真的算出了信号) | **真数据**。没观测的那些如实灰,并显示「无观测 · 未知不等于绿」 |
| ④ 当前 Loop | 至少一条**由这个进程自己开工**的运行,从起步走到关门,卡片上的数字与库里对得上 | **真数据,而且必须是真会话**——这一段是 `--real` 的前提所在(§4.3) |
| ⑤ 风险与决策 | 交棒流水显示真实记录,带险的置顶标红 | 选 aihot 的话**如实空**(它没有交棒记录);要验这一段的真数据,用 WorkflowHub 那 2 条 |
| ⑥ 交付证据 | 三栏:运行的账(来自第④段那次真运行)、每条观测的出处(导入带来的)、工作区此刻的真状态(现采) | **三栏全真数据**。第三栏用工作区里跑同一条 git 命令复核,不与库比对(工作区本身就是事实源) |

**「跑完整六段链」这句话的判据**:六段全部渲染、其中五段有真数据、第⑤段(选 aihot 时)如实空且有说明文案、第④段是一次**真会话**的完整生命周期。第④段做不到时,**不算跑完**——这正是归档旧应用要等 `--real` 的原因(§5.2)。

## 4. `--real` 全链与信任对话框:只摸事实,不拍板

台账第 6 条记着:全新工作区首次交互式启动上游 CLI 时,在进入正常界面之前会先弹两道确认;第二道的默认选项是危险方向(选错等于会话直接退出)。那一条的待办写着「需要专门设计怎么识别画面该发什么键,或者调查有没有配置能预先标记为已信任」。本节把**事实**摸清楚,把**选项**摆出来,**不做决定**——替用户点安全确认是主控明言留给用户的事。

### 4.1 已核实的技术事实(六条,逐条注明怎么核实的)

1. **信任记录是按绝对路径记的,住在上游 CLI 自己的配置文件里**(用户主目录下那份 JSON 的 `projects` 段,每个路径一个条目,里面有一个「信任对话框已接受」的布尔值)。**核实方式**:直接读该文件的结构(只读键名与布尔值,没有碰任何凭证字段)——本机 40 个项目条目,31 个已接受、9 个未接受。
2. **信任判定会向上找父目录**:先查当前工作目录这条精确路径,没命中就逐级往上找父目录,任一祖先被信任就直接通过。**核实方式**:在已安装的上游 CLI 程序文件里检索到这段判定逻辑的原文。
   - **这条直接回答了台账第 6 条留的那个问题**:BW 生产路径上每件活的工作树是主检出的**兄弟目录**,不是子目录——所以它**不会**从项目根继承信任,每一棵新工作树都是一条新路径,都会弹第一道对话框。这不是只在验证脚本里才发生的事。
3. **上游 CLI 自己给出了预置信任的路径**:程序文件里有一句面向用户的提示原文,大意是「接受信任对话框,或者在那份配置文件里把这个路径的『信任对话框已接受』设为真」。**核实方式**:同上,检索到该提示的原文字符串。
4. **第二道对话框(跳过逐次授权的模式警告)有一个对应的设置项**,而且读取自四个层级(用户设置 / 本机设置 / 命令行传入的设置 / 策略设置)。**接受那道对话框的那一支代码,自己就会把这个设置写进用户设置**——这解释了它为什么会「弹过一次就不再弹」。**核实方式**:同上。
5. **这台机器上那个设置项现在是「已开」**,而 2026-08-07 的设置备份里**没有**这一项;设置文件的修改时刻是 2026-08-10 22:05,正好落在台账第 6 条登记的那一天。合理推断是那次探针实验里手动选了「接受」,顺带把它落盘了。**因此第二道对话框在这台机器上此刻大概率不会再弹**——但这是**这台机器的现状**,不是 BW 能依赖的前提(换一台机器、清一次配置就没了)。
6. **命令行还有另一条相关旗标**(权限模式,取值里有「绕过权限」这一档),与今天在用的那个「跳过逐次授权」旗标是两个不同的入口;**两者是不是走同一道警告对话框,没有实测过**,如实标注未验证。

**顺带一条对台账第 8 条的解释**:真实并行三件那一档在临时目录里造的六个工作区,在上游配置里各自留下了条目,其中 3 个「已接受」、3 个「未接受」——说明切片三-2 补的那次自动回车**确实带过了一部分第一道对话框**,不是完全无效。

### 4.2 三条候选路线(逐条摆代价,不排序)

| 路线 | 做什么 | 代价 / 风险 |
|---|---|---|
| **甲 · 预置信任** | 造完工作树、起会话之前,由 BW 往上游那份配置文件里给这条路径写一个「已接受」 | BW 去改另一个工具的配置文件,而且是**替用户预先接受一个安全确认**;文件是上游自己的格式,它改结构 BW 就跟着坏;并发写(十件活同时开工)要考虑覆盖 |
| **乙 · 认画面应答** | 起会话后识别当前屏幕上是哪一道对话框,按需发对应的按键 | 要抓屏幕文本再判断,与「绝不抓屏幕文本」那条纪律正面冲突;对话框文案一改就失效;第二道的默认是危险方向,认错画面 = 会话被自己关掉 |
| **丙 · 让人接一次** | BW 不自动应答;第一次在某个工作区起会话时,把嵌入终端推到人面前,由人自己在终端里点那两下 | 最诚实、零越界,但**每一棵新工作树都要人点一次**(见事实 2:兄弟目录不继承信任),百级并行时这条路不成立 |

**一条能让丙变得可行的观察**(仍属事实,不是主张):既然信任判定会向上找父目录,那么**只要工作树的公共父目录被信任一次**,其下所有工作树就都通过了。今天工作树造在主检出的兄弟位置,公共父目录就是主检出的上级目录。要不要把工作树集中造到一个专门的目录下(那样只需要信任那一个目录一次),是产品与安全口径的问题,不在本稿拍。

### 4.3 解耦:什么以它为前提,什么不受它阻塞

**以它为前提的只有两件**:六段第④段「真会话的完整生命周期」,以及归档旧应用(§5.2)。

**不受它阻塞的**:导入器全套(它不碰上游 CLI)、开工闭环的用例与指挥器(mock 连接器就能跑绿)、真实项目的六段其余五段、壳上的按钮与事件订阅、验证壳深链截图。

**因此提交顺序上,`--real` 那一档排在最后,而且它失败不影响前面所有提交的验收结论**——如实标注「第④段未点亮,原因是台账第 6 条未解除」,不悄悄用 mock 顶上冒充。

## 5. 归档旧应用

### 5.1 归档对象与不动的东西

**归档的**:主线上的旧应用(仓根那个 Cargo 工作区里的旧 crate 与旧壳)。

**不动的**:

- **v1 分支永不归档**(计划第五轮定位①:它是多人协同场景的活分支,服务真实用户)。
- **用户的旧数据库不动**(归档的是代码,不是数据)。历史查询照旧直接查它。
- **旧的验证壳接法不动**(验证壳已经有指向新壳的一档,旧档保留)。
- **git 历史不动**(不改写历史,不删分支)。

### 5.2 两步走,人工确认门在中间

**第一步(本片做,全部可逆)**:

1. 常绿门禁只跑新工程那一档,旧工程的检查从 CI 里摘掉(不是删脚本,是不再跑)。
2. 仓根 `CLAUDE.md` 与旧工程各 crate 顶部加横幅:「历史档案,现状以 `next/` 为准」——照仓里既有的横幅惯例办(plan/00-05 与历史交接记录都是这么标的)。
3. 打一个名字好记的标签(例:`legacy-app-final`)指向归档前最后一次提交,让「回去看旧应用长什么样」不需要翻哈希。

**人工确认门在这里**:第一步做完之后,拿 §3.3 那张六段验收清单跑一遍真实项目,把结果给用户看;**用户点头之后才有第二步**。

**第二步(不在本片自动执行)**:把旧工程的目录挪走(或直接删,历史里还在),`next/` 提到仓根,`CLAUDE.md` 的常用命令段整段重写。这一步一动,仓里几乎每份文档的路径都要跟着改,而且它是不可逆的那一半——所以它必须是**单独一次提交**,由用户显式发话再做。

## 6. 验收

### 6.1 常绿档(进 CI,不依赖任何外部服务)

两个新的 headless 指挥器,末行各打一个标记,与仓里既有的同款惯例:

```bash
cd next && cargo run -p bw-app --example import_legacy     # 合成老库 → 导入 → 读回,末行 IMPORT_READBACK_OK
cd next && cargo run -p bw-app --example issue_kickoff     # mock 连接器的开工闭环,末行 KICKOFF_OK
```

**导入器那一档怎么做到确定性**:指挥器自己在临时目录里**手工建一个旧库**(照旧 schema 的原文建表、插入自己造的行),而不是去碰用户的真实库。这份合成旧库要**故意造出三处硬碰撞的每一种**:一族同名的阶段指标(带观测)、一条来自正本的行、一条重复的活编号(用来验「拒绝清单非空就一条都不写」)。

读回清单(逐条 sqlite 查,数字对不上就红):

1. 七类实体各写入几条 = 计数表打印的数字。
2. 观测的编号原样保留(拿旧库里的编号在新库里查得到)。
3. 被改名的指标:新名字带阶段后缀,底下的观测条数与旧库一致(**这条最关键**——它证的是「改名没有丢观测」)。
4. 来自正本的行:来源标记原样是「来自正本」(不是被导成手建)。
5. 再跑一次导入(同一份旧库):新增 0 条,总条数不变,导入流水多一行。
6. 观测表的两条数据库触发器仍然生效:试一次更新、试一次删除,都被数据库拒绝。
7. 旧库文件的修改时刻与大小,跑前跑后逐字节相同(**只读的硬证明**)。
8. 拒绝清单非空的那一档:新库里一条都没有(半截导入没发生)。

开工闭环那一档的读回清单:

1. 项目没配检出根 → 如实拒绝,一条运行行都没有。
2. 配了检出根 → 工作树真的被造出来(目录在、分支切对了)、运行行落库、工作区路径与分支名与工作树一致。
3. 同一件活再点一次开工 → 如实拒绝,并给出已有那条运行的编号;运行行仍然只有一条。
4. 连接器零条 / 多条 → 如实报,不「取第一条」。
5. 取消 → 结束事实是「取消」,账结过一次;再取消一次 → 幂等,字段一个不改。
6. 全程活的状态:开工推到「进行中」,结束之后**仍然是「进行中」**(结束不等于干成)。

### 6.2 真实项目档(不进 CI,人跑一次留证)

```bash
BW_DB=<新库> BW_OPEN="aihot 日报" BW_PANEL=hex  ~/Applications/BWDev.app/Contents/MacOS/bwdev-launcher
BW_DB=<新库> BW_OPEN="aihot 日报" BW_PANEL=attention ~/Applications/BWDev.app/Contents/MacOS/bwdev-launcher
```

判据:深链那行 stderr 出现且进程没崩(它尾部那几个数字本身就是第一层读回),再用 `sqlite3` 把六段里每个数字独立查一遍对上。截图是加分项不是必需项(agent 自己截不到真实桌面像素,这是踩过的结论;要么用验证壳由人核,要么把命令原样交给用户)。

### 6.3 `--real` 档(受信任对话框阻塞,单独一档)


三条判据:上游会话文件真的生成且非空;嵌入终端里出现真实输出;逃生舱那行命令复制到另一个终端能接回同一个会话。**撞上台账第 6 条就如实打印、如实判这一档未通过**,不回落到 mock 报成功(悄悄回落是本仓库最恨的那种假绿)。

## 12. 开放问题(拿不准的,不硬拍)

1. **产物登记(旧库 764 行)导不导?** 本稿倾向**不导**,理由是它与另外六类实体在性质上不同:观测、交棒、活、指标定义是「只此一份,丢了就没了」的事实;产物登记当初就是跑 `git ls-files` 从仓库采出来的,仓库还在就能重采,而新工程的交付证据第三栏本来就是读时现采。反方理由也成立:764 行里有 228 行带着「是哪件活登记的」这条关联,那条关联**不在仓库里**,重采采不回来。若主控更看重那条关联,就按 §2.2 第⑥条的 (c) 办(导成一张明确标注「历史存档、不再增长」的表),我不建议 (a)——那会长出一张看着像交付证据、实际永远停在导入那一刻的死表。

2. **第一个真实项目选谁?** 本稿倾向 **aihot 日报**(六段里要真数据的四段它全占;唯一缺的交棒记录如实空)。BW 仓自举的障碍不是技术,是名实:BW 仓根下那份指标正本装的是 WorkflowHub 的指标,自举时一同步就把别人的指标装进来。三条出路(沿用 WorkflowHub 这个名字 / 给 BW 另立一份正本但要先想清楚一个工作区两个项目 / 自举推后)是产品口径,请主控定。

3. **导入器的落点与形态。** 本稿倾向做成编排层的一个命令行程序,与既有指挥器同址同形(不新开 crate、不进壳)。它与指挥器的区别要写清楚:指挥器是验收工具、进常绿门禁;导入器是一次性生产工具,只有它的**合成老库那一档**进门禁,对真实旧库的那次运行不进。若主控认为「生产工具不该长在示例目录里」,备选是给它一个自己的二进制目标,代价是壳之外多一个可执行产物。

4. **幂等语义:沿用旧编号 + 撞了跳过,而不是拒绝二次导入。** 本稿倾向前者,理由是它对「第一次跑到一半断了」有救,而拒绝二次会把人锁死。代价是「重复」这件事变得静悄悄(靠导入流水那一行说人话补上)。若主控要求「第二次必须硬拒绝」,加一条判据即可,结构不动。

5. **开工之后界面靠事件广播变新,还是靠人点刷新?** 本稿倾向加事件广播(§1.4):没有它,点完开工卡片会一直停在「起步中」,看起来像假死。它不违反「壳不持有时钟」(事件到达才醒,与嵌入终端那条字节订阅同形)。反方理由是它给运行管理器的公开面又加了一个方法,而那个把手是本片之外最不该膨胀的东西。请主控划线。

6. **北极星那一行的来源怎么判定?** 本稿倾向「读项目仓正本文件比名字,对上就算来自正本」(§2.2 第②条)。它有一处不干净:导入器因此要读文件系统,而不是只读旧库。备选是「一律导成手建」,代价是下一次同步正本时会撞唯一索引报错(错在第一天就暴露,也算一种诚实)。请主控选。

7. **信任对话框怎么解除?** 本稿**不拍板**,只给了六条已核实的事实与三条路线(§4)。要请主控/用户明确的是三件事:① 允不允许 BW 去写上游 CLI 自己的配置文件(路线甲的本质就是替用户预先接受一个安全确认);② 若不允许,是否接受「每一棵新工作树都要人手工点一次」(路线丙,与百级并行的方向冲突);③ 要不要把工作树集中造到一个专门目录下,好让「信任向上找父目录」这条机制只需要人接受一次——这一条会改工作树的路径约定,牵动续接语义,不是小改。

8. **归档的第二步(挪目录)什么时候做?** 本稿倾向**不在本片**:第一步(摘门禁、加横幅、打标签)全可逆,验收通过就能做;第二步一动,仓里几乎每份文档的路径都要改,而且不可逆。请主控确认「本片只做第一步」这条划线,以及第二步的触发条件(是不是「`--real` 全链通过」这一条就够)。

9. **新库落在哪?** 本稿倾向沿用新壳自己的默认库路径(它与旧壳的默认目录已经刻意不同名,不会互相踩),导入就导进它。备选是给真实使用单独指定一个库路径。两者都不影响「旧库全程只读」,但会影响用户日后启动新壳时默不默认能看到数据。请主控确认。

10. **`--real` 那一档失败,算不算切片七未完成?** 本稿倾向:**切片七的主体(导入器 + 开工闭环 + 六段点亮五段)可以先收官**,`--real` 与归档第二步一起挂在信任问题上,如实标注、不算失败。反方理由是计划 §7 切片七的完成标准原话是「跑完整六段链**之后**才允许归档」——按字面,第④段没点亮就是没跑完。两种读法都成立:一种把切片七看成「工作」,一种看成「验收里程碑」。请主控定这条口径,因为它直接决定台账里那一条怎么记。
