## 1. 六段总控屏

### 1.1 屏的形状:两屏,不是七个面板

新壳一共只有两屏:

```
六段总控(BW_PANEL=hex)          待人处理(BW_PANEL=attention)
┌──────────────────────────┐   ┌──────────────────────────┐
│ 顶栏:项目名 · 健康点 ·    │   │ 需要你出手的事 · N 条     │
│      北极星一句话(常驻)  │   │                          │
├──────────────────────────┤   │ ① 遗留运行(关门没结账)   │
│ ① 项目目标                │   │ ② 评审中等你点            │
│ ② 五角色责任(五张责任卡) │   │ ③ 停在原地的运行          │
│ ③ 引领指标(北→滞→引)     │   │ ④ 指标没数 / 数据过期     │
│ ④ 当前 Loop(运行聚合)    │   │ ⑤ 当前阶段的带险交棒欠账  │
│ ⑤ 风险与决策              │   │                          │
│ ⑥ 交付证据                │   │ 全部安静时:一行「暂时没有 │
└──────────────────────────┘   │ 需要你出手的事」          │
                                └──────────────────────────┘
```

**为什么只有两屏**:第四轮定调第①条问的是「这让工作界面更少了还是更多了」。旧壳有三层正交导航(库 × 视图 × 面板+范围),十一个面板视图;六段总控的产品主张是**一屏看完一个项目的全部要害**。项目之间怎么切?顶栏一个项目下拉,不做项目墙(理由见 §8)。

**顶栏移植 v1 的成果**(plan/23 §2 末行点名的设计参照):项目名 + 健康点 + **北极星一句话常驻、不截断**,定义挂在悬停提示上。这三样是 v1 总览重构里被验证过的版面判断,原样照做。

### 1.2 逐段:数据从哪来,没有数据时长什么样

| 段 | 内容 | 数据来源 | 没数据时 |
|---|---|---|---|
| **① 项目目标** | 北极星一句话 + 它的精确定义 + 它这条指标的采集方案与最近一次采到的值 | 指标表里 `tier='north_star'` 那一行(来自项目仓 `.bw/metrics.toml` 的 `[north_star]` 表)+ 它的观测 | 仓里没这份文件 / 没有这一节 → 灰卡「北极星尚未定稿」+ 一行「怎么定:在项目仓写 `.bw/metrics.toml`」。**绝不显绿** |
| **② 五角色责任** | 五张责任卡:角色名 / 方法论 / 一字诀 / 核心问题 / 方法环节 / 完成清单 / 常见的坑 / 节奏;当前这一棒高亮,并显示这个阶段名下有几件活、各在什么状态 | 前七项**零数据库**,全部来自内核里的五阶段静态元数据(移植件,一个字不改);当前阶段来自项目表新加的一列;每阶段的活数来自活表新加的一列 | 阶段没设 → 五张卡照常显(方法论本来就与项目无关),只是没有一张高亮,并标「尚未开棒」 |
| **③ 引领指标** | 三层,顺序固定:北极星 → 滞后 → 引领。每条一张卡:当前值 + 目标 + 信号点 + 与上周的差 + 按周折线 + 采集方案徽记;引领卡额外带本周目标 | 指标表(定义,正本在项目仓)+ 观测表(值,只追加)→ 内核的派生链现算信号 | 该指标从没有过观测 → 虚线边框灰卡、值显「—」、折线空、尾行如实写「无观测 · Unknown ≠ 绿」。**这套灰的具体形态照搬 v1 的成果**(见 §9) |

| **⑥ 交付证据** | 三栏:① 每次运行的账(结束事实原文、耗时、上游会话号、结没结账);② 每个数字的原始出处(每条观测的来源与出处提示,点开看原文);③ 工作区此刻的真状态(提交数 / 跟踪文件数 / 未提交路径数 / 最近几条提交标题 / `docs/` 下的文档数) | ①运行表 ②观测表 ③**现采**(不落库,读时跑只读 git 命令) | 三栏各自为空时如实空着。第③栏没配工作区 → 「工作区未配置」 |

**两段留白要说清楚,免得被当成漏做**:

- **「项目要务」**(§2 六段链原文里跟在北极星后面的那半句)本片**不建**。理由:它的正本住哪没定——写进项目仓的哪份文件?还是住 BW 本地库?第四轮定调④说「项目仓是唯一事实源,不建第二个知识库」,那它就该在仓里有个正本,但今天没有这样一份文件,也没有格式约定。**凭空建一张 BW 本地表来装它,恰好是那条定调要躲的东西**。列进开放问题 1。
- **「决策」**同理(开放问题 2)。交棒记录是「某天带险交了一棒」,不是「某天拍了一个板」,两者是两回事,不混。

**第④段有一件切片四明文交接过来的活**:运行管理器的聚合快照接口今天只回一个数(当前还活着的运行数),它自己的文档注释写着「刻意保持最小……界面(切片五)真正要用聚合快照时,按那时候的真实需要再加字段,**不预先猜测形状**」。本片就是那时候。按 §1.2 第④行的内容,这一段真正要的是四个数:在跑 / 评审中 / 最近失败 / 遗留未结账。**加字段的提交属于本片**(落在 C),加的时候照四B 的既有纪律——每个字段都得有界面上的真实消费者,不多加一个「以后也许用得上」的。

### 1.3 一处纠偏:北极星也是一条指标,不是项目表上两个文本字段

**旧工程的形态**:北极星是项目表上两个自由文本列(名字 + 定义),外加两个采集方案列。后果是**它挂不上观测**——观测表的每一行必须指向一条指标,而北极星根本不是一条指标,所以它永远没有值、永远没有信号、永远是灰的。v1 的总览重构文档里把这条写成了一句无奈的留白:「北极星采不到 → 如实渲染灰,不越界建采数」。

**新工程照 v1 后来自己的修法办**:v1 在 `f0a187a`(「北极星建 metric 行」)里已经把这条修了。本片直接落修好的形态,不把旧路径带进来——这也是 `CLAUDE.md` 那条「发现过时的实现路径,直接移除它,而不是加兼容层」的直接应用。

落地形态:指标表加一列表示层级,取三个值(北极星 / 滞后 / 引领);北极星是这张表里**至多一行**的一条特殊指标(唯一索引保证至多一条)。它和其它指标走**完全同一条**派生链:有观测有目标就点灯,没观测就 Unknown 灰。项目表上不再有北极星文本列。

**代价与如实标注**:项目仓那份 `.bw/metrics.toml` 里北极星是一个单表(`[north_star]`)、滞后引领是数组表,形状本来就不同——同步器要把这三种形状归一成同一张表的三种层级。这段归一逻辑是本片新写的,不是移植件;它的正确性由指挥器读回一份真实的 `.bw/metrics.toml` 来证(§7.2 第 2 节)。

## 2. 本片的存储增量:只建真有写入方的

切片四A 的判据原样继承:**没有写入方的表就是假表**。本片新建三张表、给两张老表加几列,别的一律不建。

### 2.1 给老表加列:迁移双守卫的第一次真实使用

切片四A 把双守卫(先查列在不在、不在才加)原样移植进来了,但当时**没有调用点**,函数上挂着「留给切片五加列时」的注释。本片就是那一次。

```sql
-- project:五阶段方法论的当前一棒。1..5,NULL = 尚未开棒(不默认成 1——
-- 「还没开始」和「在原型阶段」是两件事,默认成 1 就是替用户拍板)。
ALTER TABLE project ADD COLUMN active_stage INTEGER;

-- issue:这件活归哪个阶段。NULL = 未归类(同上,不默认)。
ALTER TABLE issue ADD COLUMN stage INTEGER;
-- 活的描述正文:六段的「当前 Loop」要显示活在干什么;也是切片四留下的
-- 那条缺口(执行规格里没有任务正文字段)在编排层这一侧的真实来源。
ALTER TABLE issue ADD COLUMN body TEXT NOT NULL DEFAULT '';
```

**规矩不变,写进代码注释**:每加一列,`schema.sql` 与开库流程里的守卫调用**必须同时改**,否则存量库直接崩(本仓库踩过的真坑)。指挥器专门跑一档存量库路径来证这次真的生效(§7.2 附节)。

**顺带如实登记**:plan/23 §10 第 10 条记着「同名索引已存在时,谓词不同的建索引语句会被静默跳过」——本片新建的三张表都带唯一索引,**都是新表新索引**,不改任何既有索引的谓词,所以不触发那条缺口;如果实施中发现需要改既有索引,按那条登记的待办办(先加索引迁移,不能只改 `schema.sql`)。

### 2.2 指标表:三层同构,停用不物删

```sql
-- 指标定义的本地缓存。正本永远是项目仓的 .bw/metrics.toml,BW 只读它、
-- 同步进来,绝不反向改写那份文件(改指标和改代码一样走评审)。
CREATE TABLE IF NOT EXISTS metric (
    id             TEXT PRIMARY KEY,
    project_id     TEXT NOT NULL REFERENCES project(id),
    -- 'north_star' | 'lagging' | 'leading'。三层同构,北极星不是特例。
    tier           TEXT NOT NULL,
    name           TEXT NOT NULL,          -- 文件里没有 id,名字就是身份
    def            TEXT NOT NULL DEFAULT '',
    target_raw     TEXT NOT NULL DEFAULT '',  -- "≥5" "≤24h" "清零" …(内核解析)
    collect_kind   TEXT NOT NULL DEFAULT '',  -- 采集方案:github/connector/bw/script/manual
    collect_query  TEXT NOT NULL DEFAULT '',
    -- 'file'(从正本同步来)| 'manual'(界面手建)。同步器只碰 origin='file' 的行。
    origin         TEXT NOT NULL DEFAULT 'file',
    -- 停用:整条退出派生链,历史观测原样留着,可恢复。永不物理删除。
    archived_at    INTEGER,
    created_at     INTEGER NOT NULL,
    updated_at     INTEGER NOT NULL
);
-- 名字就是身份:同一个项目、同一层、同一个名字只能有一行。
CREATE UNIQUE INDEX IF NOT EXISTS uq_metric_identity ON metric(project_id, tier, name);
-- 一个项目至多一个北极星(部分唯一索引;和「一件活一个交付运行」同款手法:
-- 铁律钉进数据库,不是靠 if 判断)。
CREATE UNIQUE INDEX IF NOT EXISTS uq_metric_north_star
    ON metric(project_id) WHERE tier = 'north_star';
```

**同步语义**(移植旧工程的判断,不重新发明):按「项目 + 层级 + 名字」对上就原地更新定义,**保住原来的行号**(挂在它下面的观测历史不受影响);对不上就新建;正本里删掉的行**自动停用**(不物删);界面手建的行同步器不碰。

### 2.3 观测表:只追加,一个观测一个点

```sql
-- 观测:一个真实数据点。只追加,绝不修改、绝不插值,绝不为了点亮而伪造。
CREATE TABLE IF NOT EXISTS observation (
    id           TEXT PRIMARY KEY,
    metric_id    TEXT NOT NULL REFERENCES metric(id),
    project_id   TEXT NOT NULL REFERENCES project(id),  -- 冗余一列,按项目查不用连表
    ts           INTEGER NOT NULL,            -- 这个值是「什么时候测到的」
    raw_value    TEXT NOT NULL,               -- 原始显示串("60%" "5/7" "842ms")
    source       TEXT NOT NULL,               -- manual/script/github/codehub/connector/…
    source_hint  TEXT NOT NULL DEFAULT '',    -- 「这个数从哪来的」——证据链要能点开
    created_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_observation_metric_ts ON observation(metric_id, ts DESC);
```

**存储层不给这张表任何更新或删除的方法**——只有插入和查询。这不是纪律,是接口上就没有那两个方法。

**手填的值戴徽记**:来源是「手填」的观测,界面上永远带「手填 · 未接入度量源」徽记,接上真采集后徽记自动掉。这条是老规矩,原样守。

### 2.4 交棒表:移植 v1,只追加

```sql

-- 只追加、不修改,事后抹不掉。
CREATE TABLE IF NOT EXISTS handoff (
    id          TEXT PRIMARY KEY,
```

字段与索引**逐字移植** v1 的同名表。

**一处如实的留白**:`CLAUDE.md` 说带险交棒要「永久记下当时缺了什么」;v1 这张表只有一个自由文本的注记列,缺什么是人写进注记里的,没有结构化的欠账明细。要做成结构化的,前提是先有「完成清单勾没勾」的状态表——而勾选状态今天没有写入方(六段总控是只读屏,勾选入口本片不做,见 §8)。**本片照 v1 原样搬,缺什么写进注记**,并把「完成清单勾选状态与结构化欠账明细未建」登记成缺口(§12 第 2 条)。不为了好看而先建一张没人写的表。

> **2026-08-11 主控裁决(切片五-1 修复轮,task-s5a-review.md Important-3 实证)**:`from_stage`/`to_stage` 统一改成 **INTEGER**(1..5,`StageKind::index()`/`from_index()`),不再是本节原文写的 TEXT。v1 移植取的是「阶段交棒审计流水」这个语义,不是列类型本身——原文「逐字移植」的口径与 §2.1(`project.active_stage`/`issue.stage` 都已经是 INTEGER)自相矛盾:v1 从来没有 INTEGER 的 `active_stage` 可比,移植到 next 之后两制并存,评审实证过 §3.2 第⑤条查询(`h.to_stage = CAST(active_stage AS TEXT)`)会因为 `'build'` 永不等于 `CAST(2 AS TEXT)='2'` 而永远查出 0 行——看起来是「没有欠账」,实际是「查不出欠账」,是本仓库最恨的那种假绿。`CLAUDE.md`「不为向后兼容留旧路径」在此适用:next 的库还没有任何生产存量,不留 TEXT→INTEGER 的迁移路径,直接改 `schema.sql`。上面的 SQL 代码块与「逐字移植」这句话保留原文,作为设计过程的账目;实现以本条裁决为准。

### 2.6 信号不进库:读时现算

**推荐:数据库里没有任何一列存信号。** 要用信号时,从这条指标的观测和目标现算。

三条理由,按分量排:

1. **它让铁律从「靠纪律守」变成「结构上写不出来」**。旧工程靠三样东西守「健康只能推导」:一个密封类型、存储层没有设置信号的方法、只有一处重算入口。三样都在,但那一列**存在**,所以「往里写一个绿」在物理上是可能的,只是被拦住了。新工程连那一列都没有——写不出来,不是被拦住。
2. **数据量根本不需要缓存**。一个项目的指标是个位数,观测是几十到几百条;派生链是纯函数,现算的代价可以忽略。缓存是为了省算力,这里没有算力要省。
3. **它顺手消掉一整类 bug**:缓存与真值不一致、重算入口被绕过、重启后缓存陈旧。这些在旧工程都真实发生过或被专门防过。

**代价,如实说**:①「杀进程重开数字前后一致」这条铁律的验证方式变了——不再是「读回缓存列」,而是「重启后重算一遍,结果一样」,指挥器照这个新形态验(§7.2 第 4 节);②将来项目多到需要跨项目汇总时,现算可能要遍历全库,那时再谈缓存,并且要**同时**把密封手法一起搬进来,不能只加一列。

## 3. 待人处理:推导投影

### 3.1 五项,每项都必须有「自然消失条件」

**这一节的判据比清单本身更重要**:第二轮的结论是「待人处理是从数据实时推导的视图,状态恢复行自然消失,绝不做越积越多的告警表」。所以每加一项,**先回答「它什么时候会自己消失」**——答不上来的,不许进这张清单。

| # | 项 | 判据(数据来源) | 自然消失条件 |
|---|---|---|---|
| 1 | **遗留运行**:关了门但没结账 | 运行表:结束时刻有值、结算时刻为空 | 这次运行被结算一次 → 结算时刻落值 → 行退出 |
| 2 | **评审中等你点** | 活表:状态是「评审中」 | 人点「完成」(唯一入边),或退回「进行中」 |
| 3 | **停在原地的运行**:失败或遗留,而且这件活之后没有更接的运行 | 运行表:状态是失败或遗留,且同一件活没有更晚开的运行 | 对这件活重开一次运行(哪怕又失败)→ 有更晚的运行接手 → 旧行退出 |
| 4 | **指标没数 / 数据过期** | 指标表(未停用) × 观测表:一条观测都没有;或最新一条观测按这条指标的节奏窗口算已经过期 | 采到或填到一条新观测 |
| 5 | **当前这一棒的带险交棒欠账** | 交棒表:带险,且交到的那一棒**就是当前这一棒** | 阶段再往前推一棒 → 当前这一棒变了 → 这条不再匹配 → 自然消失 |

第 5 项的判据是本节最需要解释的一处。**带险交棒的记录是永久事实,永远不该消失**——它躺在交棒表里,「风险与决策」段永久可查,事后抹不掉。但如果直接把「所有带险交棒」都塞进待人处理,这张清单就会随项目变老而单调变长,变成那张要躲的告警表。**把范围收成「当前这一棒的欠账」,消失条件就自然有了**:你把这一棒交出去,欠账就不再压在你头上(它仍然被永久记着)。这是「推导投影 ≠ 告警表」的一次真实应用,也是本片最容易设计错的一处。

### 3.2 每项的查询形状

指挥器执行、并原样打印出来给人复核的五条(加两条辅助):

```sql
-- ① 遗留运行(关门没结账)。切片四设计稿 §5.2 第 9 条已经定过形状,本片接上投影。
SELECT r.id, r.issue_id, i.number, i.title, r.state, r.end_kind, r.ended_at
  FROM run r JOIN issue i ON i.id = r.issue_id
 WHERE r.ended_at IS NOT NULL AND r.settled_at IS NULL
 ORDER BY r.ended_at DESC;

-- ② 评审中等人点。「完成」的唯一入边就是这个状态,所以这张清单是 Done 的候诊室。
SELECT id, number, title, updated_at FROM issue
 WHERE status = 'in_review' ORDER BY updated_at ASC;

-- ③ 停在原地的运行:失败/遗留,且这件活之后没有更晚开的运行接手。
SELECT r.id, r.issue_id, r.state, r.end_kind, r.end_detail, r.ended_at
  FROM run r
 WHERE r.state IN ('failed', 'orphaned')
   AND NOT EXISTS (SELECT 1 FROM run r2
                    WHERE r2.issue_id = r.issue_id AND r2.started_at > r.started_at)
 ORDER BY r.ended_at DESC;

-- ④a 从来没有观测的指标(未停用的才算)。
SELECT m.id, m.tier, m.name, m.collect_kind
  FROM metric m
 WHERE m.archived_at IS NULL
   AND NOT EXISTS (SELECT 1 FROM observation o WHERE o.metric_id = m.id);

-- ④b 每条指标最新一条观测的时刻。**过不过期不写进 SQL**——那是内核按这条
--     指标的节奏窗口判的,SQL 只负责把「最新是什么时候」老实交出来。
SELECT m.id, m.tier, m.name, MAX(o.ts) AS latest_ts
  FROM metric m LEFT JOIN observation o ON o.metric_id = m.id
 WHERE m.archived_at IS NULL
 GROUP BY m.id;

-- ⑤ 当前这一棒的带险交棒欠账。
SELECT h.id, h.from_stage, h.to_stage, h.note, h.created_at
  FROM handoff h
 WHERE h.project_id = ?1
   AND h.risky = 1
   AND h.to_stage = (SELECT CAST(active_stage AS TEXT) FROM project WHERE id = ?1)
 ORDER BY h.created_at DESC
 LIMIT 1;
```

> **2026-08-11 主控裁决(切片五-1 修复轮,task-s5a-review.md Important-3 实证)**:统一 INTEGER,v1 移植取语义不取列类型;原文 TEXT 系设计稿自身矛盾,评审实证会导致第⑤项查询恒空。`handoff.from_stage`/`to_stage` 已改 INTEGER(见 §2.4 同一处裁决),这条查询里的 `CAST(active_stage AS TEXT)` 因此是多余的死代码——真要照抄这条 SQL,删掉 `CAST(... AS TEXT)`,直接 `h.to_stage = (SELECT active_stage FROM project WHERE id = ?1)` 做 INTEGER 对 INTEGER 的比较即可(评审 task-s5a-report.md「修复轮」一节在真库上验证过两种写法:①保留原文这条 CAST 查询,②去掉 CAST 的干净版,在改完 schema 之后都能匹配到行——①能匹配纯粹是 SQLite 的类型亲和力把 `CAST(2 AS TEXT)='2'` 又转换回数值去和 INTEGER 列比较这层巧合,不该依赖这种巧合,5D 实现时按②写,不要照抄本节原文①)。上面的原文 SQL 保留不改,作为设计过程的账目。

**④b 那条注释是一条设计约束,不是解释**:过期判断已经在内核里(按节奏窗口算,时钟由调用方传进去,保持纯函数)。**在 SQL 里再写一遍过期阈值,就是给同一个规则开第二本账**,两处早晚分叉。SQL 只交事实,判断留给内核——这和「采集器从不解释」是同一条老规矩。

## 4. 桌面壳骨架

### 4.1 通信模式:移植,但砍掉时钟

**移植的部分**(旧壳与 v1 都是这个形状,已被真实使用验证):一条独立的操作系统线程,里面起一个单线程的异步运行时,**整个编排层被这条线程独占持有**(不加锁、不共享)。界面与它之间只有三条通道:

- 命令进去(界面事件处理器发完就走,不等结果);
- 最新的一份可渲染数据出来(每次处理完命令重建一份,界面订阅);
- 转瞬即逝的提示出来(运行进度、错误提示这类不进持久状态的东西)。

这个形状要原样保留,理由是它已经解决了两个真问题:数据库访问不依赖界面框架自己的执行器;编排层单线程独占,不需要任何同步原语。

**砍掉的部分——壳里一个定时器都不许有。** 旧壳(以及 v1,两边这段代码逐字相同)在这条线程的主循环里挂了两个定时器:一个每 5 秒问一次「有没有定时任务到点」,一个每 100 毫秒抽一次终端字节。plan/23 §9 把前者点名成三处结构病之一(「界面层调度时钟」),§5.1 明令新壳「不持有调度时钟」。

新壳的主循环因此**只有两条路**:收命令、收编排层发回来的事件。到点触发、运行轮询这些事都归编排层自己(切片四已定:每个运行一个自己的轮询任务)。

**这条要用门禁守住,不能只靠人记**:新壳的源码里出现 `interval` / `sleep` 这类定时器构造,门禁直接红(脚本形态见 §10)。这是本片能给「结构病不复发」上的最便宜的一把锁。

### 4.2 命令与事件:按聚合拆,不是一个巨型分发器

plan/23 §1 把「近万行的单个命令分发器」列为重建的头号理由。新形态:

```
bw-app/src/
  lib.rs          ← 只做路由:按命令属于哪个聚合,转给对应模块。不含任何用例正文
  cmd/
    project.rs    ← 打开项目、切阶段、交棒
    metric.rs     ← 同步指标正本、采集、手填观测、停用指标
    issue.rs      ← 开工、取消、状态转移
  view/           ← 六段与待人处理的推导(§4.3)
```

命令与事件的形状(草案,实施时按真实需要收敛):

```rust
pub enum Command {
    Boot,
    OpenProject(ProjectId),
    SetPanel(Panel),                 // Hex | Attention
    SetActiveStage { project: ProjectId, stage: StageKind },
    HandoffStage  { project: ProjectId, risky: bool, note: String },
    SyncMetricsFile { project: ProjectId },              // 读项目仓正本
    CollectMetrics  { project: ProjectId },              // 跑采集连接器
    RecordManualObservation { metric: MetricId, raw: String },
    ArchiveMetric { metric: MetricId },                  // 停用,不物删
    RunIssue { issue: IssueId },
    CancelRun { run: RunId },
    TransitionIssue { issue: IssueId, to: IssueStatus }, // 「完成」的唯一入口
    ProbeConnectors { project: ProjectId },              // 人点才探,不自动
}
```

**「完成」在这条总线上只有一个入口,而且这个入口切片四已经建好了,本片不重新发明**:编排层已经有一个显式的状态转移方法,它的流程是「读当前状态 → 查合法转移表 → 合法才落到存储层的比较并置写」;存储层这一侧也已经拆成两条窄方法——一条是运行管理器唯一能用的、**签名上根本没有状态形参**(所以它天生只写得出「进行中」),另一条是纯机械写、合法性由调用方先查。本片的状态转移命令**直接转给那个已有的方法**,壳里不出现第二条写活状态的路径。指挥器反证的正是这一点(§7.2 第 6 节:全库搜索没有第二条写「已完成」的路径)。

### 4.3 六段的推导住哪:编排层,不新开界面 crate

**推荐:住 `bw-app/src/view/`,不新开 crate。**

三条理由:

1. **推导必须能被指挥器直接调用**。验收要求「六段每个数字读回」——如果推导住在壳里,指挥器就调不到它,只能另写一份查询来核对,那就是同一个规则的第二本账。住编排层,指挥器(编排层自己的示例程序)直接调,验的就是界面真正用的那个函数。
2. **不破五层心智**。plan/23 §5.1 说 crate 划分沿用「内核 / 引擎 / 存储 / 编排 / 壳」五层。旧工程的界面 crate 是第六层,当时的理由是「为将来的 Web 版保住纯函数层」——但新工程的 Web 保活集只有内核一个 crate(门禁只对内核跑 wasm 编译),这条理由在新工程不成立。
3. **减法是纲**。本片已经必须新增两个 crate(壳、工作区能力),第三个要有更硬的理由才配加。

**形态**:`view/` 里全是纯函数,输入是从存储读出来的行 + 一个传进来的时刻,输出是可直接渲染的数据结构。**不读时钟、不查库、不发命令**——查库在调用它的用例里做。这是旧工程界面 crate 那一层被验证过的形状,照做。

列进开放问题 3(要不要独立成 crate),但我的倾向明确。

### 4.4 深链:老纪律照搬,值集缩小

深链启动是本仓库最可靠的渲染证明(界面点击在这套桌面框架上是打不通的,这是踩过两轮的结论)。新壳原样保留这套机制:

| 变量 | 含义 | 新工程的值集 |
|---|---|---|
| `BW_DB` | 覆盖数据库路径 | 不变 |
| `BW_OPEN` | 按名字打开一个项目 | 不变 |
| `BW_PANEL` | 打开哪一屏 | **只剩两个值**:`hex`(六段总控)/ `attention`(待人处理)。旧工程那六个面板值随旧壳退役 |
| `BW_WORKSPACES` | 工作区根目录 | 不变 |

**落地方式照搬旧壳的做法,一处都不改**:解析发生在**编排层线程里、启动流程跑完之后、主循环开始之前**,而且用**真实的命令**去落位(发一条「打开项目」、发一条「切到这一屏」),不是伪造一份渲染数据。然后往标准错误打一行:

```
[BW_OPEN] "项目名" -> panel=Hex 指标=7 观测=23 运行=4 待人处理=3
```

这行出现且进程没崩 = 渲染成功。行尾那几个数字是从真实快照里读的,不是硬编——它让这行日志既是渲染证明,又是第一层读回。旧壳打的是同样形状的一行,原样照抄。

**一处新增**:`[BW_OPEN] project "xxx" NOT FOUND` 时**退出码非零**。旧壳只是打一行就继续跑;验证脚本里「项目名打错了」和「渲染成功」都得从日志文本里分辨,不如让退出码直接说话。

### 4.5 壳的杂项:crate 名、二进制名、框架版本、字体与色

- **crate 名**:`next/crates/app-desktop`(与旧壳同名;两个 workspace 独立,不冲突)。
- **二进制名**:`bw-next`。**不叫 `builders-workbench`**——旧壳的二进制就叫这个,同名会让「我刚才跑的是哪个」在验证时说不清,也会和验证壳(`~/Applications/BWDev.app`)那条已经踩通的路径打架。
- **界面框架版本**:照旧壳硬钉同一个版本(旧工程钉的是 0.7.9)。移植顶栏与指标卡的版面时,版本一致才对得上;将来要升,单独一次升,不和本片混。

## 5. 嵌入终端:本片推后,但把接入点和逃生舱写死

**推荐:切片五不做嵌入终端。**

### 5.1 四条理由

1. **它和本片的产品主张正面冲突**。plan/23 §2 写死:「一人管百级 agent 时,界面呈现的是聚合状态与例外,**永远不是一百面终端墙**」。六段总控就是这句话的落地形态。在建总控的同一片里先把终端墙建起来,顺序是反的。
2. **依赖没就绪**。终端要的是「PTY 字节从 agentcli 层出来、按会话路由到壳」。这条链在 v1 是通的(壳订阅一条带会话号的字节通道,每 100 毫秒抽一次),但在新工程里它要经过**运行管理器**——而运行管理器本体(切片四B-E)今天还没落地。现在设计这条通路,等于对着一个还没定型的口设计。
3. **减法是纲**。第四轮定调①:每个切片都要回答「这让工作界面更少了还是更多了」。本片已经在建两个新 crate 加一个新壳;把 v1 那套终端(约 380 行代码 + 三个随包前端资源,其中一个 280KB)一并搬进来,会让这一片的评审面直接翻倍。
4. **移植成本已经查清,不会丢**。见 §5.3——接入点、代码位置、行数、资源清单都在,下一片照单搬即可。**这是「推后」不是「砍掉」**,v1 伙伴的成果一行不废(第五轮定位②)。

### 5.2 逃生舱:本片给一条真能用的路,不是一个假按钮

「进行中」的运行卡上显示**真实的上游会话号**(agentcli 层首启时指派的那个),旁边一行:

```
上游会话:0f9a…  ·  暂无嵌入终端;在你自己的终端里续接:
  cd <这次运行的工作区路径> && claude --resume 0f9a…
```

三点说明:

- 这条命令是**真的能跑通的**(上游按工作目录编码存会话,同路径 + 同会话号就能接回历史——这是切片三验过的硬事实,所以工作区路径必须一起显示,不能只给会话号);
- 这正是 plan/23 §3 三档接法里的第三档(「外开 + 事实回收」)——不抓屏幕文本、不冒充已同步,状态照旧从运行表和上游会话文件回收;
- 会话号为空(这家 CLI 不能指派会话号)时,如实显示「这家不支持指派会话号,续接方式未知」,**不给一条编出来的命令**。

### 5.3 下一片照单搬什么(查清了,写死在这里)

| 件 | 在 v1 的位置 | 规模 / 形态 |
|---|---|---|
| 终端组件本体 + 前端桥接脚本 | v1 `app-desktop/src/screens/op.rs` 文件末尾一段 | 约 300 行(含常量、注入脚本、按键编码、跨批中文字符切分处理) |
| 壳侧的字节通道与抽取节奏 | v1 `app-desktop/src/kernel.rs` 若干处 | 约 60–80 行 |
| 会话管理(字节按会话路由、有界输出环、尺寸同步) | **已经在 `next/crates/bw-engine/src/terminal_manager.rs`**,原样可用 | 211 行,切片一B 已移植,一行不用改 |
| 前端资源 | v1 `app-desktop/public/` 三个文件 | 约 291KB,**随包内联、不外链**(外链失败会让会话彻底没有终端,这是 v1 踩过并明确修掉的) |
| 每卡一个终端 | v1 按会话号在前端维护一张终端实例表,组件按会话号做渲染键 | 已是多实例形态,不是单例 —— 主线旧壳那套是**单个全局终端**,别搬错那一份 |

## 6. 工作区供给落点:抽一个 crate,定名 `bw-workspace`

这一节清偿 plan/23 §10 第 7 条(「切片五正面撞上时一并解决——抽出来、定名、定落点」)与切片三开放问题 4(「内建 git 辅助住在连接器 crate 里的命名将就」)。

### 6.1 问题原样复述

- 运行管理器要求调用方给一个**已经存在、分支已经切好**的工作区,自己不造(切片三定的边界:谁给的工作区谁负责)。
- 真实使用时总得有人造工作树,而造工作树要调 git,**编排层被门禁禁止直接起进程**。
- 切片二把三个 git 辅助函数放进了连接器 crate 当「内建函数」并注明「不是连接器」——名不正,当时就记了将就。
- 另外两个移植件(工作区采证、项目正本文件解析)住在引擎 crate 里,而**编排层依赖不到引擎**(分层门禁挡着)。这两件东西切片一B 搬进来后至今**零消费者**,本片是它们第一次真正要被用上。

### 6.2 方案:本地工作区能力独立成 crate

```
bw-core   ← 内核(零 IO、wasm 可编译)
   ↑                        ↑
bw-workspace            bw-store
(本地工作区的一切)          ↑
   ↑        ↑               │
bw-connector └──── bw-app ──┘        bw-engine(PTY / agentcli)
                     ↑                    ↑
                  app-desktop ────────────┘(壳按需组装真连接器)
```

`bw-workspace` 收三类东西,**都是「对本地工作区做的事」,都不是对外连接**:

| 收什么 | 从哪来 | 处置 |
|---|---|---|
| 造一棵活的工作树、按活分支切好 | v1 工作区模块里未被移植的那一项 | **搬**(函数体不改),这是本片新增的消费面 |
| 三个 git 辅助(内部 shell-out、开仓首提交、活分支提交并推送) | 现在住在连接器 crate 的上游区 | **移**过来(单副本,不复制),连接器 crate 反过来依赖这个 crate |
| 工作区采证(提交数 / 跟踪文件 / 未提交路径 / 最近提交标题 / 文档数)、项目正本文件解析(`.bw/metrics.toml`) | 现在住在引擎 crate | **移**过来,理由是它们的消费者在编排层,而编排层依赖不到引擎 |

**为什么它不是连接器**:plan/23 §3 已经把这条写死了——「本地工作区读取不是连接器:采证是内建函数,不进连接器接口」。既然不是连接器,就不该住在连接器 crate;既然编排层要直接用,就不能住在引擎 crate。给它一个自己的家,这两处将就一次都清掉。

**为什么这不算「又加一个 crate」的膨胀**:这一片没有多出任何新功能——三类东西本来都已经在仓库里,只是分住在两个名不正的地方。crate 数从 5 变 6,而**命名将就从 2 处变 0 处**。

**移植纪律如实标注**:三个 git 辅助的函数体一个字不改,但它们的可见性要从「crate 内可见」放宽到「对外可见」,模块路径也变。这与切片一A「只改引用路径」是同一类改动(不动函数体),按同一条判例办,并在提交正文里逐项列出。

### 6.3 一条必须写死的语义:供给只造,不删

v1 那套工作树供给自带一个「作用域结束就自动清理」的守卫——对象销毁时强制删掉工作树。**这一件不搬**,而且要在代码注释里写清为什么:

上游按工作目录编码存会话,**续接必须同路径**(切片三验过的硬事实)。而一次交付运行结束之后,它的会话很可能**还活着**(「降级为咨询」这条语义就是专门为这种情况准备的:放开交付名额、会话不杀、工作区不清)。自动删工作树 = 那个还活着的会话再也接不回来了。

所以新形态:**供给只造不删**;清理是一个显式动作(将来做一条清理用例,或人自己删)。代价是工作树会越积越多,这是**已知的、如实登记的**代价(§12 第 3 条),不是漏掉的。

### 6.4 其余语义原样搬

- 路径约定:主工作区的兄弟目录,按活编号命名;分支按活编号命名。
- 幂等:目录已经在、而且确实是一棵活工作树 → 直接复用(重试友好);是残留的空壳目录 → 清掉重造。
- **调用方是编排层的开工用例**:先把工作树造好,再交给运行管理器。**运行管理器「自己不造工作区」这条边界一个字不改**——只是调用方现在有一个正经的东西可以调了。

**这条边界在切片四B 的代码里已经是硬事实**:运行管理器开工要的那个入参结构里,工作区路径和分支名都是**必填**的(没有默认值、没有「你不给我就自己造一个」的分支),而且它还会拦一种情况——这个工作区已经被别的运行占着就如实拒绝。也就是说:**今天没有任何一条生产路径能把工作区交给它**,开工命令只要一接上去就会立刻撞上这个缺口。§6 这个 crate 就是那条路径的另一头,所以它必须是本片的第一个提交(§10.2 顺序理由)。

### 7.2 深链档:渲染证明

```bash
BW_DB=<上面那个 db> BW_OPEN=<项目名> BW_PANEL=hex      ./target/debug/bw-next
```

### 7.3 `--real` 档:不进常绿

### 7.4 切片四未收官时的降级口径

**先判断,再降级**:开工时先看运行管理器落地到哪一步。三档如实处理——① 已成 commit 且五竞态验收跑绿 → 本片的运行相关数据一律经运行管理器真开工产生,不走降级;② 代码在但验收未跑绿 → 可以用,但指挥器输出里标注「运行管理器本体已在,五竞态验收尚未跑绿」;③ 还没有 → 走下面的降级。

降级口径:第 5 节的「当前 Loop」段与第 7 节的①③两项,指挥器直接往运行表插行造数据。**这时每一行输出都必须带标注**:

```
【本行由 hex_readback 指挥器直接写入运行表,非运行管理器产出——切片四 B-E 未落地】
```

并且在 plan/23 §10 追加一条缺口,写明「这两处的真实链路未验」。**不许把指挥器自己插的行当成运行管理器跑出来的**——那正是本仓库最恨的假绿。

## 10. 门禁与提交切分

### 10.1 门禁增量(接在 next 现有那套后面)

```bash
cd next && cargo check -p bw-workspace
cd next && cargo check -p app-desktop                 # 桌面壳编译过
bash scripts/guard-kernel-ui-free.sh                  # 【必须改】见下
bash scripts/guard-app-layering.sh                    # 加两条边
bash scripts/guard-no-direct-process.sh               # 覆盖面加上新壳
bash scripts/guard-shell-no-clock.sh                  # 【新增】壳里不许有定时器
cd next && cargo run -p bw-app --example hex_readback  # 末行 HEX_READBACK_OK
```

**四条要说清楚的**:

1. **内核无界面依赖的守卫今天完全没覆盖 next**。现有脚本是在仓根跑依赖树查询的,解析的是**根** workspace 的同名 crate;`next/` 是独立 workspace,它的六个 crate 一个都没被查过。今天这不要紧(next 里还没有界面 crate),**本片一把界面框架引进来,这条线就必须立刻有人守**。要么给脚本加一个 next 档,要么新写一份;两种都行,但**不能不加**——这是本片最重要的一条门禁增量。
2. **分层守卫加两条边**:工作区 crate 不准依赖连接器 / 编排层(方向单一:连接器和编排层都依赖它,它谁也不依赖);桌面壳是**唯一**允许出现界面框架依赖的 crate。这两条和已有的两条一样,查**解析后的真实依赖树**,不查清单文本(清单可以用三种合法写法绕过文本匹配,这是切片四已经踩出来并写进脚本注释的教训)。
3. **不准直接起进程的守卫,把新壳也纳进去**。壳要起进程干什么?没有正当理由——所有对外能力走连接器,所有本地工作区能力走工作区 crate。目标清单里加一行新壳的源码目录即可,脚本本身不用改(它的设计就是「列出的目录哪个存在就查哪个」)。
4. **新增「壳里不许有时钟」的守卫**:新壳源码里出现定时器构造(`interval` / `sleep` / `Instant::now` 循环这一类)就红。这是把 plan/23 §5.1 那句「壳不持有调度时钟」变成机器能查的东西——旧壳和 v1 都带着这个病,靠人记是记不住的。脚本形态与「不准直接起进程」那条同款,十几行。

**两条保持不变**:内核的 wasm 编译保活集仍然只有内核 crate(工作区 crate / 编排层 / 壳都不进);连接器的四组特性隔离编译不变。

**一条要现场决定的**:next 的现有 CI 跑的是全工作区、含示例的严格 clippy。界面框架的宏展开可能会触发一批告警。**先按全量试**;真过不去,按旧工程的既有做法排除桌面壳并**在 CI 配置里如实注明为什么**,不静悄悄地放宽(开放问题 9)。

### 10.2 建议五个可读提交(每件独立,标题带人话)

- **A** `next 切片五A · 本地工作区能力独立成 crate(造工作树 + 采证 + 读项目正本;清偿 plan/23 §10 第 7 条)`
- **B** `next 切片五B · 指标三层进库(北极星也是一行)+ 观测只追加 + 交棒记录;迁移双守卫第一次真用`
- **C** `next 切片五C · 编排层命令事件总线按聚合拆 + 六段推导(信号读时现算,库里没有信号列)`
- **D** `next 切片五D · 待人处理推导投影(五项,每项都验「造出来又消掉」)+ hex_readback 指挥器 + 门禁接上`

**顺序理由**:A 先做,因为 B 的指标同步要读项目正本文件(那是 A 搬过去的);C 依赖 B 的表;D 依赖 C 的推导;E 最后,壳一进来那三条新门禁同时生效。A–D 全部不需要界面,可以先合;E 单独一个提交,让「引入界面框架」这件事在一次干净的差异里被看见。

## 13. 开放问题(拿不准的,不硬拍)

1. **「项目要务」的正本住哪**。本稿倾向:**住项目仓**(与「知识浓缩在一个 codebase」同一条原则),但今天没有这样一份文件,所以本片留白。可选形态:①扩 `.bw/metrics.toml`(但那是指标正本,塞别的东西会让格式失焦);②新开一份 `.bw/project.toml`(干净,但又多一份正本要维护);③干脆不做,认为北极星那一句话已经够了。我倾向②,但这是产品口径,不该我定。

2. **「决策」的正本住哪,以及它和交棒记录是不是一件事**。本稿判为**两件事**(交棒是「某天带险交了一棒」,决策是「某天拍了一个板」),所以不拿交棒冒充决策。可选形态:项目仓的 ADR 目录(本仓库自己就在这么干)/ BW 本地一张只追加的表。我倾向 ADR 目录(仓是唯一事实源),但那要定一个机读约定,成本不小。

3. **六段推导住编排层还是独立成 crate**。本稿定为住编排层(§4.3:指挥器要能直接调、不破五层心智、减法)。反方理由是旧工程那层独立 crate 是 wasm 可编译的,保住了将来 Web 版的可能——但新工程的 wasm 保活集只有内核,这条理由不成立。请主控确认。

4. **信号完全不落库,是否可接受**。本稿倾向不落(§2.6:让铁律从纪律变成结构)。代价是「重启后数字一致」这条铁律的验证形态变了(从读回缓存变成重算比对),以及将来跨项目汇总时可能要遍历。请主控确认这条划线。

5. **工作区能力 crate 的命名**。本稿提 `bw-workspace`(与词表的「工作区」对齐)。备选:`bw-vcs`(强调 git,但采证和读正本文件不只是 git)、`bw-local`(太泛)。另外要确认:把两个移植件从引擎 crate **再搬一次**(切片一B 刚搬进去)是否可接受——本稿判为可接受(换落点,函数体零改写,原因是它们第一次有了消费者而消费者依赖不到引擎),但连着搬两次这件事本身值得主控看一眼。

6. **工作区采证的结果落不落库**。本稿定为**不落**(读时现采),代价是「六段每个数字 sqlite 读回」这条验收对交付证据第③栏不成立(那一栏的读回方式是「在工作区跑同一条 git 命令」)。落库的话它就是观测,能读回、有趋势,但要给它配一组指标行(旧工程 v1 的做法是自动播种一组「项目指标」:只当现状数、不点灯、不上卷)。我倾向先不落,但如果主控更看重「所有数字一律 sqlite 读回」的一致性,就照 v1 那套播种。

7. **嵌入终端推后是否同意**,以及它归到哪一片。本稿倾向推后(§5 四条理由),并给一条真能用的逃生舱。若主控要求本片就做,那 §5.3 那张表就是搬运清单,代价是这一片的评审面翻倍,而且要先和切片四的运行管理器谈好字节从哪出来。

8. **待人处理第⑤项的收窄是否同意**。本稿把「带险交棒欠账」收成「**当前这一棒**的欠账」,只为给它一个自然消失条件(§3.1)。副作用:更早的带险交棒不再出现在待人处理里(它们仍在交棒流水里永久可查)。这是产品口径——「欠账要不要一直压在头上」是个立场问题,请主控拍。

9. **新壳要不要进严格 clippy 的覆盖面**。旧工程的做法是把桌面壳排除在外。next 现有 CI 是全工作区、含示例的严格档。本稿建议先按全量试,过不去再排除并注明。若主控直接定「壳一律排除」,那就在 E 提交里一次写清楚,不留反复。

10. **顶栏的项目切换形态**。本稿定为一个下拉(不做项目墙,§8)。但一人公司常态下真的只有一个项目在跑吗?如果用户实际同时带三五个项目,下拉可能不够,那时要不要一个跨项目的「待人处理」汇总(现在的待人处理是按项目的)。本稿倾向:**待人处理天生该是跨项目的**(词表里它的定义就是「跨项目汇总需要人出手的事」),但本片只有一个项目在库里,做成跨项目也验不出差别。要不要现在就把它设计成跨项目,请主控定。

11. **新壳二进制名与验证壳怎么接**。本稿提 `bw-next`(避免和旧壳的 `builders-workbench` 撞)。配套要给 `scripts/point-bwdev-here.sh` 加一档指向新壳,否则截图核验接不上。名字与脚本形态都请主控看一眼。

12. **切片四未收官时,本片能不能先开工**。写稿当口运行管理器本体已在工作区里(未成 commit),五竞态验收还没跑。本稿倾向:**A–C 可以直接开工**(完全不依赖运行管理器),**D–E 等运行管理器成 commit 之后再做**——「当前 Loop」段和两项待人处理如果长在降级数据上,验收就是半真的,而这一片的全部价值恰恰是「六段每个数字都真」。若主控要求并行推进,§7.4 的三档降级口径就是执行时的判据。
