## 何时用 / 前置条件

- 项目已建好,工作区是一个真实 git 仓(`workspace_path` 非空)。
- 若工作区根下存在 `docs/competitive-analysis.md`,**必读**:对标名单、各家
  北极星猜测、差异定位是起草本项目北极星的第一手依据,不凭空想象。不存在
  就如实在 `docs/metrics-rationale.md` 里写一句「本轮无竞品分析报告输入,
  北极星推导仅基于项目自身意图」,不假装读过。
- 读项目自身意图:项目的 `desc`(项目类型/一句话说明)、`benchmark`(对标
  对象)、`opportunity`(差异化机会)——这些字段就是"为什么做这个项目"的
  真实来源,不是 Skill 自己现编。

## 方法论:先对后亮

### 三段拆解:供给 / 使用 / 价值

动笔起草北极星之前,先把这个项目拆成三段:

- **供给**(做出来了:功能/内容/文件被生产出来)
- **使用**(用户真的用了:打开、读、点、留存、复访)
- **价值**(用户因此变好了:省了时间、少踩了坑、多赚了钱、少受了苦……)

**北极星必须落在第二段(使用)或第三段(价值),落在第一段(供给)一律退
回重写**——供给段的指标回答的是"我们干了多少活",不是"用户过得好不好",
这两件事经常被偷换。

反例(真实):某项目自述痛点是"信息**过多**",痛点明明在价值段(用户被信
息淹没、省不下时间),但它的北极星"连续每天产出一份内容"整条量的是文件
有没有被生产出来——卡死在供给段,答非所问。

### 虚荣指标黑名单

**北极星绝为了"当前采得到"而退化成 commit 数、PR 数、issue 数这类工程虚荣
指标。** 工程活动量是引领指标的候选(甚至只是引领指标的引领指标),永远
不够格坐在北极星的位置——北极星必须是这个项目对**用户/世界**产生的真实价
值(留存、复购、解决的问题、创作产出……视项目类型而定),即使眼下这条指
标只能标 `manual` 甚至暂时想不出精确采集方案,也不能因此把它换成一条方便
采集但答非所问的指标。这条约束优先于"看起来能立刻点亮"。

反例(真实):某内容日更类项目现行北极星曾定为「连续 N 天,每天都真实产出
一份满足数量下限的内容」,精确落进"创作产出"这个合法的北极星类别,上面的
黑名单一条也拦不住它——但只要给它挂一条每日定时任务,从上线当天起这条北
极星就永久满分。cron 只保证"跑了",从不保证"有人读、有人因此变好"。

### 自动化免疫检验

与上面的虚荣指标黑名单并列,是比黑名单更上位的原则——黑名单只挡得住"看
起来像虚荣指标"的那几种,这条挡的是"任何看起来正当、实则会被自动化悄悄
刷绿"的指标。起草完北极星,问一句:

> **假如给这个项目挂一条永不失败的定时任务,这条北极星会不会永久满分?**

会 → 它量的是系统在运转,不是用户在获益,退回重写。

## 北极星判据打分(改编自 amplitude/builder-skills)

对每个候选北极星,起草前先打这 6 项判据分(1-5 分):

1. **落位**——精确落在使用/价值段,不是供给段(见上方「三段拆解」)。
2. **自动化免疫**——挂一条永不失败的定时任务会不会让它永久满分(见上方「自动化免疫检验」的真实反例)。
3. **场景契合**——是否对应项目 `desc`/`benchmark`/`opportunity` 里"为什么做这个项目"。
4. **定义精确**——有没有清晰的"怎么算作达成",不是模糊描述。
5. **采集诚实**——`collect.kind` 是否真实,不为了显得体面瞎选。
6. **难造假 + 反指标**(见下)。

任一项 ≤2 分的候选直接淘汰,不进入起草。

**反指标(counter-metric)硬性要求**:每条候选北极星必须配一条"如果只优化
这条指标会被悄悄牺牲的东西"——例如"周活跃用户数"配"客诉率/退款率",防
止靠骚扰通知刷活跃。反指标不进 `.bw/metrics.toml`(不是要采集的第四类指
标),只写进 `docs/metrics-rationale.md` 作北极星选型的护栏说明;下次复
核北极星,先看反指标有没有恶化。

**故意的坏候选对照**:草拟北极星前,先列出至少 2 个"看起来合理但会被上
面 6 项判据刷掉"的坏候选,写清楚具体是哪一项判据把它挡下——这不是走过
场,是逼自己把黑名单套在真候选身上,而不是空对空背诵。参照上面"连续 N
天产出"那条真实反例:自动化免疫这一项判据本该在起草时就把它挡下。

**BDFE 输入结构**(供下方第 2 步"拆三段"的补充视角,不是替代):把"使
用"段进一步拆成 Breadth(有多少用户在用)、Depth(每次用得多深/多少动
作)、Frequency(多久用一次)、Efficiency(达成目标花多少步/多少时间)四
个维度——北极星常常是这四维里的一个乘积或复合(如"周活跃且完成核心动作
的用户数"同时含 Breadth×Frequency)。四维选不出候选时,回落原有的供
给/使用/价值三段拆解。

**NSM↔商业 KPI 系统校验**:北极星起草完,写一句清楚的因果链——"这条北
极星如果提升,会怎样传导到项目的商业/存续指标(收入、留存付费、口碑、
下一轮资金/资源)"。传导链讲不通(想不出任何合理路径),说明这条北极
星起草得太自我中心,退回重写;如实标注这条传导链目前是否已有真实数据
验证过,还是仅逻辑推演——这点务必诚实,不假装已验证。

## 引领/滞后质量门(改编自 mohitagw15856/pm-claude-skills)

**逐指标强制判定**(下方工作步骤第 4/5 步归类前先过这条判定题,不凭直觉贴标签):

- 这个数字是在动作发生的**当下/事前**可被团队直接影响的吗?且它对滞后
  指标有**预测性**吗?两者都是 → 引领指标。
- 这个数字只能在结果发生**之后**才测得到,团队此刻改不了它吗?→ 滞后
  指标。
- 两条都答不上「是」的候选(比如纯粹的活动量,既不能预测结果也不能被
  直接推动)不配称为引领指标,退回重新定义或直接舍弃——**把无法通过这
  条判定的指标硬塞进"引领"分类,是本 Skill 明令禁止的不诚实分类**。

**成对反指标**(引领侧,与北极星判据打分的反指标机制同构):每条引领指
标配一条"如果只冲这条数字会被悄悄牺牲的东西"——如"每周合并 PR 数"配
"代码评审通过率/回滚率",防止靠灌水 PR 刷数;"队友结算 Issue 数"配
"Issue 重开率",防止靠快速潦草结算刷数。写进 `docs/metrics-rationale.md`,
同北极星反指标一样不进 `.bw/metrics.toml`。

**0-40 质量门自评**(交付前打分,写实际得分进 `docs/metrics-rationale.md`;
<24 分退回重做,不带着不及格分交付):

| 判据(每项 0-10) | 检验问题 |
|---|---|
| 分类诚实 | 有没有把不满足强制判定的指标硬贴"引领"标签? |
| 预测性 | 引领指标的变化能不能在滞后指标之前先看到征兆(时间上确实领先)? |
| 阈值真实 | `target` 是否用项目真实历史数据校准,不是拍脑袋(同下方第 4 步阈值校准要求)? |
| 防作弊完整 | 是否每条引领指标都配了成对反指标,不是只挑好写的那几条配? |

## 工作步骤

1. **读输入**:项目意图(`desc`/`benchmark`/`opportunity`)+
   `docs/competitive-analysis.md`(若存在)+ 项目现有 `.bw/metrics.toml`
   (若已存在,说明是修订而非首次起草,原地改写、不无理由推倒重来)。
   **读项目仓里既有的指标体系**:扫 `governance/`、`derive_*.py`/
   `derive_*.sh`、项目自己的 `docs/metrics-rationale.md`(非本 Skill 产出的
   那份)、任何 `[L1/L2/L3]`/`[CN/DS/DT]` 之类分层定义文件、`connectors/`
   采集脚本、`data-sources/`。**若项目已有自己的指标体系,三层指标(北极
   星/滞后/引领)优先对齐、映射到既有体系的名字与分层,不是另起炉灶自造
   一套**——项目自己的 owner 最清楚他们的业务指标怎么定义、怎么采,本
   Skill 复用而非覆盖;映射不上的才用第 2-5 步的三段拆解推导。在
   `docs/metrics-rationale.md` 里如实记一句「已对齐项目既有 X 层指标体系
   (出处 `governance/...`)」或「项目无既有指标体系,本轮首次推导」。**这
   一步是避免产出和项目真实业务对不上的「形似而神偏」指标的关键**——不
   读项目既有体系就推导,等于把 buddy 的通用模板强加给项目,会漏造项目真
   实指标、造出项目从不数的 phantom 指标。
2. **拆三段**:按上面的三段拆解(供给/使用/价值)——明确指出北极星落在使
   用段还是价值段,落不进去就还没起草完。
3. **起草北极星**:恰好一条,对应"这个项目存在的理由"。写清 `name` +
   `def`(精确到"怎么算作达成")。按上面的虚荣指标黑名单,拒绝虚荣指标
   候选;对照上一步的三段拆解——明确指出这条北极星落在使用段还是价值段。
4. **起草滞后指标**(0..N,建议 2-4 条):结果性、滞后于动作才看得出好坏
   的指标,通常是北极星的分解或先行验证。每条给 `target`(mini-DSL,同
   `metric.target_raw` 写法:`"≥5"` `"≤24h"` `"清零"` 等)——**阈值必须用
   真实历史数据校准,不能拍一个当前值远超的下限(或远低的上限)**:先去
   查项目已有的真实运行数据(日志、telemetry、既往产出记录),看清楚当
   前水位落在哪里,再决定 `target` 卡在哪条线上、卡的是上限还是下限。
   反例(真实):某项目定过一条命中量下限,而它自己 telemetry 里的真实观
   测值常年比这条下限高出一个数量级,这条下限形同虚设;项目自己的迭代记
   录里还写着优化阶段特意把输出量砍掉大半,说明这个产品的真实痛点是**上
   限**(别让用户被灌太多),指标却守着**下限**,方向完全反了,等于没守。
5. **起草引领指标**(0..N,建议 2-4 条):过程性、当下可控、驱动滞后指标
   的先行量。**优先复用项目既有指标体系里的过程性指标**(第 1 步读到的
   `governance/`/`derive_*.py` 里的);只有项目确实没有既有引领指标时,
   才用 BW 自有记账(issue 结算数、run 遥测等)或工程活动量(合并 PR 数)
   作候选——但须在 `docs/metrics-rationale.md` 标注「本条来自 BW/GitHub
   自有记账,非项目既有指标」,避免把 buddy 的概念当成项目真实的过程指
   标。同样按上一步的口径校准 `target`。
6. **给每条指标定 `collect`**:采集 kind 有两值——`script`(自动:机械解析
   数据源产出 JSON,`query`=字段在 JSON 里的点分路径)和 `manual`(人手填,
   戴「手填」徽)。`github`/`codehub`/`bw`/`connector` 是 legacy inline
   arm,正退休进 `script`——新写优先 `script`/`manual`,不写 legacy kind。
   能自动采的写 `script`(项目仓里已有 `derive_*.py` 这类脚本的,写 `script`+
   `query` 只写字段路径);暂时没有埋点/连接器、也没项目侧脚本的才诚实写
   `manual`。**不为了显得"采得到"而编一个查不出真实数字的 query,也不为了
   显得体面把项目侧自采脚本降级成 `manual`**——后者等于把自动采谎报成人填。
   格式细节(`kind` 词表、`query` 写法、`collect` 内联表语法)见衔接层
   system prompt + `docs/buddy/standards/metrics.md`。
7. **落文件**:把三层指标写进工作区 `<workspace>/.bw/metrics.toml`,格式严
   格遵照衔接层 system prompt 引用的 `docs/buddy/standards/metrics.md`。
8. **写推导文档**:`<workspace>/docs/metrics-rationale.md`——人读的推导过
   程,至少包含:输入摘要(竞品分析要点/项目意图)、北极星为什么是这条
   (以及被拒绝的虚荣指标候选是什么、为什么被拒)、滞后/引领指标的因果链
   (为什么这几条引领指标真的驱动这几条滞后指标)、每条指标当前采集方案
   的诚实评估(哪些现在采得到、哪些暂时只能 manual)。
9. **交付**:改动落在活分支(`bw/issue-<n>`,由 `RunIssue` 在跑本活前已
   经切好),正常提交改动即可,提 PR 走执行器既有机制;**合并永远是人手动
   作**(铁律见衔接层 system prompt)。

## 样例(可直接改写后使用)

以下是一份完整、结构合法的样例——虚构项目「个人知识库同步工具」,示范
"北极星不退化成虚荣指标"的正确写法(北极星是用户价值,引领指标才是工程
活动量):

```toml
schema_version = 1

[north_star]
name = "周活跃同步用户数"
def  = "过去 7 天内至少成功完成一次跨设备同步的注册用户数——不是安装量,是真的在用"
collect = { kind = "manual", query = "" }

[[lagging]]
name   = "首月留存率"
def    = "注册后 30 天内仍有同步行为的用户占比"
target = "≥30%"
collect = { kind = "manual", query = "" }

[[lagging]]
name   = "同步失败率"
def    = "过去 7 天内同步请求里以失败结束的比例——直接影响留存的产品质量信号"
target = "≤2%"
collect = { kind = "manual", query = "" }

[[leading]]
name   = "每周合并 PR 数"
def    = "过去 7 天内 merge 进 main 的 PR 数——研发产出的先行信号,工程活动量放这里合适"
target = "≥5"
collect = { kind = "manual", query = "" }
```

注意北极星 `周活跃同步用户数` 和引领指标 `每周合并 PR 数` 的位置——后者是
真实存在的工程活动量,但它只配当引领指标(驱动北极星的先行量),换到北极
星位置就是本 Skill 明令禁止的退化。

> **样例的引领指标(`每周合并 PR 数`)示范的是 BW/GitHub 自有记账口径**,
> 只在「项目无既有引领指标体系」时才照抄。若项目第 1 步读到了自己的
> `governance/`/`derive_*.py` 既有过程指标(如 maas 的 L1 自动规范问题数、
> L2 定位分析数),应优先用项目的,不是照抄这两条 buddy 自有概念——否则
> 会产出项目从不数的 phantom 指标。同理,若项目北极星(如采纳率)其实有项
> 目侧脚本机械采集(见第 6 步 `script` kind),用 `script` 而非 `manual`。

## 完成的标准(DoD)

- `<workspace>/.bw/metrics.toml` 存在、结构合法(能被衔接层 system prompt
  引用的格式 doc 无错解析)。
- 恰好一条 `[north_star]`,不是虚荣指标(能对照 `docs/competitive-analysis.md`
  或项目 `desc`/`benchmark` 说清楚"为什么是这条")。
- 每条指标(含北极星)`collect.kind` 落在合法词表内,`query` 不是为了"看
  起来能采"而瞎写的假查询。
- `<workspace>/docs/metrics-rationale.md` 存在,四块内容都有真实依据支撑,
  且含:北极星 6 项判据打分、至少 2 个被拒的坏候选记录、北极星与引领指
  标各自的反指标、引领/滞后 0-40 质量门实际得分(≥24)。
- 改动是活分支上的真实提交,不是口头描述。

## 常见坑

- **把工程活动量塞进北极星**:commit 数/PR 数/issue 数天然容易采集,诱惑
  最大,也是本 Skill 存在的主要理由——每次起草北极星前重读一遍上面的虚
  荣指标黑名单 + 自动化免疫检验段落。
- **把供给当价值**:对内容/信息类产品尤其致命——"每天出一份摘要""每周
  发一篇文章"这类供给动作看起来太像成果了,容易被直接当成北极星,而不
  去追问有没有人真的打开、读完、因此变好。检验方法就是"工作步骤"第 2
  步的三段拆解:这条指标能不能明确指出它落在使用段还是价值段;答不上来
  就还停在供给段。
- **为了让 `collect.kind` 显得"高级"而选错**:能诚实标 `manual` 就标
  `manual`,不要为了显得体面而选一个没有真实对应的接入。**反向同样错**:
  项目仓里已有自动采集脚本(机械解析真实数据源)的,该标 `script` 就标
  `script`,别降级成 `manual`——项目侧脚本是自动采集,降级人填等于把自
  动谎报成人填,看板上会平白多一个「手填」徽。
- **`docs/competitive-analysis.md` 存在却没读**:那份报告存在的唯一理由
  就是喂给这一步,跳过它等于自己现编"知道对标谁"。
- **改写已存在的 `.bw/metrics.toml` 时误删历史指标的 id 语义**:文件没有
  id 概念,`(层级, name)` 就是身份——改名字等于新建一条,历史观测会跟丢;
  只想改定义就保持 `name` 不变。
- **引领指标归类走直觉,不走强制判定题**:把工程活动量或"看起来像过程"
  的东西不经"当下可影响+对滞后有预测性"两条判定题就直接归类引领,正是
  质量门要挡的「不诚实分类」——单独一条自建基线曾在盲测里因此被扣到
  3/5(防作弊判据)。
- **只给好写的指标配反指标,难写的就跳过**:反指标要求是逐条硬性的,不
  是挑几条意思一下;漏配的那几条正是最容易被刷的那几条。
