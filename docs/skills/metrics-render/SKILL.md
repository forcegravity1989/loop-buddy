# 渲染指标(metrics-render)

指标推导出来(`north-star-discovery`)、绑上数据源(`metrics-binding`)之后的第三件:
**把此刻的真实状态渲染成一页能给人看、且对方能自己查证的东西。**

> **方法论来源(2026-08-05,plan/21 拿来主义测评)**:图表选型与色盲调色板部分
> 改编自 anthropics/knowledge-work-plugins · `data-visualization`(Apache-2.0,
> 官方,10,830 装);单文件自包含 + KPI 卡布局的形态借自同仓 `build-dashboard`
> ——但**明确反转了它的造数条款**(见下方硬性约束第一条)。业界没有一件带真实性
> 护栏的渲染 skill,这件的存在理由就是那些护栏,不是画图技巧。测评全文见
> `plan/21-metric-render-skill-evaluation.md`。

## 何时用 / 前置条件

- 项目的指标定义已经在库里(`.bw/metrics.toml` 经 `SyncMetricsFile` 同步,或界面手建)。
- **没有观测也可以渲染**——而且往往正是这个时候最该渲染:一块整片灰的看板,说的
  是「测量链还没通」,这本身就是当前最重要的信息。不要因为「数据太少不好看」而
  推迟渲染,更不要为了好看去补数。

## 硬性约束(这件 skill 存在的理由)

> **第一条,也是最容易被违反的一条:渲染器只呈现真实观测,不生成任何数据。**
>
> 业界最接近的那件 skill(`build-dashboard`)在「没有数据」时的做法是**造一份
> 贴合 schema 的真实感样例数据,并注明这是样例**。通用场景下这算体面,在 BW 里
> 是**明令禁止**的:一块本该整片灰的看板,会因为「有数据总比空着好看」被填满看
> 似合理的数字。**无数据 = Unknown 灰 ≠ 绿**,这条优先于任何美观考虑。
>
> 具体禁止:零观测时填 0、沿用上一次的值、在两个观测点之间插值、用
> `metric.value_raw` 缓存顶替真实序列、生成「示例数据」预览。

其余五条:

2. **来源徽记**。只有 `SourceKind::Manual` 戴「手填」徽——`github`/`script`/
   `codehub` 是机器采集、可独立重派生,给它们戴手填徽是谎报。`collect_kind` 是
   `bw`/`connector` 的要标「v1 未接」(采集器状态见 `docs/metrics-toml-format.md`)。
3. **数字可独立复核**。每条指标旁边给出**能直接粘进终端跑**的 `sqlite3` 命令,跑
   出来的就是页面上显示的那些点。页面自带自证方式——看的人不必信这段代码,也不必
   信你。
4. **绿色隐身**。green 不高亮、不庆祝、不用大色块;每个项目顶部只浮出
   `signal≠green` 的项(`plan/00` §6 的原始业务规则)。红黄才出声。
5. **1 个观测点不画趋势线**。画了就是插值。单点显式标「仅 1 个观测点」;非数值
   观测(如 `5/5`、`清零`)同样不画。
6. **只吃两个源**:`metric` 表的定义 + `observation` 表的值。**不接受任何数值以
   命令行参数、对话内容或估算的形式进入页面**——想让页面上出现一个数,只能先让它
   成为一条真实观测。

## 工作步骤

1. **先确认定义已入库**。`.bw/metrics.toml` 改过但没同步,渲染出来的是旧定义:
   ```bash
   cargo run -p bw-app --example sync_metrics_files -- <db> [项目名]
   ```
2. **渲染**。渲染器是 `crates/bw-app/examples/render_metrics.rs`,上面六条护栏
   写在它的代码分支里,不靠每次自觉:
   ```bash
   cargo run -p bw-app --example render_metrics -- <db> <out.html> [项目名 …]
   ```
   不给项目名 = 渲染全部项目。只读:除 `SqliteStore::open` 自身的幂等建表外不写
   库,不 recompute、不采集。
3. **读回核对**。渲染器在 stdout 打印「N 条指标 / M 个观测点 / K 条零观测」,用
   一句独立 SQL 核对,数字对不上就是渲染器有问题:
   ```bash
   sqlite3 <db> "SELECT COUNT(*), SUM(CASE WHEN obs=0 THEN 1 ELSE 0 END), SUM(obs)
     FROM (SELECT m.id, (SELECT COUNT(*) FROM observation o WHERE o.metric_id=m.id) AS obs
           FROM metric m WHERE m.stage_kind IS NULL);"
   ```
4. **交付**。产出是单个自包含 HTML,无外链、无 CDN、无服务器,浏览器直开。

## 不许手搓 HTML 顶替渲染器(可靠性的关键)

**渲染器画不出来的东西,不要改用手写 HTML 绕过去。** 手写的那一页看起来会更漂亮,
但它的真实性只存在于当时那次的自觉里:下一次、换个人、赶时间的时候,零观测就会
悄悄变成 0,单点就会连成一条线。护栏必须在**代码**里,才是「可靠」。

需要新表达(新的图形、新的分组、新的层级)时,正确做法是**改渲染器并把新护栏一
起写进去**,然后重跑。这条约束是这件 skill 与「让模型每次即兴画一页」的全部差别。

唯一例外:**面向人的分析报告**(如某次测评的结论页)不是指标看板,不归这件 skill
管——但那种页面里出现的任何指标数字,同样要能指回一条真实观测。

## 输出契约

单个自包含 HTML,包含:

- **每个项目**:名称 + 项目 signal + 当前阶段 + 工作区路径;北极星(名称/定义/
  采集方案徽记)。
- **出声区**:该项目 `signal≠green` 的项,列在最前;一条都没有时明说「没有需要
  出声的项(绿色隐身)」,而不是留白。
- **项目级业务指标表**(层 A,`stage_kind IS NULL`):指标名 + 引领/滞后 + 定义 +
  最新值(或「无数据」)+ 目标 + 真实观测点数与最近日期 + 趋势(够点才画)+ 来源
  徽记 + 逐条的 `sqlite3` 复核命令。
- **阶段指标**(层 B,`stage_kind IS NOT NULL`)收进折叠区,明标「通用项目管理
  指标,只当现状数,不进业务北极星链路」(`plan/18` §1.1 的分层)。
- **页脚**:数据源路径、渲染时间、六条护栏原文——让拿到这一页的人知道它守了什么。

配色沿用 BW 设计系统(`plan/00` §6):暖纸 `#EFEBE2`、clay `#C5654A`、三态信号
green `#5F7355` / amber `#B5862F` / red `#B0503A` + Unknown 灰;深色主题同等对待。

## 完成的标准(DoD)

- 产出的 HTML 自包含(无外链资源),浏览器直开。
- 零观测的指标渲染成「无数据」,**页面里搜不到任何一个不来自 `observation` 表的
  数字**。
- 每条指标都有可粘贴执行的 `sqlite3` 复核命令,且抽查一条,跑出来的点数与页面
  显示一致。
- 渲染器 stdout 的三个计数与步骤 3 的独立 SQL 一致。
- 观测点 <2 的指标没有趋势线。

## 常见坑

- **为了好看去补数**。最常见、也最严重。零观测的看板确实难看,但那个难看是真的
  ——`aihot 日报` 的北极星是 0,是「没数据」的 0,不是「产品不好」的 0,这两件事
  一旦在页面上混掉,后面所有决策都建立在假象上。
- **给机器采的指标戴手填徽**(或反过来)。徽记是给看的人判断「这个数字能信到什么
  程度」的,标错方向都是谎报。
- **单点连线**。两个观测点之间的那条线是画上去的,不是量出来的;只有 1 个点时更
  不用说。这是最不容易被发现的一种编造。
- **把层 B 的阶段指标混进业务指标表**。「阶段完成 Issue 数」这类是 BW 给每个项目
  自动铺的通用管理指标,不是这个项目自己的业务指标,混在一起会让北极星链路看起来
  比实际丰满。
- **渲染完就当验证过了**。渲染只证明「库里是这样」,不证明「指标是对的」——对不对
  是 `north-star-discovery` 的活;采得到采不到是 `metrics-binding` 的活。
