# V2 · Issue 调度统一方案：buddy 提示词资产 × Skill 能力资产

> **30 秒导读**：这是一份 V2 的详细设计，给后续负责落地的助手 Agent、评审者和维护者看。**设计现在作数，功能尚未开发**。它解决两个现实问题：一是任意 Issue 开工时缺少统一的 buddy 处理约束；二是「找指标 / 绑数据」规范被绑在少数标配 Issue 的技能名称上，换一张 Issue 就可能丢失。本设计把运行上下文拆成两个互不依附的维度：**所有 Issue 必带的 buddy 系统提示词与规范手册**，以及**按活选择的 Skill 方法与协作流程**。开发可以分两轮，但两轮共同遵守本文的完整模型。
>
> 初始意向见 [`roadmap.md`](roadmap.md)；V1 终端收口史实见 [`../v1-prototype/issue2-all-issues-terminal-runs.md`](../v1-prototype/issue2-all-issues-terminal-runs.md)。看不懂的领域词查 [`../../CONTEXT.md`](../../CONTEXT.md)，产品铁律和验证纪律见 [`../../CLAUDE.md`](../../CLAUDE.md)。

## 1. 要解决的真实问题

V1 已把所有 Issue 的执行收进嵌入式 Claude CLI。执行过程清楚了，但「Claude 开工前拿到什么」仍没有形成一套稳定资产。

### 1.1 Issue 处理缺少统一底座

当前一张 Issue 开工时，主要依赖 Issue 标题、描述和它恰好关联的 Skill。无技能的普通 Issue 能开工，但 Claude 不一定知道：

- buddy 管理的项目文件分别是什么，哪些是正本；
- 指标、连接器、交付状态等修改要遵守什么规则；
- 哪些动作必须留给人，例如合入与最终完成；
- 当前项目为什么存在、正在什么阶段、上一棒留下了什么。

结果是同一种修改，放在不同 Issue 里可能得到不同处理方式。

### 1.2 buddy 规范错误地依附于 Skill 名称

V1 为「找指标」和「绑数据」提供了专门约束，但约束不是独立规范，而是按这两个 Skill 的名称在程序里选择一段文字。由此产生三个问题：

1. 用户新建一张「修改某个指标名称」的普通 Issue，不一定需要任何 Skill，却仍然需要 buddy 的指标规范；现状拿不到。
2. 用户给新 Issue 选择了业界 Skill 或自建 Skill，业务方法有了，buddy 规范反而可能丢失。
3. 规范藏在程序里，不是可直接阅读、评审、复制和继承的文件资产；buddy 重构时容易再次散落。

### 1.3 阶段方法仍残留旧调度形态

V1 已不再由 buddy 脚本逐步驱动多名 Agent。现在是 Claude CLI 在一段可见会话中完成工作，并在需要时调用 SubAgent。但五阶段原有的方法循环仍主要存在于旧的阶段脚本描述中，没有成为 Issue 执行侧稳定、可选择的 Skill 资产。

## 2. 设计目标与不做什么

### 2.1 本轮必须达到

1. **任何 Issue 首次开工时，都得到同一份 buddy 系统提示词；恢复沿用首次注入的提示词，并在恢复前更新可读取的规范文件。**
2. **buddy 规范与 Skill 解耦。** 是否加载指标规范，只取决于 Claude 当前是否在处理指标事务，不取决于 Issue 名称或选择了哪个 Skill。
3. **规范按需阅读，不全部塞进提示词。** 系统提示词只告诉 Claude「有哪些规范、何时必须读、从哪里读」。
4. **系统提示词和规范都成为 Markdown 文件资产。** 程序负责填项目上下文、把文件放到可读位置并启动 Claude，不再持有大段业务契约正文。
5. **五阶段各有一个默认 Skill。** 它既保留该阶段的方法论，也说明需要多名 Agent 时如何在 Claude CLI 会话中协作。
6. **用户能用自己的 Skill 替换阶段默认 Skill。** 不要求用户修改 buddy 自带资产。
7. **这套目录可被后续 buddy 重构直接继承。** 无论桌面壳、调度实现或数据库如何变化，提示词、规范和 Skill 正文仍是可读、可迁移的正本。

### 2.2 本轮不做

- 不恢复旧的脚本式多 Agent 阶段循环。
- 不让 buddy 猜测并自动合入代码，也不改变「完成永远由人确认」等产品铁律。
- 不新增审批流、成员权限或多人协作能力；那属于 V2 的另一条能力线。
- 不要求每张 Issue 都选择 Skill；简单修改可以只靠 Issue 内容 + buddy 系统提示词完成。
- 不把所有规范一次性内联进系统提示词。
- 不提供「在线修改 buddy 官方 SOP」能力。默认方法不好用时，用户新建自己的 Skill 并在 Issue 上选择它。
- 不为旧的提示词拼装路径保留兼容层。新路径验证通过后，旧的硬编码契约直接移除。

## 3. 核心模型：两个独立维度

一张 Issue 的执行上下文由两个独立维度组成。它们可以在同一次 Claude 启动中拼装，但来源、职责和选择规则不能混在一起。

### 3.1 维度 A：buddy 系统提示词资产

**所有 Issue 必带，用户不能用 Skill 替换。** 它负责告诉 Claude「在 buddy 纳管的项目里做事，必须遵守什么」。

组成：

1. **公共系统提示词**：buddy 的角色、共同铁律、工作方式、规范索引。
2. **动态项目上下文**：项目名、项目意图、当前阶段、北极星、上一棒备注等，由 buddy 每次启动时从真实项目数据填写。
3. **按需规范手册**：指标、连接器等详细规则。它们不默认内联，由 Claude 根据当前工作内容自行读取。

### 3.2 维度 B：Skill 能力资产

**按活选择，可以没有，也可以被用户替换。** 它负责告诉 Claude「这件活用什么方法做」。

Skill 可以是：

- buddy 自带的五阶段默认方法；
- buddy 自带的「竞品分析 / 找指标 / 绑数据」等专项方法；
- 用户在 Hub 中录入的 Skill；
- 从已完成 Issue 蒸馏出来的经验；
- 说明多个 Agent 如何协作完成一件活的 SOP Skill。

### 3.3 两个维度的边界

| 问题 | 归 buddy 系统提示词与规范 | 归 Skill |
|---|---:|---:|
| 哪些动作永远由人完成 | ✅ | — |
| `.bw/metrics.toml` 是什么、怎样才合法 | ✅ | — |
| 修改指标前必须读哪份规范 | ✅ | — |
| 如何推导一条高质量北极星 | — | ✅ |
| 如何诊断一条指标最便宜的采集路径 | — | ✅ |
| 构建阶段如何让规格、实现、评审几个 Agent 协作 | — | ✅ |
| 用户自己的一套研发方法 | — | ✅ |

**判断准则**：换一个 Skill 后仍必须成立的，是 buddy 规范；只描述「如何把某类活做好」的，是 Skill。

## 4. 可继承的资产目录

### 4.1 buddy 仓内的权威正本

```text
docs/
├─ buddy/
│  ├─ README.md
│  ├─ system-prompt.md
│  └─ standards/
│     ├─ metrics.md
│     └─ connectors.md
└─ skills/
   ├─ evidence-first/SKILL.md
   ├─ spec-to-tests/SKILL.md
   ├─ baseline-before-touch/SKILL.md
   ├─ fresh-eyes-funnel/SKILL.md
   ├─ breaking-drill/SKILL.md
   └─ ...其它专项 Skill
```

说明：

- `docs/buddy/system-prompt.md` 是公共提示词正本。
- `docs/buddy/standards/*.md` 是 buddy 规范正本；V2 首轮先纳入指标与连接器两份已经实践过的规范。
- `docs/skills/*/SKILL.md` 继续是 Skill 正本，其中既有五阶段默认 Skill，也有 `competitive-analysis`、`north-star-discovery`、`metrics-binding`、`metrics-render` 等专项 Skill。
- `docs/buddy/README.md` 给出 30 秒导读、目录职责和新增规范的步骤。
- 当前散落在 `docs/metrics-toml-format.md`、`docs/connectors-toml-format.md` 的有效内容迁入新目录并校准为唯一正本；仓内引用同步改向新路径，旧文件不保留兼容副本。

### 4.2 为什么必须分目录

- `docs/buddy/` 回答「在 buddy 纳管的项目里，什么必须做对」。
- `docs/skills/` 回答「某类活怎样做得更好」。

把两者放在相邻但独立的目录下，既能整体继承，又不会再次把规范塞回 Skill。

新增一份 buddy 规范固定走三步，不另建代码映射表：

1. 在 `docs/buddy/standards/` 增加一份有 30 秒导读的 Markdown 正本；
2. 在 `system-prompt.md` 的规范索引里补上「什么事务必须读它」和运行时相对路径；
3. 由打包与启动自检核对：索引列出的文件都存在、目录里的规范都已进入索引。两边不一致就阻止发布或启动，不能让半套规范静默生效。

### 4.3 业务项目工作区里的运行副本

Claude 在业务项目工作区运行，只能稳定读取该工作区可达的内容。因此每次 Issue 启动或恢复前，buddy 把 `docs/buddy/` 的运行所需部分物化为：

```text
<业务项目工作区>/.claude/buddy/
├─ .bw-managed
└─ standards/
   ├─ metrics.md
   └─ connectors.md
```

`system-prompt.md` 的正文由 buddy 直接用于启动参数，不必再复制一份；详细规范需要 Claude 按需 `Read`，因此放进工作区。

运行副本遵守以下规则：

1. **不提交进用户项目 Git。** 它是 buddy 运行资料，不是业务项目正本。
2. **不修改项目的 `.gitignore`。** buddy 通过 Git 查询当前工作区实际使用的本地排除文件（等价于 `git rev-parse --git-path info/exclude`），把 `.claude/buddy/` 加入本地排除。这样普通 clone 与 Git worktree 都能命中正确位置；规则不进提交历史。
3. **每次物化前都核验排除规则。** 先确认当前目录是真实 Git 工作区、排除文件可写且规则已经生效，再写运行副本。任一条件不满足，本次真实 Claude 执行不启动，并给出可操作的人话错误。
4. **每次启动或恢复都校准。** 内容没变就不重写，buddy 升级后内容变化则原位更新。
5. **只覆盖 buddy 自己管理的目录。** 规范目录的 `.bw-managed` 内容为 `buddy-standards\n<资产版本>`，只标记 `.claude/buddy/` 这一棵目录；现有 Skill 目录里的同名标记继续表示各自的 Skill 身份与版本，两者互不混用。标记不存在、目录是符号链接或路径不安全时，拒绝覆盖并报告冲突；不碰用户手写文件。
6. **规范物化是独立职责。** 可以复用现有 Skill 落盘时「有标记才覆盖、路径必须安全」的守护模式，但不把两类资产塞进同一个函数或共用版本格式。
7. **写入采用临时文件后替换。** 不让 Claude 读到半份规范。

> 这里的「不提交」是产品行为，不是靠用户记得别 `git add`。实现必须在启动前机械保证。

## 5. `system-prompt.md` 应包含什么

公共系统提示词保持短而稳定，详细格式全部下沉到规范文件。建议结构如下。

### 5.1 身份与工作方式

用人话告诉 Claude：

- 当前是在 buddy 纳管的真实项目工作区里处理一张 Issue；
- Issue 标题和描述是本轮目标，不等于完整的 buddy 规则；
- 先读项目现状再改，报告不代替真实产出；
- 需要多角色协作时由当前 Claude 会话调用 SubAgent，不等待 buddy 脚本逐阶段驱动。

### 5.2 所有 Issue 共用的铁律

只保留跨事务、永远成立的公共规则，例如：

- 最终完成与合入由人确认，Agent 不替人越过验收门；
- 没有真实数据就是未知，不为点亮健康灯编造数据；
- 项目中的正本文件优先于数据库缓存，不直接篡改缓存冒充完成；
- 已发生的观测、交棒与结算记录不能被擦除或伪造；
- 失败要如实停下并说明，不假装流程前进。

系统提示词不复述实现函数、数据库表名或内部代号。

### 5.3 规范索引：由模型自己决定何时读取

系统提示词明确列出运行副本的相对路径和触发语义。例如：

```markdown
## buddy 规范索引

详细规则不在这里展开。先根据当前 Issue 判断正在修改什么；命中下列场景时，
在动手前读取对应文件：

- 新建、修改、删除、重命名项目指标，或调整指标定义、目标、层级、采集声明：
  读取 `.claude/buddy/standards/metrics.md`。
- 新建或修改采集脚本、连接器、输出文件与指标采集路径：
  读取 `.claude/buddy/standards/connectors.md`；若同时改指标，连同 metrics.md 一起读。

即使当前 Issue 没有关联 Skill，这些规则仍然成立。Skill 不能覆盖 buddy 规范。
不确定是否命中时，先读规范再做；读取失败时停下并告诉用户，不凭记忆猜格式。
```

这里不需要程序判断「当前是哪类活」，也不需要 Skill 声明依赖。Claude 根据 Issue 内容、对话和实际改动自行判断。用户在后续对话中指出遗漏时，Claude 仍能从这份索引补读正确规范。

### 5.4 动态项目上下文

静态提示词之后，由 buddy 追加真实项目上下文。示意：

```markdown
## 本次项目上下文

- 项目：cowelink
- 项目意图：帮助……
- 当前阶段：构建
- 对标对象：……
- 差异机会：……
- 北极星：周活跃使用人数
- 北极星定义：过去 7 天内至少完成一次核心动作的去重人数
- 上一棒备注：指标定义已建立，本阶段先补真实采集来源
- 工作区：当前 Claude 所在目录就是本 Issue 的真实工作区
```

字段为空时写「尚未提供」，不编造；不存在的项目信息不为了排版完整而补假值。

### 5.5 不应放进系统提示词的内容

- 某个 Skill 的完整方法论；
- 指标或连接器格式的全部字段表；
- 五阶段每一步详细 SOP；
- 某个 Issue 的专属产物清单；
- 过时的兼容说明或历史实现路径。

## 6. Skill 选择与五阶段默认 SOP

### 6.1 有效 Skill 的选择规则

一张 Issue 开工时，只选择一份**主 Skill**：

1. **Issue 显式选择了 Skill**：使用用户选择的 Skill。
2. **Issue 没有显式选择 Skill**：使用当前阶段的默认 SOP Skill。
3. **阶段默认 Skill 的文件缺失或正文为空**：这是资产损坏或打包遗漏。系统提示词仍可用，但开工前要在界面和运行日志中明确告警「当前阶段默认方法不可用，本次只依据 buddy 规范处理」，不能悄悄装成已经加载。正常发布包中的五阶段默认 Skill 必须齐全。

显式 Skill 是**替换**默认 SOP，不是与默认 SOP 叠加。这样用户选自己的方法时，不会同时被 buddy 默认流程拉向另一套做法。默认 SOP 按 Issue 自身记录的阶段选择；一张 Issue 创建后归属阶段不随项目后来交棒而改变，因此它的默认方法也不会在恢复时静默切换。

专项标配 Issue（竞品分析、找指标、绑数据）已经显式选择专项 Skill，因此使用专项 Skill，不再叠加原型阶段默认 SOP。专项 Skill 如需多个 Agent 协作，应在自己的正文里写明协作步骤。

### 6.2 五阶段默认 Skill

| 阶段 | 默认 Skill | V2 要补强的内容 |
|---|---|---|
| 原型 | `evidence-first` | 证据收集、方案形成、反方核验如何分工 |
| 构建 | `spec-to-tests` | 规格澄清 → 验收拆解 → 实现 → 独立评审的协作流程 |
| 优化 | `baseline-before-touch` | 基线测量 → 最小改动 → 前后对比 → 回归审查 |
| 运营推广 | `fresh-eyes-funnel` | 新用户走查 → 摩擦归因 → 改进 → 再走查 |
| 运维 | `breaking-drill` | 故障设计 → 演练执行 → 修复 → 恢复验证与复盘 |

这五份 Skill 已经存在，不新造第二套同义 Skill。V2 在保留原有方法论的基础上，为每份补一节「在 Claude CLI 会话里如何协作」，把旧脚本阶段循环中仍有价值的角色分工转成可读 SOP。

### 6.3 SOP Skill 的写法

每份阶段 Skill 至少讲清：

1. **什么时候适用**，什么时候不该用；
2. **主 Agent 负责什么**；
3. **哪些环节值得调用独立 SubAgent**，每个 SubAgent 只拿完成自己任务所需的上下文；
4. **各角色交接什么产物**，不能只说「分析一下」；
5. **什么时候必须回到用户确认**；
6. **失败或证据不足时停在哪里**；
7. **完成的标准**。

它描述协作方法，不要求固定 Agent 名称，不绑定某个模型，也不依赖 buddy 的旧阶段脚本。

### 6.4 buddy 官方 Skill 与用户 Skill

- buddy 自带 Skill 是随产品版本维护的原版资产。
- 不鼓励用户修改 buddy 原版；产品不再增加一套「可覆盖官方原版」的复杂配置。
- 用户认为默认方法不合适时，在 Hub 新建自己的 Skill，并在 Issue 上选择它。
- 用户 Skill 与 buddy 官方 Skill 使用同一种文件形态和装载路径，Claude 不需要理解两套协议。
- 产品指南要用这个流程讲清定制：**录入自己的 Skill → 在 Issue 上选择 → 开工时替换阶段默认方法**。

### 6.5 蒸馏经验与技能目录

现有两类增益继续保留，但不能改变主 Skill 的选择语义：

- 与项目相关的蒸馏经验继续作为补充上下文，沿用现有「同项目、同阶段优先、最多三条」规则；注入的是完整经验正文，不把它冒充第二份主 Skill。
- 当前阶段可用 Skill 目录继续写入 `.claude/skills/`；启动上下文的 Skill 目录段只放名称与一句用途，Claude 需要时再读取完整正文。
- 主 Skill、蒸馏经验、技能目录三者用清晰标题分段；补充经验和目录不能覆盖 buddy 系统提示词，也不能偷偷替换用户显式选择的主 Skill。

## 7. 一张 Issue 的完整启动流程

```text
用户点击 Issue「运行」或恢复会话
        │
        ▼
读取真实 Issue、项目、阶段、上一棒与工作区信息
        │
        ├─ 写入/校准 `.claude/buddy/standards/`
        │  （把 buddy 正本写到业务工作区供 Claude 读取）
        │  并确认它不会进入用户提交
        │
        ├─ 选择一份主 Skill
        │  显式选择 > 当前阶段默认 > 无
        │
        ├─ 物化当前阶段可按需读取的 Skill 目录
        │
        └─ 生成动态项目上下文
        │
        ▼
拼装 Claude 启动上下文
  A. buddy `system-prompt.md`
  B. 动态项目上下文
  C. 主 Skill 正文（若有）
  D. 蒸馏经验正文与可用 Skill 索引
  E. Issue 标题 + 描述（首条任务消息）
        │
        ▼
Claude 根据任务判断要读哪些 buddy 规范
        │
        ├─ 简单普通修改：可能不用额外规范
        ├─ 指标修改：先读 metrics.md
        └─ 采集装置修改：读 connectors.md，必要时同时读 metrics.md
        │
        ▼
在嵌入终端完成工作；需要时由 Claude 调用 SubAgent
        │
        ▼
如实停在现有 Issue 状态机允许的位置
最终完成与合入仍由人确认
```

### 7.1 首次启动与恢复的真实边界

Claude CLI 的真实恢复能力是接回已有会话；恢复命令不能再次追加系统提示词。V2 不为追求「看起来更新了」而放弃真实恢复，也不把旧历史伪装成一段新会话。

- **首次启动**：先校准规范运行副本，再注入当前系统提示词、当前项目上下文和本次主 Skill；Issue 标题与描述作为首条任务消息。
- **恢复会话**：恢复前再次校准规范运行副本，然后接回原 Claude 会话；不重复发送 Issue 首条任务消息，也不重新注入系统提示词、项目上下文或主 Skill。
- **版本语义**：一段会话使用首次启动时的公共提示词、项目上下文和主 Skill；规范文件路径保持稳定，恢复前更新后的规范正文可在后续读取时生效。
- **需要采用新方法时**：用户显式新开一次执行，重新注入当前提示词、上下文和主 Skill；不能在恢复时暗中换规则。

因此恢复保证的是「同一段会话真实延续」，不是「每次恢复都重写会话开场」。项目阶段、北极星或提示词版本发生重大变化时，界面应提示用户新开执行，而不是假装旧会话已经获得新上下文。

## 8. 失败与冲突如何处理

| 场景 | 产品行为 |
|---|---|
| 系统提示词资产缺失或读失败 | 不启动 Claude；告诉用户哪份 buddy 资产不可用 |
| 项目没有配置真实 Git 工作区 | 不写运行副本、不启动真实 Claude；演示路径仍可运行，但必须继续明确标成流程演示，不能冒充在项目里真实干活 |
| 无法保证运行副本不进入 Git 提交 | 不写运行副本、不启动；提示检查工作区 Git 状态/权限 |
| `.claude/buddy/` 已存在但不是 buddy 管理 | 不覆盖；提示用户移动或更名冲突目录 |
| 规范运行副本写入一半失败 | 临时文件清理；旧的完整版本保留；本次不启动 |
| 用户选择的 Skill 不存在或正文为空 | 不悄悄回落默认 Skill；告诉用户所选 Skill 不可用，让用户修正选择 |
| 阶段默认 Skill 缺失 | 系统提示词仍可用，但开工前明确告警并留痕；开发门禁应阻止官方发布包出现此状态 |
| Claude 没按索引读取规范 | 用户可在会话中提醒；系统提示词使 Claude 能定位并补读。后续评审按产物是否符合规范判定，不假设「提示过就一定做对」 |
| 规范文件与系统提示词索引不一致 | 构建/启动自检失败；不允许发布半套资产 |
| 恢复时公共提示词或项目上下文已经变化 | 继续真实恢复，并提示「本会话沿用首次启动时的上下文；要采用新版请新开执行」；规范运行副本仍在恢复前更新 |

所有错误用人话展示；内部模块名、函数名和字段名只写日志，不直接怼给用户。

## 9. 与当前实现的替换关系

本节给落地 Agent 定边界，不是要求用户理解源码。

### 9.1 删除的旧责任

- 删除按 Skill 名称选择「找指标 / 绑数据」契约正文的做法。
- 删除程序里的大段 buddy 业务契约文字；公共内容以 `system-prompt.md` 为正本。
- 删除 Skill 文档里关于「契约由某个程序函数唯一持有」的旧说明，改为指向 buddy 系统提示词与规范目录。
- 不保留旧格式文档路径的副本；全仓引用切到新正本。

### 9.2 保留并改造的能力

- 保留 Issue 标题 + 描述作为首条任务消息。
- 保留嵌入终端、一张 Issue 一段 Claude 会话和恢复能力。
- 保留项目上下文，但把它变成静态提示词之后的动态段。
- 保留 Skill 正文注入、蒸馏经验和阶段 Skill 目录物化。
- 保留五阶段现有 Skill 与阶段关系，补强为 Claude CLI 下的协作 SOP。
- 保留所有产品铁律与现有 Issue 状态机。

### 9.3 不新增数据库迁移

本设计优先复用现有 Issue 的 Skill 选择和阶段关系，不新增「规范类型」「场景标签」或第二套 Skill 选择字段。若落地时发现现有界面无法让普通 Issue 选择用户 Skill，应补齐这条已有字段的用户入口，而不是新增一套概念。

## 10. 两轮开发边界

设计一次定清，开发分两轮，减少一次改动同时触碰提示词、技能内容和界面的风险。

### 第一轮：统一 buddy 提示词与规范资产

交付：

1. 建立 `docs/buddy/` 资产目录与导读。
2. 写 `system-prompt.md`，从程序中移出公共契约与铁律。
3. 把指标、连接器规范迁到 `docs/buddy/standards/`，校准内容并成为唯一正本。
4. 实现运行副本物化、本地 Git 排除和冲突保护。
5. 所有 Issue 首次启动都注入当前系统提示词 + 动态项目上下文；恢复会话按 §7.1 延续首次注入，并更新规范运行副本。
6. 删除按 Skill 名称硬选规范的旧路径。
7. 校准「找指标 / 绑数据」Skill 的引用文字。

第一轮完成后，即使用户新建一张无 Skill 的「修改指标名称」Issue，Claude 也能从公共提示词发现并读取指标规范。此时无显式 Skill 的普通 Issue 仍不注入主 Skill，这是第一轮的预期中间态；阶段默认方法在第二轮接入。

### 第二轮：阶段默认 SOP 与用户 Skill 替换

交付：

1. 补强五份阶段 Skill 的 Claude CLI 多 Agent 协作 SOP。
2. Issue 没显式 Skill 时，自动选择当前阶段默认 Skill。
3. Issue 显式选择用户或专项 Skill 时，替换阶段默认 Skill。
4. 校准 Issue 新建/编辑界面，让用户看得懂「默认使用什么、选自己的会发生什么」。
5. 保留蒸馏经验和按需 Skill 目录，但明确它们是补充，不是主 Skill。
6. 更新产品指南的使用指导与「技能与 Prompt」维护机制章。

两轮之间不建立临时兼容层。第一轮交付后使用统一系统提示词；第二轮只在其上补主 Skill 选择，不再改维度 A 的模型。

## 11. 验收场景

### 11.1 无 Skill 的指标小改动

- 在任意阶段新建 Issue：「把注册人数指标名称改得更准确」。
- 不选择任何专项 Skill。
- 开工后 Claude 收到 buddy 系统提示词，识别到指标事务，读取 `metrics.md`。
- 它知道改名会影响指标身份与历史关联，不凭直觉直接改。

**通过标准**：规范读取不依赖 Issue 是不是标配「找指标」，也不依赖是否装了 Skill。

### 11.2 使用业界或用户 Skill 处理 buddy 项目

- 新建 Issue，选择用户录入的分析 Skill。
- 主 Skill 给方法；buddy 系统提示词仍给公共铁律和规范索引。
- 若工作触及连接器，Claude 仍能读取 connectors 规范。

**通过标准**：替换 Skill 不会替换 buddy 规范。

### 11.3 构建阶段无显式 Skill

- 构建阶段新建普通实现 Issue，不选 Skill。
- 开工时默认使用 `spec-to-tests`。
- Skill 指导 Claude 先澄清规格和验收，再实现，并调用独立评审 SubAgent。

**通过标准**：不恢复 buddy 旧脚本调度；多 Agent 协作发生在可见 Claude 会话内。

### 11.4 用户替换阶段默认方法

- 用户在 Hub 新建自己的开发 Skill，并在构建 Issue 上选择。
- 开工时只使用用户 Skill，不再叠加 `spec-to-tests`。
- buddy 系统提示词与规范索引照常存在。

**通过标准**：用户方法能真正替换默认流程，而不是两套流程打架。

### 11.5 恢复旧会话

- 首次执行后关闭 buddy，期间升级了 buddy 的规范或修改了项目阶段信息。
- 再次恢复同一 Issue。
- 规范运行副本更新；Claude 接回原会话，系统提示词、项目上下文和主 Skill 仍是首次启动版本；Issue 首条消息不重复发送。
- 界面如实提示该会话沿用首次上下文，需要新版方法时应新开执行。

**通过标准**：恢复延续真实会话、不暗换方法；可读取的规范正文保持最新。

### 11.6 运行资料绝不混入业务提交

- 启动 Issue 前后检查 Git 状态与待提交文件。
- `.claude/buddy/` 可被 Claude 读取，但不会出现在用户提交或 PR 中。
- 删除工作区重新 clone 后，buddy 下次运行会重新写入，不依赖旧机器残留。

**通过标准**：可读、可重建、不污染项目历史。

### 11.7 不覆盖用户的同名目录

- 在工作区预先建立 `.claude/buddy/`，放入用户文件，但不放 buddy 管理标记。
- 启动任意 Issue。
- buddy 报告目录冲突，不改用户文件，也不启动真实 Claude。

**通过标准**：用户目录的内容逐字不变；界面说明怎样移动或改名后重试。

### 11.8 没有真实工作区的项目

- 对未配置真实 Git 工作区的项目启动 Issue。
- buddy 不尝试把规范写到空路径，也不启动真实 Claude。
- 若走演示执行，产出继续带「流程演示」标识。

**通过标准**：不崩溃、不把演示说成真实执行，并明确告诉用户怎样配置工作区。

## 12. 验证要求

### 12.1 资产与拼装验证

- 系统提示词正本可独立阅读，里面没有实现函数名或硬编码项目值。
- 规范索引中每个路径都能在运行副本找到。
- 新增/删除规范时，索引与打包自检能发现不一致。
- 动态项目上下文来自真实项目数据；空值如实显示，不生成示例值。
- 搜索确认旧的 Skill 名称分支契约已删除。

### 12.2 行为验证

第一轮实跑 11.1、11.2、11.5–11.8；第二轮补跑 11.3、11.4，并保留：

- Claude 启动参数或可安全打印的拼装摘要，证明所有 Issue 都带系统提示词；
- 工作区文件读回，证明规范已经物化且内容与 buddy 正本一致；
- Git 状态读回，证明运行资料未进入待提交集合；
- 嵌入终端过程，证明无 Skill 指标 Issue 会按索引读取指标规范；
- 恢复会话证据，证明没有重复发送首条任务、没有暗换主 Skill，同时规范运行副本已更新；
- Issue 状态与数据库读回，证明没有改变最终完成人工确认等铁律。

### 12.3 工程门禁

按仓库 `CLAUDE.md` 跑完整门禁，另含：

- `cargo test`；
- 相关 examples 编译与行为校准；
- Windows 桌面深链启动；
- 必要的 SQLite 读回；
- `/code-review`；
- 真 Claude CLI 受网关影响时，明确标注哪些交互验收由用户完成，不用 mock 冒充。

### 12.4 产品指南

第二轮完成后更新：

- **使用指导 · 建活与选技能**：说明没选 Skill 时使用阶段默认方法，选择自己的 Skill 后替换默认方法。
- **维护指南 · 技能与 Prompt**：用两条并行资产线说明「buddy 规范总在 / Skill 按活选择」，不要按程序命令讲。
- 只写已经实跑的行为；未验证的恢复或物化行为不得提前写成已可用。

## 13. 给后续助手 Agent 的实施约束

1. 本文是 V2-① 的设计事实源；不要再从 V1 文档里复制旧的 Skill 名称分支。
2. 先实施第一轮并独立验证，再实施第二轮；不要一次提交混完。
3. 代码只负责资产打包、物化、动态上下文和拼装，业务契约正文留在 Markdown。
4. 不新增「场景标签」或 Skill 到规范的映射表；渐进读取由系统提示词索引 + Claude 对当前任务的理解驱动。
5. 启动时 A–D 四段仍拼成一份带清晰二级标题和分隔线的系统提示词，一次传给 Claude；Issue 标题与描述保持为首条任务消息。不得静默截断公共提示词、主 Skill 或蒸馏经验，若启动参数超过真实 CLI 能力应报错并记录各段长度。
6. 恢复遵守 §7.1：更新规范文件后接回原会话，不伪造重新注入。
7. 不把 buddy 运行规范提交进用户业务仓，也不修改用户项目 `.gitignore` 来隐藏它。
8. 用户显式选择的 Skill 替换阶段默认 Skill；不要叠加两份主方法。
9. 默认 Skill 缺失、所选 Skill 无效、规范写入失败都要如实报错，禁止静默回落制造「好像加载了」的假象。
10. 不改产品铁律，不恢复旧脚本式 Issue 调度，不顺手扩进多人机制。
11. 每轮开发使用 `buddy-feature-dev` 功能开发流程：开发 → 评审 → 验证 → 按需填产品指南；禁止 push，只可按用户指令 commit。

## 14. 最终判断

这套设计把 V1 的执行能力和 V2 的长期资产分开了：

- Claude CLI 负责把过程变得可见、可继续；
- buddy 系统提示词与规范保证「无论用什么 Skill，都在 buddy 里做对」；
- Skill 保证「这类活怎样做得更好、多个 Agent 怎样协作」；
- 项目上下文保证同一套方法落到当前真实项目，而不是抽象演练。

它不依赖某张标配 Issue、不依赖某个 Skill 名称，也不依赖旧的脚本调度器。后续即使 buddy 更换桌面壳、重做调度或调整存储，这个目录仍能作为真实、可读、可直接继承的产品资产。
