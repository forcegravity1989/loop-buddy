把 buddy 讲给同事听

这是什么——一份讲稿，给要把 buddy 介绍给同事、领导或者别的团队的人用。里面没有一行代码、没有一个内部代号，照着讲就行。给谁看——任何一个要开口介绍 buddy 的人。现在还作数吗——作数（2026-08-21）。

一条纪律：这份稿子不许吹。已经能跑的说能跑，还在路上的就说在路上，没做的直接说没做。讲出去的每一句都会被人拿去用，吹出来的坑最后要自己填。文中所有「还在路上」的地方都标出来了，讲的时候别顺手抹掉。

想给人演示怎么操作，给他 buddy 的产品指南；想跟人讨论「为什么这么设计」，给他设计正本。

一句话

buddy 是 AI Coding 时代里，一个人的一张工作台。 它让一个普通开发者，用 Builder 的方式，把一个三个月的小项目从想法一路管到能验收的结果。

如果只能说一句，就说这句。

如果对方追问「那到底解决什么问题」，再讲下面这段——这是产品最初的自我表述，一个字没改过：

用 AI 时代的方式，一步步把一个项目的管理体系搭起来。 每一步都先讲「为什么」，再动手做。走完，你就拥有了一套可复制的项目管理方法，而不只是一块看板。

「不只是一块看板」这半句是重点。市面上的工具帮你存卡片，但不回答两个问题：现在该干什么、做到什么算完。buddy 想回答的就是这两个。

产品哲学 · 从第一天到现在没变过

四个控制点

这四条是 buddy 全部设计的出发点。介绍产品时可以直接把这四条念出来，它们比任何功能清单都更能说清楚这个东西是什么。

01
知道对标谁
每个项目都要说清楚自己最像谁、差距在哪，否则不进入开发。
02
每周在正常演进
项目健康与否来自真实数据，不靠口头汇报，一眼可判断。
03
让 agent 干活，人只守质量门
人在验收处介入，不做微观管理；但验收信号必须足够可信。
04
目标清晰且难造假
一个项目只有一个北极星；支撑它的指标必须可控、可被真实统计。
四条里最难的是第四条。大部分工具的仪表盘是自己骗自己：数字自己填、灯自己调。buddy 从一开始就把这条钉死——健康灯只能被真实数据点亮，没有数据就是灰色的「未知」，绝不假装绿。手填的数字会带一个「手填」标记，数据过期会自动降级。这条是产品的底线，不是可配置项。
和传统项目管理比

换掉的不是「谁写代码」

先说清楚对比的对象是什么。现在人人都在用 AI 写代码，所以不存在「人写代码 vs agent 写代码」这种收益——这个不要讲，讲了会被人当外行。

真正的对比，是传统项目管理那一整套流程：大约十道工序、五个专职角色（产品经理、项目经理、技术负责人、设计师、测试），信息要靠这些角色之间反复开会、人工汇报才能流动。

五个角色靠开会流转信息 → 一个人 + agent 循环端到端负责

介绍功能的骨架

三个愿景，和它们今天各自落到了哪

这一节是介绍功能时最好的骨架——不要按屏幕讲，按愿景讲，对方才记得住。

愿景一 · 所有项目长一样
痛点：每个项目一套做法，产出没人管，资产散在聊天记录、本机目录、各人脑子里。
怎么做：接入项目时往仓里放同一套东西——名片、指标正本、活的约定、周计划位置、发版记录位置。之后所有产出都写回这个仓。
已经真走通
接入 + 铺底已跑通；给项目写开发手册还在路上（要先问你）
愿景二 · 从「开发」到「小项目的 Builder」
痛点：一两个人的项目和实验局没有角色把控，做完了但走偏了，没人知道。
怎么做：一个每周转一圈的固定剧本。指标从真实数据推导、周目标挂着具体的活、完成永远人点、健康灯不假绿。
设计+代码都建完
真实两周循环还没跑完，试点在跑，一边跑一边改
愿景三 · 一张工作台打通所有系统
痛点：在代码平台、终端、设计器、聊天工具、问题单系统之间跳来跳去。
怎么做：每张活按类别选一个开工工具，都不用离开工作台；终端嵌在界面里，全程可见、可插话、可喊停。
部分能跑
内嵌终端 + Claude 命令行能跑；真聊天工具、Cursor、内嵌设计器还没接

愿景一 · 详细

用户能感到什么：换项目不用换脑子；agent 打开仓就懂这个项目；别人把同一个仓纳入自己的 buddy，看到的是同一张总览。

今天到哪了：接入 + 铺底这条路已经真走通了，而且有一条硬规矩——buddy 往你仓里写的东西全部收在一个专门的目录下，仓根一个字不动。你原本的说明文档、原本的 agent 约定，buddy 根本不碰。

还在路上的：「给这个项目写一份开发手册」——buddy 起一次会话真读一遍你的仓，把读出来的摊给你看，问你要不要，你点头才写。这一步还没实现。为什么要先问：给别人的项目加规范，性质上是「建议改造你的项目」，得先读懂、先问过。

愿景二 · 详细

用户能感到什么：每周有一个可验证的增量，不靠会议和口头汇报。

今天到哪了：剧本本身设计完了、代码也建出来了；但真实的两周循环还没跑完——试点在跑，一边跑一边改。这一条讲的时候要说清楚：这是我们自己正在用的东西，不是已经打磨了半年的成品。

愿景三 · 详细

用户能感到什么：少切窗；工具是缝进来的，不是自己造的。

今天到哪了：内嵌终端 + Claude 命令行这条已经能跑；项目群的接口定了、假群能跑通，真实的内部聊天工具还没接（实现由同事补）；Cursor 和内嵌设计器还没接。

这里有一条我们自己的纪律，值得讲出来：能力底座一律用业界成熟的东西，buddy 只写薄薄一层适配。自建要举证。已经包装好的东西，永远不改写成自己的原生实现。
演示时的主线

一个项目在 buddy 上是怎么转的

这是演示时的主线。一次准备，然后每周六步。

准备只做一次；一 → 二 → 三 → 四 → 五 → 六，六之后回到一
准备
一次性
把项目接进来
填两张卡：这个项目在哪（从你账号下的仓里选，或者直接打地址）、这个项目是什么（名称、你想做什么、最像的对标、三个月后怎样算成了）。最后一格就是北极星——它是唯一必填的目标，而且必须可度量。点完成之后，buddy 自动开一条分支、把管理体系的骨架写进你的仓、提一个合并请求，然后停下来等你合。它不会自动合，也不会自动把这件事标成完成。
第一步
周一看总览
一屏看完这个项目是什么、健康不健康。健康灯只有四种颜色：绿（平稳）、黄（需要关注）、红（阻塞）、灰（没数据），旁边把判断理由三条全列出来——不是一个孤零零的圆点让你猜。第一次打开多半是灰的。这是对的，不是 bug。
第二步
开始本周
点一下「开始本周」，buddy 起一次 agent 会话，在同一次对话里做完三件事：复盘上周 → 把指标补齐、给绑不上数据的找一条最便宜的采集路径 → 和你一起把这周的目标和活清单聊出来。这里有个容易被误解的地方，讲的时候要点破：周目标不是你「写」出来的，也不是 agent 替你决定的——它是在这次对话里，结合指标、代码现状和上周记录聊出来的。你只在首尾出现：点一下开始，和最后确认一下。
第三步
干活
每张活按类别默认好了用什么工具，点开工，agent 就在这张活自己的工作目录里干起来。你在嵌进来的终端里全程看得见。agent 干完，最远只能把活推到「评审中」。
第四步
验收
看改动、看文档、看原型，合并，然后你亲手点「完成」。这一下永远是人点的。这不是配置项，是写死在类型系统里的：「完成」这个状态只有一个入口，就是「评审中」，而且必须来自一次显式的人工动作。
第五步
记一笔发版
周末把这周完成的活归到一个版本号下，写进仓里的发版记录。
第六步
定时盘点
每周固定时间，buddy 自己建一张「资产盘点」的活并自动开工：看看文档齐不齐、规范有没有过期、指标数据新不新鲜、有没有该拆的大文件。盘点只写建议，不动手改代码。报告停在「评审中」等你周一来看，你勾选哪几条建议，才真的建成活。这一条正好说明前面那条铁律：定时任务只会自动建活，绝不自动完成活。
有人一定会问

有人一定会问的几个问题

它是不是又一个看板？
不是。看板只是其中一屏。真正的东西是那套每周转一圈的方法，以及「这个项目健康不健康」是被算出来的，不是被填出来的。
数据在哪？会不会传到什么地方去？
全在你自己机器上，一个本地数据库文件；项目相关的正本在你自己的代码仓里。AI 执行就是你本机的命令行工具，在嵌进来的终端里全程可见、可中止，花费你自己把握。不是云服务。
我们团队五个人，能用吗？
buddy 里没有成员、没有权限、没有群聊、没有收件箱，它假设你就是那一个 Builder。但多人协作是允许的，靠代码仓发生：有合并权限的同事把同一个仓纳入自己的 buddy，就能在自己的待办里看到评审中的活，审完点合并。跨人的提醒走项目本来就有的聊天群。
界面上的数字我怎么信？
每一个都能自己查证——数据库可以直接查，仓里的文件可以直接打开看。工具说的话不用信，可以验。这是产品的设计前提，不是附加功能。
已经跑了很久的老项目能接进来吗？
能。接入时 buddy 会发现这是个有历史的仓，把它自己的历史（提交、合并、标签）按同样的格式补成周记录和发版记录，标明是回填的。回填只解释过去，不点亮健康灯——灯只看接入那天之后的真实数据。这条已经能跑一半：确定性的那半（直接从历史算出来的数字）做完了，需要 agent 读文档补充的那半还在路上。
什么时候能用上？
今天它是我们自己在用的东西，试点在跑。macOS 能装，Windows 的安装包还没出。说这句的时候不要含糊——含糊会让人以为下周就能拿到。
讲完之后，别忘了这两句

如果整场只有两句话能被记住

应该是这两句：

「完成」永远由人点。agent 干完最远到「评审中」；定时任务只会自动建活，绝不自动完成活。
没数据就是灰，不是绿。健康只能从真实数据推出来，界面上任何一个数字都能自己查证。

这两句说完，对方大概就懂这个产品是什么脾气了。
