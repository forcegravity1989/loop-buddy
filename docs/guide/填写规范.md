# buddy 指南 · 填写规范

> 本文件是 `buddy-guide.html` 原型的**填写规范**。HTML 是可复用的原型样式模板，本规范说明两本的组织方式、每屏结构模式、组件用法、如何扩展。后续实践推进时照着填即可，无需改样式。**未来这是整个产品指南的种子。**

---

## 1. 两本的组织方式

两本用**不同的维度**组织，互为索引：

- **使用指导** = 按**界面操作阶段**组织。实践推进到哪、能见到哪，就写到哪。不预先猜未来阶段。
- **维护指南** = 按**跨阶段机制**组织，站在高 level 汇总。一个机制往往被多个阶段共用（如 connector 同时服务纳入与采数；Issue 调度同时服务找指标与绑数据；预制技能同时被找指标/绑数据加载），所以按机制成章，并在章首标注「用到此机制的阶段」。

> 为什么不按阶段切维护指南？因为同一个机制会被多个阶段共用，按阶段切会把它拆散到多屏、重复盘点。按机制汇总才是一份能长期生长的产品指南。

### 当前已写入的内容

V1 产品化按**三个窗口**推进（W1 纳入项目 / W2 找指标·绑数据 / W3 总览重构），**各窗口只填自己实践得来的内容**，非本窗口的章节只留章节名占位、待对应窗口棒补。当前 W1 已打结。

使用指导（操作阶段屏）：

| # | 阶段 | 窗口 | 状态 |
|---|---|---|---|
| 01 | 纳入项目 | W1 | ✅ 实体（操作→背后→得到什么） |
| 02 | 找指标 | W2 | ⬜ 占位（章节名） |
| 03 | 绑数据 | W2 | ⬜ 占位（章节名） |
| 04 | 总览呈现 | W3 | ⬜ 占位（章节名） |

维护指南（跨阶段机制章）：

| # | 机制章 | 窗口 | 状态 |
|---|---|---|---|
| 01 | 架构与铁律 | 共享底座 | ✅ 实体 |
| 02 | Hub 全局库 | W1（connector/script/cron 三层） | ✅ 实体（skill 渠道只留种A） |
| 03 | Issue 与调度 | W1（三件套自动建）/ W2（状态机·调度执行） | 🟡 半（只留三件套，其余占位） |
| 04 | 技能与 Prompt | W2 | ⬜ 占位 |
| 05 | 执行与证据 | W2 | ⬜ 占位 |
| 06 | 指标与健康 | W2 / W3 | 🟡 半（只留「纳入时种默认 metric」一句） |

> 跨阶段通用基础（命令门禁、设计 token）暂未单独成屏。等实践推进到某机制章需要它时再补，或并入「架构与铁律」章。不提前猜。

## 2. 使用指导 · 操作阶段屏结构

每屏四段式：**操作 → 背后 → 得到什么**（+ callout 坑 + linker + foot）。「背后」讲这一步做完 buddy 自动干了啥（白话），「得到什么」讲用户手上多了啥、关注啥。

```
<eyebrow>   使用指导 · 阶段 0X
<h1.disp>   阶段名
<lede>      一句话定位（用户视角，讲心智不是讲机制）
<h2.sec> 操作        → .ops 有序步骤
<img>       截图按步放（每步下面放该步的截图，不堆在末尾）
<h2.sec> 背后        → .res 三轴白话（见下）
<h2.sec> 得到什么    → .res 用户手上多了啥
<callout>           可选：该阶段坑/边界
<p.linker>          指向对应维护指南机制章
<.foot>             事实源脚注
```

### 必填内容
- **操作**：界面上的真实操作步骤，按序号写，能照着点。**截图按步放**——每步下面放对应截图，不在末尾堆连续截图；本质上同一 UI 界面的步可共用一张。
- **背后**：点完关键操作（如「确认」）buddy **一次性**在背后干了啥。用**白话三轴**组织，**不按 `Command::` 代码命令、不用 CRUD 黑话**：
  - **对远端代码仓**（GitHub/CodeHub）：建仓 / 开 Issue / 推提交……
  - **对用户的机器**：clone / 写文件 / 探活……
  - **对 buddy 数据库**：落 project 行 / 建阶段 / 挂连接器 / 排定时器 / 建 Issue / 种 metric……
  - 给个地址 + 一笔核心信息描述即可，代码级细节（具体表名/字段/函数）放维护指南机制章，这里只讲用户能感知的。
- **得到什么**：用户建完手上多了啥、该关注啥（不是"看到界面呈现"那种流水账，是"你得到了什么能力/资产"）。

### 规范
- **窗口边界**：只填本窗口实践得来的阶段屏。非本窗口的阶段屏**只留章节名占位**（`<h1>` + 一句「待 X 窗口棒补」+ `.foot` 指 `plan/08`），不预先填内容。
- 只写已实践/可见的，不猜、不发明指标。
- 表名、文件名、命令、状态值用 `code` 包裹（真实值）。
- 每屏末 `.foot` 标事实源（代码仓文件名用 `code`）。
- `.linker` 指向该阶段涉及的维护指南机制章（可多个，用 `go('mX')`）。

## 3. 维护指南 · 机制章结构

每章 = 一个跨阶段机制，开头标注用到此机制的阶段，然后按子主题分组的概念卡。

```
<eyebrow>   维护指南 · 机制 0X
<h1.disp>   机制名
<lede>      一句话定位 + 跨阶段关系
<.stages>   用到此机制的阶段徽（.s 标签）
<h2.sec> 子主题    → .cc 概念卡列表
<.foot>     事实源脚注
```

### 概念卡四要素
```
<div class="cc">
  <div class="h">术语 中文 <span class="term">英文/别名</span></div>
  <div class="d">是什么 + 机制</div>
  <div class="src">事实源：<code>文件</code></div>
</div>
```

### 规范
- **窗口边界**：只填本窗口实践/感知到的特性卡。非本窗口的机制章**只留章节名占位**（`<h1>` + 一句「本机制服务于 X 窗口，待对应棒补」+ `.stages` + `.foot` 指 `plan/08`），不预先盘点机制内容。
- 一章一机制，章首 `.stages` 必填——标清哪些阶段用到它（这是「跨阶段」的可读证据）。
- 一个概念一张卡，不合并无关概念。
- 跨章共享的概念放它的**主机制章**（如 Issue 状态机主属「Issue 与调度」章），其它章用到时用脚注/链接指回，不重复盘点。
- 只盘点当前真实实践到的机制，不补未来阶段才有的。
- 特性卡反链使用步骤：本机制用在哪个使用指导步骤，卡末加「见 <code>go('uX')</code> 步骤Y」。

## 4. 组件清单（class 名 + 用途）

| class | 用于 | 出现位置 |
|---|---|---|
| `.ops` + `.li` | 操作有序步骤（带序号圆点） | 使用指导·操作 |
| `.res` + `ul/li` | 结果清单（落库与产出） | 使用指导·结果 |
| `.see` | 看到（界面呈现） | 使用指导·看到 |
| `.stages` + `.s` | 用到此机制的阶段徽 | 维护指南·章首 |
| `.cc` + `.h/.d/.src` | 概念卡（术语/机制/事实源） | 维护指南 |
| `.linker` | 跳转到对应维护机制章 | 使用指导屏末 |
| `.callout` `.warn/.note/.danger` | 提示框（坑/说明/铁律） | 通用 |
| `.cards` + `.card` | 卡片网格 | 通用 |
| `.flow` + `.node` | 横向流程链 | 通用 |
| `.lights` + `.light` | 健康灯四态 | 总览呈现 |
| `.rules` + `.rule` | 铁律/控制点四宫格 | 架构与铁律 / 概览 |
| `.checklist` + `.chk` | 安装清单 | 前置准备 |
| `pre.code` | 代码块 | 前置准备等 |
| `.foot` | 事实源脚注 | 每屏末 |

> 排版组件：`.eyebrow`（阶段/机制标签）/ `h1.disp`（标题）/ `.lede`（导语）/ `h2.sec`+`.n`（小标题带序号徽）。新内容尽量复用现有组件，不新增 CSS。

## 5. 扩展规范

两本用不同维度，所以**加新阶段**和**加新机制**是两件独立的事，互不强制绑定：

### A. 加新操作阶段（使用指导）
实践推进到新阶段（如「阶段交棒」「Hub 全局库管理」）：
1. 复制一个现有阶段 `<section class="screen" id="uX" data-title="阶段名" data-sec-name="使用指导">`，按三段式填。
2. 侧栏「使用指导」组加一行 `<div class="nav-item" data-screen="uX">`。
3. 若该阶段引入了**新机制**，去 B；否则只用 `.linker` 指回已有机制章。

### B. 加新机制章（维护指南）
某机制跨多个阶段、值得独立汇总（如「阶段与交棒」「autopilot 定时」「蒸馏复利」单独深化）：
1. 复制一个现有机制章 `<section class="screen" id="mX" data-title="机制名" data-sec-name="维护指南">`，填 `.stages` + 概念卡。
2. 侧栏「维护指南」组加一行 `<div class="nav-item" data-screen="mX">`。

`data-screen` 指向 `id`，JS 自动接管切换 + localStorage 持久化（key `buddy-guide-screen`）。无需改 JS。

## 6. 内容规范

- **窗口边界（核心纪律）**：V1 按三窗口推进，**只填本窗口实践得来的内容**。非本窗口的阶段屏/机制章只留章节名占位、标「待 X 窗口棒补」+ `.foot` 指 `plan/08`，不预先填、不猜、不抄代码里的未来特性。遗留问题统一进 `docs/v1-prototype/LEFTOVERS.md`，不在指南里堆。
- **真实实践优先**：只写已实践/已可见的阶段与机制。未实践的不写、不猜。
- **背后事务用白话三轴**（对远端代码仓 / 对用户机器 / 对 buddy 数据库），不按 `Command::` 命令、不用 CRUD 黑话；代码级细节留维护机制章。
- **事实源脚注**：每屏末 `.foot` 必填，标代码仓真实文件（`code` 包裹）。
- **术语统一**：以 `CONTEXT.md` 为唯一规范词表（Builder / 队友 / 阶段 / 交棒 / Issue / 观测 / 指标 / 信号 / 北极星 等），不自造同义词。
- **诚实口径**：无数据 = Unknown ≠ 绿；Done 永不自动；manual 带徽；数字可 sqlite3 查证。涉及健康处必须重申。
- **跨章概念不重复**：放主机制章，其它章指回。

## 7. 视觉规范摘要（buddy 自有设计系统）

- **色**：暖纸底 `#EFEBE2` / clay 主色 `#C5654A`（文本用深调 `#A84A30`）；信号四态：Green 隐身、Amber 黄、Red 红、Unknown 灰。绿色不出声，只有红黄出声。
- **字**：Noto Serif SC（display）/ Noto Sans SC（body）/ JetBrains Mono（code·数字）。
- **字距**：ALL CAPS ≥ 0.06em；display 标题 -0.02em；body 行高 1.6。
- **accent 节制**：clay 作结构色（序号/eyebrow/激活态/阶段徽），不泛用为 CTA。
- token 全在 `:root`，改一处全局生效。
