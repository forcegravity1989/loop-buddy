# Builders' Workbench(buddy)V4 MVP · 专家评审一页纸

> **30 秒导读**:给内部专家 5 分钟看的一页纸(2026-08-19,评审用,人话)。说清:buddy 是什么、V4 MVP 要推给更多人的是什么、一周怎么跑一圈、我们做了哪些关键取舍、能带来什么、以后怎么长。想看更多:20 分钟看 [deck.html](deck.html)(翻页讲稿),60 分钟以上按 [README.md](README.md) 的顺序看高保真原型与全貌草案。看不懂的词查仓里 `CONTEXT.md`。

## 1 · 一句话

**buddy 是 AI Coding 时代里「一个人的一张工作台」**:让传统开发者按 Builder 的方式,把一个小项目(约三个月)从想法管到能验收的结果。V4 MVP = 把这句话做成**每周都能真跑一圈**的最小闭环,推给公司内更多人(codehub 项目为主,GitHub 同样能用)。

## 2 · 痛点(为什么要它)

- 现在人人都在 AI Coding,agent 产出越堆越多、没人管,项目**无限膨胀**;每个项目、每个人一套做法。
- 资产散在聊天记录、本机目录、各人脑子里,**换个 agent、换个人就看不见**。
- 很多项目 / 实验局只有 1-2 个人,没有传统项目里那五个角色十道流程把控,**做完了但走偏了、没人知道**。
- 人在 codehub、终端、设计器、聊天工具、问题单之间**跳来跳去**;好用的组件 / agent / skill 靠各自摸索。

## 3 · 三个愿景 → MVP 里落成什么

| 愿景 | MVP 落成 |
|---|---|
| ①**规范**:所有项目都长一样;**知识管理**:项目所有知识都在项目代码仓,大模型皆可见 | **规范铺底模块**:接入项目时往仓里放同一套文档与约束(章程 PROJECT.md、agent 工作约定 AGENTS.md、指标正本、周计划、发版记录、默认 skill/agent),后续都写回仓;规范本身是独立、可评审、可持续优化的一个目录 |
| ②从开发者变成小项目的 **Builder**(1 Builder + Agent Loop),靠 buddy 把控交付质量 | **周循环**:看总览 → 更新指标与定计划 → agent 干活人守门 → 评审 / 合入 / 人点完成 → 发版 → 定时盘点 → 回到总览 |
| ③**一张工作台**,内嵌 Open Design、Claude CLI、Cursor 等成熟组件,打通所有系统 | **会话屏**:每张活按类别选开工工具(原型 → Open Design;构建 → Claude CLI / Cursor),不出工作台;右侧代码结构侧栏(借 Orca);MVP 打通开工工具 + codehub / GitHub,聊天 / 问题单是同一条「适配模块」路上的下一批 |

## 4 · 用户旅程:第 0 站一次 + 每周六站

```
第0站 接入项目 + 规范铺底(一次;buddy 建分支写规范件 → 提 MR → 有权限的人合入)
   ▼
第1站 周一看总览:项目信息 + 健康灯 + 指标(北极星→滞后→引领,每个指标下挂着推它的活)+ 本周进度 + 版本
第2/3站 运作活①「更新指标 + 制定本周计划」:人点「开始本周」,agent 在终端里复盘上周、更新指标、和人交流出周目标与活草稿,人确认才建活;变更走 MR
第4站 执行:六列看板 / 会话屏,每张活按类别选工具(Open Design / Claude CLI / Cursor),agent 干、人守门;干完最远到「评审中」
第5站 验证闭环:评审(builder 或 committer)→ 合入 → **人点完成** → 周末发版本(仓里记一行)
第6站 定时:运作活②「资产盘点与代码微重构」自动建并自动开工,停在评审中等人看 → 下周一回到总览
```

**角色**:主角 Builder;**leader** 不做专门界面——把大家的仓纳入自己的工作台,项目墙就是 leader 视图;**committer**(有合代码权限的人)同样纳入同一仓,在自己的「通知」里看到评审中的活,审完点合入。

## 5 · 关键策略决策(十二条,每条一句为什么)

1. **0→1 按旅程建,不是 10→5 缩减**:旅程用不到的不带(工作流库、阶段轴、聊天面板、多面板),不列「不做清单」。
2. **完成永远由人点,agent 最远到「评审中」**;同一件活绝不记两次——产品铁律,状态机锁死。
3. **健康只从真实数据推导,没数据就是灰,绝不假绿**;手填的带徽记。
4. **凡要留痕的事都是「活」(issue)**:需要一次 agent 会话的是活,**要往代码仓写东西的也是活(写仓一律走分支 + MR,MR 必挂活)**——铺底、改名片也不例外;只动本机库的纯人工动作(合入、点完成)不建活。
5. **触发只有两种:人触发、定时触发**;事件触发(远端新 issue / CI 红 → 自动建活)留到 MVP 后。
6. **指标四层链**:北极星 1 个(接入必填)→ 滞后 ≤3 → 引领 ≤3 → 周目标 + 活(每张活可标「预期推动的指标」);总览按这条链画,指标不靠解释靠挂活。
7. **规范是文档和约束,不是代码**:正本在 buddy 仓 `standard/`(八个大类,有版本、有变更记录),铺底 = 按清单写进项目仓;改规范 = 改文件过评审,不改 buddy。
8. **agent 会话里的规范手册渐进加载**(第 0-4 层:系统提示词 → AGENTS.md → 本活 skill → 规范件按需 → 项目知识),不一次性灌全部。
9. **开工工具三个(Open Design / Claude CLI / Cursor),按活的类别选**;两类接法(终端类 / 本机网页内嵌类),新工具只加一条声明 + 一个适配模块。
10. **默认件业界优先、自建最少**(superpowers、grillme + buddy 自建三个运作 skill + 两个 agent);资产来源只两种:buddy 内置 / 项目导入。
11. **多人协作靠代码仓,不在 buddy 里建成员 / 权限 / 群聊**:committer 纳入同一仓合入;跨人通知走内部聊天工具增量包。
12. **建法:新壳 + 旧内核 + 模块管控,不推倒 V3 的视觉与好组件**:一屏一模块、一个外部能力一个适配模块(附 README 记借自哪)、文件行数守卫;减负线(PR #102)先合入再开 V4。

## 6 · MVP 特性清单(按屏)

- **项目墙**(leader 视图):V3 卡片(灯 + 一句话 + 本周目标 + 待办数)、本机环境「测一下」(失败项跳指南)、指南抽屉。
- **接入**两卡:项目地址(新建 / 已有)+ 基础信息四字段(名 / 想做什么 / 对标 / 三个月长成什么样 = 北极星);铺底走 MR。
- **总览**:项目信息 + 健康(大灯 + 三条理由)/ 北极星 / 滞后 / 引领(每卡挂活)/ 项目指标(仓统计)/ 本周计划进度 / 在研版本与发版记录。
- **计划**:周视角 + V3 六列看板一个界面(待办池 → 待办 → 进行中 → 评审中 → 已完成 → 阻塞);周头有周目标、进度、运作活状态、发版本、「预览 · 未合入」。
- **会话**(按 Orca):会话按目录 / worktree 分组,仓根常驻 shell;终端 / 文件只读视图 / diff / 内嵌 Open Design;文件树可点、改动文件 diff、git 状态、MR 卡;▶开工 / ■停止 / 推到评审 / 蒸馏。
- **通知**:待处理(评审中待合入、已合入待点完成、指标过期、名片修改待合入)+ 事件流。
- **配置**:开工工具映射(类别 → 工具 → agent → skill)、skill 表、agent 表、连接器 + 定时;导入。
- **知识库**:知识(仓内文档树)/ 代码图(codegraph:模块依赖、大文件榜、符号影响面)/ 资产(skill、agent、运作 skill、产物、仓统计)。
- **设置**:工作区根目录、claude / Cursor / Open Design 路径、codehub / GitHub 登录。
- **运作活三张**:①更新指标 + 制定本周计划(人触发)②资产盘点与代码微重构(定时自动开工)③规范铺底(接入时一次,含成熟仓的合并调整)。
- **数据增量**:活多了 周 / 版本 / 工具 / 种类 / 来源 / 推动指标;新增 发版记录、周计划索引;项目多了 规范版本 / 在研版本。信息分三层住:仓(正本,全可见)/ 本机文件 / 本机库(只做记账与推导)。

## 7 · 能带来什么(对比对象是「AI Coding 时代里没有 buddy」)

| 没有 buddy | 有 buddy(V4) | 证据 |
|---|---|---|
| 每个项目一套做法,agent 产物越堆越多,项目无限膨胀 | 所有项目同一套规范运作;运作活②每周盘点与微重构 | 多个仓同一套骨架;`docs/plan/` 里的盘点记录 |
| 资产散在聊天、本机、脑子里 | 所有资产在项目代码仓、有规范位置,任何大模型打开仓就看见 | 仓文件本身 |
| 1-2 人的项目没人把控,做完了但走偏了 | 周循环:指标从真实数据推导、周目标挂着活、完成永远人点、健康灯不假绿 | 总览 + SQL 读回;`.bw/metrics.toml` 变更史 |
| 在 codehub、终端、设计器、聊天、问题单之间跳 | 一张工作台里开工、评审、合入、发版 | 会话屏 + 运行记录 + MR |
| 好用的组件 / agent / skill 各自摸索 | 严选默认件随规范铺进每个项目,用过就记账 | skill 使用记录、战绩 |

## 8 · 未来怎么大一统(MVP 后,顺序按证据来)

1. **同事贡献**:好提示词 → `standard/` 的 AGENTS.md 模板;锐评过的 skill / agent → buddy 内置;打通内部通信工具的人 → 一个适配模块(顺带每个项目在聊天工具里有个助手)。贡献 = 往 buddy 仓提 PR。
2. **打通更多系统**:内部聊天、问题单、DSH 一类的 agent 网页——都是「一个外部能力一个适配模块」。
3. **事件触发**:远端新 issue / CI 红 / 指标过期 → 自动建活(不自动开工)。
4. **同一项目多条版本线**、**观测快照回写仓**(leader / committer 也看得见过程数据)、**codegraph 符号级侧栏**。
5. GitHub 走同一流程(连接器已在),内外一致。

## 9 · 风险与验收

- **风险**:真实 `claude` 执行受网关抖动影响(只在监理脚本里跑,可重试,不作常绿验证);Windows PTY 后端未真机验证、macOS 已验;规范件在试点里「用没用上」要靠两周试点证据修订(没被用到的降为扩展件)。
- **MVP 做完的定义**:一个真实内部项目在 V4 上跑完两个完整周循环(两份周计划、两轮运作活①②、至少一次发版记录都在仓里);总览灯不是灰的且每个数字能用 SQL 或仓文件核对;至少一张活用 Open Design、一张用 Claude CLI 开工且产物进仓;第二台 buddy 纳入同一仓,leader 看到同一张总览、committer 能合入;Windows 安装包 `0.4.0-v4` 在同事机器上装得上跑得起。

## 10 · 请专家拍的五个问题

1. 「写仓一律走 MR 并挂活」在内部 codehub 权限模型下是否顺(铺底、改名片这种小改也走 MR,会不会太重)?
2. 运作活②「资产盘点与代码微重构」定时**自动开工**、停在评审中——尺度是否合适?哪些改动应禁止它碰?
3. 规范八大类的「核心 / 扩展」划分与 AGENTS.md 固定章节,是否与各团队现有 CLAUDE.md / README 习惯冲突?成熟仓的「合并调整」由 agent 提 MR 是否可接受?
4. 开工工具首批三个(Open Design / Claude CLI / Cursor)与「按类别默认」的映射,是否覆盖大家的真实工作方式?缺哪一个?
5. leader 视图 = 纳入所有人的仓 + 项目墙,不做成员 / 权限体系——对内推广时够不够?

## 11 · 评审结果与处置(2026-08-19 内部专家评审,会后补)

专家的意见与会议结论已全部折进草案(第四轮),编号 待拍-24~28,一句话对应:

| 专家意见 | 处置 |
|---|---|
| 配置里的开工工具映射去掉 agent,只留 类别 → 开工工具 → workflow;workflow 的入口就是 SOP 类的 skill,它自己调度 agent(mattpocock-skills 是完整开发工作流,grillme 只是单个 skill);buddy 带通用件,各人可导入自己的 | 映射改三列;buddy 不再维护 agent 名单,战绩记在 workflow / 技能上;配置屏 = 映射 / workflow 表 / skill 表 / 连接器 + 定时(待拍-24;预研 `research/workflow-skill-packages.md`)|
| 计划的 Issue 卡片能不能拖,提高易用性;待办池和待办有什么区别 | 拖拽只用于排期(待办池 ⇄ 待办 = 排进 / 移出本周,列内排序),状态流转仍走按钮(▶开工要起 agent、✓完成是铁律里人显式点的那一下,拖错一下代价太大);待办池 = 未排进任何一周,待办 = 已排进本周,写在列头(待拍-25;预研 `research/kanban-drag-dioxus.md`)|
| 总览加项目元数据「群号」;群像 codehub / GitHub 一样分内外(内部 WeLink,外部待定),工厂模式;用途:通知直达群、定计划时收上周群消息 | 名片加「项目群」;群适配按工厂,接口两个函数(发消息 / 拉历史);通知同步(评审中 / 已合入 / 发版)+ 运作活①喂上周群摘要;WeLink 收发实现由同事负责(待拍-26;预研 `research/chat-group.md`)|
| 第 0-6 站流程要保持易用 | 新增 §3.5 每站几下的审视表:不加步骤、每站 ≤ 3 下、能自动的自动、待办带行内动作、「合入并完成」一键(待拍-28)|
| 老项目进来,能按它千奇百怪的记录回填成 buddy 规范下的信息,总览看到过去的运作 | 运作活③多一步「历史回填」:git 历史 / 仓内文档 / 远端 issue·MR / 群历史 → 发版记录历史段、按周历史运作、章程草稿、指标候选、issue 行(来源 = 回填,不算战绩、不点灯);总览多「历史运作(回填)」块(待拍-27;预研 `research/legacy-backfill.md`)|

会议整体结论:**易用性是为了推广,老项目捞回来是为了 MVP 一出组内所有项目就能纳入**;流程保持简单,后面看大家用的反馈再加。详细设计已开写:`../design/`。

**第五轮补记(2026-08-20,用户回二次握手清单后,上表中两处处置已被改掉,以草案为准)**:①拖拽改为**所有列都能拖**——排期直接生效,拖到状态列则弹窗二次确认(开工 / 推评审 / 完成 / 阻塞填原因),不合法的转移弹回,卡面不再摆按钮(待拍-25 改写);②历史回填**不喂群历史**(原料只有 git / 仓内文档 / 远端 issue·MR),并定性为运作活②「资产盘点」workflow 的首次模式(待拍-27);另:默认 workflow 定为 mattpocock-skills(待拍-10)、库在本机 + 周计划记指标读数(待拍-29)、试点 = buddy 自己的仓。用户回复原文与逐条处置见 `../design/00-handshake.md` 顶部。
