V4 MVP · 专家评审

Builders' Workbench(buddy)
V4 MVP

buddy 是 AI Coding 时代里「一个人的一张工作台」:让传统开发者按 Builder 的方式,把一个小项目(约三个月)从想法管到能验收的结果。V4 MVP = 把这句话做成每周都能真跑一圈的最小闭环,推给公司内更多人(codehub 项目为主,GitHub 同样能用)。

2026-08-19 内部专家评审 · 20 分钟
为什么要它

痛点:四件事逼着 buddy 出现

项目无限膨胀
人人都在 AI Coding,agent 产出越堆越多、没人管;每个项目、每个人一套做法。
资产看不见
散在聊天记录、本机目录、各人脑子里,换个 agent、换个人就看不见。
做完了但走偏了
很多项目 / 实验局只有 1-2 个人,没有五个角色十道流程把控,走偏了没人知道。
在系统间跳来跳去
codehub、终端、设计器、聊天工具、问题单之间跳;好用的组件 / agent / skill 靠各自摸索。
从愿景到落地

三个愿景,MVP 里落成什么

愿景MVP 落成
① 规范:所有项目都长一样;知识管理:知识都在项目代码仓,大模型皆可见 规范铺底模块:接入时往仓里放同一套文档与约束(章程、agent 工作约定、指标正本、周计划、发版记录、默认件),后续都写回仓
② 从开发者变成 Builder(1 Builder + Agent Loop),靠 buddy 把控交付质量 周循环:看总览 → 更新指标定计划 → agent 干活人守门 → 评审合入人点完成 → 发版 → 定时盘点 → 回总览
③ 一张工作台,内嵌 Open Design、Claude CLI、Cursor 等成熟组件,打通所有系统 会话屏:每张活按类别选开工工具,不出工作台;MVP 打通开工工具 + codehub / GitHub
用户旅程

第 0 站一次,之后每周一圈

0 接入项目 + 规范铺底(一次;建分支写规范 → 提 MR → 有权限的人合入)
1 周一看总览:项目信息 + 健康灯 + 指标(挂着推它的活)+ 本周进度 + 版本
2/3 运作活①:人点「开始本周」,agent 复盘上周、更新指标、与人交流出周目标与活草稿,人确认才建活
4 执行:六列看板 / 会话屏,agent 干、人守门;最远到「评审中」
5 验证闭环:评审 → 合入 → 人点完成 → 周末发版本
6 定时:运作活②自动建并自动开工,停在评审中等人看 → 下周一回到总览
谁在用

角色:一个主角,两种「被纳入」

主角
Builder
一个人把控一个小项目的交付质量;周循环里首尾都是他:触发运作活、确认周计划、评审、点完成。
不做专门界面
leader
把大家的仓纳入自己的工作台;项目墙 + 每个项目的总览,就是 leader 视图。
有合入权限
committer
同样纳入同一仓;在自己的「通知」里看到评审中的活,审完点合入,顺手点完成。
关键策略决策 · 1/2(共十二条)

十二条关键决策(1–6)

1
0→1 按旅程建,不是 10→5 缩减
旅程用不到的不带(工作流库、阶段轴、聊天面板、多面板),不列「不做清单」。
2
完成永远由人点,agent 最远到「评审中」
同一件活绝不记两次——产品铁律,状态机锁死。
3
健康只从真实数据推导,没数据就是灰,绝不假绿
手填的观测带「手填」徽记。
4
凡要留痕的事都是「活」(issue)
要往代码仓写东西的也是活(写仓一律走分支 + MR);铺底、改名片也不例外;只动本机库的纯人工动作不建活。
5
触发只有两种:人触发、定时触发
事件触发(远端新 issue / CI 红 → 自动建活)留到 MVP 后。
6
指标四层链
北极星 1 个 → 滞后 ≤3 → 引领 ≤3 → 周目标 + 活;总览按这条链画,指标不靠解释靠挂活。
关键策略决策 · 2/2(共十二条)

十二条关键决策(7–12)

7
规范是文档和约束,不是代码
正本在 buddy 仓 standard/(八大类,有版本有变更记录);改规范 = 改文件过评审,不改 buddy。
8
agent 会话里的规范手册渐进加载
五层:系统提示词 → AGENTS.md → 本活 skill → 规范件按需 → 项目知识,不一次性灌全部。
9
开工工具三个,按活的类别选
Open Design / Claude CLI / Cursor;两类接法(终端类 / 本机网页内嵌类),新工具只加一条声明 + 一个适配模块。
10
默认件业界优先、自建最少
superpowers、grillme + buddy 自建运作 skill / agent;资产来源只两种:buddy 内置 / 项目导入。
11
多人协作靠代码仓,不在 buddy 里建成员 / 权限 / 群聊
committer 纳入同一仓合入;跨人通知走内部聊天工具增量包。
12
建法:新壳 + 旧内核 + 模块管控,不推倒 V3 的视觉与好组件
一屏一模块、一个外部能力一个适配模块 + 文件行数守卫;减负线先合入再开 V4。
总览怎么画

指标四层链:不靠解释,靠挂活

总览就按这条链画:每个指标卡下面列「本周哪些活在推它」——活完成后,指标的下一次观测就是它的效果。早期定不出指标时允许为空,如实显灰。

例子 · 「建木」项目(假设值)
北极星:3 个月内 3 个真实团队跑通一条流水线
滞后:接入团队数(目标 3)· 一次跑通率(目标 80%)
引领:本周合入活数(目标 ≥5)· 原型评审通过数(目标 ≥1)
第 3 周周目标:「跑通 A 团队第一条流水线」→ 4 张业务活,其中「DSL 解析器」推动「一次跑通率」,「接入向导原型」推动「原型评审通过数」
机制

触发与介入:人在首尾,只有两种触发

凡要留痕的事只有一种承载——活(issue);只动本机库、不碰仓的纯人工动作(合入、点完成)不建活。人永远在首尾:首 = 触发或确认,尾 = 评审 / 合入 / 点完成。

事项触发承载人在哪介入
接入 + 规范铺底人(两卡)→ 自动建一次性运作活③活(轻量,不起 agent)首(填卡)· 尾(合入、完成)
运作活①更新指标 + 定计划人触发(总览「开始本周」)活(Claude CLI)首(触发)· 中(对话)· 尾(确认、评审、完成)
业务活开工人触发(会话屏 ▶开工)活(按类别选工具)中(对话、停)· 尾(评审、合入、完成)
运作活②资产盘点与微重构定时自动建 + 自动开工活(停在评审中)尾(评审、合入、完成)
评审 / 合入 / 点完成人纯 UI 动作全程
发版本人(计划屏)纯 UI(可选一次会话)首尾

特性清单

MVP 特性清单(按屏)

项目墙
V3 卡片(灯+一句话+目标+待办)· 环境测一下 · 指南抽屉
接入
两卡:项目地址 + 四字段(含北极星)· 铺底走 MR
总览
名片 + health + 北极星/滞后/引领(挂活)+ 仓统计 + 本周进度 + 版本
计划
周视角 + V3 六列看板一体;周头带预览未合入
会话
按 Orca:目录分组 · 终端/只读/diff/内嵌设计器 · 文件树+MR卡
通知
待处理(待合入/待完成/指标过期/名片待合入)+ 事件流
配置
开工工具映射 · skill 表 · agent 表 · 连接器+定时 · 导入
知识库
知识(文档树)/ 代码图(codegraph)/ 资产(skill·agent·产物·仓统计)
运作活三张
①更新指标+定计划(人触发)②盘点+微重构(定时)③规范铺底(接入一次)
数据增量
活多了周/版本/工具/来源/推动指标;信息分三层住(仓/本机文件/本机库)
收益

能带来什么(对比:AI Coding 时代有没有 buddy)

没有 buddy有 buddy(V4)证据
每个项目一套做法,agent 产物越堆越多,项目无限膨胀所有项目同一套规范运作;运作活②每周盘点与微重构多个仓同一套骨架;docs/plan/ 里的盘点记录
资产散在聊天、本机、脑子里所有资产在项目代码仓、有规范位置,任何大模型打开仓就看见仓文件本身
1-2 人的项目没人把控,做完了但走偏了周循环:指标从真实数据推导、周目标挂着活、完成永远人点、健康灯不假绿总览 + SQL 读回;.bw/metrics.toml 变更史
在 codehub、终端、设计器、聊天、问题单之间跳一张工作台里开工、评审、合入、发版会话屏 + 运行记录 + MR
好用的组件 / agent / skill 各自摸索严选默认件随规范铺进每个项目,用过就记账skill 使用记录、战绩

风险与验收

风险
  • 真实 claude 执行受网关抖动影响,只在监理脚本里跑,可重试,不作常绿验证
  • Windows PTY 后端未真机验证(macOS 已验)
  • 规范件「用没用上」要靠两周试点证据修订,没被用到的降为扩展件
MVP 做完的定义
  • 真实内部项目跑完两个完整周循环(两份周计划、两轮运作活①②、至少一次发版记录都在仓里)
  • 总览灯不是灰的,每条理由、每个数字能用 sqlite3 或仓文件核对
  • 至少一张活用 Open Design、一张用 Claude CLI 开工且产物进仓
  • 第二台 buddy 纳入同一仓:leader 看到同一张总览,committer 能合入
  • Windows 安装包 0.4.0-v4 在同事机器上装得上、跑得起

请专家拍的五个问题

1
「写仓一律走 MR 并挂活」在内部 codehub 权限模型下是否顺?铺底、改名片这类小改也走 MR,会不会太重?
2
运作活②定时自动开工、停在评审中——尺度是否合适?哪些改动应禁止它碰?
3
规范八大类核心/扩展划分与 AGENTS.md 固定章节,是否与各团队现有习惯冲突?成熟仓「合并调整」由 agent 提 MR 可接受吗?
4
开工工具首批三个(Open Design / Claude CLI / Cursor)与按类别默认映射,覆盖大家真实工作方式吗?缺哪一个?
5
leader 视图 = 纳入所有人的仓 + 项目墙,不做成员 / 权限体系——对内推广时够不够?
