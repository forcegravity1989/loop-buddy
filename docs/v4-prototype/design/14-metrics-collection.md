# 14 · 指标采集与读数

> **30 秒导读**:这是什么——指标的数字**到底怎么来**的完整设计:哪些指标不用存
> (每次现算)、哪些必须存进仓、脚本怎么写、读数落在哪个文件、手填的怎么提醒人。
> 给谁看——接着做 V4 的会话,以及要写采集脚本的人。现在还作数吗——**这是设计,
> 还没落地**;今天 V4 一条采集都没接,`.bw/metrics.toml` 里的采集方案没有任何程序
> 执行它。看不懂的词查 [`../../../CONTEXT.md`](../../../CONTEXT.md);代号查
> [`../../code-schemes.md`](../../code-schemes.md)。

## 0 · 这篇管什么、不管什么

**管**:一条指标的数字从哪来、什么时候来、存不存、存哪;`.bw/metrics.toml` 的新格式;
采集脚本的输入输出协议;读数文件格式;手填指标怎么走到人面前;这些和总览指标卡、
走势图、健康第二条判据的接口。

**不管**:指标**定义**得好不好(那是 `metrics-refresh` 那份剧本的方法论,不是代码的事);
健康三条判据本身([08 篇](08-overview-derivation.md) §2.4);周计划文件的其余段落
([06 篇](06-plan-screen.md));代码仓级那块的统计(它不走 `.bw/metrics.toml`,是独立
一块,见 08 篇⑤)。

**与 08 篇的关系**:08 篇写的是「总览这一块显示什么」,它假定读数已经存在。本篇补的
就是它假定的那一半——读数怎么产生。08 篇 §2.3 ② 说的「按 `collect.kind` 分两路」被
本篇 §2.1 取代:分类判据不是采集方式,是**可回溯性**。

## 1 · 为什么要重写这一块

**今天的实况**:`.bw/metrics.toml` 里每条指标都带一个采集方案,格式上支持五种采集方式
(`github` / `connector` / `bw` / `script` / `manual`)。而在 V4 里,这个字段**唯一的用处
是判断要不要在卡片上显示「手填」两个字**——没有任何一处真的去执行采集。指标读数的唯一
来源是运作活①里 agent 手抄进周计划文件的那几行。

**V3 的实况也好不到哪去**(2026-08-21 读回核实):五种采集方式里只有 `script` 一条是活的,
其余四种早在 2026-08-07 就被统一改成「只计数、不采集」。而 buddy 自己那份
`.bw/metrics.toml` 五条指标全写的 `bw`——**这种采集方式从来没有实现过**,那句看着像查询
语法的 `"issue.settled_at within 30d ∧ exists workflow_run(...)"` 没有任何程序读它,是写给
人看的口径说明。所以这五条指标从写下那天起没被真实采集过一次。

**V3 那条活路径踩过的三个坑,本篇逐条避开**:

| V3 怎么做的 | 后果 | 本篇怎么改 |
|---|---|---|
| 起脚本时**不传任何参数**,脚本自己决定吐多少历史 | buddy 自带脚本里历史窗口写死 30 天,而面板按 8 周(56 天)画 → 前三四周永远是空的,或靠「补前值」连成一条骗人的直线 | **buddy 传窗口给脚本**(§2.3)。面板要几周就采几周,不存在错配 |
| buddy 每次采集前**无条件覆盖**自己铺的采集脚本 | 项目改了窗口或采法会被静默抹掉 | 铺一次,之后归项目;升级走对账提示,不覆盖(§2.4) |
| 采集结果**不看 stdout,只读脚本写出的文件** | 真实事故:agent 写的脚本只 `print` 到屏幕、`output` 字段留空 → 每次采集都报「成功」,而指标永远没数 | **只认 stdout 的 JSON**,不是 JSON 就算失败(§2.4) |

## 2 · 设计

### 2.1 核心判据:这条指标的历史,现在还能不能重新算出来

**整个设计只有这一条分水岭。** 不是按「用什么工具采」分类(那是 V3 的分法,分出五种里三种
从没实现),而是问一句:

> 今天能采到这个数,那么「上周三那天的值」现在还能算出来吗?

按这一问分三类,处理方式完全不同:

| 类 | 判据 | 存不存 | 例子 |
|---|---|---|---|
| **A · 可回溯** | 能采今天,就能采过去任意一天/周 | **一个字都不存**。要看四周就现算四个窗口,要看八周就算八个 | git 提交数、合入数、PR 数、远端 issue 数、某天的代码行数 |
| **B · 不可回溯** | 过了那一刻就没了,历史再也采不到 | **必须落进仓库**。定时到点采一次,追加一行 | 外部系统只给「当前在线数」;看板只显示今天的转化率 |
| **C · 手填** | 压根没有采集路径 | 同 B,落进同一份文件,带手填标注 | 需要人去某个后台看一眼才有的数 |

**这一条判据一立,三件事同时被解决**:

1. **要存的东西降到最少**。A 类不落地,所以它天然难造假——数字是每次重算出来的,没有一个
   可以被改的中间值。这比「存下来然后保证没人改」强一个量级,也和「健康永远推导」是同一
   套思路。
2. **走势图不需要历史数据管道**。A 类现算就能出完整序列,新接入的项目**第一天就有四周走势**,
   不用先攒几周。
3. **B 和 C 合流**。它们的区别只是「谁去采」(脚本 / 人),落点、格式、进仓方式完全一样,
   代码里不必分两条路。

**判据谁来定**:写在 `.bw/metrics.toml` 里(§2.6 的 `window` 字段),由定指标那次对话
(`metrics-refresh` 剧本)和人一起判断。判错的代价是可预期的:把 A 类误标成 B,结果是白存
一堆本可以现算的数;把 B 误标成 A,结果是走势图上除了当前点之外全是空——**空,不是假数**。

### 2.2 采集方式只有两种

V3 那五种收成两种,理由是 V3 自己的规范文档已经承认过的:「`github`/`codehub`/`bw`/
`connector` 只是不同的脚本实例,不是并列的种类」。

- **`script`** —— buddy 起一个子进程,跑仓里的一个可执行文件,读它 stdout 的 JSON。
  连 GitHub、连 codehub、连内网系统、读一个本地文件、算 git 历史,**全是脚本自己的事**;
  buddy 不认识这些系统,只认识「起进程、传窗口、读 JSON」。
- **`manual`** —— 没有采集路径,到点提醒人去填(§2.8)。

**没有第三种。** 尤其**不要**把「buddy 内建的 git 算子」做成第三种——那等于把算法藏进
二进制,项目看不见、改不了、也说不清这个数怎么来的。git 类的统计一样走脚本,只不过
**脚本由 buddy 铺一份现成的**(§2.4),它就摆在仓里,人能读能改,而且脚本本身就是
「这个数怎么来的」的文档。

### 2.3 窗口由 buddy 给,不是脚本自己决定

这是和 V3 最关键的一处分歧,也是「能采一天就能采历史每一天」这句话的工程落点。

**buddy 起脚本时把要算的时间范围作为参数传进去**:

```bash
# A 类(window = true):buddy 说要哪一段,脚本照着算
.bw/scripts/merged-mr.sh --since 2026-06-29 --until 2026-08-23 --grain week

# B 类(window = false):没有历史可言,不传窗口,只问「现在是多少」
.bw/scripts/online-now.sh
```

面板要四周就传四周,要八周就传八周,**采多少和画多少永远一致**。V3 把这个决定权留在
脚本里(硬编码 30 天),于是面板和数据长期对不上还没人发现。

### 2.4 脚本协议

**输入**:两种形态,由 `window` 字段决定(见上)。除窗口外不传别的——脚本要知道自己算
哪条指标,靠它是哪个文件,不靠参数。工作目录 = 仓根。

**输出**:**只认 stdout 的一个 JSON 对象**,不是 JSON 就算这次采集失败。

```jsonc
// A 类:一个序列。at 是 ISO 周(grain=week)或日期(grain=day)
{"series": [{"at": "2026-W31", "v": 3}, {"at": "2026-W32", "v": 5}, {"at": "2026-W33", "v": 4}]}

// B 类:一个当下的值
{"value": 128}
```

`v` / `value` 可以是数,也可以是给人看的字符串(`"3.2%"`、`"5/7"`、`"842ms"`)——
**原样保留,不在采集这一层解析**。要画走势时才解析,解析不出来的点跳过、不画,不猜。

**失败一律如实**:非零退出、超时、stdout 不是 JSON、缺字段——都记这条指标这次「没采到」,
**绝不写一个 0 进去**。0 是一个真实的数值,「没采到」不是。失败原因原样端到界面上。

**buddy 铺的脚本,铺一次就归项目**。规范铺底时往 `.bw/scripts/` 放几份现成的(git 提交数、
合入数、PR 数、远端 issue 数这些通用的),之后**再也不覆盖**——项目改了窗口、改了算法、
换了远端,都是它自己的事。规范升级时按指纹比对,变了就只提示差异、不动它(和
[03 篇](03-standard-and-backfill.md) 的铺底规矩同一套)。

### 2.5 读数落在哪:和周计划彻底解耦

**A 类不落地**,没有落点这回事。

**B 和 C 落进一份只追加的读数文件**——`.bw/metrics/readings.jsonl`,一行一个观测点:

```jsonl
{"metric":"周活跃用户","at":"2026-W33","v":1240,"by":"script:.bw/scripts/wau.sh","ts":"2026-08-17T09:00:00+08:00"}
{"metric":"试用转化率","at":"2026-W33","v":"3.2%","by":"manual","ts":"2026-08-18T14:20:00+08:00"}
```

**这一份为什么不用 markdown 表格、也不用 toml**:它和另外两份文件的读者不一样。
指标**定义**是人要反复读写、还要写口径注释的,所以是 toml(§2.6);给人看的**快照**在
周计划文件里,所以是 markdown。而读数是**机器一行一行往上追加**的流水:jsonl 追加天然
(不用解析整份文件再重写)、数值里带竖线或换行也不会把格式撑散(markdown 表格会当场
散架)、每一行自解释。人不直接读它,人读的是快照。

**只追加,永不修改已有行**。同一个指标同一个时点采到了不同的值,追加新行,读的时候取
最后一条——历史上那次采到什么,永远查得到。这条和「观测只追加」那条产品铁律是同一件事,
只不过 V4 的落点从库表换成了仓文件。

**为什么必须离开周计划文件**:今天读数住在 `.bw/plan/YYYY-Www.md` 的「本周指标读数」段里,
这有三个问题——①周计划是人和 agent 反复编辑的正本,定时采集的机器往里插行会打架;
②要看八周趋势得回扫八个文件;③把「这周干什么」和「指标是多少」焊在一起,而这两件事的
更新节奏根本不同。**指标记录不该和计划耦合。**

**周计划文件那一段保留,但改性质**:它从「读数的正本」降级成「这一周的快照」,由运作活①
在收尾时从读数文件 + 现算结果生成一份抄进去,并注明是快照。保留的理由是一个真实需求:
让别人 clone 下这个仓就能看到数,不用装 buddy、不用跑脚本。

### 2.6 `.bw/metrics.toml` 的新格式

```toml
schema_version = 2

[north_star]
name = "每月被真实交付的活数"
def  = "..."

  [north_star.collect]
  kind   = "script"                    # script | manual —— 只有两种
  run    = ".bw/scripts/delivered.sh"  # 相对仓根
  window = true                        # 能接 --since/--until → A 类,不落地
  grain  = "week"                      # week | day

[[leading]]
name   = "试用转化率"
def    = "..."
target = "≥3%"

  [leading.collect]
  kind  = "manual"
  grain = "week"
  ask   = "去增长后台看本周的试用转化率"   # 提醒人的时候说这句
```

较今天的三处变化:

1. **`kind` 从五值收成两值**。`github`/`connector`/`bw` 三个直接退场,不留兼容——它们从来
   没有实现过,留着只会让人以为写上就能采(仓里「不为向后兼容留旧路径」)。
2. **新增 `window`**,这是 §2.1 那条判据在文件里的表达,也是整个格式里最重要的一个字段。
3. **`query` 换成 `run` + 可选 `field`**。V3 的 `query` 是「从一堆连接器输出的大 JSON 里按
   点分路径取一个字段」,那是「一个脚本产多条指标」的产物;改成一条指标一个脚本之后,
   路径就不需要了。

**`schema_version` 从 1 跳到 2,不写迁移**。试点期只有一个真实项目,重新定一次指标比写
迁移便宜;而且那五条老指标本来就要重定(它们的采集方式从没实现过)。老格式的文件读到
`schema_version = 1` 就报「这份指标文件是旧格式,运作活①会带你重定一遍」,**不猜、不半读**。

### 2.7 手填这一类怎么走到人面前

C 类(以及采集连着失败的 B 类)不能只是灰在那儿——**得有人被叫住**:

1. 定时到点,发现某条手填指标这个粒度周期内还没有读数;
2. buddy **建一张活**(和资产盘点同一条路:自动建、不自动完成),标题写清是哪条指标、
   正文放 `ask` 那句话;
3. 人可以直接在活里填掉,也可以点开工让 agent 帮着去查——**查到了同样追加进读数文件**,
   来源标成脚本还是手填,取决于它真的是怎么拿到的。

**目标是让 C 类越来越少。** `metrics-refresh` 那份剧本里要写死一条:每次跑到手填指标,
都要认真问一次「这个数能不能写成脚本」——agent 的价值是**帮人把 C 类升级成 A 类**,
而不是每周替人抄一次数。

### 2.8 什么时候采

| 时机 | 采什么 |
|---|---|
| 打开总览 | A 类现算一次,结果放本机缓存(纯缓存,丢了重算即可) |
| 定时到点 | B 类采一次;C 类检查该不该建提醒活 |
| 人点「↻ 立即采集」 | 全部重采,缓存作废 |
| 运作活①开工时 | 不额外采——agent 读到的和总览显示的是同一份数据 |

**缓存不做自动作废判据**(2026-08-21 拍板)。原本考虑过「仓的 HEAD 变了就作废」这类
机制,取消了:界面上本来就有「↻ 立即采集」,人知道自己刚合了东西,点一下就是了。
为了省这一下点击去猜「什么时候该重算」,换来的是一套没人说得清什么时候生效的规则。
缓存只管「同一屏反复重绘时别每次都起十几个子进程」这一件事。

## 3 · 工程对照

### 3.1 解析器是 V4 自己的第 8 个,不借 V3

今天 V4 读 `.bw/metrics.toml` 用的是 `bw_engine::metrics_file`——**V3 的解析器**,带着那五种
采集方式。而 V4 自己的 `crates/bw-v4/src/repo/` 下已经有 7 个仓文件解析器(项目名片、周计划、
发版记录、活的约定、规范清单、指纹清单……),**唯独指标是借的**。这个不一致本身就说明
V4 当初做到指标这里就停了。

新解析器落在 `crates/bw-v4/src/repo/metrics_file.rs`,和另外 7 个并列。**不动 `bw-engine` 里
那一份**——V3 还在用它,而 V4 的新格式和它已经不是一回事了。

### 3.2 模块位置

| 干什么 | 落在哪 |
|---|---|
| 解析 `.bw/metrics.toml`(新格式) | `crates/bw-v4/src/repo/metrics_file.rs`(新) |
| 解析/追加 `.bw/metrics/readings.jsonl` | `crates/bw-v4/src/repo/readings_file.rs`(新) |
| 起脚本、传窗口、读 stdout JSON | `crates/bw-v4/src/app/collect.rs`(新) |
| A 类现算 + 缓存 | 同上 |
| 定时检查 B/C(建提醒活) | `crates/bw-v4/src/app/ops.rs`(已有定时那一处扩写) |
| 指标卡与走势图的 ViewModel | `crates/app-shell/src/bridge/vm_panels.rs`(已有 `build_metrics` 改写) |
| 走势图几何 | 搬 `crates/ui` 的纯函数(见 §3.4) |

### 3.3 这些 V3 概念不带进来

- **`metric` 表 / `observation` 表**:V4 没有库表装指标,定义在 `.bw/metrics.toml`、读数在
  `.bw/metrics/readings.jsonl`,都是仓文件。
- **`connector` 表与 `.bw/connectors.toml`**:V4 不需要「连接器」这个中间概念——一条指标
  直接指向一个脚本。**顺带要处理一个孤儿**:V4 配置屏今天还在读 `.bw/connectors.toml` 并
  显示「配了哪些连接器」,而 V4 根本没有采集在消费它,显示了一个没人用的东西,这块要删。
- **九种 `SourceKind`**:收成两个词——脚本 / 手填。读数文件的「来源」列直接写人话。
- **V3 那条「脚本自己吐 history 数组、buddy 做差集补写」的机制**:被 §2.3 取代。

### 3.4 走势图直接搬 V3 的几何函数

`crates/ui` 里那两个纯函数(小型走势线、带坐标轴的周走势图)是干净的:不依赖 Dioxus、
wasm 可编译、只依赖内核 crate。搬过来即可,它们的取舍照抄:x 轴按点均分、标签反推每周
周日日期;y 轴走 min-max 不从 0 起(小波动不被压平);全平的序列人为撑出量程不贴边;
**空数据整块不画,显示「尚无观测」**。

**但它上游那个 `weekly_spark` 不要搬**——它做的是「按周分桶 + 空周补前值」,补前值会把
「这周没采到」画成一条和上周一样高的直线,读的人分不出「没变」和「没数」。A 类现算不
存在空桶(要几周算几周),B/C 类真的缺一周就该**断开**,不补。

## 4 · 边界与失败

**不做**:

- 不做指标的「目标达成度」自动打分——`target` 那个迷你门槛(`≥5` `≤24h`)只用来判红黄
  绿(这一条今天恒为不成立,见 `LEFTOVERS.md` V4A-5),不做加权评分。
- 不做跨项目的指标对比或排行。
- 不替项目写业务采集脚本——buddy 只铺通用的那几份(git/远端统计),业务指标的脚本是
  项目自己的,`metrics-refresh` 那次对话会引导人写。
- 不做采集失败的自动重试。失败就是失败,下一个周期再采;连着失败要在卡片上看得见。

**失败如实**:

| 场景 | 显示 |
|---|---|
| `.bw/metrics.toml` 解析失败 | 三块指标整体灰 + 解析错误原文,不用旧值顶上 |
| 读到 `schema_version = 1`(旧格式) | 「这份指标文件是旧格式,运作活①会带你重定一遍」,不半读、不猜字段 |
| 脚本非零退出 / 超时 / stdout 不是 JSON | 这条指标这次没采到,卡片显示上一次的值 + 「最近一次采集失败:{原话}」;**不写 0** |
| 脚本返回的序列缺某几周 | 那几周在走势图上**断开**,不补前值 |
| `window = true` 但脚本不认 `--since` | 和采集失败同等对待,并提示「这个脚本可能不支持时间窗口,检查 `window` 标对了没有」 |
| 读数文件解析失败 | B/C 类读数整体不显示 + 报错原文;A 类不受影响(它不读这个文件) |

## 5 · 验收与读回

```bash
# A 类:界面上的走势数,必须能用同一个窗口自己复算
.bw/scripts/merged-mr.sh --since 2026-06-29 --until 2026-08-23 --grain week
git -C <ws> log --merges --since=2026-08-17 --until=2026-08-24 --oneline | wc -l

# B/C 类:读数文件是唯一落点,只追加
cat <ws>/.bw/metrics/readings.jsonl
git -C <ws> log -p --follow .bw/metrics/readings.jsonl   # 历史行有没有被改过,一看便知

# 库里不该有任何指标数据
sqlite3 <db> ".tables"     # 仍然只有 project / issue / claude_conversation / app_meta
```

**验收场景**:①新接入项目铺完脚本,总览第一天就有四周走势(证明 A 类不需要攒历史);
②杀进程重开,A 类的数一模一样(纯现算);③手填指标到点建出提醒活,活是「待办」不是
「完成」;④故意把脚本改成非零退出,卡片显示上次的值 + 失败原话,**不是 0**;⑤读数文件
里手改一行再打开界面,`git log -p` 能查出这次修改(只追加是靠可审计保证的,不是靠锁)。

## 6 · 开放问题

1. ~~**A 类现算的缓存什么时候作废**~~ —— **已定(2026-08-21)**:不做自动作废判据,靠
   「↻ 立即采集」这颗按钮。缓存只为了同一屏重绘时不反复起子进程,见 §2.8 末段。
2. **定时器对哪些项目跑**。前提已经澄清一半:buddy 是常驻开着的,所以「进程没开会错过
   一拍」这件事不用设计补偿。剩下的问题是**界面上没选中的那些项目**要不要也采
   (`LEFTOVERS.md` V4B-7 今天的行为是不采)。倾向**分开对待**:采集本身不打扰人,对所有
   项目跑;而**建提醒活会出现在人面前**,只对打开着的项目建 —— 这样数据保持新鲜,又不会
   一打开某个项目就撞见一堆自己没点过的活。待拍。
3. **`grain` 只有天和周够不够**。月度指标(月活、月收入)现在只能标 week 然后每四周有一个
   点,读起来别扭。加 `month` 不难,但会让走势图的 x 轴逻辑多一个分支。
4. **一条指标多个脚本 / 一个脚本多条指标**。本篇定的是一对一(简单、失败边界清楚),
   代价是同一个数据源要拉两次(比如 PR 数和 issue 数都要连一次远端)。真跑起来慢的话,
   要不要允许一个脚本一次返回多条指标——那会把 V3 的「字段路径」重新引回来,先不做。
5. **读数文件按什么分片**。现在是一份 `readings.jsonl` 一直追加。跑几年会很长,要不要按年
   分片(`readings-2026.jsonl`)?等它真的长到难读再说,别提前设计。
