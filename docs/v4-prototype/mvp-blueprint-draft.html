§1

V4 MVP 是什么(一句话)与三个愿景怎么落地

对这节有意见
仅存在你自己的浏览器里,不会自动发送给任何人

一句话:buddy 是 AI Coding 里一个人的一张工作台,让传统开发者按 Builder 的方式,把一个小项目(约三个月)从想法管到能验收的结果。V4 = 把这句话做成每周都能真跑一圈的最小闭环,推给公司内更多人(codehub 项目为主,GitHub 同样能用)。

收益怎么说(第三轮用户补充,§9 的对比按此写)

现在用不用 buddy 都已经是 AI Coding 时代,不存在「人写代码 vs agent 写代码」的对比;buddy 带来的是四件别的事:

  • ①所有项目按同一套规范运作,不会无限膨胀下去;
  • ②所有资产都在项目代码仓,有规范、大模型可见;
  • ③传统项目靠很多人很多角色把控,AI Coding 下很多项目 / 实验局只有 1-2 个人——buddy 让项目不只是在 AI Coding 下开发完,还不走偏(这就是 Builder);
  • ④一张工作台打通所有系统,理论上活都是 agent 干,人不用在很多工作台之间跳来跳去——不只是各开发阶段的工具和 codehub,后面还包括内部聊天系统、问题单系统;好用的组件、好用的 agent / skill 集成进来。
愿景(口述原文)MVP 里落成什么用户能感到的收益
①规范:所有项目都长一样;知识管理:项目所有知识都在项目代码仓,大模型皆可见 规范铺底模块(见 §4):接入项目时往仓里放同一套文档与约束(章程、agent 工作约定、指标正本、周计划、发版记录、默认件),后续都写回仓;规范本身是独立、可被人深度评审、持续优化的一个模块 换项目不用换脑子;agent 打开仓就懂这项目;leader / committer 纳入别人的仓就能看同一张总览、审同一批活
②从开发变成小项目的 Builder(1 Builder + Agent Loop),基于 buddy 把控交付质量 周循环剧本(§2、§3):看总览 → 更新指标与定计划 → agent 干活人守门 → 验证发版 → 回到总览 每周有可验证增量,不靠会议和口头汇报;完成永远人点
③一张工作台,内嵌 Open Design、Claude CLI、Cursor 等成熟组件,打通所有系统 会话屏(第 4 站):每张活按类别选「开工工具」,原型类走 Open Design、构建类走 Claude CLI 或 Cursor,不出工作台;开工工具按「终端类 / 本机网页内嵌类」两种接法声明,新工具加一条声明一个模块;右侧代码结构侧栏(借 Orca)。MVP 打通的系统 = 开工工具 + codehub / GitHub;内部聊天、问题单系统是同一条「适配模块」路上的下一批(MVP 后,见 §7) 少切窗;工具由 buddy 缝合,不自造;以后缝新系统(聊天、问题单、DSH 一类)不用改架构

继承不再讨论的(V1-V3 已用真实数据证明、且 V4 旅程每站都用到):四条铁律——完成永远人点且同一件活绝不记两次;健康只从真实数据推导、没数据就是灰;交棒 / 观测这类记录只追加;做完的活可蒸馏成技能、胜率由真战绩算。以及内核 crate:状态机、信号密封、只追加表、交互式执行器、连接器、指标正本管道。

反命题(按第一轮反馈精确化)

buddy 里不建成员、权限、群聊、收件箱;不是通用看板、不是审批系统、不是云服务。但多人协作是允许的,靠代码仓发生:V3 实践里已经遇到 builder 没有合代码权限的情况——解法不是在 buddy 里加成员系统,而是 committer 把同一个仓纳入自己的 buddy(V2 已支持同一仓多台 buddy),在自己的总览「待人处理」里看到评审中的活(代码 MR、文档、原型都算),审完点「合入」。跨人的通知靠内部聊天工具,留给内部增量包,不进 MVP 主线(详见第 5 站,待拍-13 已定)。

§2.5

指标、周目标、活:一张关系图

对这节有意见
仅存在你自己的浏览器里

第一轮里「总览不直观」「指标定不出来」「运作活算不算计划」都卡在同一件事:指标、周目标、活三者的关系没说清。这一节说清,并给一个例子。

北极星(1 个)不允许为空
「三个月长成什么样」的可度量说法,来自第 0 站意图卡。谁定 / 何时:人,接入时;可改。
↑ 逼近
滞后指标(≤3)允许为空(早期没有,灰)
结果量,月/周更新(用户数、成功率、收入…)。谁定 / 何时:人 + agent,在运作活①里逐周补。
↑ 带动
引领指标(≤3)允许为空(早期没有,灰)
本周可控的先行量,直接由活推动(本周合入活数、原型评审通过数、发版次数、覆盖率…)。谁定 / 何时:人 + agent,在运作活①里逐周补。
↑ 推动
周目标(1 句)+ 业务活(N 张)周目标不允许为空活可为 0
周目标 = 这周要把哪几个指标往哪推;每张业务活可标「预期推动的指标」(0..n)。谁定 / 何时:人在运作活①里与 agent 一起定,人确认才建。

关系:活推动引领指标 → 引领指标带动滞后指标 → 滞后指标逼近北极星。总览就按这条链画:每个指标卡下面列「本周哪些活在推它」,活完成后指标的下一次观测就是它的效果。这就是让引领/滞后指标「直观」的办法——不靠解释,靠把活挂上去。

早期定不出指标怎么办:允许。接入只要北极星;运作活①每周都会尝试「补一个引领、补一个滞后」;规范里写进 DoD——「原型阶段交棒前,至少 1 个引领 + 1 个滞后有真实观测」。在此之前总览指标区就是灰,如实。

例子(新建项目「建木」,假设值,只为说明关系)
  • 北极星:三个月内 3 个真实团队用建木跑通一条流水线。
  • 滞后:接入团队数(目标 3)、流水线一次跑通率(目标 80%)。
  • 引领:本周合入的活数(目标 ≥5)、原型评审通过数(目标 ≥1)。
  • 第 3 周周目标:「把 A 团队的第一条流水线跑通」→ 业务活 4 张,其中「流水线 DSL 解析器」标「推动:一次跑通率」,「A 团队接入向导原型」标「推动:原型评审通过数」。
  • 运作活①②不占周目标、不标指标,在计划屏单独一栏「本周运作」。

活的边界(第一轮 14 问的,第三轮收紧):活 = 任何要留痕的事项:需要一次 agent 会话的,或要往代码仓写东西的——代码、文档、原型、指标、盘点、铺底、改名片都算,不限于提代码;只动本机库的纯人工动作(点合入、点完成、切在研版本)不是活。会话工具三选一:Claude CLI / Cursor / Open Design。业务活进周计划、可标指标;运作活是 buddy 的标准活,MVP 里两张周期性 + 一张一次性:①「更新指标 + 制定本周计划」(周一,人触发,含上周复盘)②「资产盘点与代码微重构」(定时,自动建并自动开工,停在评审中)③「规范铺底」(接入时自动建一次,buddy 写规范件走 MR;成熟仓多一步 agent 合并调整,见第 0 站)。

(以下三条规矩第三轮按用户四问收紧。)

规矩①· 承载只有一种凡是要留痕的事,承载都只有一种——活(issue):需要一次 agent 会话的是活;要往代码仓里写东西的也是活(写仓一律走分支 + MR,MR 必挂在一张活上,这样才能出现在「待人处理」、才能让 committer 合入)——所以铺底、编辑项目名片这类「buddy 替人写仓」的动作也建活(轻量,无 agent 会话);只动本机库、不碰仓的纯人工动作(合入、点完成、切在研版本)不建活;唯一例外:新建的空仓,首提交直推(没有可以开 MR 的默认分支)。
规矩②· 触发只有两种MVP 只有人触发、定时触发两种;「事件触发」(远端新 issue → 自动建活、CI 红 → 自动建活)是 MVP 之后。
规矩③· 人永远在首尾自动触发的活最远只到「评审中」,人永远在首尾——首 = 触发或确认,尾 = 评审、合入、点完成。

用户四问的答案

(1)站 0 铺底也走 issue + MR接入的人未必有合入权限,所以铺底 = 一次性运作活③「规范铺底」:buddy 建分支写规范件 → 提 MR → 有权限的人(自己或 committer)在工作台合入;成熟仓已有手写 README / CLAUDE.md / AGENTS.md 时,这张活多一步 agent「合并调整」再提 MR。
(2)运作活①不绑周一判据是「当前周没有 docs/plan/ 文件」:铺底合入后总览立刻提示「本周还没有计划 → 开始本周」;任何时候进总览看到本周无计划都能点。触发入口在总览,逻辑在活里:点「开始本周」= buddy 建这张运作活①并跳到会话屏 ▶开工,和其它活一样;计划屏 / 会话屏里也能直接建它、开工它,总览的按钮只是最顺手的入口。
(3)运作活②也是一张活定时到点 buddy 自动建 issue(来源 = 自动建)并自动 ▶开工(走同一个交互式执行器),它出现在会话屏活列表和总览「本周运作」栏,人随时能点进去看终端。
(4)编辑项目信息也建活走 MR名片「编辑 → 保存」= buddy 建轻量活 + 分支提交 PROJECT.md / .bw/project.toml + MR → 待人处理 → 合入 → 完成;有合入权限的人两下点完。

§4

规范铺底模块

对这节有意见
仅存在你自己的浏览器里

母文档 §4 只留结论,完整设计单独成篇 standard-module-draft.md,以下把八大类展开为手风琴。

一句话:规范 = 仓内独立目录 standard/,有版本、有 CHANGELOG、每类一份模板 + 一份说明;铺底 = 按 manifest 把核心件写进项目仓并提交;升级 = 算差异、人确认;校验 = buddy 对账缺什么、过期什么并在项目空间提示。规范本身独立(不散落在代码里)、能被人深度评审并持续优化——规范是文档和约束,不是代码,改规范只需改文件、过评审,不需要改 buddy。

原则① 正本只有一份住在仓里,人可读;每个规范件是 Markdown 或 TOML 文件;buddy 只负责「铺进项目、对账、提示升级」,不在代码里藏第二份内容。
原则② 严选、可拔插核心件(每个项目必有,否则旅程走不通)与扩展件(铺底时勾选,任何时候可加可拆);默认件业界优先(superpowers、grillme),自建最少,其余进鱼塘。
原则③ 进仓、可见、可审所有铺进项目的文件都提交 git(带 .bw-managed 标记与版本),agent 打开仓即读到,leader / committer 纳入仓即看到;人手改过的文件 buddy 不覆盖,只提示差异。

stablyai/orca(~47k star)

Electron+React+node-pty+xterm6,MIT。结论:借模式,不整体嵌。
  • 不是可单独复用的库;新快照已没有独立 daemon,本地 PTY 直接托管在 Electron 主进程里
  • 约 30 个 agent 靠一张 promptInjectionMode(六分类)注册表接入,不是靠 SDK/stream-json
  • agent 状态判定优先用 CLI 原生 hook/statusLine 上报本机 HTTP,不猜终端输出
  • 右侧栏 = 文件树 + Git 状态/diff/checks,没有符号级大纲
  • 隔离单位 = 一个 git worktree;并行 fan-out 就是重复调用创建命令,无专门原语
  • 恢复命令表(claude --resume id 这类,一 agent 一行)与 BW 现有设计方向一致
  • 与 BW 产品命题零重叠(无周计划/健康信号/技能蒸馏概念)
  • 体量 ~300MB+ 的独立 Electron 应用,和 BW「单一原生二进制」立场冲突

借:xterm 6 选中即复制的完整实现;原生 hook 优先于终端猜测的状态判定思路;右侧栏范围参照(文件树+diff 就是业界这一档的常见落地);每活一 worktree(已有,保持)

不借:Orca 整体(独立 Electron 桌面应用);其 daemon 复用路径(已不存在);CLI↔本地 socket 协议(非公开契约)

deepseek-ai/deepseek-harness(dsh)

TS/Node Cordis 插件框架,MIT,developer preview。结论:只借接口设计判断。
  • 发布形态 = npx @deepseek-ai/dsh web 起本机 Web UI(127.0.0.1:3080),不是桌面 App,Electron 壳只是预留架构位
  • 自建 agent loop,不是套壳 claude/codex CLI;支持多家模型(Anthropic/OpenAI/Bedrock…),非 DeepSeek 专属
  • UI 插件是同源 JS 模块联邦,和宿主共享 window,没有 iframe 隔离
  • 插件发现靠 GitHub 话题标签,无官方审核市场;安装期代码执行不受 agent 工具沙箱保护
