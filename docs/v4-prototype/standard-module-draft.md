# 规范铺底模块:八个大类、每类怎么做、正本住哪、怎么演进

> **30 秒导读**:这篇管 V4 的**规范**——buddy 接入一个项目时,往它仓里铺的那一套文件到底有哪些、每一份为什么存在、谁写谁更新、怎么升级。落地成愿景①「所有项目都长一样、项目所有知识都在项目代码仓、大模型皆可见」。**给谁看**:要往规范里加东西的人、要理解铺底铺了什么的人、接着做 V4 的会话。**现在还作数吗**:作数,并且已经铺进代码——`crates/bw-v4/src/standard/` 是写核心件那一半的实现,铺底流程怎么跑见 [design/03-standard-and-backfill.md](design/03-standard-and-backfill.md);**八个大类没有全部建齐**,今天仓根 `standard/` 里真有哪些目录,以 03 篇 §2.7 的清单为准。八个大类**故意用数字不用字母**编号(A–H 会和 [`../code-schemes.md`](../code-schemes.md) 登记过的 A/B/G 系列撞车),正文写「第 N 类」。

**一句话**:规范 = 仓内一个独立目录 `standard/`,八个大类,每类 = 一份说明(为什么、给谁、怎么用)+ 一到多份模板;有版本、有变更记录;buddy 接入项目时按清单把核心件写进项目仓——**建分支、提 MR、人合入**(接入的人未必有直接合入权限;新建空仓例外,首提交直推),之后每周对账、有新版就提示升级。**规范是文档和约束,不是代码**——改规范只需改文件、过评审,不需要改 buddy。

## §0 · 今天已经有的(不是从零)

接入时 buddy 已往项目仓提交:`PROJECT.md`(章程)、`.bw/project.toml`(意图正本)、`.bw/metrics.toml`(指标正本)、`.bw/connectors.toml`(采集配置)、`.bw/collect_stats.*`(采集脚本)。另有两样放进项目目录但**故意不入 git**:`.claude/buddy/standards/*.md`(只有「指标」「连接器」两篇)、`.claude/skills/`(物化技能)。五阶段方法论 8 份 SKILL.md 编译在 buddy 二进制里。**没有** AGENTS.md / CLAUDE.md,没有周计划、发版记录、决策记录的位置约定,没有规范版本号,没有对账。

V4 的改动:把散落的这些收进一个目录、补齐缺的类、**全部进仓**、加版本与对账。

## §1 · 三个原则

1. **正本只有一份,住在仓里,人可读**:每个规范件是 Markdown 或 TOML 文件;buddy 只负责「铺进项目、对账、提示升级」,不在代码里藏第二份内容。
2. **严选、可拔插**:分**核心件**(每个项目必有,否则旅程走不通)和**扩展件**(铺底时勾选,任何时候可加可拆);默认件业界优先(mattpocock-skills 为构建类默认、superpowers 可换、grillme 单技能),自建最少,其余进鱼塘。
3. **进仓、可见、可审**:所有铺进项目的文件都提交 git(带 `.bw-managed` 标记与版本),agent 打开仓即读到,leader / committer 纳入仓即看到;人手改过的文件 buddy 不覆盖,只提示差异。

## §2 · 八个大类(每类:目的 / 落什么文件 / 谁写·何时更新 / 核心或扩展 / buddy 怎么对账)

### 1 · 项目身份与章程

- **目的**:任何人(含 leader、agent)打开仓 30 秒知道这是什么项目、要长成什么样。总览「项目名片」从这里读。
- **文件**:`PROJECT.md`。固定四段 + 信息段:名称 / 想做什么(一句话)/ 最像的对标 / 三个月长成什么样(北极星,可度量)/ 项目信息(仓、负责人、在研版本、**项目群**)。(第二轮起意图卡不再问「类型」。)**项目群**(专家评审反馈)正本在 `.bw/project.toml` 的 `[chat]` 段:`provider = "welink"`(内部)或外部提供方名 / `group_id`(群号)/ `notify = ["review","merged","release"]`(哪些事同步到群);PROJECT.md 信息段只显示群名,不放登录信息(用户定:WeLink 登录不归 buddy 管,用户在本机提前登好;buddy 只在「测一下」里探活)。`.bw/project.toml` 同时记 `standard_version`(所用规范版本)与 `current_version`(在研版本)——这些都只在仓文件里,库不存副本(母文档 §6 盘点表:库只剩四张表)。
- **谁写·何时**:意图卡填的内容由 buddy 首次写入;之后总览名片「编辑」改;agent 在运作活里可建议改北极星,人确认。
- **核心**。
- **对账**:四段缺任一 → 项目空间提示「章程不完整」;北极星为空 → 总览灯不亮(灰),理由写明。

### 2 · agent 工作约定(起手 AGENTS.md / CLAUDE.md)

- **目的**:让任何 agent 工具(Claude CLI、Cursor、Codex…)一进仓就按 buddy 方式干活。
- **文件**:`AGENTS.md`(正本)+ `CLAUDE.md`(只有一行 `@AGENTS.md`)。AGENTS.md 固定章节:
  1. 这项目按 buddy 方式运作(一句话 + 指向 PROJECT.md);
  2. 每次会话先读什么(PROJECT.md、本周 `docs/plan/`、`.bw/metrics.toml`);
  3. 目录约定(见第 3 类);
  4. 活怎么做:一活一分支、提 MR、DoD、干完最远推「评审中」、**完成永远由人点**;
  5. 指标怎么碰:只改 `.bw/metrics.toml` 正本、观测只追加、不造假、不手改历史;
  6. 禁止事项(不改只追加的记录、不删 `.bw/`、不绕过评审直接合入);
  7. 代码图怎么用(若项目已建 codegraph 索引:`codegraph explore / node / callers / impact` 的用法一句话,见母文档预研 [research/codegraph.md](../archive/v4-prototype/research/codegraph.md));
  8. 项目自定义段(人写,buddy 升级时不动)。
- **谁写·何时**:buddy 铺底写模板;项目自定义段人写;升级时 buddy 只替换带标记的段。
- **核心**。
- **对账**:缺 AGENTS.md 或缺固定章节 → 提示;仓里已有人手写的 README / CLAUDE.md / AGENTS.md(成熟项目接管)→ **不跳过、不覆盖、也不只是追加一段**:铺底的那张一次性运作活③「规范铺底」多一步,由 agent 把 buddy 约定合并进已有文件、和铺底件一起提 MR、人评审(待拍-20 用户定调:纳入管理就要相信管理;规范绝大多数内容在独立目录,正常不冲突;运作活②每周还会持续调节)。

### 3 · 目录与知识结构

- **目的**:知识有固定的家,agent 和人都知道去哪找、往哪写。
- **文件/目录**:
  - `docs/plan/YYYY-Www.md` 周计划(周目标、业务活清单、本周运作、周末完成情况、复盘)——每周一份;
  - `docs/releases.md` 发版记录(一行一版);
  - `docs/decisions/NNNN-*.md` 决策记录(模板)——**扩展**;
  - `docs/design/` 原型与设计产物(Open Design 文件、导出的 HTML)的约定位置;
  - `docs/method/` 五阶段打法与 DoD(今天编译在二进制里的 8 份)——**扩展**。
- **谁写·何时**:周计划由运作活①写、人确认;发版记录由第 5 站「发版本」写;决策记录人或 agent 写。
- **核心**:`docs/plan/`、`docs/releases.md`、`docs/design/`;**扩展**:`docs/decisions/`、`docs/method/`。
- **对账**:本周没有 `docs/plan/` 文件 → 总览 health 输入(a)为假;发版记录格式坏 → 提示。

### 4 · 指标与数据

- **目的**:指标只从真实数据推导;正本在仓;定义有规矩(北极星 1 个、滞后 ≤3、引领 ≤3,每个有目标与保鲜期)。
- **文件**:`.bw/metrics.toml`(正本)、`.bw/connectors.toml`(采集配置)、`.bw/collect_stats.*`(自带采集脚本)、`docs/metrics.md`(人话说明:每个指标是什么、为什么、数据从哪来)——后者由运作活①维护。
- **谁写·何时**:运作活①每周;人可手填(带「手填」徽记)。
- **核心**。
- **对账**:指标过保鲜期 → 总览「待人处理」;`metrics.toml` 与库不一致 → 以仓为准重读(今天已如此)。

### 5 · 活的约定(类别、工具、评审、合入)

- **目的**:一张活从建到完成的规矩统一;开工工具与默认件按类别映射;committer 流程有据可依。
- **文件**:`.bw/issue-policy.toml`:类别标签 → 默认开工工具 → 默认 workflow(**三列,专家评审反馈去掉 agent 列**;母文档第 4 站的表;workflow = SOP 类技能包,自己调度 agent);评审规则(代码走 MR、文档/原型走提交 + 评审中);谁能合入(不存角色,写「有仓权限者」);运作活的节律(①周一人触发、②周五定时);看板规矩(待办池 = 未排周、待办 = 已排本周;拖拽只用于排期)。
- **谁写·何时**:buddy 铺底写默认;项目在「配置」屏改,写回此文件。
- **核心**。
- **对账**:活的类别没有映射 → 建活时提示选工具;运作活②未按节律出现 → 提示定时器状态。

### 6 · 默认件与鱼塘(workflow / 技能)

- **目的**:严选、少而好用、业界优先。
- **文件/目录**:`.claude/skills/<name>/SKILL.md`(**进仓**,带 `.bw-managed`)——一个目录既可能是**单个技能**(一件事,如 grillme),也可能是 **workflow**(SOP 类技能包:入口 SKILL.md 用正文把包内其余技能串成整套流程、流程里现场起 Claude 内置子代理,如 mattpocock-skills、superpowers;官方支持包自带 `.claude/agents/`,实测这两个包都没带);buddy 靠包的结构(有 `plugin.json` 且 `skills/` 下多个技能目录)区分两者并在配置屏分开列,「谁是入口技能」导入时允许人工补标(预研见母文档同目录 `research/workflow-skill-packages.md`);**buddy 不再单独维护 `.claude/agents/` 的 agent 名单**——agent 定义随 workflow 包走(专家评审反馈);`standard/pond/`(鱼塘:未严选的技能与 workflow 清单,不做界面,不铺进项目,要用就在配置里导入)。
- **默认件初稿**(待拍-10 专家评审后改、用户定默认,按使用证据持续增删):workflow——**mattpocock-skills(构建类默认)**与 superpowers(可换)、buddy 自建运作 workflow「更新指标与周计划」「资产盘点」(每周模式 / 首次模式 = 老项目历史回填)「规范铺底」(含合并调整)、原型设计 workflow(配 Open Design);单技能——grillme(需求打磨)、蒸馏。**workflow 自产的文档**(研究笔记、领域模型、决策记录……)不纳入规范管辖:规范只约束 buddy 必需的位置,其余当普通仓内文档,知识库能翻到,第一版实践后再看。buddy 带的都是通用件,各人 / 各项目可导入自己的。
- **谁写·何时**:业界件随 buddy 版本更新;自建件在 `standard/` 里改、过评审;蒸馏出的项目技能人决定要不要升到 `standard/`。
- **核心**:上述默认件;**扩展**:鱼塘任选。
- **对账**:默认件版本落后 → 项目空间提示升级;人手改过(无标记)→ 不覆盖。

### 7 · 运作节律与运作活

- **目的**:让「每周一圈」自动发生,人只在门口。
- **文件**:写在第 5 类的 `issue-policy.toml` 里(节律段)+ 三份运作技能(第 6 类的自建默认件)。运作活①「更新指标 + 制定本周计划」(周一,人触发):复盘上周 → 更新指标 → 引导出本周目标与活 → 人确认 → 变更走 MR;运作活②「资产盘点」(定时,自动建并自动开工;去掉「与代码微重构」):盘点仓内**全部资产**(`docs/`、产物、默认件与规范对账、指标新鲜度、代码图大文件榜)→ 报告写进本周 `docs/plan/` 尾段 → 小 MR;可做可不做的微重构只列成建议活草稿,人勾选才建;运作活③「规范铺底」(一次性,接入时自动建):buddy 建分支写全套核心件;成熟仓已有 README / CLAUDE.md / AGENTS.md 时多一步 agent 把 buddy 约定合并进去;**仓有历史(提交 / 标签 / 远端 issue·MR / CHANGELOG)时再多一步「历史回填」**(专家评审反馈):= 「资产盘点」workflow 的首次模式:从 git 历史、仓内文档、远端 issue 与 MR 里(群历史不当原料)按**同一格式**补出缺的历史周文件 `docs/plan/YYYY-Www.md`(front matter `origin: backfill`)与 `docs/releases.md` 历史版本行,外加 PROJECT.md 草稿、指标候选,全标「回填」、不发明数据 → 一个 MR → 人合入;界面不为回填另开块(用户定)。触发、注入、人介入的全景见母文档 §2.6;回填的详细设计见母文档同目录 `design/`。
- **核心**。
- **对账**:总览「本周运作」栏。

### 8 · 规范自身的元信息(版本、清单、升级)

- **目的**:项目知道自己用的是哪版规范、启用了哪些件;buddy 能算差异、提示升级。
- **文件**:`.bw/standard.toml`:`version = "4.0"`、`enabled = ["charter","agents","docs-core","metrics","issue-policy","defaults-core","cadence"]`、`extensions = [...]`、`source = "builtin"`;每个铺进去的文件带 `.bw-managed` 标记文件(记录来源版本与指纹)。
- **谁写·何时**:铺底时 buddy 写;升级时 buddy 改。
- **核心**。
- **对账**:`standard.toml` 缺 → 视为未铺底,总览提示「一键铺底」;版本落后 → 项目空间「看差异 → 升级」。

## §3 · 正本住哪、怎么演进、怎么被人评审

- **正本**:buddy 仓内 `standard/` 目录(独立于 crates/,**不是代码**),结构:`standard/README.md`(这套规范是什么、八大类总表)、`standard/CHANGELOG.md`、`standard/01-charter/`(README 说明 + `PROJECT.md.tmpl`)、`standard/02-agents/`、… `standard/08-meta/`、`standard/pond/`。编译时把 `standard/` 打进 buddy 二进制(今天 8 份方法论 SKILL.md 就是这么打的),铺底时从二进制写出。
- **演进**:改规范 = 改 `standard/` 下的文件 → 一条 PR → 评审(人 + `/code-review` 看文档)→ 合入 → CHANGELOG 记一行 → 版本号 +0.1;buddy 不需要改代码。项目升级由人在项目空间点。
- **深度评审怎么做**:每个大类的 README 都写「为什么要它、不要它会怎样、试点项目里的真实反馈」;试点(§母文档 §8)跑完两周后,把每个件在试点里「用没用上、agent 读没读、人改没改」记进 CHANGELOG 作为下一版依据。**没在试点里被用到的件降为扩展或进鱼塘**——和技能一样,严选靠使用证据。
- ✅**待拍-16 已定**:八大类与核心/扩展先按本文;后续按业界与内部实践持续修。
- ✅**待拍-20 已定(按用户改)**:成熟项目也铺**全套核心件**;铺底本身是一次性运作活③「规范铺底」+ MR;已有 README / CLAUDE.md / AGENTS.md 在同一张活里多一步「合并调整」,不跳过、不覆盖。
- ✅**待拍-02 已定**:规范全部进仓,含 `.claude/skills/` 与规范说明文档。

## §4 · 落地顺序(母文档 §7 之后的第二步)

1. 建 `standard/` 目录与八类 README + 模板(纯文档,先过一遍你的评审);
2. buddy 侧:铺底命令(接入流末尾调用)、`.bw/standard.toml`、对账(项目空间显示缺/过期)、升级(看差异 → 提交);
3. 三份运作技能(第 6/7 类)写成 SKILL.md,先在一个真实仓上手跑一遍再接进定时;
4. 试点两周 → 按 §3 的证据修订 → 4.1。
