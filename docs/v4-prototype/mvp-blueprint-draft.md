## §1 · V4 MVP 是什么(一句话)与三个愿景怎么落地

**一句话**:buddy 是 AI Coding 里一个人的一张工作台,让传统开发者按 Builder 的方式,把一个小项目(约三个月)从想法管到能验收的结果。V4 = 把这句话做成**每周都能真跑一圈**的最小闭环,推给公司内更多人(codehub 项目为主,GitHub 同样能用)。

**收益怎么说(第三轮用户补充,§9 的对比按此写)**:现在**用不用 buddy 都已经是 AI Coding 时代**,不存在「人写代码 vs agent 写代码」的对比;buddy 带来的是四件别的事——①**所有项目按同一套规范运作,不会无限膨胀下去**;②**所有资产都在项目代码仓,有规范、大模型可见**;③传统项目靠很多人很多角色把控,AI Coding 下很多项目 / 实验局只有 1-2 个人——buddy 让项目**不只是在 AI Coding 下开发完,还不走偏**(这就是 Builder);④**一张工作台打通所有系统**,理论上活都是 agent 干,人不用在很多工作台之间跳来跳去——不只是各开发阶段的工具和 codehub,后面还包括内部聊天系统、问题单系统;好用的组件、好用的 agent / skill 集成进来。

| 愿景(口述原文) | MVP 里落成什么 | 用户能感到的收益 |
|---|---|---|
| ①规范:所有项目都长一样;知识管理:项目所有知识都在项目代码仓,大模型皆可见 | **规范铺底模块**([standard-module-draft.md](standard-module-draft.md)):接入项目时往仓里放同一套文档与约束(章程、agent 工作约定、指标正本、周计划、发版记录、默认件),后续都写回仓;规范本身是独立、可被人深度评审、持续优化的一个模块 | 换项目不用换脑子;agent 打开仓就懂这项目;leader / committer 纳入别人的仓就能看同一张总览、审同一批活 |
| ②从开发变成小项目的 Builder(1 Builder + Agent Loop),基于 buddy 把控交付质量 | **周循环剧本**(§3):看总览 → 更新指标与定计划 → agent 干活人守门 → 验证发版 → 回到总览 | 每周有可验证增量,不靠会议和口头汇报;完成永远人点 |
| ③一张工作台,内嵌 Open Design、Claude CLI、Cursor 等成熟组件,打通所有系统 | **会话屏**(§3 第 4 站):每张活按类别选「开工工具」,原型类走 Open Design、构建类走 Claude CLI 或 Cursor,不出工作台;开工工具按「终端类 / 本机网页内嵌类」两种接法声明,新工具加一条声明一个模块;右侧代码结构侧栏(借 Orca)。MVP 打通的系统 = 开工工具 + codehub / GitHub + **项目群**(专家评审第四轮加:每个项目在聊天工具里本来就有一个群,buddy 只做两件事——往群里发通知、定计划时拉上周群消息当参考;内部群 = WeLink,外部群待定,按工厂设计,见 §6 / §7);问题单系统是同一条「适配模块」路上的下一批(MVP 后,见 §7) | 少切窗;工具由 buddy 缝合,不自造;以后缝新系统(问题单、DSH 一类、别的聊天工具)不用改架构 |

**继承不再讨论的**(V1-V3 已用真实数据证明、且 V4 旅程每站都用到):四条铁律(完成永远人点且同一件活绝不记两次;健康只从真实数据推导、没数据就是灰;交棒/观测这类记录只追加;做完的活可蒸馏成技能、胜率由真战绩算)、内核 crate(状态机、信号密封、只追加表、交互式执行器、连接器、指标正本管道)。

**反命题,按第一轮反馈精确化**:buddy 里**不建成员、权限、群聊、收件箱**;不是通用看板、不是审批系统、不是云服务。**但多人协作是允许的,靠代码仓发生**:V3 实践里已经遇到 builder 没有合代码权限——解法不是在 buddy 里加成员系统,而是 **committer 把同一个仓纳入自己的 buddy**(V2 已支持同一仓多台 buddy),在自己的总览「待人处理」里看到评审中的活(代码 MR、文档、原型都算),审完点「合入」。跨人的通知靠**项目群**:项目名片上配了群号,评审中 / 已合入 / 发版这类事 buddy 往群里发一条(第四轮专家反馈进 MVP;WeLink 收发的具体实现由同事负责,buddy 只定接口与工厂)。详见第 5 站(待拍-13 已定)与待拍-26。

   │
   ▼

│     │                                                       │
│  第2站 运作活①「更新指标 + 制定本周计划」(人触发,一次 agent 会话)

│     │                                                       │

│     │                                                       │

│     │                                                       │

## §2.5 · 指标、周目标、活:一张关系图(第一轮 03/05/14 的根)

第一轮里「总览不直观」「指标定不出来」「运作活算不算计划」都卡在同一件事:**指标、周目标、活三者的关系没说清**。这一节说清,并给一个例子。

**四层,从上到下:**

| 层 | 是什么 | 谁定 / 何时 | 允许为空吗 |
|---|---|---|---|
| **北极星**(1 个)| 「三个月长成什么样」的可度量说法。来自第 0 站意图卡 | 人,接入时;可改 | **不允许**(接入必填)|
| **滞后指标**(≤3)| 结果量,月/周更新(用户数、成功率、收入…)| 人 + agent,在运作活①里逐周补 | 允许(早期没有,灰)|
| **引领指标**(≤3)| 本周可控的先行量,**直接由活推动**(本周合入活数、原型评审通过数、发版次数、覆盖率…)| 人 + agent,在运作活①里逐周补 | 允许(早期没有,灰)|
| **周目标**(1 句)+ **业务活**(N 张)| 周目标 = 这周要把哪几个指标往哪推;每张业务活可标「预期推动的指标」(0..n)| 人在运作活①里与 agent 一起定,人确认才建 | 周目标必填,活可为 0 |

**关系**:活推动引领指标 → 引领指标带动滞后指标 → 滞后指标逼近北极星。总览就按这条链画:每个指标卡下面列「本周哪些活在推它」,活完成后指标的下一次观测就是它的效果。**这就是让引领/滞后指标「直观」的办法——不靠解释,靠把活挂上去。**

**早期定不出指标怎么办**:允许。接入只要北极星;运作活①每周都会尝试「补一个引领、补一个滞后」;规范里写进 DoD——「原型阶段交棒前,至少 1 个引领 + 1 个滞后有真实观测」。在此之前总览指标区就是灰,如实。

**例子(新建项目「建木」,假设值,只为说明关系)**:
- 北极星:三个月内 3 个真实团队用建木跑通一条流水线。
- 滞后:接入团队数(目标 3)、流水线一次跑通率(目标 80%)。
- 引领:本周合入的活数(目标 ≥5)、原型评审通过数(目标 ≥1)。
- 第 3 周周目标:「把 A 团队的第一条流水线跑通」→ 业务活 4 张,其中「流水线 DSL 解析器」标「推动:一次跑通率」,「A 团队接入向导原型」标「推动:原型评审通过数」。
- 运作活①②不占周目标、不标指标,在计划屏单独一栏「本周运作」。

**活的边界**(第一轮 14 问的,第三轮收紧):**活 = 任何要留痕的事项:需要一次 agent 会话的,或要往代码仓写东西的**——代码、文档、原型、指标、盘点、铺底、改名片都算,不限于提代码;只动本机库的纯人工动作(点合入、点完成、切在研版本)不是活。会话工具三选一:Claude CLI / Cursor / Open Design。**业务活**进周计划、可标指标;**运作活**是 buddy 的标准活,MVP 里**两张周期性 + 一张一次性**:①「更新指标 + 制定本周计划」(周一,人触发,含上周复盘)②「资产盘点与代码微重构」(定时,自动建并自动开工,停在评审中)③「规范铺底」(接入时自动建一次,buddy 写规范件走 MR;成熟仓多一步 agent 合并调整,见第 0 站)。

- ✅**待拍-05 已定**:周期性运作活两张,①人触发、②定时自动开工(另有一次性③「规范铺底」,接入时出现)。用户追问「自动开工走什么机制、活是不是只有 issue 一种承载、人怎么介入」——答案在 §2.6。
- ✅**待拍-14 已定**:活的边界按上面定义。用户纠正一处:**周目标不是人「写」出来的**——人只在首尾(触发、确认),周目标是在 Claude CLI 会话里由技能引导、结合代码与上周记录交流出来的,再落成活并带属性,UI 只呈现。上文与第 2/3 站已照此改。
- ✅**待拍-03 已定**:总览按 §2.5 的链画(指标卡挂活)+ 项目名片(这项目干什么、现在什么样);高保真两版后定为一列横块、health 在第一块右侧、待办移到「通知」。

## §2.6 · 触发与介入全景表(用户第二轮点名要的「清晰全景图」)

**三条不变的规矩**(第三轮按用户四问收紧):①**凡是要留痕的事,承载都只有一种——活(issue)**:需要一次 agent 会话的是活;**要往代码仓里写东西的也是活**(写仓一律走分支 + MR,MR 必挂在一张活上,这样才能出现在「待人处理」、才能让 committer 合入)——所以铺底、编辑项目名片这类「buddy 替人写仓」的动作也建活(轻量,无 agent 会话);只动本机库、不碰仓的纯人工动作(合入、点完成、切在研版本)不建活;唯一例外:新建的空仓,首提交直推(没有可以开 MR 的默认分支)。②触发方式 MVP 只有两种——**人触发**、**定时触发**;「事件触发」(远端新 issue → 自动建活、CI 红 → 自动建活)是 MVP 之后;③**自动触发的活最远只到「评审中」,人永远在首尾**——首 = 触发或确认,尾 = 评审、合入、点完成。

**用户四问的答案**:(1)**站 0 铺底也走 issue + MR**——接入的人未必有合入权限,所以铺底 = 一次性运作活③「规范铺底」:buddy 建分支写规范件 → 提 MR → 有权限的人(自己或 committer)在工作台合入;成熟仓已有手写 README / CLAUDE.md / AGENTS.md 时,这张活多一步 agent「合并调整」再提 MR。(2)**运作活①不绑周一**——判据是「当前周没有 `docs/plan/` 文件」:铺底合入后总览立刻提示「本周还没有计划 → 开始本周」;任何时候进总览看到本周无计划都能点。**触发入口在总览,逻辑在活里**:点「开始本周」= buddy 建这张运作活①并跳到会话屏 ▶开工,和其它活一样;计划屏 / 会话屏里也能直接建它、开工它,总览的按钮只是最顺手的入口。(3)**运作活②也是一张活**:定时到点 buddy 自动建 issue(来源 = 自动建)并自动 ▶开工(走同一个交互式执行器),它出现在会话屏活列表和总览「本周运作」栏,人随时能点进去看终端。(4)**编辑项目信息也建活走 MR**:名片「编辑 → 保存」= buddy 建轻量活 + 分支提交 PROJECT.md / `.bw/project.toml` + MR → 待人处理 → 合入 → 完成;有合入权限的人两下点完。

**agent 会话里的「规范手册」怎么渐进加载**(每张活开工时一样,五层,不用字母代号以免与已登记的度量派生链 L0-L6 撞车):第 0 层 buddy 系统提示词(固定、短,V2 已有)→ 第 1 层 仓内 `AGENTS.md`(agent 进仓自己读;里面写着「先读什么、活怎么做、指标怎么碰」)→ 第 2 层 本活的技能 `SKILL.md`(按活注入)→ 第 3 层 规范件按需(AGENTS.md 指引下,agent 需要时才 Read 具体规范:指标规矩、活的约定、目录约定)→ 第 4 层 项目知识(PROJECT.md、本周 `docs/plan/`、`docs/metrics.md`、codegraph 索引)。**不一次性灌全部规范**,靠 AGENTS.md 当目录。

|---|---|---|---|---|---|---|---|---|

**「workflow」这个词在 V4 里的意思**(第四轮专家纠正,与旧聊天式引擎的「工作流」无关):**workflow = SOP 类的技能包**——入口是一份 SKILL.md,里面写的是一整套做事流程(如 mattpocock-skills 是「完整的开发项目工作流」:研究 → 领域建模 → TDD → 评审;superpowers 是「头脑风暴 → 写计划 → 子代理执行 → 验证」),**流程里该用哪个 agent 由这个包自己调度**——预研([research/workflow-skill-packages.md](research/workflow-skill-packages.md))实读两个真实包后核实:它们是在入口 SKILL.md 的正文里现场让 Claude 起内置子代理(Explore / general-purpose),**没有**自带一份持久的 agent 人设文件(官方支持 `.claude/agents/`,两个真实包都没用),buddy 不插手也不替它们建名单。**单个技能**只做一件事(如 grillme 只是引导模型追着用户问,它不是流程)。所以配置里的开工工具映射只需要三列:类别 → 开工工具 → 默认 workflow;buddy 不再单独维护 agent 名单(待拍-24)。buddy 自带的都是通用的 skill 与 workflow,各人 / 各项目可以导入自己的。

**为什么运作活①是人触发而不是定时**:它的产出(周目标、本周活)必须有人在场确认才有意义;定时建好一张等人开工也可以,但「开始本周」这一下就是人对这周负责的仪式,先保留。**为什么运作活②可以自动开工**:它只碰 `docs/`、`.bw/`、小范围重构,产出全在 MR 里等人审。

## §3 · 逐站:看到什么 / 做什么 / 留下什么 / 沿用什么 / 不带什么

「留下什么」分**仓**(进项目代码仓,LLM、leader、committer 可见)和**库**(buddy 本机 SQLite,只做记账与推导)。

### 第 0 站 · 接入项目 + 规范铺底(一次)

- **看到什么**:项目墙(所有已纳入项目,每卡一盏灯 + 一句话)→「接入项目」两张卡:**项目地址**(新建 / 已有:codehub 或 GitHub,可搜索或粘贴地址;**不问分支、不问本机目录**——分支用远端默认分支,目录落在设置里配好的工作区根目录下,「关联已有 clone」不进 MVP)→ **基础信息**(四个字段):项目名称(默认取仓名,可改)、你想做什么(一句话)、最像的对标(产品或仓)、三个月长成什么样(= 北极星,可度量)。**不问「类型」**——「新建还是成熟」的区别只是仓里有没有代码,buddy 自己探测,不让用户选一个后面用不上的属性(待拍-01 按用户意见去掉)。
- **做什么**:人填两卡点完成;buddy 自动建一张一次性运作活③「规范铺底」:建分支、往仓里写**全套核心件**([standard-module-draft.md](standard-module-draft.md))、提一个 MR(标题写明规范版本),活停在评审中 → 有合入权限的人(自己或 committer)在工作台点合入 → 点完成;然后进总览(第一次多半是灰,如实,并提示「本周还没有计划 → 开始本周」)。**为什么走 MR 而不是直接提交**:接入的人未必有合入权限(第三轮用户指出);唯一例外是新建的空仓,首提交直推。若仓里已有 `.bw/project.toml`(别人先接过),读正本预填、不重铺(V2 已有)。若仓里已有人手写的 README / CLAUDE.md / AGENTS.md(成熟项目),**不跳过、不覆盖**:同一张运作活③多一步——agent 把 buddy 约定合进已有文件后再提 MR(待拍-20 按用户意见:纳入管理就要相信管理;规范绝大多数内容在独立目录,正常不冲突;运作活②每周还会持续调节)。
- **老项目怎么进来(第四轮专家反馈:「期望老项目进来,能根据老项目自己记录的千奇百怪的记录,完成 buddy 规范下的信息回填,总览能看到之前的运作情况」)**:铺底探测到仓有历史(有提交 / 有标签 / 远端有 issue·MR / 有 CHANGELOG)时,同一张运作活③再多一步**「历史回填」**——不另开流程、不多问用户一个字。agent 拿三种原料:①git 本地历史(提交、标签、合入记录、按 ISO 周的吞吐);②仓里已有的 README / CHANGELOG / docs / wiki 导出;③远端 issue 与 MR 列表(codehub / GitHub 连接器已能拉)。**群历史不当回填原料**(设计期统一:它隐私边界不清、也没法复算;只在运作活①里当上周参考,不进仓不进库)。产出全部**标「回填」**、走同一个 MR、人评审:仓——`docs/releases.md` 历史段(标签 / CHANGELOG 里的版本一行一个)、`docs/plan/history.md`(按周的历史运作:合了几个 MR、动了哪些目录、关了几个 issue;不是「周计划」,是「回填的周记录」)、PROJECT.md 草稿(从 README 提)、`.bw/metrics.toml` 候选(仓里本来就在量的东西:CI、测试数、发布频率);库——远端 issue 同步成 issue 行(**来源 = 回填,状态照远端,已关的记远端关闭时间;不算任何人 / workflow 的战绩**——它们是历史,不是 buddy 里干出来的活)。老项目的 README / CLAUDE.md 合并调整与历史回填是同一张活的两步,合成一个 MR。**回填绝不发明数据**:git / 远端 / 群里没有的东西就空着;回填只解释历史,不点灯——灯从接入那天起只看真实观测(唯独「上周有交付」这条从 git 合入记录推,那也是真数据)。做法与验证的详细设计见 [design/](design/)(老项目回填一篇)。
- **留下什么**:仓:规范骨架(PROJECT.md 章程、AGENTS.md/CLAUDE.md、`.bw/*`、`docs/plan/`、`docs/releases.md`、默认技能等);老项目多一份回填(`docs/releases.md` 历史段、`docs/plan/history.md`);库:project 行 + 所用规范版本 + 在研版本(新建默认 `v0.1`);老项目多一批来源 = 回填的 issue 行。
- **沿用现有**:两卡创建流(V3 同事用过,已修列仓 999/可搜索/`claude.cmd`/探活三区);codehub 与 GitHub 连接器;`.bw/project.toml` 正本与后来者接入;PROJECT.md 章程写入机制;北极星/项目身份更新命令。
- **不带**:接入时自动生成「竞品分析→找指标→绑数据」三张活(找指标+绑数据并入运作活①;对标改由意图卡直接问)。

- ✅**待拍-27 已定(第四轮专家反馈)**:老项目历史回填是运作活③的第三步(探测到历史才有),原料 = git 历史 / 仓内文档 / 远端 issue·MR(群历史不算原料),产出全标「回填」、同一个 MR、不算战绩、不点灯。

### 第 1 站 · 周一看总览:这项目是什么、health 吗

- **看到什么**:一屏「总览」,**一列横块、只呈现信息、不编号**(高保真两版反馈后定):①**项目信息**(名称、想做什么、对标、三个月长成什么样、**项目群**(第四轮专家反馈加的元数据:内部 = WeLink 群号,外部群待定;空着显示「未配 · 配置」一键补,配了显示群名 + 「通知同步中」)——除群外全部来自 PROJECT.md,群写在 `.bw/project.toml`;右侧 **health 面板**:大灯绿/黄/红/灰 + 状态词 平稳 / 需要关注 / 阻塞 / 无数据 + 三条理由全部可见,一眼知道项目什么情况);②**北极星**(1 张);③**滞后**(N 张横排);④**引领**(N 张横排)——每个指标卡:目标、现值、保鲜期、趋势、**本周哪些活在推它**(§2.5);⑤**项目指标 · 代码仓级**(仓统计现状数,不点灯);⑥**本周计划进度**(目标、进度、运作活①②③状态);⑦**在研版本与发版记录**;⑧**历史运作(回填)**——只有老项目才有、新项目不显示:版本时间线(来自标签 / CHANGELOG)、近 N 周合入吞吐(来自 git 合入记录)、远端 issue 累计、贡献者数,每个数字带「回填自 git / codehub」徽记,不点灯。**待人处理不在总览**——它在左栏「通知」入口(项目墙卡片上有 ⚑ 数);本周运作并入计划屏 / 会话屏。这些信息全部自动获取(项目信息 ← PROJECT.md,指标 ← `.bw/metrics.toml` + 观测,挂活 ← 活的推动指标属性,进度 ← 活状态与远端 MR,版本 ← 发版记录,仓统计 ← git / codegraph,灯是推导),没数据就灰。
- **做什么**:只看;要处理的事从左栏「通知」进(合入 / 点完成 / 去补数据);点「开始本周」触发运作活①(第 2/3 站)。
- **留下什么**:总览本身不写东西。灯与理由**读时现算**(库里不存灯)。
- **health 推导规则(推荐,只用真实数据)**:三个输入——(a)本周有周目标且业务活有进展;(b)业务指标在保鲜期内有真实观测;(c)上周有交付(合入或发版)。**绿** = 三项都真;**黄** = 任一项缺;**红** = 连续两周无进展,或任一业务指标为红;**灰** = 没数据。手填的观测带「手填」徽记。
- **沿用现有**:今天进度面板的指标卡与灰卡诚实、信号密封推导、周信号快照概念(`weekly_review` 表,注意减负线删了它,V4 按新模型重建)。
- **不带**:五阶段轴与阶段舱、进度趋势(手工维护)、五阶段 × 健康灯矩阵。
- ✅**待拍-04 已定**:不做多版本线;一个「在研版本」(计划屏顶部可切,新建默认 `v0.1`),总览只看它;旧版本 = 发版记录里的行,维护活打旧版本标签 + 类别标签「运维/运营推广」。

### 第 2/3 站 · 运作活①「更新指标 + 制定本周计划」(一次会话,人触发)

- **看到什么**:周一在总览点「开始本周」→「计划」屏顶部出现运作活①(状态待做,开工工具 Claude CLI,技能「更新指标与周计划」),右侧是嵌入终端。计划屏三栏:左=周列表(本周置顶)+ 在研版本;中=本周:周目标(可编辑)+ 业务活清单 + 「本周运作」栏;右=选中活详情。
- **做什么**:人点 ▶开工 → agent 在一次会话里按顺序:(1)读上周 `docs/plan/` 与发版记录做**复盘**;(2)**更新指标**:读 `.bw/metrics.toml`,补缺的引领/滞后、给绑不上的找最便宜数据源、改 `connectors.toml`、跑一次采集;(3)**引导出本周**:技能结合指标、代码现状与上周记录,与人在终端里交流出周目标一句 + 业务活清单(每张带:标题、说明、类别标签、预期推动的指标、建议开工工具与技能)——**人不「写」周目标,人在首尾:触发与确认**;(4)人在同一屏改、确认 → buddy 真建活(同时建到 codehub / GitHub issue),`.bw/*` 与 `docs/plan/YYYY-Www.md` 的变更**走 MR**(待拍-21 按用户改),活推评审中 → 人评审(可先**预览**未合入效果,见下)→ 合入 → 点完成。
- **预览未合入的效果**(待拍-21 用户提出):运作活的 MR 合入前,总览 / 计划屏可切到「预览:活 X 的 worktree」——buddy 从该活的 worktree 读 `.bw/metrics.toml`、`docs/plan/` 渲染,顶部横幅「预览 · 未合入」;人看着效果回到终端指挥 agent 调整,满意再合。每活一 worktree(v1 已有)让这件事只是「换个目录读文件」。观测数据不预览(它在库里、只追加)。
- **留下什么**:仓:`.bw/metrics.toml`、`connectors.toml`、采集脚本变更;`docs/plan/YYYY-Www.md`(周目标、活清单、上周完成情况);库:观测(只追加)、issue 行(`week_of`、`version`、`tool`、`kind`、`origin`、`metric_ids`)、运作活记账。
- **沿用现有**:指标正本管道、脚本连接器与采集、`north-star-discovery` + `metrics-binding` 两技能(合成一个)、Issue 创建与远端同步、按活选技能(V2-①)。

| 层 | 住什么 | 特点 |
|---|---|---|
| **仓**(项目代码仓,正本)| 章程、AGENTS.md、规范件、`.bw/project.toml`、`.bw/metrics.toml`、周计划、发版记录、技能、产物 | 人 / agent / leader / committer 全可见;变更走 MR;换机器不丢;**不需要在 buddy 里特别关注** |

## §8 · 验收:什么叫 MVP 做完

1. 一个真实内部项目(点名四个之一,用户在内部选)在 V4 上**跑完两个完整周循环**:两份周计划文件、两轮运作活①②、至少一次发版记录,都在仓里。
2. 总览灯**不是灰的**,且灯的每条理由、每个数字都能用 `sqlite3` 或打开仓文件核对出来;至少一个引领指标卡下挂着推动它的活。
3. 至少一张活用 Open Design 开工、至少一张用 Claude CLI 开工(装了 Cursor 的机器再加一张 Cursor),产物真进了仓;终端内容能复制;右侧代码结构侧栏能看到本活改动的文件。
4. 第二台 buddy 纳入同一仓:leader 看到同一张总览;committer 在「待人处理」看到评审中的活并成功合入。
5. Windows 安装包 `0.4.0-v4` 在同事机器上装得上、跑得起;GitHub 仓走同一流程能接入。
6. 每站至少一条 E2E 读回记录(深链启动 + SQL 读回 + 截图)进 `docs/v4-prototype/`。
7. **老项目**(第四轮加):至少一个有历史的内部项目接入后,总览「历史运作(回填)」块里的版本 / 周吞吐 / issue 数每个都能对回 git 或远端;回填的 issue 行 `origin = backfill`、不进任何战绩。
8. **项目群**(第四轮加;WeLink 实现到位后验):配了群的项目,一次评审中 / 一次合入 / 一次发版各在群里收到一条;`chat_outbox` 里能读回、不重发;定计划那次会话的终端里能看到 agent 引用了上周群摘要。

## §9 · 「为什么在 buddy 上运作项目」:前后对比怎么给

不编数字。一页对比放在项目墙的空态与安装包的使用指南里,证据来自试点项目的真实周记录。**对比对象不是「传统方式」,是 AI Coding 时代里「没有 buddy」的做法**(第三轮用户纠正:现在人人都在 AI Coding,不存在人写代码 vs agent 写代码的收益):

| AI Coding 时代,没有 buddy | 有 buddy(V4) | 证据从哪来 |
|---|---|---|
| 每个项目、每个人一套做法,agent 的产物越堆越多、没人管,项目无限膨胀 | 所有项目按同一套规范运作:同样的章程、约定、目录、节律;运作活②每周盘点与微重构,不让它膨胀 | 多个仓的同一套骨架;`docs/plan/` 尾段的盘点记录 |
| 资产散在聊天记录、本机目录、各人脑子里,换个 agent / 换个人就看不见 | 所有资产都在项目代码仓、有规范位置,任何大模型打开仓就看得见 | 仓文件本身 |
| 1-2 个人的项目 / 实验局没有角色把控,做完了但走偏了、没人知道 | Builder 一个人 + 周循环:指标从真实数据推导、周目标挂着活、完成永远人点、健康灯不假绿——项目不走偏 | 总览截图 + SQL 读回;`.bw/metrics.toml` 变更史 |
| 在 codehub、终端、设计器、聊天工具、问题单之间跳来跳去 | 一张工作台:活按类别在工作台里用 Open Design / Claude CLI / Cursor 开工;评审、合入、发版都在同一张台面上;聊天、问题单是下一批接进来的适配模块 | 会话屏 + 运行记录 + MR |
| 好用的组件 / agent / skill 靠各自摸索 | 严选的默认件随规范铺进每个项目,鱼塘里挑,用过就记账 | 技能使用记录、战绩 |
