## 1 · V4 是什么

> 这一章的正本原文在 [`../archive/v4-prototype/mvp-blueprint-draft.md`](../archive/v4-prototype/mvp-blueprint-draft.md) §1、§9。

### 1.1 一句话

buddy 是 AI Coding 里**一个人的一张工作台**,让传统开发者按 Builder 的方式,把一个小项目(约三个月)从想法管到能验收的结果。

**V4 = 把这句话做成每周都能真跑一圈的最小闭环**,推给公司内更多人用(内部 codehub 项目为主,GitHub 同样能用)。

### 1.2 三个愿景怎么落地

对比的对象**不是「传统开发方式」**——现在用不用 buddy 都已经是 AI Coding 时代,不存在「人写代码 vs agent 写代码」这种收益。buddy 带来的是另外三件事:

| 愿景 | V4 里落成什么 | 用户能感到的收益 |
|---|---|---|
| **所有项目按同一套规范运作;项目的知识都在项目代码仓里,大模型都看得见** | **规范铺底**(第 4 章):接入项目时往仓里放同一套文件——项目名片、指标正本、活的约定、周计划目录、发版记录;之后所有产出都写回这个仓 | 换项目不用换脑子;agent 打开仓就懂这个项目;别人把同一个仓纳入自己的 buddy,看到的是同一张总览 |
| **从「开发」变成「小项目的 Builder」:一个人 + agent 循环,靠 buddy 把控交付质量** | **周循环剧本**(第 2 章):看总览 → 更新指标与定计划 → agent 干活人守门 → 验证发版 → 回到总览 | 每周有可验证增量,不靠开会和口头汇报;「完成」永远是人点的那一下 |
| **一张工作台打通所有系统**,把成熟的组件缝进来,而不是自己造 | **会话屏**(第 7 章):每张活按类别选开工工具,原型类走 Open Design、构建类走 Claude CLI 或 Cursor,都不用离开工作台;远端走 codehub / GitHub;项目群走聊天工具 | 少切窗;以后要缝新系统(问题单、别的聊天工具)只加一个适配模块,不改架构 |

### 1.3 四条不变的铁律

这四条从 V1 一路到 V4 没变过,V4 每一站都用到:

1. **「完成」永远由人点,同一件活绝不记两次。** agent 干完最远只能到「评审中」;定时任务只会自动**建**活,绝不自动**完成**活。
2. **健康只从真实数据推导,没数据就是灰。** 信号不能手动设置;数据过期自动降级;手填的数字带「手填」徽记。**灰 ≠ 绿**。
3. **交棒、观测这类记录只追加,不修改。** 事后抹不掉。V4 里这条的落点从数据库表换成了仓文件(第 3 章、第 10 章)。
4. **做完的活可以蒸馏成技能,下次同类活自动带上;好用与否由真实使用记录说话,不手工设定。**

### 1.4 反命题:V4 故意不是什么

- **不是团队协作平台**——buddy 里不建成员、权限、群聊、收件箱。**但多人协作是允许的,靠代码仓发生**:有合入权限的人(committer)把同一个仓纳入自己的 buddy,在自己的通知入口里看到评审中的活,审完点合入。跨人的提醒靠**项目群**(第 9 章),不靠 buddy 自己发明一套协作面。
- **不是通用看板**——没有甘特图、没有里程碑实体(版本就是里程碑)。
- **不是审批系统**——交棒只留痕不拦人。
- **不是云服务**——AI 执行 = 本机的 `claude` / `cursor` 命令行,在内嵌终端里全程可见、可中止,花费由用户自己把握。
- **永远不替用户捏造健康**。

### 1.5 V4 和 V3 的关系(一句话)

**并存、将删。** V3 的旧壳与旧库原样留着继续跑,V4 用自己的三个 crate 与自己的库文件,两边零依赖、互不影响;什么时候能把 V3 整片删掉,判据在第 12 章 §12.6(逐条核对过,今天一条都不满足)。当前节奏是**一心 V4,V3 不再投入**。

## 2 · 一个项目怎么转:第 0 站 + 每周六站

> 这一章的正本原文在 [`../archive/v4-prototype/mvp-blueprint-draft.md`](../archive/v4-prototype/mvp-blueprint-draft.md) §2、§2.5、§2.6、§3、§3.5。

### 2.1 旅程总图

```
第0站 接入项目 + 规范铺底(一次)
   │
   ▼
┌─ 第1站 周一看总览:这项目是什么、健康吗 ◄──────────────────┐
│     │                                                      │
│  第2/3站 运作活①「更新指标 + 制定本周计划」(人触发,一次 agent 会话)
│     │   → 周目标 → 业务活挂本周 / 在研版本 / 预期推动的指标   │
│     │                                                      │
│  第4站 执行:每张活按类别选开工工具,agent 干、人守门        │
│     │                                                      │
│  第5站 验证闭环:评审 → 合入 → 人点完成 → 记发版             │
│     │                                                      │
└─ 第6站 定时:运作活②「资产盘点」自动建活并自动开工 ──────────┘
```

第 2 站(更新指标)和第 3 站(定计划)在**同一次会话**里先后做完,编号保留是为了讲清里面有两件事。

**角色**:主角是 Builder。**leader 不做专门界面**——他把大家的仓纳入自己的工作台,项目墙加每个项目的总览就是 leader 视图。**committer**(有合代码权限的人)同样靠纳入同一个仓来评审和合入。

### 2.2 指标、周目标、活:一条链

「总览不直观」「指标定不出来」「运作活算不算计划」这三个问题卡在同一件事上:**指标、周目标、活三者的关系**。四层,从上到下:

| 层 | 是什么 | 谁定 / 何时 | 允许为空吗 |
|---|---|---|---|
| **北极星**(1 个)| 「三个月长成什么样」的可度量说法 | 人,接入时填;可改 | **不允许**(接入必填)|
| **滞后指标**(≤3)| 结果量,月/周更新(用户数、成功率、收入……)| 人 + agent,在运作活①里逐周补 | 允许(早期没有,显示灰)|
| **引领指标**(≤3)| 本周可控的先行量,**直接由活推动**(本周合入活数、原型评审通过数、覆盖率……)| 人 + agent,在运作活①里逐周补 | 允许 |
| **周目标**(1 句)+ **业务活**(N 张)| 周目标 = 这周要把哪几个指标往哪推;每张业务活可标「预期推动的指标」| 人和 agent 在运作活①里一起定,人确认才建活 | 周目标必填,活可为 0 |

**关系**:活推动引领指标 → 引领指标带动滞后指标 → 滞后指标逼近北极星。总览就按这条链画:**每个指标卡下面列出本周有哪些活在推它**。让引领/滞后指标「直观」的办法不是加解释文案,是把活挂上去。

**早期定不出指标怎么办**:允许。接入只要北极星;运作活①每周都会尝试补一个引领、补一个滞后。在补上之前,总览的指标区就是灰,如实。

**一个例子**(演示项目「建木」,数字是假设值,只为说明关系):北极星 = 三个月内 3 个真实团队用它跑通一条流水线;滞后 = 接入团队数(目标 3)、流水线一次跑通率(目标 80%);引领 = 本周合入的活数(目标 ≥5)、原型评审通过数(目标 ≥1);第 3 周周目标 =「把 A 团队的第一条流水线跑通」,底下 4 张业务活,其中「流水线解析器」标着推动「一次跑通率」。运作活不占周目标、不标指标,在计划屏单独一栏。

### 2.3 三条不变的规矩

**规矩①:凡是要留痕的事,承载只有一种——活。**

- 需要一次 agent 会话的,是活;
- **要往代码仓里写东西的,也是活**——写仓一律走分支加合并请求(下文简称 MR),而 MR 必须挂在一张活上,这样它才会出现在「待人处理」里、才能让 committer 合入;
- 所以铺底、编辑项目名片、发版本这类「buddy 替人写仓」的动作也建活,只是它们**不起 agent**,叫**轻量活**;
- 只动本机库、不碰仓的纯人工动作(点合入、点完成)不建活。

**规矩②:触发方式只有两种——人触发、定时触发。** 「事件触发」(远端来了新 issue 就自动建活、CI 红了自动建活)是 MVP 之后的事。

**规矩③:自动触发的活最远只到「评审中」,人永远在首尾。** 首 = 触发或确认,尾 = 评审、合入、点完成。

### 2.4 每件事谁触发、用什么、人在哪介入

| 旅程里的事 | 触发 | 承载 | 开工工具 | 产出 | 人在哪介入 |
|---|---|---|---|---|---|
| 接入项目 + 规范铺底 | 人(两张卡)→ buddy 自动建一次性运作活③ | 轻量活(buddy 自己写模板,不起 agent) | — | 仓:分支上的 `.bw/` 骨架 + MR;库:项目行 | 首(填两卡)· 尾(合入、点完成) |
| 老项目历史回填 | 铺底探测到仓有历史 → 起一次资产盘点的**首次模式** | 活 | Claude CLI | MR:同格式的历史周文件 + 历史发版行 | 尾(评审、合入、点完成) |
| 周一看总览 | 人 | 纯界面(只读) | — | — | 全程 |
| 运作活①更新指标 + 定本周计划 | 人(总览「开始本周」) | 活 | Claude CLI(内嵌终端) | MR:`.bw/*` 变更 + 本周计划文件;活草稿(人确认后才真建活) | 首(触发)· 中(终端里对话)· 尾(确认、评审、点完成) |
| 业务活开工 | 人(会话屏 ▶开工) | 活 | 按类别:Open Design / Claude CLI / Cursor | 代码 / 文档 / 原型 + MR | 中(对话、停)· 尾(评审、合入、点完成) |
| 运作活②资产盘点 | **定时**(默认周五晚)自动建活 + 自动开工 | 活 | Claude CLI | 盘点报告写进本周计划文件尾段 + 建议活草稿 | 尾(周一评审、合入、点完成、勾选要建的建议活) |
| 评审 / 合入 / 点完成 | 人(Builder 或 committer) | 纯界面动作 | — | 库:结清时间、合入人 | 全程 |
| 发版本 | 人(计划屏一个按钮) | 直接写仓 | — | `.bw/releases.md` 追加一行 + 给这批活回填版本号 | 首(点一下) |
| 蒸馏 | 人(会话屏) | 活的附属动作 | Claude CLI | 项目仓 `.claude/skills/` 里多一份技能(记着来源活) | 首(触发)· 尾(看一眼) |
| 编辑项目名片 | 人(总览「编辑」) | 轻量活 + MR | — | 仓:项目名片文件 | 首(改)· 尾(合入、点完成) |

### 2.5 agent 会话里的知识是渐进加载的,不一次性灌

每张活开工时给 agent 的材料分五层,**故意不编字母代号**(避免和已登记的度量派生链撞车),正文写「第 N 层」:

- **第 0 层**:buddy 系统提示词。固定、短,四段——身份与这张活、铁律、规范索引、本活的剧本(第 7 章 §7.5)。
- **第 1 层**:仓根的 `AGENTS.md`,agent 进仓自己会读。**这是项目自己的文件,buddy 不铺、不改**(第 4 章 §4.3)。
- **第 2 层**:这张活挂的那一份技能——提示词里只给名字、一句话和完整路径,正文让 agent 按需读。
- **第 3 层**:规范件按需读——指标的规矩、活的约定、目录约定。
- **第 4 层**:项目知识——项目名片、本周计划、指标定义、代码图索引。

### 2.6 易用性守则

MVP 的流程不再加步骤;**每站人的动作 ≤ 3 下**;凡是 buddy 能替人做的(建活、开分支、提 MR、写模板、探测、回填)一律自动;人只做「触发 / 确认 / 评审 / 点完成」;每条待办都带行内动作,不让人满屏找按钮。有合入权限时,「合入」和「点完成」合成一颗「合入并完成」按钮——仍然是人点的那一下,只是少点一次。

## 3 · 数据与文件:仓是正本,库只有四张表

> 这一章的正本原文在 [`../archive/v4-prototype/design/02-data-and-files.md`](../archive/v4-prototype/design/02-data-and-files.md),信息盘点的原始论证在 [`../archive/v4-prototype/mvp-blueprint-draft.md`](../archive/v4-prototype/mvp-blueprint-draft.md) §6。

### 3.1 三条判据

**一句话结论:仓是正本,库只有四张表,别的数字全部现算。**

1. **别人要看的进仓**——第二台 buddy、leader、committer、不装 buddy 的人都要能看见的,进项目代码仓、走 MR。
2. **只有这台机器产生、丢了不影响项目的进库**——库是本机的过程数据与显示缓存,仓里已有的不复制一份进库。
3. **说不出哪个界面或命令会来取的,不存**——每一类数据都要说得出哪个界面会来取它;说不出就不建表、不加列、不缓存。

按这三条把 V4 的全部信息过了一遍,结果是**库从 V3 的二十张表掉到四张**:数字不再信库,全部从 git、远端、仓文件当场算。

### 3.2 住在仓里的(正本,走 MR,换机器不丢)

**buddy 铺进用户仓的东西全都在 `.bw/` 底下,一个例外都没有**——仓根一个字不写(为什么见第 4 章 §4.3)。

| 文件 | 装什么 | 谁写 | 谁读 |
|---|---|---|---|
| `.bw/PROJECT.md` | 项目名片:名称 / 想做什么 / 最像的对标 / 三个月长成什么样(北极星)/ 项目信息 | 接入两卡、改名片 | 总览名片、项目墙一句话 |
| `.bw/project.toml` | 仓与远端地址、规范版本、在研版本、`[chat]`(项目群提供方 / 群号 / 同步哪些事) | 接入、配群 | 总览、通知同步、配置屏 |
| `.bw/metrics.toml` | 指标**定义**:北极星 / 滞后 / 引领,各自的目标、采集方式、能不能回溯 | 运作活①、人手改 | 指标卡、健康灯的推导 |
| `.bw/metrics/readings.jsonl` | 指标**读数**,只追加,一行一个观测点(只有不可回溯与手填的才落这里,见第 10 章) | 定时采集、手填 | 指标卡、走势 |
| `.bw/scripts/*` | 采集脚本。铺一次就归项目,之后 buddy 再也不覆盖 | 铺底铺通用的几份;之后项目自己改 | 采集 |
| `.bw/issue-policy.toml` | 开工工具清单、「类别 → 工具 → workflow」映射、运作节律、看板列定义 | 铺底写默认;配置屏改 | 配置屏、▶开工、定时判据 |
| `.bw/standard.toml` + `.bw/managed.toml` | 用的是哪版规范、开了哪几类件;buddy 托管件的内容指纹(人改过没有) | 铺底、升级 | 规范对账 |
| `.bw/plan/YYYY-Www.md` | **本周的一切**:周目标、业务活清单(每行带顺序 / 类别 / 工具 / workflow / 挂哪个指标)、本周指标读数快照、盘点报告尾段。回填的历史周同格式 | 运作活①②、回填、拖拽排期 | 计划屏、总览、知识库 |
| `.bw/releases.md` | 版本 → 包含的活。回填的历史版本同格式 | 发版本、回填 | 总览发版记录 |
| `.bw/design/README.md`、`.bw/decisions/*.md` | 设计产物的约定位置、决策记录(扩展件,可以不要) | 人或 agent | 知识库 |
| 仓根 `AGENTS.md`(+ `CLAUDE.md` 一行导入) | **这个项目自己的开发手册**。**buddy 不铺这份**;buddy 自己的运作规矩每场会话现给 agent,不往用户仓写第二份副本 | 资产盘点首次模式里的子技能,人点头才写 | 项目自己的 AI 工具 |
| `.claude/skills/**/SKILL.md` | **项目自有**的技能:蒸馏产出、人手加的、导入的。buddy 自带的那十一份**不在这里** | 蒸馏、导入、人手加 | 配置屏、知识库;开工时 agent 在仓里原生发现 |
| 代码、文档、产物 | 项目本体 | agent / 人 | 知识库、会话屏文件树。**不另建产物登记表**——`git log --name-only` 就是登记 |

**排期为什么写进周计划文件**:本周排了哪些活、什么顺序、每张用什么工具,全写在周计划文件的活清单里——别人 `git pull` 就看得到,不用装 buddy,改动走 MR 有记录,断网也能用。远端平台上顺手打的周标签是**镜像不是正本**,打不上不影响任何功能。

### 3.3 住在本机库的(四张表,删了能重建)

| 表 | 为什么它非在库不可 |
|---|---|
| 项目 | 项目墙要在**不打开任何项目**时列出 N 个项目的名字和灯——不能每次启动扫 N 个仓。只存定位(路径 / 远端 / 名称)+ 灯的显示缓存,打开项目时以仓文件为准刷新 |
| 活 | 远端 issue 的**本机缓存**(离线可看、启动快);没配远端的项目它是唯一落脚点 |
| 会话 | 活 ↔ claude 会话 ↔ 工作目录 ↔ 分支,恢复会话必需。纯本机、纯过程 |
| 元信息 | schema 版本;通知屏「事件流看到哪个时间点」也以键值对放这里,不为它开第五张表 |

活这张表上有 9 个 V4 扩展列:排期到哪一周、在研版本、开工工具、种类(业务活 / 运作活 / 轻量活)、来源(人建 / agent 拆 / 自动建 / 回填)、用的 workflow、类别标签、列内顺序、预期推动的指标。

**这 9 列是缓存,不是正本。** 它们的正本是周计划文件里活清单那一行。库里留一份的唯一理由是:①计划屏、会话屏要能离线快速渲染、按周按列过滤排序,不能每次开屏都解析 Markdown;②拖卡片要即时跟手,不能等文件写完才看到卡片动。所以写入顺序是「缓存先动、文件随后追上」;**两边不一致时以文件为准**,下一次对账用文件覆盖缓存,不是反过来。

**一张活最多挂一个指标**,用单列表达,不建关联表——总览的核心画法是「每个指标卡下面列本周哪些活在推它」,单列反查已经够;要推动多个指标就把活拆细,粒度变细本身也更符合「一件活 = 需要一次 agent 会话」的边界。

### 3.4 完全不存、每次现算的

| 要看的东西 | 现算方式 |
|---|---|
| 健康灯的三条判据 | 读周计划文件 + 问 git,当场判(第 5 章 §5.3) |
| 技能 / workflow 用了几次 | 按活的 workflow 列分组计数 |
| 「本周建过资产盘点没有」 | 查本周有没有这张运作活 |
| 远端连不连得通 | 探活是即时结果,拿到就用,不存 |
| 产物是什么 | `git log --name-only` |
| 代码仓统计与近四周走势 | 现跑 git 与远端查询 |
| 群通知发过没有 | 不追踪,发送即完成,不做去重 |

### 3.5 砍掉的表,和换来的三个代价

V3 那二十张表里,V4 只留了四张。被砍掉的大致是三类:①**第二副本**(指标定义、指标读数、发版记录、周计划索引、技能登记、连接器配置——正本都在仓文件里,库里那份是抄的);②**没人取的账本**(战绩台账、群通知去重账本、产物登记表、技能包导入登记);③**跟着功能一起退场的**(队友名单、阶段轴与阶段舱、聊天式工作流的正文与版本)。

**换来的三个代价,知情接受**:

1. 打开项目、切周时要现算(扫 git、解析文件)。buddy 自己的仓几百个提交是几十毫秒级;万级提交的老仓将来可能要加内存缓存。
2. 指标读数是周粒度,没有每日曲线。
3. **「每次运行的成败与耗时自动入账」这条老铁律在 V4 没有持久载体了**——它被更硬的东西取代:**活干没干成,看远端 MR 合没合入**,那个造不了假。这是产品哲学的一处改动,用户知情拍板。

### 3.6 不兼容老库

V4 用**新的库文件**,和 V3 的库文件并存互不影响;schema 按四张表**直接写全**,**不写任何 V3 → V4 迁移**。V1-V3 项目的队友战绩、旧版本记录等历史数据不搬运,用户已明确接受这个取舍。

开发期每次改 schema 直接删库重建,不写迁移脚本;**「加列必须同时改 schema 并加迁移守卫」这条纪律从试点起恢复执行**——一旦有第一个真实用户开始用 V4 库存了数据,这份库就变成了需要保护的存量库,那个切换点要在试点开始那次改动里明确标注,不是自然过渡。

### 3.7 工程落点

- 库:`crates/bw-v4/src/store/`,`schema.sql` 里恰好 `project` / `issue` / `claude_conversation` / `app_meta` 四张表;活的 9 个扩展列是 `week_of` / `version` / `tool` / `kind` / `origin` / `workflow` / `category` / `sort_order` / `metric_key`;`issue` 表里**没有** `assignee` 列(V4 的活不「指派给队友」,而是「配开工工具 + workflow」)。
- 仓文件解析器:`crates/bw-v4/src/repo/` 下一份文件一个模块(项目名片、周计划、发版记录、活的约定、规范清单、指纹清单、指标定义、读数流水)。统一风格:只读加解析、拒收未知字段、文件不存在返回「没有」而不是报错、解析失败整份拒收且绝不写半份缓存。
- 命令与事件:`crates/bw-v4/src/command.rs` 里是**全新的一对枚举**,和 V3 那对没有继承关系、不互相引用。

## 4 · 规范铺底:铺什么、怎么对账、老项目怎么回填

> 这一章的正本原文在 [`../archive/v4-prototype/standard-module-draft.md`](../archive/v4-prototype/standard-module-draft.md) 与 [`../archive/v4-prototype/design/03-standard-and-backfill.md`](../archive/v4-prototype/design/03-standard-and-backfill.md)。

### 4.1 规范是什么

**规范 = buddy 仓里一个独立目录 `standard/`,是文档和约束,不是代码。** 改规范只需要改文件、过评审,不需要改 buddy 的任何一行 Rust。它有版本号,编译时打进 buddy 二进制,接入项目时从二进制写出到项目仓。

三个原则:

1. **正本只有一份,住在仓里,人可读**——每个规范件是 Markdown 或 TOML;buddy 只负责「铺进项目、对账、提示升级」,不在代码里藏第二份内容。
2. **严选、可拔插**——分**核心件**(每个项目必有,否则旅程走不通)和**扩展件**(任何时候可加可拆)。
3. **进仓、可见、可审**——铺进项目的文件都提交 git,agent 打开仓即读到;**人手改过的文件 buddy 不覆盖,只提示差异**。

### 4.2 `standard/` 长什么样

```
standard/
├── VERSION                 # 纯文本版本号,今天是 5.0;铺底与对账都读这一个值
├── README.md               # 这套规范是什么,含「还没做的部分」如实说明
├── 01-charter/             # 项目名片模板
├── 03-docs/                # 周计划目录说明与周文件模板、设计产物目录说明、发版记录模板
├── 04-metrics/             # 指标定义模板
├── 05-issue-policy/        # 活的约定模板(三列映射 + 评审规则 + 节律 + 看板列定义)
├── 08-meta/                # 规范清单模板
└── skills/                 # buddy 自带的技能与运作剧本,一个平铺目录,11 份
    └── <slug>/SKILL.md
```

**关于 `standard/skills/`(2026-08-21 收敛)**:buddy 自带的技能此前散在两处——`docs/skills/` 下九份方法论技能,`standard/06-defaults/ops/` 下四份运作剧本,而且用目录层级表达「谁带着谁」。现在收敛成 **`standard/skills/<slug>/SKILL.md` 一个平铺目录、共 11 份**:九份方法论去掉两份僵尸(`north-star-discovery` 与 `metrics-binding`,内容已并进 `metrics-refresh`)剩七份,加四份运作剧本(`week-planning`、`metrics-refresh`、`asset-audit`、`project-handbook`)。**谁调用谁写在文件头部的 frontmatter 里,不再用目录层级表达从属**。`docs/skills/` 保留给 V3 用,V4 不再读它。

**还没建的,如实标注**:`CHANGELOG.md`(每次改动记一行,含「试点里用没用上」的证据)、`07-cadence/`(运作节律的文字说明,实际配置目前和活的约定一起铺)、`pond/`(鱼塘:未严选的技能与 workflow 清单,不铺进项目,要用就在配置里导入)。

**规范第 2 类「agent 工作约定」的模板已经整个删除**——理由见 §4.3。

### 4.3 铺底只有一步:把核心件写进 `.bw/`,仓根一个字不写

接入两卡填完、项目行写进库、工作区就绪之后,buddy 自动建一张一次性的**运作活③「规范铺底」**,立刻同步跑完:

1. **给这张活开一棵自己的工作目录和分支**(主仓的兄弟目录,分支名带活号)。核心件写进这棵树,**人的主检出一个字节都不碰**,两张活同时在跑也不会撞车。新仓老仓走同一条路,没有「空仓直推默认分支」这种例外。
2. **按二进制里那张模板表铺**,每份模板自己标着「哪一站铺」:项目名片和规范清单在接入这一刻就铺;周计划目录说明、发版记录空表头、设计产物目录说明、指标定义、活的约定这几份,**走到那一站才铺**(或者人在配置屏点一次「规范铺底」全铺上)。
3. **人手改过不覆盖**:只在目标路径不存在、或存在但内容指纹与记录一致时才写;两者都不满足就跳过,并在活的正文里写一行「某文件已存在且非 buddy 管理,跳过」。
4. **这一站不铺的件,也要看一眼**:标了「走到那一站才铺」的件,如果仓里已经躺着一份、而且不在 buddy 的指纹清单里,就在活的正文里单开一段说清楚——不覆盖、不删除、不猜它对不对,只保证人知道它在那儿。加这一条是因为真撞上过:项目仓里躺着一份**另一个项目**的指标文件,铺底当时连它在不在都没看,人以为铺完了,而总览的指标卡读的是别人的指标。界面会把这些文件**当正本读**,所以不能装看不见。
5. **指纹清单最后写**,保证记的是刚落盘那一刻的真实内容。
6. 真提交出东西了就推分支、开 MR、把活推到「**评审中**」等人合。每一种「没有 MR」的情况都在活的正文里写清楚为什么(没挂远端 / 这次没有新东西要提交 / 推分支失败带原话 / 开 MR 失败带原话)——**不摆一个来历不明的空号**。

**为什么仓根一个字不写。** 仓根的 `AGENTS.md` / `CLAUDE.md` 是**这个项目自己的**文件。给别人的仓写一份开发手册,性质是「**建议改造你的项目**」,而接项目那一刻 buddy 才刚 clone 完:既没读过这个仓,也没问过人愿不愿意。当时那半步自己就把这件事说破了——成熟仓仓根已经有 `AGENTS.md`,按「人手改过的不覆盖」整份跳过,该起作用的地方一个字没写;空仓那边写得出来,但只能写成一张七成是「(还没填)」的表。**一个功能在该起作用的地方空转、在不该起作用的地方产出占位符,那就不是时机问题的边角,是这一步本身放错了地方。**

它挪去了**资产盘点的首次模式**(第 8 章 §8.2),因为那次会话本来就在干「读一遍这个仓、看它有什么缺什么」,而且它是一次**真的 agent 会话**,能做铺底做不到的两件事:真读懂这个仓,以及先问人愿不愿意。

铺底仍然探一下仓根有没有 README / `CLAUDE.md` / `AGENTS.md`,但**这条探测不触发任何一步**,只写进活的正文当证据,并如实写上「提议给这个项目写一份开发手册——那是在改你的项目,得先问过你才写,不在接项目这一步做」。

### 4.4 老项目历史回填

**它不是一条独立产线,就是「资产盘点」这个 workflow 第一次跑**(首次模式)。铺底探测到仓有历史时触发一次,产出和铺底件合成同一个 MR。

**探测判据**(任一为真即算有历史):提交数大于 1(1 是 buddy 自己的骨架提交);有 git 标签;仓根有 CHANGELOG / RELEASES;远端有已关闭的 issue 或已合并的 MR;项目名片里已经配了群。**今天只实现了前三条**——远端信号与群配置这两条代码里根本没有对应查询,不是判了否。设计仍保留五条。

**产出形态(拍板过的)**:不另开一份「历史运作」新文件,而是**把本该有、但老项目没攒出来的同格式正常文件补出来**——某个历史周有过提交或合入、当时却没有周计划文件,就按运作活①写周计划**同一套模板**补一份,文件头标明来源是回填;某个历史版本(git 标签 / CHANGELOG)在发版记录里没有对应行,就按同一张表格式补一行,来源列标「回填」。**界面不为回填开辟任何专门区块**:历史周天然出现在计划屏左栏的周列表里,历史版本天然出现在总览的发版记录里,只带一个小「回填」徽记。

**三层流水线**:①buddy 主机代码先算完能算的一切(首末提交时间、按周提交数、按周合入数、带日期的标签),直接写成同格式的仓文件;②agent 只读文本、不算数字(从 README / CHANGELOG 里提项目名片草稿、列指标候选);③人评审这个 MR。

**回填绝不发明数据**,五条防伪规则:

1. **合入记录用双亲结构判定**,不用提交消息文字匹配——文字匹配会漏掉手写的合并提交(真实样例:71 条真实合入漏掉 23 条)。
2. **远端 MR 数与本地合并提交数分开报**——两个口径不是一回事,不可混用;完全没有远端连接时才用本地口径当退化替代,并注明。
3. **无标签、无 CHANGELOG 就诚实写「未发现可回填的版本记录」**,绝不拿提交日期倒推版本号。
4. **批量关闭事件不当速率信号**:数字照实呈现,某一周关闭数占比过半时附一句提示,不改数字本身。
5. **每个数字标复算命令**:产出里带一句「这个数用什么命令算出来的」。

**其余边界**:往前最多回填两年(104 周),扫到就停并如实写进回执;已经存在的周文件一律不碰(那可能是人自己写的),只补「这一周有过提交、但没有对应周文件」的;**回填只解释历史,不点灯**——它的产出不参与健康推导;在研版本的起点,能从标签或 CHANGELOG 认出来就取那个值,完全没有版本记录的老项目保持空、**不自动定成 v0.1**(那个默认值只属于新建项目)。

### 4.5 对账与升级

**对账**是纯读操作,任何时候都能跑:比对规范清单里开了哪几类、当前规范版本、指纹清单里每个文件的指纹,分三类,**一个文件只落一类**:

- **缺**——清单里有这一类却没有对应记录,或记录了但磁盘上没有这个文件;
- **过期**——记录的版本低于当前规范版本,**且磁盘指纹与记录一致**(没人碰过,是干净的升级候选);
- **人改过**——磁盘指纹与记录不一致,不看版本号,**永远不参与自动覆盖**。

指纹算法:文件原始字节的 SHA-256,逐字节比,不做语义或空白归一化——简单确定。对账在两处跑:知识库屏渲染时现算;运作活②每周固定跑一遍,结论追加进那周的周计划尾段。

**升级**:人在知识库屏对「过期」文件点「看差异 → 升级」→ buddy 算文本差异 → 人选要升哪几个 → 干净的那批建一张轻量活直接换新内容提 MR;「过期且人改过」的那批走一次真实 agent 会话做合并,并进同一张升级活、同一个 MR。

**老项目已经有一份发版记录时怎么办**:发版记录解析器只认 buddy 自己那张五列表头下面的行;表头对不上就**在文件末尾另起一段「buddy 管理的发版记录」**,项目原有的那份一个字都不动。两张表要不要合并,由人在 MR 里看到提示后自己决定,不是解析器该做的事。

### 4.6 同事怎么往规范里加东西

一条 PR 直接改 `standard/`,和改代码一样过评审、合入、版本号按需 +0.1——buddy 不需要为此改任何 Rust 代码。最常见的场景是往 `standard/skills/` 加一份新的内置技能或运作剧本,照着已有的加一个目录即可。

**深度评审怎么做**:每个大类的说明里都要写「为什么要它、不要它会怎样、试点里的真实反馈」;试点跑完两周后,把每个件在试点里「用没用上、agent 读没读、人改没改」记进规范的变更记录,作为下一版的依据。**没在试点里被用到的件降为扩展或进鱼塘**——和技能严选同一个逻辑:靠使用证据,不靠拍脑袋。

### 4.7 工程落点

- 探测与写核心件:`crates/bw-v4/src/standard/bootstrap.rs`;编排在 `crates/bw-v4/src/app/bootstrap.rs`;历史回填在 `crates/bw-v4/src/app/backfill.rs`。
- 指纹清单的读写、指纹算法、对账判定:`crates/bw-v4/src/repo/managed_file.rs`,对账结果是「缺 / 过期 / 人改过 / 已是最新」四态。
- 规范素材编译进 `crates/bw-v4/src/standard/`;版本号读 `standard/VERSION`。**别把它和项目仓里生成的规范清单混**——前者记「当前 buddy 二进制自带哪版」(随发布走),后者记「这个项目用的是哪版」(随项目走),数值常相等但含义不同,不合并成一个字段。
- 铺底活的**标题是幂等键**,固定就是「规范铺底 v{版本}」,**探测到什么写进正文、不拼进标题**——踩过:标题带上探测结论后,第一次铺底自己写出了某个文件,第二次探测结论一变标题跟着变,幂等失效、重跑多建一张活。

## 5 · 总览与健康

> 这一章的正本原文在 [`../archive/v4-prototype/design/08-overview-derivation.md`](../archive/v4-prototype/design/08-overview-derivation.md)。

### 5.1 一列横块,只呈现信息

**总览一个数都不存。** 指标定义读指标文件,读数读读数文件,发版记录读发版文件,其余现场算;没数据就是灰。

屏上从上到下:

| 顺序 | 块 | 点灯吗 | 数据来源 | 刷新时机 |
|---|---|---|---|---|
| 1 | **项目信息 + 健康面板** | 健康灯点,名片本身不点 | 项目名片文件 + 名片文件里的项目群段 + 现算的健康 | 每次打开现读现算 |
| 2 | **北极星**(1 张宽卡) | 是 | 指标定义 + 读数 | 每次打开现读 |
| 3 | **本周计划进度** | 否 | 周计划文件(正本)+ 活缓存(离线快速渲染) | 每次打开现读 |
| 4 | **滞后指标**(≤3,横排) | 是 | 同北极星 | 同上 |
| 5 | **引领指标**(≤3,横排) | 是 | 同上 | 同上 |
| 6 | **项目指标 · 代码仓级** | 否(只是现状数) | 现跑 git 与远端 | **只在人点「立即采集」时采** |
| 7 | **在研版本与发版记录** | 否 | 项目名片文件里的在研版本 + 发版记录文件 | 每次打开现读 |

**头三块连起来读是一条线**:这项目是什么 → 顶层目标是什么 → 这周在往那个目标上推什么。指标那两层是展开看的细节,所以让到后面。

**老项目没有额外的块**——回填出来的历史发版行就混在第 7 块里(带「回填」小字),历史周在计划屏左栏,总览与计划屏都不写老项目专用代码。**新项目什么都不缺,老项目也不留一个永远空着的坑。**

每张指标卡上有:目标、现值、保鲜期、趋势、**本周哪些活在推它**、手填徽记。空态要区分两种「没有」:**还没定出来**(指标文件里一条都没有)显示「还没有引领 / 滞后指标 → 去运作活①补一个」;**定了但没测过**显示「—」加「无观测」。前者是正常状态,不是错误。

### 5.2 总览上能点的几处

**待人处理不在总览**——合入、点完成这些动作在左栏的「通知」入口。总览这一屏能点的只有:

- **名片的「编辑」**:点保存不是直接写库,而是后台建一张轻量活、开分支写名片文件、开 MR,横幅显示「修改已提 MR · 待合入」;人合入并点完成才生效,合入前旧值原样显示。
- **名片区的「↻ 拉到最新」**:把这个项目工作目录的主检出快进到远端最新。**为什么非要有这一颗**:buddy 只在「合入并完成」某张活的时候自动拉一次;人在网页上直接合了 MR,buddy 完全不知道,工作目录就一直停在旧提交——合进去的规范件在本机根本不存在,而界面照常显示旧内容,此前没有任何入口能补这一下(高保真里也没有这一格,是设计漏了)。只做**快进**这一种拉法:这颗按钮动的是人自己的工作目录,不该有任何需要人去解冲突的后果;拉不动(工作区脏、和远端岔开、没网)就把 git 的原话端出来,**绝不假装拉过了**。
- **代码仓级那块的「↻ 立即采集」**:那一块的数要起好几个 git 子进程加几次远端查询,不在每次打开时自动跑,点了才采。
- **「开始本周」横幅**:判据是**当前周的周计划文件在不在**(不是「周列表里有没有本周」——本周永远在列表里)。文件不在时出横幅,分两态:这周的运作活①还没建过 → 给「开始本周」按钮;已经在路上 → 不再给按钮,换成一句「已开工 · {状态}」加一条去会话屏的路。**再点一次会被挡住,那不是错误,是幂等。**

### 5.3 健康怎么算

三条判据,全部现算,**库里不存灯**:

- **(a)** 本周有周目标(周计划文件存在且有目标)**且**本周真有 git 提交;
- **(b)** 本周或上周的记录里有真实的指标读数;
- **(c)** 上周有交付(有合入,或发版记录上周多了一行)。

判定顺序**先判红**:

- **红** = 任一业务指标越线,**或者**「git 读得动、而连着两周一条提交都没有」——真的停了;
- **绿** = (a)(b)(c) 三条都真;
- **灰** = 三条都不成立、又没有「确实停了」的证据——就是没数据;
- **黄** = 其余(缺其中一两条)。

**两处特别说明**:

1. **「git 读不读得动」是一条独立输入,不是「零提交」的同义词。** 没配工作区、目录不是 git 仓、机器上没装 git,这一条就是假;此时「两周零提交」这句话本身没有意义,不能拿去判红。没数据的项目显示的是**灰**,不是红,也不是绿。
2. **判定必须是纯函数**:输入采集(读文件、问 git)和判定颜色分两处,判定函数除输入之外没有任何隐藏状态——同样的输入永远同样的输出。这就是「杀进程重开,数字前后一致」这条铁律在总览的落点。

**手填的观测带「手填」徽记;回填的历史不参与健康推导**——历史周文件和标了回填的版本行只解释过去,不点灯。

### 5.4 代码仓级那一块

**它和业务指标分层,不点灯、不上卷进健康**——这是工程现状数,不是业务成效。形态是**一行小字 + 三条近四周走势**:一行小字给累计提交、跟踪的文件数、没提交的改动、文档篇数、首次提交日期、标签数,每一项标注从哪采的;三条走势是**每周提交**(本机 git)、**每周合入的 PR**(远端)、**未处理 issue**(远端,每周周末那一刻还开着几张),**一个数都不存**,现问 git 与远端。

**PR 只认远端这一个口径**(2026-08-21 试点拍板,原来还画一条本机的合并提交数)。同一件事摆两个口径,读的人分不清该信哪个:squash 合的 PR 在本机一个合并提交都没有,而本机 `git pull` 产生的合并提交又不对应任何 PR。**合没合入看远端,那个造不了假**——这和第 3 章 §3.5 那条「活干没干成看远端 MR 合没合入」是同一条。本机的合并提交数没有消失,它还在健康判据里当「上周有没有交付」用(§5.3 的 (c)):**健康是现算的、不该依赖网络**,远端连不上时健康该照常算得出来,而走势图本来就是「点了才采」的那一块。

**前两条是流量,第三条是存量**,放在一排的理由是互补:提交和合入告诉你这周推了多少,未处理 issue 告诉你欠的有没有被推下去。第三条同样满足第 10 章 §10.1 那条「历史还能不能重新算出来」——某周末还开着几张 = 到那一刻建过的减去到那一刻关掉的,拿同一份流水换个时刻就算得出来,不需要谁提前存。

**远端那两条一趟拉全、本地按周分桶,不按周去查**:按周查画四周就发四次、画八周就八次,而且真机上撞到过搜索接口直接断连(`Get https://api.github.com/search/issues…: EOF`),四条线里断一条;何况「未处理 issue」这种存量值,本来就得拿全量流水才算得出来。一趟拉回来的条数顶到上限(1000)时**整条线不画并说明原因**,不端一个少算的数出去。

**采不到的点断开,不补前值**——补了就分不出「没变」和「没数」。

**只在人点「立即采集」时采**,打开总览不自动跑:采一次要在项目仓里跑好几条 git 再加一次远端往返,那不该在每次进项目、每次重绘时发生。

### 5.5 失败如实

| 场景 | 显示 |
|---|---|
| 项目名片缺某一段 | 「章程不完整」+ 具体缺哪一段 |
| 名片文件解析失败(格式错、未知字段) | 名片区整体灰 + 解析错误原文,**不猜、不用旧缓存顶上** |
| 指标文件解析失败 | 三块指标整体灰 + 同样的错误原文 |
| 周计划文件解析失败 | 本周进度块整体灰,**不假装进度是 0** |
| 代码仓级的 git 子进程失败 | 整块显示「无法读取仓统计:{git 原话}」,不是空白也不是假数据 |
| 健康计算中途出错 | 大灯直接灰 + 「health 计算失败:{错误}」,**绝不吞掉错误凑一个颜色** |

### 5.6 工程落点

界面在 `crates/app-shell/src/screens/overview/`;输入采集在 `crates/bw-v4/src/app/health.rs`(只读不判断),唯一判定颜色的纯函数在 `crates/bw-v4/src/derive/`(密封类型,store 层没有任何设置信号的方法);走势现算在 `crates/bw-v4/src/trend.rs`。项目表上的两个信号列只服务项目墙的显示缓存,总览自己从不读它们当输入,只在算完一次之后顺手写回。

**已知留白**:「指标越线」这条输入目前恒为假——指标目标的比对还没接,所以灯今天只会因为「两周零提交」变红,不会因为读数难看变红。这是留白,不是 bug。

## 6 · 计划与周循环

> 这一章的正本原文在 [`../archive/v4-prototype/design/06-plan-screen.md`](../archive/v4-prototype/design/06-plan-screen.md)。

### 6.1 一个界面装下「这周干什么」和六列看板

- **左栏**:窄周列表——最上面「全部」,往下按时间倒序(本周置顶),最下面是在研版本下拉。
- **中栏**:选中一周时,顶上一条**周头**(周目标一句、按状态分段的进度条、三张运作活各一个状态点、「新建活」「发版本」「预览·未合入」),下面是**六列看板**。选「全部」时周头换成筛选条(类别 / 版本 / 来源 / 状态 / 关键字)。
- **右栏**:点卡片标题滑出活详情。

### 6.2 周怎么算

**周用 ISO 周文本**表示(形如 `2026-W34`,周一为起点),按机器本地时区判定「现在是哪一周」。存文本不存时间戳:①直接对应周计划文件名,免去格式转换;②避免「周边界算哪个时区」的歧义。

**周列表没有索引表,现算**:扫周计划目录得到的周,并上活缓存里出现过的周(哪怕这周还没有正式文件,比如刚被拖进一个新周),取并集去重。**本周永远置顶**,哪怕它还没有文件、也没有活——空的本周才有地方触发「开始本周」。

**周头的每个数都是现读仓文件**:周目标现读周计划文件的「周目标」段;进度条按周匹配到的活分组计数(查缓存);三张运作活的状态点查本周的运作活;发版默认版本号现读项目名片文件里的在研版本(**这个值不在库里**)。

### 6.3 六列看板

六列就是活的六个真实状态:**待办池**(未排进任何一周)、**待办**(已排进本周,等开工)、**进行中**(agent 在干)、**评审中**(MR 开着,等人审)、**已完成**(人点过完成)、**阻塞**(填了原因)。**列头下一行小字把定义写出来,不让人猜。**

第七个状态「已取消」不占列(那是被丢掉的活,不是要从这里管理的状态),但在「全部」视角的筛选条里能单独看到。

**待办池不按选中周过滤——这是设计决定**:待办池的定义就是「没排进任何一周」,按周过滤的结果永远是空集。这一列存在的意义就是给一个跨周、随时能看见「有哪些活没排期」的地方。**其余五列只显示这一周的活**——包括已经推进到进行中 / 评审中 / 已完成 / 阻塞的,只要当初排的是这一周就一直留在这周的看板里,能看出「这周排的活走到哪一步」。

**卡面不摆按钮**——标题整行不省略,顶行是活号和类别标签加来源徽记,再挂一两个小标签(开工工具、推动的指标、和默认不同的 workflow)。动作全部收进拖拽的确认弹窗和右侧详情面板。

### 6.4 拖拽:六列全都能拖

用户拍板过:**拖动要统一,都能拖;动作性的拖完弹窗二次确认;卡面更清爽。**

- **排期动作**(待办池 ⇄ 待办、列内调先后):松手**直接生效**,不改任何状态。
- **状态动作**(拖到进行中 / 评审中 / 已完成 / 阻塞):松手**先弹一个确认框**,确认才真的发生——拖到进行中 = ▶开工(框里显示开工工具与 workflow,可改;确认才真起 agent 会话,这不是免费动作);拖到评审中 = 推到评审中;拖到已完成 = ✓完成(**仍是铁律里「人显式点」的那一下,只是点在弹窗上**,而且只有评审中的活能被拖进这一列);拖到阻塞 = 填原因,**必填**。
- **不合法的转移**(比如待办池直接拖到已完成):松手**即弹回原位并提示原因**,不静默失败、不出现确认框。
- **状态永远只经同一套合法转移判断**:无论走确认框还是详情面板按钮,发出的都是同一批命令,判分依据只有一个——拖拽只是给已有状态机多了一个触发入口,不新开一条判断逻辑。
- **取消确认框**:不发任何命令,卡片弹回原位,和什么都没发生一样。

### 6.5 排期落到三个地方

1. **缓存层(立即)**:命令一发出先更新活缓存的周与顺序两列,界面马上跟手。
2. **文件层(同步,原地换表)**:紧接着把目标周计划文件里「业务活」「本周运作」两节的**表格原地换掉**,文件里人自己写的周目标、风险记录、自定义小节一个字不动。**这一步是同步直接写工作区文件**,不建活、不开分支、不开 MR——拖拽落定的那一刻文件已经是新内容,所以界面上也没有「排期待合入」这种中间态要提示。**这是一处已知的欠账**:规矩①说「凡写仓都是活 + MR」,排期是今天还没走上这条路的三处之一(另两处是改名片、发版本),登记在 `docs/LEFTOVERS.md`。
3. **远端标签(镜像,尽力而为)**:给活对应的远端 issue 打一个周标签,让不开 buddy 的人在平台上也看得出排期。**今天一行没做**,设计保留。

**顺序用浮点数**做插入排序——新卡片插进两张卡之间取中间值,不必整列重排;精度用尽后需要一次性重新铺号,再平衡算法留到实现阶段。

### 6.6 发版本:一个按钮,一次点击直接生效

不是三步向导:

- **没有选活步骤**——自动取当前看板「已完成」列的全部卡。
- **没有版本号输入框**——从在研版本按「主.次」递增算出下一个,人不填也改不了。
- **说明写死**——固定一句「本周完成的活」。
- **没有活、没有分支、没有 PR**——直接往发版记录文件追加一行,**成功写进文件之后才把这些活的版本号回填上去**。顺序不能反:否则重复点一个已经存在的版本号会把活打上标签、发版记录里却没有这一次,账就对不上。

**两条护栏**:①版本号认不出「数字.数字」格式(最常见的是还没设过在研版本)时按钮置灰,内核也拒收——不给发版记录写进一行叫「(待填)」的版本;②追加按版本号幂等,同一个版本号不会追加第二行,也就不会给活重复打标签。

**没有「合入才生效」这一步**——没有分支就没有合入,写文件的那一刻就是主干上的内容。

### 6.7 预览未合入

运作活的 MR 合入之前,人想先看看效果:当前周有一张运作活还停在评审中、MR 没合时,「预览 · 未合入」开关能点开——buddy 从**那张活自己的工作目录**读指标文件和周计划文件,用同一套解析代码重渲染周头,顶部横幅写明「预览 · 未合入」。**纯粹换个目录读文件**,没有副作用,关掉立刻恢复。

指标现值跟不跟着切,按第 10 章的分类走:**可回溯的那类不受影响**(它现算,打在主干上);**不可回溯与手填的那类**,预览时额外展示这份草稿即将追加的新读数,和主干上现有的读数**并排标注来源、不互相覆盖**——这正是评审运作活 MR 时最该看的东西之一。

### 6.8 右侧活详情

标题、说明、类别、开工工具、workflow、推动的指标、周、版本、来源、远端号、会话记录、产物。**来源只读**(历史事实不允许事后改),产物现算(`git log --name-only`)。会话记录里**不展示逐次运行的成败与耗时**——V4 没有那张表了,一轮跑成没成看远端 MR 合没合入。

**拖拽统一之后,详情面板是所有按钮语义唯一常驻的落脚点**:▶开工 / ■停止 / ⬇合入 / ✓点完成 / ⛔阻塞原样摆在这里,和拖拽 + 确认弹窗是同一批命令的两条触发路径。重开一张已完成的活(返工)放在这里、要一次确认,不放卡片一键——密集卡片容易手滑。

### 6.9 工程落点

界面在 `crates/app-shell/src/screens/plan/`,用例在 `crates/bw-v4/src/app/plan.rs`。命令:排进/移出某周是同一条(参数为空 = 移回待办池)、列内调先后、发版、切在研版本、开关预览、给活换 workflow。**没有周计划索引表、没有发版表**——周列表扫目录,发版记录只认那份仓文件。

**Windows 上必须关掉窗口框架自带的文件拖放处理器**,否则 WebView 会屏蔽页面内拖放;macOS 侧的页面内拖放**还没有真机验证过一次**,如实标注。

**两处已知未做**:给活挂指标的命令没有接进来(建活时这一列恒为空);切在研版本要不要建活走 MR,母文档把它归成「纯本机动作」,但在研版本只存在仓文件里——这处张力没消解,留给人拍。

## 7 · 会话与执行:活怎么被真干起来

> 这一章的正本原文在 [`../archive/v4-prototype/design/05-session-screen.md`](../archive/v4-prototype/design/05-session-screen.md) 与 [`../archive/v4-prototype/design/04-tools-and-workflows.md`](../archive/v4-prototype/design/04-tools-and-workflows.md)。

### 7.1 三栏

- **左列**:会话按目录分组。最上面永远有一行「仓根 · main」,是一个常驻的**纯 shell 会话**——不跑 agent、不注入提示词,就是主工作区里的普通终端,给人手动敲命令用,不用自己另开一个终端窗口。往下每一件正在进行或刚推到评审的活各占一组,组名是这件活的工作目录名加分支名,行上有活标题、状态点、最近一次动静的时间。
- **中栏**:标签页。默认是**终端**(这件活正在跑或跑过的交互式对话,内容和真终端一样能选中复制);从右栏点开的文件是只读视图;点改动文件开单文件 diff;原型类活多一个内嵌 Open Design 标签。
- **右栏**:这个工作目录的代码结构侧栏——可展开的文件树(点文件即在中栏打开)、改动文件清单(点一行即开 diff)、一小块 git 状态(分支名、领先/落后主干几个提交)、开了 MR 就有一张 MR 卡。
- **顶部一行**:活标题、状态、动作条。

**一件活最多一个 agent 会话**——这不是新规则,是会话表上「一活一行」这条已有约束的直接结果。「+ 新会话」开的是同一个工作目录下**再加一个纯 shell**(用途是人想在 agent 跑着的同时手动跑一次测试),不是给这件活开第二个 agent。

**右栏四类数据全部现算**:文件树懒加载(点开哪层读哪层,跳过 `.git` / `target` / `node_modules`);改动文件用 `git status --porcelain`(提没提交都算);单文件 diff 把暂存和未暂存两段拼起来,没跟踪的文件退回全文并标一行,不给人看空白;分支状态问不出来就显示「—」,**不显示 0**(0 会被读成「和主干一样」)。

### 7.2 顶部动作条:干完了怎么交出去

动作是:**▶开工 / ■停止 / 提交并开 MR / 只推到评审 / 蒸馏**。

agent 是在这张活自己的工作目录里改的文件,那棵树和它的分支在别人那儿是看不见的。**「提交并开 MR」就是把它变成可评审的东西**:把树里的改动提交掉(agent 自己已经提交过的就跳过)→ 推分支 → 开 MR → 活进「评审中」。三条守则:

- **由人点,而且最远只到「评审中」。** agent 什么时候算干完只有人知道;「完成」还得评审完再点一次。**没有任何东西会自动开 MR。**
- **没干出东西就如实弹回。** 判据是这棵树比主检出多几个提交,不是「有没有文件动过」;0 个就直接拒绝,活留在原地,不留分支、不留 MR 号。
- **每一条不做的理由都说出来。** 没挂远端、推分支失败、开 MR 失败,都写进回执;界面上绝不出现一个来历不明的空 MR 号,失败也不假装进了评审,可以重试。

「只推到评审」是**纯状态动作**,不碰仓——留给「改动不在这棵树里」或「远端还没挂上」的情况。

**■停止只关终端,状态原地不动**——停下来既不是失败也不是完成。

### 7.3 开工工具怎么注册

开工工具的声明住在项目仓的活的约定文件里,每个工具一段,三个字段:

- **接法类型**只有两类:**终端类**(真实的伪终端子进程:Claude CLI、Cursor)与**本机网页内嵌类**(探活拿到本机地址后嵌一个网页视图:Open Design)。将来接别的 agent 网页也走后者。
- **探活方式**对照三套已有的真实机制:按序试候选路径(第一个真实存在的文件赢)、跑一条版本命令、握手一个本机套接字。
- **能力清单**把散在代码里的判断声明化:能不能注入技能、能不能续接会话、能不能靠官方回调主动回报状态。**不支持的能力如实留空数组。**

**新增一个开工工具**:仓里的声明加一段 + 新壳里加一个适配模块目录;终端类要真支持时再加一份工具配置。**不需要碰命令与事件**——路由读的是声明,不是硬编码分支。

**探活如实**:未装就是灰,不是隐藏、不是假装能点。灰底加一句「未装 · 怎么装 →」,跳项目墙那个指南抽屉的对应章节。

### 7.4 workflow 是什么,怎么识别

**workflow = SOP 类的技能包**(与旧的聊天式「工作流」引擎完全无关,只是同名):入口是一份技能文件,里面写的是一整套做事流程,**流程里该用哪个 agent 由这个包自己调度**。实读两个真实包核实过:它们是在入口文件的正文里现场让模型起内置子代理,**没有**自带一份持久的 agent 人设文件。**单个技能**只做一件事,不是流程。

所以 buddy **不再维护 agent 名单**,配置里也没有 agent 表;战绩这件事的主体也随之改变——见 §7.6。

**识别规则,现场判、不建登记表**:扫技能目录,每个顶层目录套一次判据——顶层有插件清单文件,或者子目录下有两个以上独立技能,就是一个包(workflow);都不满足就是单技能。包内再找「入口技能」(被标为不让模型自动调用、且正文引用了其它技能名的那一份),猜不出就显示「未标注」,**不提供持久的人工覆盖**——这份猜测只在配置屏渲染那一次用一次,不值得为它开一个可写的存储位。「自带 agent 数」照样现数目录里的文件数,两个真实样本都是 0,**如实显示 0,不瞎猜**。

判据判出来的不是「账」,是**结构事实**;结构事实永远能从文件重新读出来,不需要另开一张表缓存一个可以重算的结论。

### 7.5 技能怎么到 agent 手里

**两批东西,两个地方,不要混**:

| | buddy 自带的十一份 | 项目自己的 |
|---|---|---|
| 有哪些 | 七份方法论技能 + 四份运作剧本(`standard/skills/`) | 蒸馏产出、人手加的、导入的 |
| 正本在哪 | 编在 buddy 二进制里,开工前展开到 buddy 自己的资产目录 | 项目仓 `.claude/skills/` |
| 进用户的版本控制吗 | **不进** | 进,随 MR 可见 |
| 每个项目一份吗 | 不,全局一份 | 是,各是各的 |
| agent 怎么拿到 | 系统提示词给名字加路径 + 把资产目录声明给 CLI | CLI 在仓里原生发现 |

**为什么 buddy 自带的不复制进用户仓**:一次真实接入当场证伪了旧方案——buddy 自己的仓把 `.claude/` 写进了 `.gitignore`,复制进去的十几份技能**一个都没进第一个 MR**,而界面上还显示铺好了。用户仓怎么写 `.gitignore` 不该由 buddy 决定;何况每个项目复制一份 buddy 自带的东西本来就没道理。当时撑着旧方案的那句「CLI 只在项目仓里找技能,不复制进来就读不到」**已被证伪**:给绝对路径加一个「多读一个目录」的开关一样读得到。

**开工时那份系统提示词一共四段**:①身份与这张活(你是谁、活号标题、类别、挂的 workflow);②铁律(最远到「评审中」;合并永远是人;指标读数只能来自真实采集;干砸了如实停);③规范索引(`.bw/` 下**这个仓里真有**的那几份,一份一行「路径 —— 一句话」);④本活的剧本(名字 + 一句话描述 + 完整路径)。

**规范索引只列真存在的文件**——铺底还没跑的项目一条都不列。**列一条不存在的路径,agent 读一次失败一次,比不列更糟。**

这就是渐进加载:提示词里放索引,正文按需读。实测数字堵死了另一条路——单个技能正文均值八千多字符,而注入护栏上限约六千字符,整包塞进提示词根本装不下。

### 7.6 用了几次:现算,不记战绩

盘点之后**「战绩」这个持久账本概念本身被取消**,不只是换一个记账主体:**「干没干成」不再由 buddy 自己判定和记账,看的是远端 MR 合没合入**,这条判据造不了假。所以库里不需要战绩表,不需要「结算」这类事件,也不需要在状态机的完成边或运行失败两处各挂一次记账动作。

**「用过几次」完全现算**:按活的 workflow 列分组计数,每次现查、不缓存汇总数。这条数字统计的是「挂了这个 workflow 的活有几张」,不是「成功了几次」——所以**建活那一刻就 +1,不等它走到评审中或完成**;反复推拖同一张活的状态,这个数字不该变化。

**不再显示胜率**——没有结算记录,胜率这一列直接不放,不是显示「暂无」占位:连「暂无」背后那套判定逻辑都不存在了。

**回填的活也会被计入用量**(历史上真跑过某个 workflow 的活,回填后一样该算);实际上回填进来的老活 workflow 列通常是空,天然被过滤掉,不需要一条专门的排除规则。

### 7.7 agent 状态:只显示真的

设计里有四态:运行中 / 等你输入 / 空闲 / 已推评审。数据来源**不是猜终端文字**,而是 Claude CLI 官方的生命周期回调打到本机一个回环端口上——这在 buddy 里不是新引进的能力,只是覆盖面不够(今天只收「会话开始」和「一轮说完」两种事件)。

**今天真实做到的只有两态**:进程在 = 运行中,不在 = 空闲。「等你输入」**不显示,不猜**。这和「没数据就是灰、绝不假装绿」是同一条精神。

**Cursor 没有这套回调机制,状态如实退化**:只显示「运行中」(进程活着)和「未知」,**绝不伪造「等你输入」这种细粒度状态**。

端口不新开——一个 buddy 进程一个监听端口,按工作目录路由到具体哪件活。

### 7.8 蒸馏

顶部「蒸馏」是活的附属动作:起一次真实的交互式会话,agent 把这件活的过程整理成一篇技能草稿,人确认名字 / 描述 / 正文,**直接产出到项目仓的技能目录**——**不再有落库这一步**。「记着来源活」这件事因此挪进产出的文件本身(写进文件头部)。这条链路 V1/V2 已用真实数据跑通,V4 只是把入口搬到会话屏顶部、去掉库那一步。**按钮今天还是灰的**,命令没接。

### 7.9 边界与失败

**不做**:同一件活多个 agent 会话(那种「一个需求分给五个 agent 各自比赛」的模式不在旅程里);符号级大纲(首版刻意延后,留了接口);终端录像回放(会话记录本来就是终端滚屏加会话文件本身)。

| 场景 | 怎么显示 |
|---|---|
| claude 未装 / 探不到 | 终端里直接看到原始报错,状态点保持「空闲」,**绝不误标「运行中」** |
| 首次进新目录的信任对话框挡住 | 如实显示终端画面(人手动按一下确认),**不做自动按键模拟** |
| 终端子进程死了 | 状态点变灰、状态词写「已停止」、带真实错误原文,人可重新开工 |
| 工作目录建不出来 | ▶开工 禁用,会话行显示「worktree 未就绪」加真实错误,**不生成假会话行** |
| Open Design 没起 | 标签显示「未探测到本机 Open Design,请先启动它」,不是空白页 |
| 活挂的 workflow 名字在技能目录里找不到 | 如实跳过、不猜、不错记到别的目录上,活照常能开工 |
| 选了 Cursor 但探活失败 | 开工前置校验直接拒绝报错,**不悄悄退回 Claude CLI**——静默换工具会让人以为在用一个工具、实际在用另一个 |

### 7.10 工程落点

界面在 `crates/app-shell/src/screens/session/`(只做布局与状态,不直接碰终端、不直接拼 git 命令行);内嵌终端在 `crates/app-shell/src/adapters/terminal_xterm/`;终端生命周期在 `crates/bw-v4/src/app/session.rs`;四个现算的 git 查询在 `crates/bw-v4/src/git.rs`。伪终端后端在 `crates/v4-engine/src/pty_backend.rs`,Windows 与 macOS/Linux 各一家,都验过能起子进程、能读回、能收尾、中止不留孤儿。

**终端字节流不走 ViewModel、也不走事件总线**——桥上单开一条通道,内核线程定时往里推。两条理由都是真会出事:终端一秒能吐几百批字节,每批都重拼一次 ViewModel 会把界面拖垮;而且字节是一次性的流,进了 ViewModel 每次重渲染都会被重新写进终端一遍。

**「点开一个文件」「展开一个目录」这类纯导航不做成命令**——它们不改任何数据,做成命令会让「命令 = 会改变什么」这条线变模糊;走桥自己的请求,只改壳这边的界面状态。

**没做的**:Cursor 适配、内嵌 Open Design 标签、蒸馏按钮、agent 四态回报、MR 卡上的「检查过没过」那一列、代码图接口。

## 8 · 运作活:buddy 自己的三张标准活

> 这一章的正本原文在 [`../archive/v4-prototype/design/09-ops-workflows.md`](../archive/v4-prototype/design/09-ops-workflows.md)。

**共同的体感**:agent 干活的过程始终看得见,人可以随时插话、随时点停;**但推进到「完成」永远是人自己点的那一下**,不管是不是自动建、自动开工。

### 8.1 运作活①「更新指标 + 制定本周计划」(人触发)

**入口**:总览横幅「开始本周」最顺手;计划屏、会话屏手动建一张也行,同一条命令。

**两条判据分管两件事**:

- **横幅出不出**——看当前周的周计划文件在不在;
- **会不会建出第二张活**——**按标题查**,不按「这周有没有活」查。按周查的话,人把这张卡拖回待办池就查不到了,而建活本身又是按标题幂等的,于是会拿回同一张活重新开工——那张活可能已经在评审中。查到同名活且不是已完成,就如实回一句「这周的运作活①已经在跑,状态是 X」。

**剧本四步**(技能 `week-planning`):

1. **复盘上周**——读上一周的周计划与发版记录;没有上一周文件就如实说明「首次制定周计划,无历史可复盘」,不假装有数据;只读不改。
2. **更新指标**——调用子技能 `metrics-refresh`:补缺的引领 / 滞后指标、给绑不上的找最便宜的采集路径、跑一次采集。**绝不伪造观测、绝不为了点亮改指标定义。** 每撞到一条手填指标都要认真问一次「这个数能不能写成脚本」(第 10 章 §10.6)。
3. **引导出本周**——结合指标现状、代码现状、上周记录(配了群的话还有上周群消息摘要),和人在终端里交流出**周目标一句 + 业务活草稿**(每张带标题、说明、类别、预期推动的指标、建议工具与 workflow)。**不许自己下结论**:写完草稿必须停下,等人明确确认才能进第四步。
4. **落文件(需人确认后才能做)**——写指标文件、写本周计划文件、写指标说明;正常提交、开 MR,把 MR 地址打屏。**开 MR 允许,合入禁止。**

**人不「写」周目标,人在首尾**:触发与确认。周目标是在会话里由技能引导、结合代码与上周记录交流出来的,界面只呈现。

**周计划文件谁写**:真跑时,点「开始本周」这一下**一个文件都不写**——周计划文件由这次会话在活自己的工作目录里产出、走 MR、人合入后才落进主检出。**仓是正本,合入才算数。** 早先会先往主检出写一份骨架,那会留下一个没进版本控制的同名文件:MR 合入后拉取被它顶住,而总览一直显示骨架里的演示目标。用替身跑(没有真会话可以产文件)时,骨架加草稿就是这条路的全部产出,**处处自我标注**,不冒充真实对话的结论。

**时长(估计)**:约 20-40 分钟,人机对话 3-6 轮;第一次跑(指标从零起草)明显更长。

### 8.2 运作活②「资产盘点」(定时;首次模式 = 老项目历史回填)

**一个包两种模式**,读一个模式参数:**每周模式**(默认,定时触发)只盘这一周的变化;**首次模式**(接入老项目时触发一次)全量回填历史。两种模式共用同一份入口剧本,第一步先判模式,后续按模式分支——**不是两份文档、两条产线**。模式参数**不加命令字段**,写进这张活自己的说明里一句结构化文字,复用「活的说明进初始提示」这条既有机制。

**触发与判据**(每周模式):默认每周五 20:00(可改),到点自动建活并**自动开工**——三张运作活里唯一不需要人点一下才开工的一张。**判据是「本周有没有一张这样的活」**,查活表这一行在不在,不查什么「上次触发过没有」的状态表。前提是 buddy 当时在运行;错过不需要额外补建逻辑——同一条判据在下次启动的第一次心跳时天然成立,自动补建。

**每周模式的剧本**:

- **盘点仓内全部资产**(不只代码):周计划与发版记录齐不齐;新增文档、产物、技能与 workflow 有没有登记;规范对账(缺 / 过期 / 人改过,只记录差异**不擅自升级**);指标数据新鲜度;代码图大文件榜。
- **可做可不做的代码微重构只列成建议活草稿,不动手**——死码、格式、命名、该拆的大文件,每条整理成一张草稿(类别「优化」),连同盘点报告一起进这次 MR 的说明,人周一评审时勾选,勾了才真建成活。需要动业务逻辑或公开接口的一律只写建议、连草稿都不生成。
- **不做「零调用者就当死码删」**——代码图对动态分发看不见,会误判;疑似未使用的只写进报告。
- **写盘点报告**追加进本周计划文件尾段。没有可重构的东西是正常结果,如实写「无」,**不硬造改动**。

**首次模式多一个提议:给这个项目写开发手册。** 子技能 `project-handbook`,三条要点:**先读**(仓根有没有人写的约定文件、README、构建文件、CI 配置、逐个顶层目录;空的 CI 目录不算);**再问**(把读出来的摊给人看,说清楚要动哪个文件,**人点头才写**;人说不要或说不确定都当不要——沉默不是同意;把「提过、人不要」写进回执,下次不再问);**才写**(每条命令真跑过一次才写进去;人写过的原文一字不删,只补缺的几节;buddy 自己的规矩一个字都不往里写)。

**这次会话很可能无人在场**——剧本里明说:不要假设有人立刻回应终端,**按「能做的先做、拿不准写进报告」推进,不要因为没人回应就等待或卡住流程**。

**时长(估计)**:每周模式约 10-25 分钟,人机对话通常 0 轮。

### 8.3 运作活③「规范铺底」:没有需要 agent 的步骤

铺底就一步:buddy 自己把核心件写进 `.bw/`,提交、开 MR、停在评审中。**不起 agent,不碰仓根。** 全部细节在第 4 章。探测到仓有历史时会另起一次资产盘点的首次模式,两次会话的改动合成同一个 MR。

### 8.4 停在评审中怎么保证

三张活走同一条通路:会话收尾 → 提交推分支开 MR(agent 自己已经开过 MR 的,遇到「已存在」诚实认领,不重复开)→ 官方回调的「一轮说完」事件触发一次轮询,探测到分支有开着的 MR 就推「评审中」。**这是「评审中」的唯一来源;「完成」仍须人手动点。** 自动开工与人工开工用同一条执行器和同一套状态机,没有特殊待遇。

### 8.5 失败如实

| 场景 | 表现 |
|---|---|
| 采集脚本失败 | 对应指标保持灰,原因写进指标说明 |
| 远端 issue 建失败 | 本地活照样建、标「未同步」,不阻塞其余 |
| 定时到点但工作区不可用 | 如实跳过不建活,不产生任何库记录;下次心跳用同一条判据重试,自然补建 |
| agent 中途断 | 活如实停在「进行中」(**不自动判失败**),可重试 |
| MR 开不出来 | 停在原状态,**不假装到了「评审中」** |

## 9 · 通知与项目群

> 这一章的正本原文在 [`../archive/v4-prototype/design/07-notify-and-chat-group.md`](../archive/v4-prototype/design/07-notify-and-chat-group.md)。

### 9.1 通知入口:上段待处理、下段事件流

Builder 平时不会主动点开通知——左栏入口的徽章和项目墙卡片上的旗标数会告诉他「有 N 件事等你」。

**上段「待处理」五类,判定全部是推导,没有一张待处理表**:每一行对应别处一个真实状态,状态变了这一行就自动消失,不需要「标记已读」这类动作。

| 类型 | 怎么判定 | 行内动作 |
|---|---|---|
| 评审中待合入 | 活在评审中、有 MR 号、远端 MR 仍开着 | **合入并完成** |
| 已合入待点完成 | 活在评审中、有 MR 号,但轮询发现该 MR 已被合并(别人在网页上合了,或另一台 buddy 合过) | **点完成**(直接结清,**不再调一次合入**) |
| 指标过期 | 某个指标声明了保鲜期,最近读数早于「现在 − 保鲜期」,或从未有过读数 | **去补数据** |
| 带险交棒 | 只追加的交接记录里最近一条标了「带险」 | 打开会话(纯只读跳转) |
| 名片修改待合入 | 编辑名片产生的轻量活停在评审中 | **合入并完成** |

**「带险交棒」的现状如实说明**:产生这类记录的动作,其界面入口在不随 V4 搬迁的旧阶段轴屏上。这一行大概率长期是空的——不是判定逻辑有问题,是产生数据的动作暂时没有入口。

**下段「事件流」六类**,纯时间线、倒序、可点跳转,**不参与待处理计数**——它记录的是「发生过什么」而不是「等你做什么」:agent 等你输入、定时活已建并开工、MR 检查失败、蒸馏完成、采集完成、已同步到项目群。

### 9.2 徽章怎么算:不建表

**徽章就是待处理条目的计数,不是「未读数」。** 待处理段本身没有「已读」这个中间态可言——一行要么还在待处理,要么处理完自动消失,不需要一张表记「谁看过哪一行」。

事件流是纯日志,同样不需要已读/未读的业务语义。但为了让人一眼看出「上次看过之后又发生了什么」,要记一个「这个项目的事件流我看到了哪个时间点」——**这个时间戳以键值对写进元信息表,不为它开第五张表**。晚于这个时间点的条目加粗或带一个小圆点,**完全不参与徽章计数**,丢了、清零都不影响任何业务状态。

### 9.3 「合入并完成」

这不是新机制,是把已有行为正式命名。流程与守卫一字不差:

① 已经结清了就幂等短路,提示「已完成,无需重复合入」,**不重复调远端、不重复记账**;② 必须是「评审中且有 MR 号」才继续,否则拒绝并提示改用「点完成」;③ 项目没挂远端就拒绝;④ 调远端合入——失败则「合入失败,活留在评审中:{错误原文}」,状态不变、可重试;⑤ 成功后走既有的「评审中 → 完成」记账路径;⑥ 配了群且勾了「已合入」就往群里发一条,**失败不回滚已经发生的合入与记账**。

**任何一步失败都停在那一步、如实显示**,不出现「合入成功但没记账」或「记了账但没真合入」这种中间态。

**「点完成」保留、不合并进来**:「已合入待点完成」和「没有 MR 的活」两种场景点的是裸的完成动作——这两种场景下再合一次要么会失败、要么根本没有 MR 可合,是浪费一次远端调用。两个按钮共享同一条完成记账尾巴,只是「要不要先合入」这一步有没有发生。

### 9.4 项目群:适配一个本来就存在的群

**buddy 只做两件事**:往群里发一条通知;定计划时拉一段群历史当参考。**不是发明一个新的协作面。**

**配置分两层**:

- **项目正本**在项目名片文件的 `[chat]` 段——提供方、群号、同步哪些事。**改它走「编辑项目信息」同一条轻量活 + MR 流程**,不给项目群开一条平行的配置通道。
- **本机只探活、不登录**:设置屏**不放**「聊天工具登录」这颗按钮——登录态不归 buddy 管,用户在本机用官方渠道自己登好(一次基本永久),buddy 不碰、不存这份凭证。buddy 只在项目墙「本机环境 · 测一下」里加一项探活。**群号是项目的事,登录是机器的事。**

**接口就两个函数 + 一个工厂**:发一条消息、拉一段历史(外加一个可选的「测一下这个群通不通」)。提供方分支只在工厂这一处,调用点只调方法。四个提供方位:内部 WeLink(**实现由同事补,buddy 侧只留接口和一份对接说明**)、未配置(两个函数都直接返回「没配」,让「没配群时别的流程不会崩」这件事可验证)、本机假群(内存态,给端到端验证与联调用)、外部待定(工厂留位,不预先选型、不预先写代码)。

**「这个提供方天生做不到拉历史」是正常返回值,不是异常**——核实过,好几家聊天工具的群机器人都是只发不读;调用方看到这个分支要安静跳过,不重试、不报错。

### 9.5 通知同步与群摘要

**默认同步三类事**:评审中、已合入、发版。**文案一行**:`【<事件>】#<活号> <活标题> · <MR 号与状态> · <谁该动> → <工作台深链>`。**不 @ 人**——buddy 不建成员,没有身份映射可 @。

**不做去重,发送即完成**:不写库、不记「尝试中 / 成功 / 失败」、不做幂等查重。**代价如实写**:极小概率下(比如进程在发送前后意外重启)同一事件可能被重复推送一条,用户已知情接受——「重发一条能忍」。

**失败如实,但不是「重试队列」**:发送失败不回滚已经发生的合入 / 完成 / 发版——群通知只是链路末尾一个「锦上添花、失败不影响主干」的旁支。失败当时在界面上如实提示一次,**没有持久状态支撑的自动重试**。想让消息重新发出去,只能等下一次同类事件自然发生——**这不是「重试同一条失败」,而是「下一次全新的一次尝试」**,如实说清楚这个区别,不假装有一套可靠的失败恢复机制。

**运作活①的群摘要**:拉「上周一 00:00 → 本周一 00:00」的群历史,按天分组、每条一行「时刻 昵称 文本」,去表情、图片用占位符、长度设上限。**住本机文件,不进仓不进库,用完可删。** 拿不到就安静跳过,agent 少一份参考而已。**只喂给运作活①这一张活**——资产盘点不论哪种模式都不读群历史,历史回填也不拿群消息当原料。**只做参考,不做数据点、不点灯。**

### 9.6 MVP 不做

双向对话机器人(群里 @buddy 发指令);群里点按钮改活状态(违反「完成永远人点」,不给群消息任何改状态的权力);一个项目多个群;除 WeLink 外任何一家的正式实现;通知屏自己的收件箱语义(标记已读、批量已读、归档)。

### 9.7 工程落点

`crates/bw-v4/src/chat/`:接口与工厂、未配置实现、假群实现(每发一条往标准错误打一行结构化日志当证据)、WeLink 留位(模块文档写清要实现什么、错误怎么带、登录态为什么不归 buddy 管)。同步用例在 `crates/bw-v4/src/app/chat_notify.rs`。壳里那份只有接口的占位已经删掉——真实现落地后留两份接口就是「为向后兼容留旧路径」。

**一个已知的能力缺口**:「已合入待点完成」与「MR 检查失败」都需要一个「查 MR 当前状态 / 检查结果」的查询,今天远端接口里没有。

## 10 · 指标采集与读数

> 这一章的正本原文在 [`../archive/v4-prototype/design/14-metrics-collection.md`](../archive/v4-prototype/design/14-metrics-collection.md)(2026-08-21 定稿)。**A 类那条已经落地了**(2026-08-21 试点第 2 站):脚本协议、窗口传参、三类判定、界面「采一次指标」都真能跑,读回见 §10.10。**B 类与手填那条还没落地** —— 只追加的读数流水与定时采集都没接,界面上如实说。
>
> **归档那份原文的字段名已经和实现对不上了**(它写的是 `window` / `run` 是一行 shell 命令 / `--grain` / `{"series":[{"at","v"}]}`),**照它写会写错**。字段级的正本见 §10.8。

### 10.1 核心判据:这条指标的历史,现在还能不能重新算出来

**整个设计只有这一条分水岭。** 不是按「用什么工具采」分类,而是问一句:

> 今天能采到这个数,那么「上周三那天的值」现在还能算出来吗?

| 类 | 判据 | 存不存 | 例子 |
|---|---|---|---|
| **A · 可回溯** | 能采今天,就能采过去任意一天/周 | **一个字都不存**。要看四周就现算四个窗口,要看八周就算八个 | git 提交数、合入数、PR 数、远端 issue 数 |
| **B · 不可回溯** | 过了那一刻就没了,历史再也采不到 | **必须落进仓库**。定时到点采一次,追加一行 | 外部系统只给「当前在线数」 |
| **C · 手填** | 压根没有采集路径 | 同 B,落进同一份文件,带手填标注 | 要人去某个后台看一眼才有的数 |

**这一条判据一立,三件事同时被解决**:①要存的东西降到最少,A 类天然难造假(数字每次重算,没有一个可以被改的中间值),这比「存下来然后保证没人改」强一个量级;②走势图不需要历史数据管道,新接入的项目**第一天就有四周走势**,不用先攒;③B 和 C 合流,它们的区别只是「谁去采」,落点、格式、进仓方式完全一样。

**判错的代价是可预期的**:把 A 误标成 B,白存一堆本可以现算的数;把 B 误标成 A,走势图上除了当前点之外全是空——**空,不是假数**。

**但判 B 之前必须先真的去找一遍有没有带时间戳的接口,这是一条动作要求,不是建议。** 试点第一天就判错过一次:agent 把「GitHub star 数」判成不可回溯,理由是「接口只给当前值」。实际上 stargazers 接口带一个特殊的 Accept 头就返回每个 star 的 `starred_at`,于是任意一天的存量都能倒推——它是 A 类。

```bash
gh api -H "Accept: application/vnd.github.star+json" repos/<owner>/<repo>/stargazers --jq '[.[].starred_at]'
```

判错的后果很实:一条本来能画出四周走势的指标,被画成只有一个孤点;而且它会顺着「B 类必须落读数流水」一路走到「那条路还没接」,把人堵在那里。**「看起来只有当前值」不等于「历史采不到」。**

### 10.2 采集方式只有两种

- **脚本**——buddy 起一个子进程,跑仓里的一个可执行文件,读它标准输出的 JSON。连 GitHub、连 codehub、连内网系统、读一个本地文件、算 git 历史,**全是脚本自己的事**;buddy 不认识这些系统,只认识「起进程、传窗口、读 JSON」。
- **手填**——没有采集路径,到点提醒人去填。

**没有第三种。** 尤其**不要**把「buddy 内建的 git 算子」做成第三种——那等于把算法藏进二进制,项目看不见、改不了、也说不清这个数怎么来的。git 类统计一样走脚本,只不过脚本由 buddy 铺一份现成的,**脚本本身就是「这个数怎么来的」的文档**。

**没有「连接器」这一层**——一条指标直接指向一个脚本。

### 10.3 窗口由 buddy 给,不是脚本自己决定

**buddy 起脚本时把要算的时间范围作为参数传进去**:可回溯的那类传起止日期和粒度,不可回溯的那类不传窗口、只问「现在是多少」。面板要四周就传四周,要八周就传八周,**采多少和画多少永远一致**。

这是和 V3 最关键的一处分歧。V3 把这个决定权留在脚本里(自带脚本硬编码 30 天),而面板按 8 周画,于是前三四周永远是空的,或者靠「补前值」连成一条骗人的直线,长期对不上还没人发现。

### 10.4 脚本协议

**输出只认标准输出的一个 JSON 对象,不是 JSON 就算这次采集失败。** 可回溯的返回一个序列(每项是时点和值),不可回溯的返回一个当下的值。值可以是数,也可以是给人看的字符串(百分比、比值、耗时),**原样保留、不在采集这一层解析**;要画走势时才解析,解析不出来的点跳过、不画、不猜。

**失败一律如实**:非零退出、超时、输出不是 JSON、缺字段——都记这条指标这次「没采到」,**绝不写一个 0 进去**。0 是一个真实的数值,「没采到」不是。失败原因原样端到界面上。

这一条同样是 V3 踩过的真实事故:V3 只读脚本写出的文件、不看标准输出,agent 写的脚本只打印到屏幕、输出字段留空,结果**每次采集都报「成功」,而指标永远没数**。

**buddy 铺的脚本,铺一次就归项目**——规范铺底时放几份现成的通用脚本,之后**再也不覆盖**;规范升级时按指纹比对,变了只提示差异、不动它。V3 每次采集前无条件覆盖自己铺的脚本,项目改了窗口或采法会被静默抹掉。

### 10.5 读数落在哪:和周计划彻底解耦

**可回溯的那类不落地**,没有落点这回事。**不可回溯与手填的落进一份只追加的读数流水文件**(`.bw/metrics/readings.jsonl`),一行一个观测点,带指标名、时点、值、来源、采集时间。

**为什么不用表格、也不用 TOML**:它和另外两份文件的读者不一样。指标**定义**是人要反复读写、还要写口径注释的,所以是 TOML;给人看的**快照**在周计划文件里,所以是表格。而读数是**机器一行一行往上追加**的流水:追加天然(不用解析整份文件再重写)、数值里带竖线或换行也不会把格式撑散、每一行自解释。人不直接读它,人读的是快照。

**落在哪个检出——固定分支 + 固定活(2026-08-21 拍板的简单方案,试点实践后再看)**。「攒在本地」不能是往主检出写:主检出里躺一个未提交的被跟踪文件,MR 一合入拉取就被它顶住——周计划骨架那次撞过的坑,同一类。所以机器**绝不写主检出**:

- 每个项目一条固定分支 `bw/metrics`、一棵常驻工作目录(`<仓名>-metrics`)、一张固定标题的运作活「指标读数」(标题幂等,和别的运作活同一套建活路径)。
- 定时到点:采 → 追加进那棵工作目录里的读数文件 → 提交 → 推送(有远端时)→ 没有开着的 MR 就开一个。**合入永远人点**;不合也不断旅程——**界面读数一律读那棵工作目录里的文件**,它是唯一写入点,天然最新。
- 手填:人在提醒活里填的值由 buddy 代写进同一条分支,人不碰 git。
- 两台 buddy 都开着开关时,第二台推送会被拒(非快进),**如实报「另一台已经在替这个项目采,建议关掉这台的开关」,不静默强推**。

**只追加,永不修改已有行。** 同一个指标同一个时点采到了不同的值,追加新行,读的时候取最后一条——历史上那次采到什么,永远查得到。这条和「观测只追加」那条产品铁律是同一件事,只不过 V4 的落点从库表换成了仓文件。

**周计划文件里那一段保留,但改性质**:它从「读数的正本」降级成「这一周的快照」,由运作活①收尾时从读数文件加现算结果生成一份抄进去,并注明是快照。保留的理由是一个真实需求:**让别人 clone 下这个仓就能看到数,不用装 buddy、不用跑脚本。**

### 10.6 手填怎么走到人面前

手填(以及连着采集失败)的指标不能只是灰在那儿——**得有人被叫住**:定时到点发现某条手填指标这个周期内还没有读数 → buddy **建一张活**(和资产盘点同一条路:自动建、不自动完成),标题写清是哪条指标、正文放提醒语 → 人可以直接在活里填掉,也可以点开工让 agent 帮着去查,查到了同样追加进读数文件,来源标脚本还是手填取决于它真的是怎么拿到的。

**目标是让手填这一类越来越少。** `metrics-refresh` 那份剧本里写死一条:每次跑到手填指标,都要认真问一次「这个数能不能写成脚本」——**agent 的价值是帮人把手填升级成可回溯,而不是每周替人抄一次数。**

### 10.7 什么时候采

| 时机 | 采什么 |
|---|---|
| 打开总览 | **不采**。原本设计成「可回溯的现算一次」,落地时改了:一次要起好几个采集脚本、每个还可能各自连远端,放在每次进项目、每次重绘的路上会把内核那条单线程按住(代码仓级那一块吃过同一个亏)。所以和它一样,**点了才采** |
| 人点「采一次指标」 | 三层全采一遍,结果放本机缓存(纯缓存,丢了重算即可) |
| 定时到点 | 不可回溯的采一次;手填的检查该不该建提醒活 |
| 运作活①开工时 | 不额外采——agent 读到的和总览显示的是同一份数据 |

**定时对所有纳管项目跑,不看你正在看哪个项目**(2026-08-21 拍板:定时要定时跑,除非主动关了)。**唯一的闸是项目级开关**:存本机(**不进仓——进仓就成了「每台 buddy 都要采」,正是要避免的重复触发**),**默认开**;关了这个项目的不可回溯采集和手填提醒活都停。配置屏的定时表加「指标采集」一行,带「立即执行」和「暂停 / 恢复」。这条同时取代了此前「定时只对打开着的项目跑」那个旧决定。

**缓存不做自动作废判据**(2026-08-21 拍板)。原本考虑过「仓的 HEAD 变了就作废」这类机制,取消了:**界面上本来就有「立即采集」,人知道自己刚合了东西,点一下就是了。为了省这一下点击去猜「什么时候该重算」,换来的是一套没人说得清什么时候生效的规则。** 缓存只管「同一屏反复重绘时别每次都起十几个子进程」这一件事。

### 10.8 指标定义文件的新格式

三处变化:①采集方式从五种收成两种(**退场的那三种从来没有实现过,留着只会让人以为写上就能采**);②新增一个字段表达「这条指标的历史现在还能不能重新算出来」,这是 §10.1 那条判据在文件里的落点,也是整个格式里最重要的一个字段;③原来那个「从一堆输出的大 JSON 里按路径取一个字段」的写法换成「指向哪个脚本」——一条指标一个脚本之后,路径就不需要了。

**字段契约(这一段是正本,别处不要再写第二份)**:

```toml
schema_version = 2          # 只认 2。读到别的值整份拒收,不半读、不迁移

[north_star]                # 北极星 1 个;滞后 [[lagging]] ≤3;引领 [[leading]] ≤3
name   = "..."              # 给人看的一句话
def    = "..."              # 口径:数什么、不数什么
target = "≥5"               # 迷你门槛;空 = 目标未设
collect = { kind = "script", run = ["python3", ".bw/scripts/x.py"], retro = true }
#            ^^^^ 只有 "script" 和 "manual" 两种
#                                 ^^^ argv 数组,不走 shell;路径相对仓根
#                                     写成数组是为了在 Windows 上能明确指定解释器
#                                                              ^^^^^ §10.1 那条判据
```

**类别由两个字段推出来**:`script` + `retro = true` → A 类可回溯;`script` + `retro = false` → B 类不可回溯;其余(含 `kind` 为空)→ C 类手填。**`kind` 写了 `script` 但 `run` 是空的,那是一条写了一半的定义**,界面如实说,不当成手填。

**脚本协议**:buddy 给 A 类追加 `--since YYYY-MM-DD --until YYYY-MM-DD --granularity week`(左闭右开,本机时区),B 类不传窗口;脚本往标准输出打一个 JSON 对象——A 类 `{"points":[{"week":"2026-W34","value":12}]}`,B 类 `{"value":12}`;`value` 是数或给人看的字符串,**原样保留**。

**这份契约有第二个到达点,是有意的**:跑运作活①的 agent 在**用户的项目仓**里干活,读不到 buddy 仓的这份设计文档。所以铺进项目的 `.bw/metrics.toml` 顶部注释里也写着同一份字段说明——它不是复制品,是**这份契约面向 agent 的那一端**。改字段名要两处一起改;正本模板在 `standard/04-metrics/metrics.toml.tmpl`。

**格式版本号跳一档,不写迁移**:试点期只有一个真实项目,重新定一次指标比写迁移便宜;而且那几条老指标本来就要重定(它们的采集方式从没实现过)。读到旧格式就报「这份指标文件是旧格式,运作活①会带你重定一遍」,**不猜、不半读**。

### 10.9 失败如实

| 场景 | 显示 |
|---|---|
| 指标定义文件解析失败 | 三块指标整体灰 + 解析错误原文,不用旧值顶上 |
| 读到旧格式 | 「这份指标文件是旧格式,运作活①会带你重定一遍」 |
| 脚本非零退出 / 超时 / 输出不是 JSON | 这条指标这次没采到,卡片显示上一次的值 + 「最近一次采集失败:{原话}」;**不写 0** |
| 脚本返回的序列缺某几周 | 那几周在走势图上**断开**,不补前值 |
| 声明了可回溯但脚本不认时间窗口参数 | 和采集失败同等对待,并提示「这个脚本可能不支持时间窗口,检查标对了没有」 |
| 读数文件解析失败 | 不可回溯与手填的读数整体不显示 + 报错原文;可回溯的不受影响(它不读这个文件) |

### 10.10 落地到哪一步了(2026-08-21 试点第 2 站)

| 这一章的哪一条 | 落地了吗 |
|---|---|
| §10.1 三类判据 | **是**。`repo/metrics_file.rs::MetricClass`,由 `kind` + `retro` 推出来 |
| §10.2 采集方式只有脚本与手填 | **是**。旧格式(五种)整份拒收 |
| §10.3 窗口由 buddy 传 | **是**。`app/collect.rs` 按面板要几周就传几周 |
| §10.4 只认标准输出的 JSON | **是**。非零退出、超时、不是 JSON、周号对不上,一律记「没采到」并把原话端到卡片上,**绝不写 0** |
| §10.5 读数落只追加的流水 | **否**。B 类今天在界面上如实说「这条路还没接上」,不假装采过、也不悄悄当成手填 |
| §10.6 手填走到人面前 | **否**。定时建提醒活没做;`metrics-refresh` 剧本里那条「每次都问一遍能不能写成脚本」已经写死了 |
| §10.7 什么时候采 | **部分**。人点「采一次指标」通;定时那条随 §10.5 一起没做 |

**读回**(不碰本机库、不碰 claude):

```bash
cargo run -p bw-v4 --example metrics_smoke -- <仓路径> [周数]
```

它先把定义原样摊一遍(每条标着 A/B/C),再真采一遍,最后打印每条自己复算的命令。**手填不采、B 类如实说没接、A 类出真数** —— 三类各走各的路,一眼看得出来。

### 10.11 边界与工程落点

**不做**:指标的「目标达成度」自动打分(目标只用来判红黄绿,不做加权评分);跨项目的指标对比或排行;替项目写业务采集脚本(buddy 只铺通用的那几份);采集失败的自动重试(失败就是失败,下一个周期再采,连着失败要在卡片上看得见)。

模块落点:新的指标定义解析器落在 `crates/bw-v4/src/repo/metrics_file.rs`(**不动 V3 那份**——V3 还在用它,而 V4 的新格式和它已经不是一回事),读数流水解析器还没建;起脚本、传窗口、读输出与可回溯的现算落在 `crates/bw-v4/src/app/collect.rs`;界面「采一次指标」走桥上那一对 `CollectMetrics` / `MetricsCollected`,和代码仓级那一采同一个做法(派出去跑,不占内核那条单线程);定时检查随 §10.5 一起还没做;走势图的几何函数直接搬 V3 那两个纯函数(x 轴按点均分、y 轴不从 0 起、全平序列不贴边、**空数据整块不画显示「尚无观测」**),**但它上游那个「按周分桶 + 空周补前值」的函数不要搬**——补前值会把「这周没采到」画成一条和上周一样高的直线,读的人分不出「没变」和「没数」。

## 11 · 知识库

> 这一章的正本原文在 [`../archive/v4-prototype/design/11-knowledge-base.md`](../archive/v4-prototype/design/11-knowledge-base.md)。

**三个页签一张登记表都不读**:现扫仓内文档、现跑代码图、现读 git 与发版记录。顶部一条横幅贯穿三页签:「规范 v{版本} · 对账 缺 N / 过期 N / 你改过 N · 看差异 · 升级」,数字来自第 4 章 §4.5 的对账,不是装饰。

- **知识**:不是扫全仓,是**按规范大类固定分组、每组按约定路径找文件**——项目名片、规范件、周计划(倒序)、发版记录、决策记录、设计产物。**懒加载**:打开页签只拿清单,点了才现读那一个文件。**只读渲染,没有编辑按钮**——改内容一律走活 + MR(改名片走总览「编辑」、改本周计划走计划屏或运作活①、升级规范文件走顶部横幅的「升级」)。**老项目回填的历史周不是单独一组**,和人写的本周文件同目录同格式,靠文件头和一个小徽记区分,不是两套渲染逻辑。
- **代码图**:本机装了代码图工具就现跑,没装就整块置灰并给一句怎么装;装了但这个仓没建过索引,提示先建索引。**首版只做了大文件榜**;符号搜索与模块依赖概览没做——后者连有没有稳定的结构化输出都还没核实过,**不猜一个解析格式**。**不做「零调用者 = 死代码」判定**:实测动态分发会让调用方查询漏边,只如实展示原始数字。
- **资产**:五个区块——项目自有技能、蒸馏技能(带「来源活」链接,链接目标解析自文件内容,不是关联表查询)、workflow(**没有胜率这一列**)、产物登记(`git log --name-only` 就是登记)、发版记录,最下一条仓统计小字(和总览那块同一次调用逻辑,不额外起子进程)。

**代码图与资产这两个页签不跟着每次重拼界面数据跑**——它们加起来要起好几个子进程,人在别的屏点一下就把它们跑一遍是不能接受的,所以只在**点页签或点「重新跑一次」那一刻**跑。这不违背「不缓存」的取舍——每次点开都是全新的子进程调用,只是不替人自动重跑。

**工程落点**:界面在 `crates/app-shell/src/screens/kb/`,数据拼装在桥的一个模块里(这三个页签全是现扫文件、现跑子进程,没有一句业务判断);代码图子进程封装在 `crates/app-shell/src/adapters/codegraph/`。有一个专用的读回口子:启动时带一个环境变量,把三个页签的数字打进标准错误——**截图对不了数,这个能。**

## 12 · 架构:三个 crate,怎么防止散弹

> 这一章的正本原文在 [`../archive/v4-prototype/design/01-architecture.md`](../archive/v4-prototype/design/01-architecture.md)、[`../archive/v4-prototype/design/12-build-plan.md`](../archive/v4-prototype/design/12-build-plan.md) 与 [`../archive/v4-prototype/design/13-shell-hifi-gap.md`](../archive/v4-prototype/design/13-shell-hifi-gap.md)。

### 12.1 V4 的三个 crate

```
crates/bw-v4       V4 内核:四张表的本机库 + 仓文件解析 + 现算推导
                   + 自己的一对命令/事件 + 规范铺底 + 三张运作活 + 项目群工厂
crates/v4-engine   V4 的能力底座:交互式 claude 执行器、伪终端内嵌终端、
                   工作目录供给、git 读数、GitHub / codehub 两个远端
crates/app-shell   V4 新壳:九屏 + 主题 + 内核桥 + 适配模块(bin 名 bw-v4-dev)
```

**V4 对 V3 的六个 crate 零依赖。** 这不是洁癖:用户拍板「V3 那一整个目录最终会被整体删掉」,所以 V4 不能有任何一条依赖指向那边——包括「只依赖 V3 的能力层」这种看起来很轻的耦合,因为**它自己还依赖 V3 内核**,V4 会顺着传递过去;而改 V3 的能力层又会动到还在跑的 V3。

所以 2026-08-21 把能力层**拷过来接管**(不是复用),同时做了三件减法:①**断掉对 V3 内核的依赖**——底座只认裸的通用 id,它本来就不该知道一个 id 背后是「活」还是「会话」,语义类型留给上层,进出各转一次;②**删只有 V3 用的出口**——三份仓文件解析器(V4 有自己的一套)、V3 专用的读数与配置结构,以及那个拼中文业务提示词的函数(**业务语义不该住在底座里**);③**删两条零调用的死链**。V3 那份原样留着伺候 V3,直到它被删。

**新库不摞在旧内核上的理由**:本机库缩到四张表之后,旧库的二十张表与架在这些表上的用例整片接不上,改它等于把旧库拆了重装,还会连累仍在跑的 V3。

**名字里的版本号**:`bw-v4` 与新壳的二进制名 `bw-v4-dev` 都带着版本号,那是共存期的权宜——删旧壳那次一并改回不带版本号的名字。

### 12.2 目录:一屏一模块,一个外部能力一个适配模块

```
crates/app-shell/src/
├── main.rs        入口:起窗口、起内核桥线程、读深链环境变量
├── bridge/        内核桥(独立线程)
├── theme/         视觉 token(来自高保真那张样式表)
├── vm.rs          V4 自己的 ViewModel 类型(不是 V3 的 ui crate)
├── screens/       一屏一目录,九个:项目墙 / 接入 / 设置 三顶层
│                  + 总览 / 计划 / 会话 / 通知 / 配置 / 知识库 六个项目内入口
└── adapters/      一个外部能力一个目录:内嵌终端 / Claude CLI / Cursor /
                   Open Design / 代码图 …… 每个目录必须有一份 README
```

**老 buddy 走不下去的原因之一是某个文件动辄一万多行,改一处散弹一片。** V4 立三条规矩,而且**不靠自觉,靠机制钉死**:

1. **每屏只有一个公开出口**——屏内部随便拆文件,但除这一个函数外不再有第二个能被外部引用的公开项。
2. **共享数据只能经共用的 ViewModel 模块**——两屏都要展示同一样东西时,类型定义在共用模块里各自引用,**永远不允许一屏直接引用另一屏**:每层只能向下依赖,不能跨并列层互相伸手。
3. **每个适配模块的 README 固定三段**:借自哪个项目哪个文件、借了什么、**没借什么**。以后持续借鉴只在该模块内增量,不散弹。

**门禁里的三条结构守卫**(纯文本检查、不编译,所以 CI 里照跑):

- **屏与屏不互相引用**——逐目录检查,命中除自己以外的屏幕名就报错。
- **单文件 1500 行硬上限**(阻断)+ 600 行软目标(只提醒)。**只查 V4 那三个 crate**——旧壳反正要删,没必要为将死代码返工;**新壳从第一天起就该守规矩**,它是重写不是迁移,没有「存量文件一时改不完」的过渡借口。
- **用界面框架 hook 的函数必须是组件**。这条是评审抓到真 bug 之后补的:普通函数在渲染宏里被直接调用时,它的 hook 落在**调用方**的槽位上按序号取;切一次屏,序号还在、类型换了,取的时候类型转换失败,**整次渲染崩溃**——用户看到的是一块空白面板,编译期一点征兆都没有。放在循环里更糟:hook 数量随列表长度变,行与行的输入框内容会串位。

### 12.3 命令与事件

通路不变:**界面只发命令、只收事件**,内核是唯一执行用例的地方。V4 的这一对枚举是**全新的**,和 V3 那对没有继承关系、不互相引用。

**回执里带的是「真发生了什么」,不是「命令收到了」**——比如发版那条回执带一个「这次有没有真的写进一行」,为假就表示这个版本号已经在发版记录里、这次没写第二行。

**没有一条命令要求改动内核的状态机、「信号只能从数据推导」这条铁律、或只追加的机制**:合法转移表原样复用,健康灯由密封类型守着,store 层没有任何设置信号的方法。

**已经退场的命令,新库里从来没有过**:队友的增删改导入、技能包整包导入登记——**不是「删表」,是「新库从未建过」**,效果同样是存量数据不迁移、不可逆(已提请用户点头)。

### 12.4 深链

深链(用环境变量直接启动到指定项目 / 屏幕)是 V4 最主要的验证手段之一,启动时标准错误上打两行证据日志:深链解析结果、界面已渲染的证明。

- `BW_DB` 覆盖库路径;`BW_WORKSPACES` 覆盖工作区根。
- `BW_OPEN=<项目>` + `BW_PANEL=overview|plan|session|notify|config|kb` 打开项目内六入口。
- `BW_VIEW=onboard|settings` 打开不依赖项目的顶层屏(项目墙是默认视图,不需要变量)。
- `BW_SEL=<kind>:<uuid>` 定位到具体一张活。
- **旧壳那套 Hub 深链直接删除,不留兼容层**;遇到未落地的枚举值**如实打印「未知值」,不静默退回某个默认屏**。

### 12.5 视觉:不推倒 V3,壳只重排

**视觉正本是 [`hifi/index.html`](hifi/index.html)**(单文件、浏览器直接打开、可点击),桌面壳的样式表就是从它整体搬过去的,九个屏也是照它重排的。项目墙卡片、本机环境条、健康概览条、指标卡与灰卡的诚实文案、活列表行、内嵌终端面板、创建流两卡、暖纸色 token,一律沿用 V3 的样子;新壳只重排信息架构。

**明确不抄的**:阶段轴(V4 总览是一列横块,不分阶段视角)、旧壳左侧那排十个图标(V4 是六入口)。

**几处真壳故意不照抄高保真**,因为高保真是演示,真壳没有那个东西——与其照抄一个假的,不如如实改掉并在界面上说清楚:顶栏的「演示数据 / 重置 / 头像」换成库文件名加「刷新」(数据来自本机库和项目仓,没有可重置的演示数据,也没有账号);提示条从「2.6 秒自动消失」改成「点 ✕ 才关」(**这里放的是「铺底失败,原话是……」,自动消失等于把失败藏起来**);设置屏库文件的「更改…」按钮换成一句「改它要在启动前设哪个环境变量」(进程起来后库连接已经建好,那个按钮真做出来就是哑弹);代码图那张依赖图不画、页面上直说(那张图是照 buddy 自己的仓画死的,换个项目就是假的);项目卡的删除叉不放(内核没有删除项目这条命令,摆一个按不动的叉不如不摆)。

**按不动的留位一律灰态、鼠标停上去写明为什么,不放模拟数据**——这条不因为「高保真上有」而松动。

**一条教训**:曾经有一行写着「接入屏列不出可点的仓列表,因为要调平台接口」。**那句话是错的**——两个平台的列仓接口早就有、V3 一直在用,只是没接到 V4 的界面上。试点第一天用户当场指出来,已经接上。**「没接」和「做不到」是两回事,别把前者写成后者。**

### 12.6 什么时候能把旧壳删掉

把「跑通后删旧壳」落成可核对的判据。**逐条核对过,今天一条都不满足,旧壳不能删**:

| # | 判据 | 今天满足没有 | 差在哪 |
|---|---|---|---|
| 1 | 每个模块的验收读回都跑过至少一次,证据落成文件进仓 | **否** | 读回跑过(深链 + SQL + 各屏的结构化日志),但证据没有落成文件;按用户这次的要求也没做截图——全旅程由用户自己点 |
| 2 | 整体验收八条全满足(第 13 章 §13.1) | **否** | 差五条:两个真实周循环(要真过两周)、真跑 claude 各跑通一张活、第二台 buddy 纳入同仓审核合入、Windows 安装包、项目群真连 |
| 3 | 没有标「未建」的功能挡在日常路径上 | **否** | 至少五处:蒸馏按钮、MR 检查那一列、Cursor 开工工具、内嵌 Open Design 标签、agent 四态 |
| 4 | 满足以上后**同一次改动**删干净 | 不适用 | 前三条没满足 |

**删的时候一次删干净**:删旧壳 crate、工作区成员表里去掉那几行(V3 的库层、编排层、ViewModel 层新壳一个都不依赖)、新壳的二进制名改回不带版本号、验证脚本只指新壳、旧壳那套深链读取代码彻底删除、旧指挥器退役。**不分批半删**——半吊子共存本身就是要避免的过渡态。

**Windows 安装包的实情**:安装脚本**不在这个仓里**,当初是在 Windows 机器上单独维护的,所以那一包在这台机器上出不了;macOS 那条路是补齐的(有打包脚本)。Windows 包记在 `docs/LEFTOVERS.md`。

### 12.7 Web 版留门,不多做

内核有 wasm32 编译检查,注释里写着「以后也许」。新壳不改这个决定:不为 Web 版新增抽象;新增的 ViewModel 类型一样要过 wasm32 门禁——**这就是留门的全部代价,不多花力气,也不倒退。**

## 13 · 验收与读回:怎么证明做对了

> 这一章的正本原文在 [`../archive/v4-prototype/design/10-e2e-acceptance.md`](../archive/v4-prototype/design/10-e2e-acceptance.md)。

**验证手段只有三样:headless 指挥器 + `sqlite3` 读回 + 深链启动的标准错误日志。不做点击巡航。**

### 13.1 什么叫 MVP 做完(整体八条)

1. **试点项目在 V4 上跑完两个完整周循环**——两份周计划文件、两轮运作活①②、至少一次发版记录,都在仓里。试点项目 = buddy 自己的仓(开发环境连不到内部平台,就用自己的);内部平台项目的接入留给内部试用时验。
2. **总览灯不是灰的**,且灯的每条理由、每个数字都能用 `sqlite3` 或打开仓文件核对出来;至少一个引领指标卡下面挂着推动它的活。
3. **至少一张活用 Open Design 开工、至少一张用 Claude CLI 开工**(装了 Cursor 的机器再加一张),产物真进了仓;终端内容能复制;右侧侧栏能看到本活改动的文件;**干完的活能通过「提交并开 MR」真的交出去**,而没干出东西时点它要如实弹回、不留分支不留号。
4. **第二台 buddy 纳入同一仓**:leader 看到同一张总览;committer 在待处理里看到评审中的活并成功合入,结清只有一次。
5. **Windows 安装包在同事机器上装得上、跑得起**;GitHub 仓走同一流程能接入;计划屏拖拽在 Windows 上真能用。
6. **每个模块至少一条读回记录**(深链 + SQL + 截图)。
7. **老项目**:至少一个有历史的项目接入后,计划屏周列表里的历史周、总览发版记录里的历史版本,每个数字都能对回 git 或远端;回填的活标着回填来源、不进任何用量统计;**总览和计划屏没有任何专门的回填块**。
8. **项目群**:配了群的项目,一次评审中 / 一次合入 / 一次发版各在群里收到一条;定计划那次会话里能看到 agent 引用了上周群摘要。**重复触发允许再发一条**——不做去重是知情代价,验收时确认它「确实会重复」,而不是反过来验证「不会重复」。

### 13.2 headless 指挥器

不开界面、直接驱动内核走完一整套 V4 主环的脚本:接入 → 铺底(含历史回填的确定性那一半)→ 开始本周 → 建活并确认 → 一张业务活开工推评审完成 → 发版本 → 定时那一跳 → 项目群假群 → 导出证据 JSON。

**四条取舍**:

1. **工作区用 buddy 仓的本地浅拷贝**,不是空仓——回填要读真实 git 历史来验证防伪规则,数字可以对照。
2. **不真开 MR、不依赖网关**——「开 MR 才能进评审中」这一步退化成既有的「没有 MR → 人点确认完成」路径,并**明写「脚本代人确认」**;真远端的完整合入链路只手动验证一次。
3. **重复跑不产生重复数据**——项目按名字、活按标题、周计划按文件在不在、发版按版本号判断是否跳过。**群通知重复触发允许真的重发一条**(没有去重表兜底,这是知情代价不是 bug),不计入幂等断言。
4. **证据 JSON 不手写数字**,全部是真实读回的现成来源。

**任一步失败都停在那一步、打印真实错误、非零退出**,不静默跳过。

### 13.3 读回的样子

```bash
# 库里恰好四张表,一张不多
sqlite3 <db> "SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%';"

# 本周业务活数与仓文件一致(缓存对文件)
sqlite3 <db> "SELECT COUNT(*) FROM issue WHERE project_id='<pid>' AND kind='business' AND week_of='2026-W34';"
#   ↑ 应等于 <ws>/.bw/plan/2026-W34.md 「业务活」表格的行数

# 自动建的活绝不被自动推进到完成
sqlite3 <db> "SELECT COUNT(*) FROM issue WHERE kind='ops' AND settled_at IS NOT NULL;"   # 期望 0

# 项目群配置不在库里——查不到就是预期
cat <ws>/.bw/project.toml     # 看 [chat] 段

# 深链:标准错误出现证据行 = 真的渲染到了
BW_DB=<db> BW_OPEN=<项目名> BW_PANEL=overview ./target/debug/bw-v4-dev

# 内嵌终端的地基(不碰 claude、不碰网关)
cargo run -p v4-engine --example pty_smoke [-- --teardown|--abort]
```

**「实际输出」要真实粘贴,不是转述**——拿截图或 agent 自报当读回,是这条纪律要避免的反例。

### 13.4 边界

- **不真跑 `claude` 当门禁**——指挥器全程用自我标注的替身,真跑只在试点由人手动做。替身路径的产出**必须带自我标注**,mock 存在的唯一目的是廉价验证管线本身,**绝不冒充真实执行**。
- **端到端验证不进门禁,进验收**——它依赖真实仓、部分真实 CLI、人工截图,不设为 CI 必过项。
- **不假装 UI 测试**——「界面看到了什么」一律要求深链 + 证据日志 + 截图。
- **库是本机的**:「第二台 buddy 纳入同一仓」验收的是**从同一份仓加远端能重算出一致的名片 / 指标定义 / 计划**,**不是「两台库表内容逐行相等」**。两台机器的健康灯可能因为各自数据不同而不同,这不是 bug。MVP 不做远端库、不做库同步;运作活①把本周指标读数快照写进周计划文件随 MR 进仓,是这条铁律下让「别人在仓里也能看到数」的唯一补丁。
- **computer-use 摸桌面应用的已知坑**:截图真实可用,点击与键盘**永久受阻**(是界面框架这层更深的窗口限制,不是权限或封装问题)。所以验证手段是用环境变量深链**直接终端调用**把目标视图摆到位再截图,不要指望点击导航。
