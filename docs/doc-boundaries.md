# 文档边界(写到哪、不写到哪)

> **30 秒导读**:给写文档和改 buddy 的人看。回答两个问题——给人看的文档分几层、每层写什么;文档整理什么时候做。**现在作数**(2026-08-21 随 V4 文档收敛成四件套更新)。当前运作:**一心 V4**,V3 不再投入、等删。版本号与出包见 [`releases.md`](releases.md);还没干的活只认 [`LEFTOVERS.md`](LEFTOVERS.md)。

看不懂的词查 [`../CONTEXT.md`](../CONTEXT.md)。

## 读者是谁(影响怎么写)

buddy 现在的使用者主要是**内部同事**;对外目前只有 buddy 自己这一个项目,短期不推广。所以下面定的产品指南,按"内部同事直接上手用 + 出问题时交接给内部开发"的力度写——说清楚"怎么用、卡在哪找谁",不按对外发布软件的力度写(不用面向陌生用户把每个术语都从零解释、不用做营销向的包装)。这条会随读者变化而重新评估,不是永久设定。

## 三层结构(2026-08-20 定稿)

给人看的文档分三层,谁写、给谁看、什么时候更新都不一样,不要混着写:

### 1. 产品指南(`docs/guide/`,给人用、不谈实现)

再分两块:

- **产品指南**:[`v4-产品指南.html`](guide/v4-产品指南.html)。上半「怎么用」——一步步的操作,跟着实践走,**只写已经真走过一遍的站**,没走到的站写明「还没走到」;下半「特性开发维护」——写给要给 buddy 开发新特性的人(crate 布局、门禁怎么跑、深链与读回怎么做、headless 例子清单)。
- **对外宣讲**:[`v4-对外宣讲.html`](guide/v4-对外宣讲.html)。把 buddy 讲给同事听的讲稿:产品命题、四个控制点、三个愿景各落到哪、一个项目每周怎么转、和传统项目管理的对比。**通篇人话,零实现术语、零代号**;没做的就说在路上,不许吹。

两篇共同的规矩:**上半部分(怎么用)与宣讲稿里的「今天到哪了」只写已实践**,未实践的功能、开发过程中的中间态,不进这一层。

### 2. 设计(当前迭代的设计事实源,给接手的会话看)

现在是 [`v4-prototype/design.md`](v4-prototype/design.md)(**一篇,唯一**;2026-08-21 由母文档 + 14 篇细分设计蒸馏重写,原文归档在 [`archive/v4-prototype/`](archive/v4-prototype/))。规矩:**一站走完,就把那一站相关的章节改成实况**——不是另开一篇「V4 第 N 次修订记录」去描述发生了什么,是直接把设计篇本身改对,让下一个接手的会话打开就是当前该怎么做,不用先扒一遍修订史。V3 时代的等价物是 `docs/v3-prototype/`(bug 修复设计),V1/V2 时代的等价物已于 2026-08-20 大部分归档(见下「历史档案怎么算」)。

### 3. 欠账(`docs/LEFTOVERS.md`,唯一)

还没干完的活只有这一份清单,不设第二个。PRACTICE §4 可以记当周发现,消化后要么迁进这份清单,要么关掉,不在别处再养一份「未决事项」总表。

## 节奏:文档整理什么时候做

**不在开发过程中做。** 一站还没定型时就去扫文档,大概率白扫——设计还会被推翻,扫完可能立刻过时,而且开发和整理文档同时进行,容易出现「代码改完文档没跟上,文档改完代码又变了」的拉扯。

**在每一站用户验证通过之后,单独开一个 subagent 做一次。** 具体流程:一站的功能做完 → 用户在真实环境里验证「这一站没问题」→ 这时候另开一个会话(subagent),专门去把这一站相关的设计篇改成实况、把该补的使用指南补上、该归档的旧设计归档。不要在开发那个会话里顺手做,那个会话的注意力应该留给下一站,不要被文档拉扯回头。

|---|---|---|

| `docs/LEFTOVERS.md` | **还没干完的唯一清单**(开着的 + 已关的史实条目) | 当周叙事、设计正文、第二份未决总表 |

| `docs/guide/` | 产品指南(怎么用 + 怎么开发新特性)与对外宣讲(见上「三层结构·1」),只写已实践 | 未实践功能、开发过程中间态、开发流水 |
| `docs/releases.md` | 版本号、出包时间、本版特性 / 修过的问题 | 设计论证 |
| `.claude/skills/` | agent 怎么干活 | 瞬时窗口号、当前遗留正文 |

## 落盘规则

1. **新特性** → 写进 [`docs/v4-prototype/design.md`](v4-prototype/design.md) 对应那一章(**不新开平行篇**;设计正本只有这一篇)。走 `buddy-feature-dev`。
2. **V3 的 bug / 使用修复** → 设计落 `docs/v3-prototype/`(已有篇就改状态,不要新开平行文)。走 `buddy-bugfix`。当前 V3 不再投入、等删。
3. **还没干** → 只追加 `docs/LEFTOVERS.md`。PRACTICE §4 可以记当周发现,消化后迁进清单或关掉,不在 §4 养第二份总表。
4. **实践过程** → PRACTICE。已解的坑嵌进对应操作步;和后来实测矛盾就加「归正」,不悄悄改写。
5. **出一包** → 在 `docs/releases.md` 加一行:版本号、出包日、这一包相对上一包多了什么 / 修了什么。安装器 `AppVersion` 与这一行对齐。
6. **过时的版本目录** → 不整目录删,按篇判断:已落地且没有现役文档引用为当前权威的篇章搬 `docs/archive/`(加历史横幅,规则见其 README);仍被引用为当前权威、或含未关闭欠账线索的篇章原地留着,不因为目录「大体过时」就连坐搬走。
7. **同一决定只在一处写正文**。别处只留指针。例如 V3-use-fix 的修法正文已归档在 [`archive/v3-prototype/onboard-list-and-claude-resolve.md`](archive/v3-prototype/onboard-list-and-claude-resolve.md),PRACTICE 只指过去。
8. **文档整理不跟开发混在一次会话里做** → 见上「节奏」一节:等用户验证过这一站,另开会话专门做。
