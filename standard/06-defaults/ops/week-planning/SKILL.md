# 更新指标 + 制定本周计划(week-planning)

一周的开头。人只点一下「开始本周」,剩下的是一次对话:先看上周实际发生了什么,再把
绑不上数据的指标接上最便宜的采集路径,最后和人一起敲定这周要干哪几张活。

**人不写周目标——你引导他说出来,然后照着写。** 这条是整篇的重心,搞反了这次会话就
白跑了。

## 何时用

只在运作活①被开工时用。判据由 buddy 在建活时把过:当前 ISO 周还没有
`docs/plan/YYYY-Www.md` 才建得出这张活,所以你被开工时这份文件一定还不存在。

`.bw/metrics.toml` 不存在(项目刚接入,第一次跑)则第二步走**完整起草**而不是补齐。

## 第一步 · 复盘上周

读上一周的 `docs/plan/YYYY-Www.md` 与 `docs/releases.md`。

- 上周计划的活,哪些真做完了、哪些没动、哪些中途换了方向。
- 上周有没有发版,发的是什么。
- **没有上一周文件就如实说「首次制定周计划,无历史可复盘」**,不要用空话填满这一段,
  更不要根据 git log 编一段"上周大概做了这些"冒充上周计划。

这一步**只读不改**。

## 第二步 · 更新指标

调用子技能 `metrics-refresh`(见 `skills/metrics-refresh/SKILL.md`):补齐缺的引领/滞
后指标、给绑不上的找最便宜的采集路径、必要时改 `.bw/connectors.toml`、跑一次采集。

两条硬性约束,和整个产品的健康推导链是同一条:

- **绝不伪造观测**。采不到就是采不到,指标保持灰。
- **绝不为了点亮而改指标定义**。把"周活跃用户"改成"注册用户总数"因为后者好采——这
  是把管理体系变成自欺,比灰着更糟。

改动**先不提交**,和第四步合成一次提交。

## 第三步 · 引导出本周(不许自己下结论)

结合指标现状、代码现状(codegraph 索引)、上周记录,以及(若这个项目配了项目群)一份
上周群消息摘要,和人交流出:

- **周目标一句话**。人说的话你来记,不是你写一句让人点头。
- **业务活草稿若干张**,每张:标题 / 说明 / 类别 / 预期推动哪个指标 / 建议的开工工具与
  workflow。

**写完草稿必须停下来等人明确的确认信号**,才能进第四步。人没说"确认"之前不许落文件、
不许建活。

## 第四步(需人确认后才能做) · 落文件

写这三份:

1. `.bw/metrics.toml`(第二步的改动)
2. `docs/plan/YYYY-Www.md`(本周计划)
3. `docs/metrics.md`(指标现状说明,仍是 Unknown 的要有诚实说明)

`docs/plan/YYYY-Www.md` 除周目标、业务活清单外,必须有一段 **「本周指标读数」**:每个
已绑定的引领/滞后指标各一行——数字 · 来源 · 采集时间。这一段的意义是,别人打开仓就
能看到数,不用装 buddy、不用连库。

然后正常提交,`gh pr create` 开 PR,把 PR 地址打屏。**`gh pr merge` 禁止**——合入是人
的动作,和所有 Issue 共用同一条铁律。

## DoD

- 三份文件结构合法(TOML 能解析、Markdown 表格列数对得上)。
- 改动是这条活分支上的真实提交,不是只写在工作区里。
- 仍然 Unknown 的指标,每条都有一句诚实说明:为什么采不到、最便宜的下一步是什么。

## 常见坑

- 把「引导」做成「代写」——人还没说话,周目标已经写好了。
- 跳过复盘直接进第三步:没有上周的账,这周的计划就是拍脑袋。
- 给绑不上的指标编一条看起来能跑的 query,跑出来的数没人核对得了。
- 人说了"看起来不错"就当成确认——那不是确认信号,再问一句。
