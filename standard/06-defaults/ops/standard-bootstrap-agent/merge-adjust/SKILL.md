# 合并调整(merge-adjust)

规范铺底(运作活③)的第 2 步。第 1 步 buddy 已经自己把核心件写进仓了——但如果这个仓
本来就有人手写的 `AGENTS.md` / `CLAUDE.md` / `README.md`,那些内容是这个项目自己的决
定,**一个字都不能删**。你的活是把 buddy 的固定章节**合并**进去。

**合并,不是拼接,不是覆盖。** 这是整篇唯一的重点。

## 第一步 · 找到现有约定

按这个顺序找:

1. 仓根 `AGENTS.md`(项目自己写的那份;buddy 自己那份在 `.bw/AGENTS.md`,别混)
2. 没有就看仓根 `CLAUDE.md`
3. 再没有就看 `README.md` 里类似「开发约定」「贡献指南」的章节

三处都没有,说明探测判断错了,如实写进 MR 说明并停下,不要凭空造一份。

## 第二步 · 合并原则

- **已有内容一字不删、一段不改**。包括你觉得过时的、写得不好的、和 buddy 约定矛盾的
  ——矛盾写进 MR 说明让人看,不要自己裁决。
- **buddy 的固定章节插在靠前位置**:标题之后、原文之前。**不要追加到文件末尾**——很多
  agent 工具按上下文预算截断长文件,强约束必须优先被读到,排在最后等于没写。
- **标题字面撞车时不覆盖原标题**:buddy 版本的标题后缀「(buddy 补充)」插入,并在 MR
  说明里提醒人核对这两段是不是该合成一段。
- **项目自定义段原样保留**,位置也不动。

buddy 的固定章节共七类内容:读什么、活怎么做、指标怎么碰、禁止事项、代码图怎么用、目
录结构、以及项目自定义段的占位。模板在第 1 步已经写进仓了,直接从那份模板里取。

## 第三步 · `CLAUDE.md` 单独处理

| 现状 | 怎么办 |
|---|---|
| 不存在 | 只写一行 `@.bw/AGENTS.md`(第 1 步已经写好了,通常轮不到你) |
| 空壳,或只有一行导入 | 换成 `@.bw/AGENTS.md` |
| 有实质内容 | 在最前面插入 `@.bw/AGENTS.md` + 一行分隔说明,原内容整段后移,**不删** |

**buddy 的固定章节写进 `.bw/AGENTS.md`,不写进仓根那份。** 仓根的 `AGENTS.md` 是项目
自己的,你只在它和 buddy 约定矛盾时列出来提醒人核对,不去改它。

## 第四步 · 写 MR 说明草稿

你不判断「合并得对不对」——那是人评审的事。你要写的是:**每个文件按哪种情况处理的**,
一个文件一行。撞车的标题、原文里和 buddy 约定矛盾的地方,单独列一段提醒人核对。

## DoD

- 原有内容一字未删——`git diff` 里应当只见新增行,删除行为零(除非是把 `CLAUDE.md` 的
  空壳换成标准写法这一种情况,那要在 MR 说明里单独说明)。
- 七类固定内容都在。
- MR 说明里每个动过的文件都有一行交代。

## 常见坑

- 把「合并」做成「覆盖」:看到已有内容和 buddy 模板讲的是同一件事,就用模板那段替换掉。
- 把原有的历史说明当成冲突强行改写。
- 追加到文件末尾而不是靠前插入——编译不报错,人也看不出来,但 agent 读不到。
- 顺手把原文里的错别字、格式一起改了:这次 MR 只做合并,别的改动会让评审的人分不清哪
  些是必要的。
