# 写开发手册(merge-adjust)

规范铺底(运作活③)的第 2 步。第 1 步 buddy 已经把骨架写好了 —— 但它**不起 agent、
只读得懂构建文件**,所以仓根 `AGENTS.md` 里有几节明写着「还没填」。你的活是把它们填成
真的。

**这份文件是给这个项目的,不是给 buddy 的。** 它写的是「进这个仓的 agent 该怎么干活」:
怎么建、怎么跑、怎么测、目录里什么在哪、这个项目和别处不一样的地方。buddy 自己的规矩
(完成由人点、指标只能真采、合并永远是人)**不写进来** —— 那些每次开工都会注入,写在
仓里只会变成第二份会漂移的副本。

## 第一步 · 读,别猜

按这个顺序读,读到什么写什么,读不到就留着那句「还没填」:

1. `README.md` —— 项目自己怎么介绍自己、有没有现成的构建/测试说明。
2. 构建文件(`Cargo.toml` / `package.json` / `pyproject.toml` / `go.mod` / `Makefile`)
   —— 真实的目标名、脚本名、workspace 成员。
3. CI 配置(`.github/workflows/` 或 `.gitlab-ci.yml`)—— **这是「算不算过」最硬的证据**,
   CI 跑哪几步,门禁就是哪几步。
4. 顶层每个目录进去看一眼,搞清楚它装什么。
5. 有没有人手写过的开发约定(`CONTRIBUTING.md`、`README` 里的「开发」章节、
   仓根已有的 `AGENTS.md` / `CLAUDE.md`)。

## 第二步 · 填,别覆盖

`AGENTS.md` 里 buddy 已经写好的部分:

| 这一节 | 你怎么办 |
|---|---|
| `bw:managed` 标记之间那段 | **一个字都不许动**,规范升级时 buddy 会整段替换 |
| 「怎么建、怎么跑、怎么测」 | 补成真的:命令要能原样复制去跑。CI 里那几步优先 |
| 「目录导览」 | 每个目录补一句它装什么。看不懂的目录写「(没看懂,待补)」,不编 |
| 「这个项目特有的规矩」 | 只写你**在仓里真看见过**的约定;一条都没看见就如实说没有 |
| 其余几节 | 和这个仓的实际做法冲突时按实际的改,并在 MR 说明里单独列出来 |

**仓根本来就有人手写的 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`**:那些内容是这个
项目自己的决定,**一个字都不能删**。这时候 buddy 第 1 步根本没写(它跳过已存在的文件),
所以你的活变成:把缺的那几节**补进人写的那份**,原有内容整段保留;并在最前面加上
`bw:managed` 那一段。合并,不是拼接,不是覆盖。

## 第三步 · 仓根 `CLAUDE.md`

| 现状 | 怎么办 |
|---|---|
| 不存在 | 只写一行 `@AGENTS.md`(第 1 步通常已经写好了,轮不到你) |
| 空壳,或只有一行导入 | 换成 `@AGENTS.md` |
| 有实质内容 | 在最前面插入 `@AGENTS.md` + 一行分隔说明,原内容整段后移,**不删** |

## 第四步 · 写 MR 说明草稿

你不判断「写得对不对」——那是人评审的事。你要写的是:**每一节的内容是从哪读来的**,
一节一行(例:「构建命令取自 `.github/workflows/ci.yml` 第 12-18 行」)。凭推测填的、
和现有文档矛盾的,单独列一段请人核对。

## DoD

- `AGENTS.md` 里没有「还没填」字样了 —— 除非那一节确实无从得知,那要在 MR 说明里说明为什么。
- 每条命令都真跑过一次,跑不通的不写进去。
- 原有内容一字未删:`git diff` 里只见新增行(把 `CLAUDE.md` 空壳换成一行导入是唯一例外,
  要在 MR 说明里单独说明)。
- `bw:managed` 那一段原样未动。
- MR 说明里每一节都有一行交代来源。

## 常见坑

- **照 README 抄命令**。README 常年不更新,CI 配置才是当下真跑的东西。两者冲突时以 CI 为准,
  并在 MR 说明里指出 README 过时了。
- **把 buddy 的规矩写进去**。「完成由人点」这类不属于这份文件,写进来就是第二份会漂移的副本。
- **给看不懂的目录编一句用途**。写「(没看懂,待补)」比编一句准确得多。
