# 给这个项目写开发手册(project-handbook)

资产盘点(运作活②)首次模式里的一个**提议**。

**先搞清楚这是谁的东西。** `AGENTS.md` / `CLAUDE.md` 在仓根,是**这个项目自己的**
文件,不是 buddy 的资产 —— buddy 的资产全在 `.bw/` 底下。所以这件事的性质是
「buddy 建议改造你的项目」,不是「buddy 铺自己的东西」。**接项目的时候一个字都
不该写**,那时候 buddy 才刚 clone 完,既没读过这个仓,也没人问过人家愿不愿意。

**buddy 自己的规矩不写进来。** 完成由人点、指标只能真采、合并永远是人 —— 这些
每次开工都会注入给 agent,写进用户仓只会变成第二份会漂移的副本。

## 第一步 · 先看这个仓已经有什么

1. 仓根有没有 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md`?有的话通读一遍,
   记住:**原文一个字都不能删**。
2. `README.md` —— 项目自己怎么介绍自己、有没有现成的构建/测试说明。
3. 构建文件(`Cargo.toml` / `package.json` / `pyproject.toml` / `go.mod` /
   `Makefile`)—— 真实的目标名、脚本名、workspace 成员。
4. CI 配置(`.github/workflows/` 或 `.gitlab-ci.yml`)—— **这是「算不算过」最硬的
   证据**,CI 跑哪几步门禁就是哪几步。**空目录不算**。
5. 顶层每个目录进去看一眼,搞清楚它装什么。

## 第二步 · 问人,别自己拍板

把上一步读出来的摊给人看,一句话说清楚你想干什么、会动哪个文件:

> 「你这个仓根还没有 `AGENTS.md`。我读了 README、`Cargo.toml` 和
> `.github/workflows/ci.yml`,能写出一份开发手册:怎么建、怎么跑、怎么测、
> 七个顶层目录各装什么。要写吗?写的话会新增仓根 `AGENTS.md` 和一行
> `CLAUDE.md`,提个 MR 给你评审。」

已经有那份文件时,提议换成「补进去」:说清楚缺哪几节、你打算补什么、
**原文一字不删**。

**人说不要就到此为止**,把「提过、人不要」写进这次盘点的回执,下次盘点不再问
同一件事。人说不确定,也当不要 —— 沉默不是同意。

## 第三步 · 写

人点头了才动手。

| 这一节 | 怎么写 |
|---|---|
| 怎么建、怎么跑、怎么测 | 命令要能原样复制去跑。**每条都真跑过一次**,跑不通的不写进去 |
| 门禁 | 以 CI 配置为准。README 和 CI 冲突时以 CI 为准,并在 MR 里指出 README 过时了 |
| 目录导览 | 每个顶层目录一句它装什么。看不懂的写「(没看懂,待补)」,**不编** |
| 这个项目特有的规矩 | 只写你**在仓里真看见过**的约定;一条都没看见就如实说没有 |
| `bw:managed` 标记之间那段 | 「本项目由 buddy 管理,正本在 `.bw/`」那一小段,**规范升级时整段替换**,别的地方别动 |

仓根 `CLAUDE.md`:不存在就写一行 `@AGENTS.md`;是空壳或只有一行导入就换成
`@AGENTS.md`;有实质内容就在最前面插入 `@AGENTS.md` + 一行分隔说明,原内容整段
后移、**不删**。

## 第四步 · 写 MR 说明草稿

你不判断「写得对不对」——那是人评审的事。你要写的是:**每一节的内容是从哪读来
的**,一节一行(例:「构建命令取自 `.github/workflows/ci.yml` 第 12-18 行」)。
凭推测填的、和现有文档矛盾的,单独列一段请人核对。

## DoD

- **人明确说要,才有产出**;人没说要就零改动 + 一句回执。
- 每条命令都真跑过一次,跑不通的不写进去。
- 原有内容一字未删:`git diff` 里只见新增行(把 `CLAUDE.md` 空壳换成一行导入是
  唯一例外,要在 MR 说明里单独说明)。
- MR 说明里每一节都有一行交代来源。

## 常见坑

- **没问就写**。这是在改人家的项目,不是铺 buddy 自己的东西。
- **照 README 抄命令**。README 常年不更新,CI 配置才是当下真跑的东西。
- **把 buddy 的规矩写进去**。「完成由人点」这类不属于这份文件。
- **给看不懂的目录编一句用途**。写「(没看懂,待补)」比编一句准确得多。
