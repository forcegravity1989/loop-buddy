# 资产盘点(asset-audit)

一周的收尾。周五晚上没人在场的时候,把这个仓里所有资产过一遍:文档齐不齐、新东西登记
了没有、规范件落后没有、指标数据还新不新鲜、有没有大到该拆的文件。

**这次会话很可能没有人在场。** 按「能做的先做、拿不准的写进报告等人看」推进,不要因为
没人回应就停下来等。

## 第一步 · 判断模式

读这张活自己的说明(issue body),找一行 `mode: ...`。

| `mode` | 什么时候 | 干什么 |
|---|---|---|
| `weekly`(默认,没写就是它) | 定时,默认每周五 20:00 | 只盘这一周的变化,走下面第二至五步 |
| `first` | 接入老仓时一次,或人手动重跑一次 | 全量回填历史,走本篇末尾的「首次模式」段 |

判错模式会造成很难收拾的后果(把历史回填当周盘点跑,报告是空的;反过来则会重写一遍已
经存在的历史文件)——**读不到 `mode` 就按 `weekly` 走,并在报告里写明"说明里没写模式,
按每周增量处理"**,不要猜。

## 第二步(`mode=weekly`) · 盘点仓内全部资产

五类,一类一段,每段写清楚「查了什么、发现了什么、要不要人管」:

1. **文档**——`.bw/plan/` 这周的文件在不在、`.bw/releases.md` 有没有落下版本;这周新增
   的文档有没有登记进知识库资产页。
2. **产物与技能 / workflow**——新增的技能包、新挂的 workflow 有没有登记。
3. **规范对账**——对照 `.bw/managed.toml` 里的指纹,检查规范件版本是否落后、有没有人改
   过。**只记录差异,不擅自升级**——人改过的规范件是这个项目自己的决定。
4. **指标数据新鲜度**——`.bw/metrics.toml` 里哪些指标超过保鲜期没有真实观测。
5. **代码图大文件榜**——`codegraph files -j` 找超过行数上限的文件。

**不做「零调用者就当死码删」**:`codegraph` 对 `dyn Trait` 这类动态分发看不见,零调用者
经常是误判。疑似没人用的东西只写进报告,不动手删。

## 第三步(`mode=weekly`) · 微重构只写建议,不动手

格式、命名、疑似死码、该拆的大文件——这类「可做可不做」的改动**不在这次会话里直接改
代码**。每条整理成一张建议活草稿:

- 标题、说明、类别「优化」
- 为什么值得做、不做的话会怎样

草稿连同盘点报告一起写进这次 MR 的说明。人周一评审时勾选要建的,勾中的那些才真的建成
正式活。

需要动业务逻辑或公开接口签名的,一律只写建议,连草稿都不生成——那种改动要人自己拍板
才动得。

## 第四步(`mode=weekly`) · 写盘点报告

追加进本周 `.bw/plan/YYYY-Www.md` 的尾段。

**没有可重构的东西是正常结果**,如实写「无」。不要为了让报告看起来有产出,硬凑几条改
名建议。

## 第五步 · 提交 + MR

正常提交,`gh pr create` 开 PR,把地址打屏(多半没人当场看,仍然要打)。`gh pr merge`
禁止——合入是人的动作。

## DoD(`mode=weekly`)

- 报告确实追加进了本周的计划文件。
- 建议活草稿都在 MR 说明里,一条不落。
- **这次会话自己没有直接改动业务代码**:`git diff --stat` 应当只见格式/命名类小改动,
  或者完全没有代码改动。

## 首次模式(`mode=first`) · 回填老项目历史

一个项目通常只跑一次:把这个仓已经发生过的历史,整理成和新项目一样格式的文件,让老项
目一接入就有骨架。

**这一步分三层,你只干第二层。** buddy(Rust 代码)已经先把证据算好了——历史提交按周
分桶、标签与版本、远端 issue 与 MR、CHANGELOG 段落,都在一份本机证据文件里(不进仓、
不进库)。**你的活是读那份证据文本、按格式抄成文档,不是自己去跑 git 命令重算一遍。**
第三层是人确认。

产出四份仓文件 + 一类库缓存行:

1. 历史周文件 `.bw/plan/YYYY-Www.md`——每周一份,格式和正常周文件一样,**顶部必须
   标明「回填」**,让人一眼看出这不是当时真写的计划。
2. `.bw/releases.md` 的历史版本行。
3. `.bw/PROJECT.md` 草稿(从 README / 提交历史里能看出来的部分,看不出来的留占位符,不编)。
4. 指标候选(能从历史里看出来这个项目在乎什么,写成候选,不直接写进 `.bw/metrics.toml`)。
5. 回填出来的活各一行库缓存,`origin='backfill'`。

**回填的诚实底线**:证据里没有的东西不写。历史上某一周什么都没发生,那一周就写「无记
录」,不要根据前后两周脑补一段。回填出来的每一份文件都要能对回 git——人拿 `git log`
一比就该对得上。

失败与边界:证据文件读不到 → 如实停下,报告写清楚缺什么,不要退回去自己跑 git;仓太大
跑得久是正常的,不要中途换成抽样。

## 常见坑

- 把「疑似未使用」直接删掉,而不是先写成建议活。
- 报告写空话:「整体质量良好,建议继续保持」——这一行等于没查。
- 微重构悄悄做了,却不在 MR 说明里说清楚它是「这次自己动手改的」还是「一条建议」。
- 没人应答就卡住等待。这次会话大概率无人在场,等不来的。
- `mode=first` 时自己去跑 git 重算历史,而不是读 buddy 已经算好的证据文件——两边算出
  来的数不一样,人核对时就废了。
