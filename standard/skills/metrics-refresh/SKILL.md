# 更新指标(metrics-refresh)

运作活①「更新指标 + 制定本周计划」第二步调用的子技能。第一步的复盘已经
做完,现在要做的是:把 `.bw/metrics.toml` 里的三层指标(北极星/滞后/引
领)补齐到位,能自动采的接上最便宜的采集路径,采不到的诚实说明——不是
编一个假指标或假数字去点亮看板。

> buddy 规范(产出格式、`collect_kind` 词表)由 `docs/buddy/standards/metrics.md`
> 唯一持有,本技能只讲方法论。

## 第一步 · 先判断走哪条路

打开工作区 `<workspace>/.bw/metrics.toml`:

- **不存在**(项目第一次跑运作活①,从未起草过指标体系)→ 走下面「完整
  起草」全套流程,产出恰好一条北极星 + 若干滞后/引领。
- **存在,且北极星/滞后/引领三层都已经有内容** → 走「增量校准」:只补
  缺、只修采不到的指标,**不重排已经定下的北极星**,除非人在第三步「引
  导出本周」的对话里明确提出要重推北极星。

两条路径共用同一套硬性约束和 `collect.kind` 诊断表(均见下)。

## 硬性约束(两条路径都适用,白纸黑字)

> **绝不伪造观测。** 本技能的产出是"怎么点亮"的方案和更新后的 `collect`
> 字段,**不是**手填一个假的观测值去骗过看板。看板上的每一盏灯必须来自
> 真实观测——Unknown 就是 Unknown,不因为跑过一遍本技能就假装变绿。
>
> **绝不为了点亮而改指标定义。** 如果一条指标真实的 `def`/`target` 采不
> 到,正确动作是找到能采到*那条定义*的路径(换数据源、换查询、换成人工
> 记账节奏),而不是把 `name`/`def` 悄悄改写成另一条方便采集但答非所问
> 的指标——那是"绑数据"伪装成"找指标"的退化,会破坏下面已经守住的
> "先对后亮"。

## 完整起草(仅当 `.bw/metrics.toml` 不存在时)

### 方法论:先对后亮

**三段拆解:供给 / 使用 / 价值。** 动笔前先把项目拆成三段:**供给**(做
出来了:功能/内容/文件被生产出来)、**使用**(用户真的用了:打开、读、
点、留存、复访)、**价值**(用户因此变好了:省了时间、少踩了坑、多赚了
钱、少受了苦……)。**北极星必须落在第二段或第三段,落在第一段一律退回
重写**——供给段回答的是"我们干了多少活",不是"用户过得好不好"。反
例(真实):某项目痛点明明在价值段(信息过多、用户被淹没),北极星却定
成"连续每天产出一份内容",量的是文件有没有被生产出来,卡死在供给段。

**虚荣指标黑名单。** 北极星绝不为了"当前采得到"而退化成 commit 数、PR
数、issue 数这类工程虚荣指标。工程活动量最多是引领指标的候选,永远不够
格坐北极星的位置——即使这条指标眼下只能标 `manual` 甚至暂时想不出精确
采集方案,也不能因此换成一条方便采集但答非所问的指标。反例(真实):某
内容日更项目北极星定为「连续 N 天每天产出一份满足数量下限的内容」,合
法落进"创作产出"类别,但只要挂一条每日定时任务,它从上线当天起就永久
满分——cron 只保证"跑了",从不保证"有人读、有人因此变好"。

**自动化免疫检验**(比黑名单更上位)。起草完北极星,问一句:

> 假如给这个项目挂一条永不失败的定时任务,这条北极星会不会永久满分?

会 → 它量的是系统在运转,不是用户在获益,退回重写。

### 北极星判据打分(6 项,每项 1-5 分)

1. **落位**——精确落在使用/价值段,不是供给段。
2. **自动化免疫**——挂一条永不失败的定时任务会不会让它永久满分。
3. **场景契合**——是否对应项目 `desc`/`benchmark`/`opportunity`。
4. **定义精确**——有没有清晰的"怎么算作达成",不是模糊描述。
5. **采集诚实**——`collect.kind` 是否真实,不为了显得体面瞎选。
6. **难造假 + 反指标**(见下)。

任一项 ≤2 分的候选直接淘汰,不进入起草。

**反指标(counter-metric)硬性要求**:每条候选北极星必须配一条"如果只
优化这条指标会被悄悄牺牲的东西"——如"周活跃用户数"配"客诉率/退款
率",防止靠骚扰通知刷活跃。反指标不进 `.bw/metrics.toml`,只写进
`docs/metrics-rationale.md` 作护栏说明,下次复核北极星先看它有没有恶
化。引领指标侧同构:每条引领指标也配一条反指标(如"每周合并 PR 数"配
"评审通过率/回滚率","队友结算 Issue 数"配"Issue 重开率"),同样只进
`docs/metrics-rationale.md`,不进 `.bw/metrics.toml`。

**故意的坏候选对照**:草拟北极星前,先列出至少 2 个"看起来合理但会被
上面 6 项判据刷掉"的坏候选,写清楚具体是哪一项判据把它挡下——逼自己
把黑名单套在真候选身上,不是空对空背诵。

**BDFE 输入结构**(拆"使用"段的补充视角,不是替代):Breadth(有多少
用户在用)、Depth(每次用得多深)、Frequency(多久用一次)、Efficiency
(达成目标花多少步/多少时间)。北极星常是这四维里的一个乘积或复合(如
"周活跃且完成核心动作的用户数"同时含 Breadth×Frequency)。四维选不出
候选时,回落三段拆解。

**NSM↔商业 KPI 系统校验**:北极星起草完,写一句清楚的因果链——"这条
北极星如果提升,会怎样传导到项目的商业/存续指标(收入、留存付费、口
碑、下一轮资金/资源)"。传导链讲不通就退回重写;如实标注这条链目前是
已有真实数据验证过,还是仅逻辑推演——务必诚实,不假装已验证。

### 滞后/引领指标:强制判定与质量门

逐指标先过判定题,不凭直觉贴标签:当下/事前可被团队直接影响、且对滞后
指标有预测性 → 引领指标;只能在结果发生之后才测得到、团队此刻改不了
→ 滞后指标。两条都答不上「是」的候选(纯活动量)不配称引领,退回重定
义或舍弃——硬塞进"引领"是不诚实分类。

交付前打一次 0-40 质量门自评,写进 `docs/metrics-rationale.md`,<24 分退
回重做:

| 判据(每项 0-10) | 检验问题 |
|---|---|
| 分类诚实 | 有没有把不满足强制判定的指标硬贴"引领"标签? |
| 预测性 | 引领指标的变化能不能在滞后指标之前先看到征兆? |
| 阈值真实 | `target` 是否用项目真实历史数据校准,不是拍脑袋? |
| 防作弊完整 | 是否每条引领指标都配了成对反指标,不是只挑好写的配? |

### 起草步骤

1. **读输入**:项目 `desc`/`benchmark`/`opportunity` + `docs/competitive-analysis.md`
   (若存在;不存在就在 `docs/metrics-rationale.md` 写一句「本轮无竞品分
   析报告输入」)+ 项目仓既有指标体系(`governance/`、`derive_*.py`、
   `connectors/`、`data-sources/`)。有既有体系,三层指标优先对齐映射到
   它的名字与分层,不是另起炉灶。
2. **拆三段**,明确指出北极星落在使用段还是价值段。
3. **起草北极星**(恰好一条):`name`+`def`(精确到"怎么算作达成"),
   过黑名单与 6 项打分。
4. **起草滞后指标**(建议 2-4 条):每条给 `target`(mini-DSL,如
   `"≥5"` `"≤24h"` `"清零"`),阈值用项目真实历史数据校准,不拍一个当
   前值远超的下限(或远低的上限)。
5. **起草引领指标**(建议 2-4 条):过强制判定题,优先复用项目既有过程
   指标,没有才用 BW/GitHub 自有记账或工程活动量,并在
   `docs/metrics-rationale.md` 注明来源。
6. **给每条定 `collect`**(见下方诊断表)。
7. **落文件**:写进 `<workspace>/.bw/metrics.toml`,格式遵照
   `docs/buddy/standards/metrics.md`。
8. **写推导文档**:`<workspace>/docs/metrics-rationale.md`,含输入摘要、
   北极星判据打分、≥2 个被拒坏候选、北极星与引领指标的反指标、质量门
   实得分(≥24)、每条指标当前采集方案的诚实评估。

## 增量校准(`.bw/metrics.toml` 已有完整三层指标时)

不重新走起草,只做三件事:

1. **补缺**:三层里若有明显缺口(比如只有北极星没有滞后指标),按上面
   「起草步骤」对应那一步补,新条目同样要过打分/判定题。
2. **修采不到的**:对每条 `collect.kind` 仍是 `manual` 或空 `query` 的指
   标,走下面的诊断表找更便宜的路径。
3. **不重排已定的北极星**,除非第三步「引导出本周」的对话里人明确提出
   要重推——重推走完整起草的北极星部分,不在本技能内自作主张。

## `collect.kind` 诊断(两条路径都用)

先扫项目仓既有采集脚本(在按下表分支前):遍历 `governance/`、
`derive_*.py`/`derive_*.sh`、`connectors/`、`data-sources/`、`cron/`。若
某条标着 `manual` 或 legacy kind 采不到,其实有项目侧脚本在机械解析真
实数据源——**这是 `script` kind,不是 `manual`**,别把自动采谎报成人
填。

采集 kind 合法词表两值:`script`(自动,机械解析数据源产出 JSON,
`query`=字段在 JSON 里的点分路径)、`manual`(人手填,戴「手填」徽)。
`github`/`codehub`/`bw`/`connector` 是退休中的 legacy kind,新写不用。

| 现状 | 诊断 | 最便宜路径建议 |
|---|---|---|
| `kind="github"`,`query` 为空或明显查不出预期结果 | 查询串没写对,不是数据源问题 | 按占位符语法重写 `query`(`repo:{owner}/{repo} …`、时间窗 `@{Nd}`),优先复用其它指标已验证过的查询模式;写完用 `gh api search/issues -f q="<展开后的真实查询串>"` 真实跑一次校验。或改用 `script`+项目侧脚本。 |
| `kind="connector"` 或 `"bw"` | legacy inline arm,采集器未接,不是配置问题 | 如实标注"等 legacy kind 退休进 script 后接上"。若项目已有自动脚本机械解析真实数据源,改成 `script`+字段路径,不降级 `manual`。 |
| `kind="script"` | 项目侧自采脚本(buddy shell-out 调它读结果) | 确认脚本能独立跑(脚本自身依赖由项目侧管);`query` 只写字段路径(如 `leading.L1`),脚本路径与输出文件在 `.bw/connectors.toml` 配,`query` 不含脚本路径、不带前缀。 |
| `kind="manual"` | 靠人手填,可能没有节奏 | 给出具体、可持续的手填节奏(如"每周一 5 分钟从 XX 后台截数填"),记进 `docs/metrics-rationale.md`——节奏本身就是"点亮路径",不是无解。 |
| 对应外部系统压根不存在(如没有真实竞品数据源) | 指标定义本身的问题,不是绑定问题 | 如实标注"采集依赖尚不存在,建议 `manual` 过渡或下一轮重新评估这条指标是否成立",**不代为改写定义**——只指出问题,决策权留给下一轮。 |

### `script` kind 搭装置

1. 在交互式会话里和人一起把采集脚本写到 `.bw/scripts/<slug>.py`(或复
   用项目侧 `derive_*.py` 留原位),写连接器清单 `.bw/connectors.toml`
   (格式见 `docs/buddy/standards/connectors.md`),给 metric 配
   `collect_kind='script'` + `collect_query=字段路径`。
2. `output` 字段视为必填——脚本必须把 JSON 真的写进 `output` 指向的文
   件,只 `print()` 到 stdout 等于没接(buddy 采集完全不看 stdout)。
3. `[[connector]]` 是单数数组表键名,写成 `[[connectors]]`(复数)会让
   整份文件解析失败。
4. 提交后 buddy 的感知路径:`.bw/connectors.toml` → upsert 连接器行 →
   cron 到点自动跑 script connector → 取字段 → observation → signal 点
   亮,agent 不调 buddy API。

## 落文件与交付

改动只落在 `.bw/metrics.toml`(首次起草时还有 `docs/metrics-rationale.md`)
本身,**本步骤不单独提交**——和运作活①第四步的三份文件合成一次提
交,PR 由第四步统一开。原地按 `(层级, name)` 更新,不新建重复条目、不
改名字(改名字等于新建一条指标,历史观测会跟丢)。

## DoD

- `.bw/metrics.toml` 结构合法,恰好一条 `[north_star]`,能对照
  `docs/competitive-analysis.md` 或项目 `desc`/`benchmark` 说清楚"为什
  么是这条"。
- 每条指标 `collect.kind` 落在合法词表内,`query` 不是编出来的假查询。
- 首次起草时 `docs/metrics-rationale.md` 存在且含:6 项判据打分、≥2 个
  坏候选记录、北极星与引领指标各自的反指标、质量门实得分(≥24)。
- 增量校准时,已定北极星的 `name`/`def` 未被改动过;`name`/`def`/`target`
  只有明确要重推才动。
- 仍然 Unknown 的指标每条都有诚实说明:为什么采不到、最便宜的下一步是
  什么。

## 常见坑

- **把工程活动量塞进北极星**——每次起草前重读虚荣指标黑名单 + 自动化
  免疫检验。
- **把供给当价值**——"每天出一份摘要"这类供给动作太像成果,容易被直
  接当北极星,而不去追问有没有人真的打开、读完、因此变好。
- **顺手把"采不到"的指标改成另一条采得到的指标**——这是伪装成绑数据
  的找指标退化,回头交给第三步「引导出本周」的对话重新评估,不在本技
  能里代劳。
- **给 legacy kind 编一个假 `query` 掩盖"采集器未接"**——应改用
  `script`+项目侧脚本,或诚实标 `manual`。
- **把项目侧自采脚本误降级 `manual`**——降级等于把自动采谎报成人填,
  看板上会平白多一个「手填」徽。
- **增量校准时手痒把北极星也重推了一遍**——没有人在第三步明确要求,
  别碰已定的北极星。
