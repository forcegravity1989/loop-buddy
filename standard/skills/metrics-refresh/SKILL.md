# 更新指标(metrics-refresh)

运作活①「更新指标 + 制定本周计划」第二步调用的子技能。第一步的复盘已经做完,现
在要做两件事:

1. 把 `.bw/metrics.toml` 里的三层指标(北极星 / 滞后 / 引领)补齐到位;
2. 给每一条指标判一次**「这条指标的历史,现在还能不能重新算出来」**,能自动采的
   写成脚本,采不到的诚实标手填——不是编一个假指标或假数字去点亮看板。

> **指标定义文件的字段表这里一个字都不复述**,同一件事写两份必然漂移。**要写文件时
> 先读 `<workspace>/.bw/metrics.toml` 顶部的注释**——铺底铺进项目的那份自带完整的
> 「每条指标怎么填、`collect` 怎么写、脚本协议是什么」,那就是你要照着写的正本;设计
> 层面的完整说明在 `docs/v4-prototype/design.md` 第 10 章 §10.8(在 buddy 自己的仓
> 里,用户项目里读不到)。本篇只讲方法与判据。

---

## 一、核心判据:这条指标的历史,现在还能不能重新算出来

**整篇只有这一条分水岭**,先判它,再谈怎么采。不是按「用什么工具采」分类,而是问
一句能当场执行的话:

> 今天我能采到这个数,那么**「上周三那天的值」现在还能算出来吗?**

| 类 | 判据 | 存不存 | 例子 |
|---|---|---|---|
| **A · 可回溯** | 能采今天,就能采过去任意一天/周 | **一个字都不存**。要看四周就现算四个窗口,要看八周就算八个 | git 提交数、合入数、PR 数、远端 issue 数、GitHub star 数(见下方常见坑) |
| **B · 不可回溯** | 过了那一刻就没了,历史再也采不到 | 必须一行一行记下来 | 外部系统只给「当前在线数」;看板只显示今天的转化率 |
| **C · 手填** | 压根没有采集路径 | 同 B,只是采的人是人 | 要人去某个后台看一眼才有的数 |

**判成 A 的好处**:走势图不需要历史数据管道,项目**第一天就有四周走势**,不用先攒
几周;而且数字每次重算,中间没有一个可以被改的值,天然难造假。

**判错的代价是可预期的,但不对称**:把 A 误判成 B,白存一堆本来可以现算的数;把 B
误判成 A,走势图上除了当前那一个点之外全是**空**——空不是假数,但一条本该有四周走
势的指标画成一个孤点,读的人会以为这个项目刚开始测。

**这一判要落进文件**:A/B/C 是说给人听的分法,落到 `.bw/metrics.toml` 里就是采集方
案(`collect`)里那个「能不能回溯」的字段加上「脚本还是手填」两个词——**具体字段名
和写法看那份文件顶部的注释**,别照本篇拼。

### 判 B 之前,必须真的去找一遍有没有带时间戳的接口

**这是今天真撞出来的坑,不是假想。** 别想当然地认为一个数「只有当前值、查不到历
史」——很多接口把历史藏在一个不显眼的参数里。

真实反例:**GitHub 的 star 数**。仓库信息接口只给一个 `stargazers_count`,看起来是
典型的 B 类;但 stargazers 接口带一个特殊的 Accept 头,就会返回**每一个 star 的时间
戳**:

```bash
gh api -H "Accept: application/vnd.github.star+json" \
  repos/<owner>/<repo>/stargazers --jq '[.[].starred_at]'
```

有了这一串时间戳,任意一周的 star 数都能现算出来——所以它是 **A 类**,不是 B 类。

**动作要求**:每判一条 B,先在会话里真的试一次「有没有带时间戳/带时间范围参数的接
口或导出」,试过再判。判 B 的理由要写进指标说明,写成「查过 XX 接口,只有当前值」,
不能写成「应该没有历史」。

## 二、采集方式只有两种:脚本、手填

- **脚本**——buddy 起一个子进程,跑仓里的一个可执行文件,读它**标准输出**的 JSON。
  连 GitHub、连内网系统、读一个本地文件、算 git 历史,**全是脚本自己的事**;buddy
  不认识这些系统,只认识「起进程、传窗口、读 JSON」。
- **手填**——没有采集路径,到点提醒人去填。

**没有第三种。** 尤其不要把「buddy 内建的 git 算子」当成一种——那等于把算法藏进二
进制,项目看不见、改不了、也说不清这个数怎么来的。git 类统计一样走脚本,只不过脚本
由 buddy 铺一份现成的;**脚本本身就是「这个数怎么来的」的文档**。

**没有「连接器」这一层**:一条指标直接指向一个脚本,不经过任何中间清单文件。V3 那
份 `.bw/connectors.toml` 在 V4 里已经整个不存在了,**不要写它、不要读它**。

### 脚本怎么写

**具体的写法这里一个字都不复述**——参数名、输出的 JSON 字段名、`collect` 里那几个字
段怎么填,正本是**你正在改的那份 `.bw/metrics.toml` 顶部的注释**(铺底铺进项目的那
份就带着完整说明),更完整的设计在 `docs/v4-prototype/design.md` 第 10 章 §10.3 /
§10.4。**照那两处写,不要照本篇猜、更不要照 V3 的老经验写。**

这里只讲几条不会变的规矩:

- **窗口由 buddy 传给脚本,不是脚本自己决定**。可回溯的那类,buddy 把起止日期和粒度
  当参数传进来,脚本照着算;不可回溯的那类不传窗口,只问「现在是多少」。面板要四周
  就传四周,要八周就传八周,**采多少和画多少永远一致**。**脚本里硬编码一个时间范围
  (比如「最近 30 天」)是错的**:面板按八周画时,前几周会永远空着,而且长期对不上
  还没人发现——V3 就是这么翻的车。
- **输出只认标准输出的一个 JSON 对象**,不是 JSON 就算这次采集失败。值可以是数,也
  可以是给人看的字符串(`"87%"`、`"3.2h"`)——原样输出,不在这一层解析。

  > **这一条和 V3 正好相反,别照着老经验写。** V3 是只读脚本写出的文件、不看标准输
  > 出,于是 agent 写的脚本只往屏幕上打、输出字段留空,**每次采集都报「成功」而指标
  > 永远没数**。V4 只认标准输出;往文件里写不算数。

- **失败一律如实**:非零退出、超时、输出不是 JSON、缺字段——都记这条指标这次「没采
  到」,**绝不写一个 0 进去**。0 是一个真实的数值,「没采到」不是。
- **工作目录是仓根**,脚本靠「自己是哪个文件」知道自己算哪条指标,不靠参数区分。
- **buddy 铺的脚本,铺一次就归项目**。规范铺底会往 `.bw/scripts/` 放几份通用起手式
  (每周提交数、每周合入的 PR 数、GitHub star 数),之后**再也不覆盖**——改窗口、改
  口径、换数据源都是项目自己的事。**先看有没有现成的能直接放开用或照着改**,比从零
  写一份省事得多。

### 今天的实情:别假设 buddy 已经在替你采

采集这条链正在落地的过程中,**以你这次会话里看到的实际情况为准**——界面上说「还没
接」的就是还没接,不要写一份「已经在自动采了」的报告。所以这次会话里:

- 你写好或改过的脚本,**自己在终端里真跑一遍**,确认它能跑通、输出是合法 JSON。跑
  不通的不算接上了,如实写「脚本已写、尚未跑通」,并写清楚卡在哪。
- 真采到的读数,抄进本周计划文件的「本周指标读数」那一段(那是**这一周的快照**,不
  是读数的正本)。
- 不可回溯与手填读数的正式落点是 `.bw/metrics/readings.jsonl`(只追加的流水),
  **由 buddy 自己写**。这次会话**不要**替 buddy 建那条固定分支、不要手工往里补历史
  行——补出来的行没人分得清是采到的还是编的。

## 三、手填:每撞到一条,都要认真问一次能不能写成脚本

**目标是让手填这一类越来越少。** 每次跑到一条手填指标,不要直接跳过去写「继续手
填」,而是当场问一次:

> **这个数能不能写成脚本?**

问完给出结论,三选一,写进指标说明:①能——那就当场写脚本,顺带按第一节重判一次
它是不是 A 类;②暂时不能,缺的是什么(没有接口 / 没有账号 / 数据在人脑子里),下一
步怎么补;③永远不能,理由是什么。

**agent 的价值是帮人把手填升级成可回溯,而不是每周替人抄一次数。** 一条指标连着几
周都是「继续手填」而说不出缺什么,那是这次会话没干活。

仍然只能手填的,给一个具体、可持续的节奏(如「每周一 5 分钟从 XX 后台截数填」)和
一句提醒语——提醒语是 buddy 到点建提醒活时说给人听的那句话,写清楚去哪儿看、看哪
个数。

## 四、先判断走哪条路

打开工作区 `<workspace>/.bw/metrics.toml`:

- **不存在**(项目第一次跑运作活①)→ 走「完整起草」,产出恰好一条北极星 + 若干滞
  后/引领。
- **是旧格式**(格式版本号还停在 1、或者采集方案里出现 `github`/`bw`/`connector`
  这些已经退场的词)→ **不半读、不猜字段**,当面告诉人「这份指标文件是旧格式,这次
  会带你重定一遍」,然后按「完整起草」重定。V4 不写格式迁移:那几条老指标的采集方
  式从来没有实现过,本来就要重定。
- **是现行格式、三层都有内容** → 走「增量校准」:只补缺、只修采不到的,**不重排已
  经定下的北极星**,除非人在第三步「引导出本周」的对话里明确提出要重推。

三条路共用下面这套硬性约束和第一、二、三节的判据。

---

## 硬性约束(白纸黑字)

> **绝不伪造读数。** 本技能的产出是「怎么点亮」的方案和更新后的采集方案,**不是**
> 手填一个假数字去骗过看板。看板上每一盏灯都必须来自真实采集——没数据就是没数据,
> 不因为跑过一遍本技能就假装变绿。
>
> **绝不为了点亮而改指标定义。** 一条指标真实的定义/目标采不到,正确动作是找到能采
> 到*那条定义*的路径(换数据源、换查询、换成人工记账节奏),而不是把名字/定义悄悄
> 改写成另一条方便采集但答非所问的指标——那是「绑数据」伪装成「找指标」的退化。

---

## 完整起草(仅当没有可用的指标文件时)

### 方法论:先对后亮

**三段拆解:供给 / 使用 / 价值。** 动笔前先把项目拆成三段:**供给**(做出来了:功能
/内容/文件被生产出来)、**使用**(用户真的用了:打开、读、点、留存、复访)、**价值**
(用户因此变好了:省了时间、少踩了坑、多赚了钱)。**北极星必须落在第二段或第三段,
落在第一段一律退回重写**——供给段回答的是「我们干了多少活」,不是「用户过得好不
好」。反例(真实):某项目痛点明明在价值段(信息过多、用户被淹没),北极星却定成
「连续每天产出一份内容」,量的是文件有没有被生产出来,卡死在供给段。

**虚荣指标黑名单。** 北极星绝不为了「当前采得到」而退化成提交数、PR 数、issue 数这
类工程虚荣指标。工程活动量最多是引领指标的候选,永远不够格坐北极星的位置——即使这
条指标眼下只能标手填,也不能因此换成一条方便采集但答非所问的指标。

**自动化免疫检验**(比黑名单更上位)。起草完北极星,问一句:

> 假如给这个项目挂一条永不失败的定时任务,这条北极星会不会永久满分?

会 → 它量的是系统在运转,不是用户在获益,退回重写。反例(真实):某内容日更项目北
极星定为「连续 N 天每天产出一份满足数量下限的内容」,只要挂一条每日定时任务,它从
上线当天起就永久满分——定时任务只保证「跑了」,从不保证「有人读、有人因此变好」。

### 北极星判据打分(6 项,每项 1-5 分)

1. **落位**——精确落在使用/价值段,不是供给段。
2. **自动化免疫**——挂一条永不失败的定时任务会不会让它永久满分。
3. **场景契合**——是否对应项目名片里的「想做什么」与「最像的对标」。
4. **定义精确**——有没有清晰的「怎么算作达成」,不是模糊描述。
5. **采集诚实**——A/B/C 判得对不对,采集方案是不是真的,不为了显得体面瞎选。
6. **难造假 + 反指标**(见下)。

任一项 ≤2 分的候选直接淘汰,不进入起草。

**反指标硬性要求**:每条候选北极星必须配一条「如果只优化这条指标会被悄悄牺牲的东
西」——如「周活跃用户数」配「客诉率/退款率」,防止靠骚扰通知刷活跃。反指标不进
`.bw/metrics.toml`,只写进指标说明作护栏,下次复核北极星先看它有没有恶化。引领指标
同构:每条引领指标也配一条反指标(如「每周合入的 MR 数」配「评审通过率/回滚率」)。

**故意的坏候选对照**:草拟北极星前,先列出至少 2 个「看起来合理但会被上面 6 项判据
刷掉」的坏候选,写清楚具体是哪一项判据把它挡下——逼自己把黑名单套在真候选身上,不
是空对空背诵。

**BDFE 输入结构**(拆「使用」段的补充视角,不是替代):Breadth(有多少用户在用)、
Depth(每次用得多深)、Frequency(多久用一次)、Efficiency(达成目标花多少步/多少时
间)。北极星常是这四维里的一个乘积或复合。四维选不出候选时,回落三段拆解。

**北极星与商业指标的传导链校验**:北极星起草完,写一句清楚的因果链——「这条北极星
如果提升,会怎样传导到项目的商业/存续指标(收入、留存付费、口碑、下一轮资源)」。
传导链讲不通就退回重写;如实标注这条链目前是已有真实数据验证过,还是仅逻辑推演。

### 滞后/引领指标:强制判定与质量门

逐指标先过判定题,不凭直觉贴标签:当下/事前可被直接影响、且对滞后指标有预测性 →
引领指标;只能在结果发生之后才测得到、此刻改不了 → 滞后指标。两条都答不上「是」的
候选(纯活动量)不配称引领,退回重定义或舍弃——硬塞进「引领」是不诚实分类。

交付前打一次 0-40 质量门自评,写进指标说明,<24 分退回重做:

| 判据(每项 0-10) | 检验问题 |
|---|---|
| 分类诚实 | 有没有把不满足强制判定的指标硬贴「引领」标签? |
| 预测性 | 引领指标的变化能不能在滞后指标之前先看到征兆? |
| 阈值真实 | 目标值是否用项目真实历史数据校准,不是拍脑袋? |
| 防作弊完整 | 是否每条引领指标都配了成对反指标,不是只挑好写的配? |

### 起草步骤

1. **读输入**:项目名片 `.bw/PROJECT.md`(想做什么 / 最像的对标 / 北极星那一句)+
   `docs/competitive-analysis.md`(若存在;不存在就在指标说明里写一句「本轮无竞品分
   析报告输入」)+ 项目仓既有的采集脚本与指标体系。有既有体系,三层指标优先对齐映
   射到它的名字与分层,不是另起炉灶。
2. **拆三段**,明确指出北极星落在使用段还是价值段。
3. **起草北极星**(恰好一条):名称 + 定义(精确到「怎么算作达成」),过黑名单与 6
   项打分。
4. **起草滞后指标**(建议 2-4 条):每条给目标(迷你门槛,如 `≥5` `≤24h` `清零`),
   阈值用项目真实历史数据校准,不拍一个当前值远超的下限。
5. **起草引领指标**(建议 2-4 条):过强制判定题,优先复用项目既有过程指标。
6. **给每条判 A/B/C**(第一节),再定采集方式(第二节)——顺序不能反:先判历史能不
   能重算,再谈用什么采。
7. **落文件**:写进 `<workspace>/.bw/metrics.toml`,格式照本篇开头指的那份正本。
8. **写指标说明**:`<workspace>/docs/metrics.md`,含输入摘要、北极星判据打分、≥2 个
   被拒坏候选、北极星与引领指标的反指标、质量门实得分(≥24),以及**每条指标的
   A/B/C 判定和判定理由**(判 B 的必须写清楚「查过什么、只有当前值」)。

## 增量校准(现行格式、三层已有内容时)

不重新走起草,只做四件事:

1. **补缺**:三层里若有明显缺口(比如只有北极星没有滞后指标),按「起草步骤」对应
   那一步补,新条目同样要过打分/判定题。
2. **重判一遍 A/B/C**:上次判 B 或判手填的,这次再按第一节找一遍带时间戳的接口——
   接口会变,上次找不到不等于这次也找不到。
3. **修采不到的**:脚本跑不通、连着采集失败的,当场跑一遍看真实报错,按第二节修;
   修不了就如实写清楚卡在哪。
4. **不重排已定的北极星**,除非人在第三步「引导出本周」的对话里明确提出要重推——重
   推走完整起草的北极星部分,不在本技能内自作主张。

## 落文件与交付

改动落在 `<workspace>/.bw/metrics.toml` 和 `<workspace>/docs/metrics.md`,以及新写
或改过的 `.bw/scripts/` 下的脚本。**本步骤不单独提交**——和运作活①第四步的文件合成
一次提交,MR 由第四步统一开。

原地按「层级 + 名字」更新,不新建重复条目、**不改名字**(改名字等于新建一条指标,历
史读数会跟丢)。

## DoD

- `.bw/metrics.toml` 结构合法,恰好一条北极星,能对照竞品分析或项目名片说清楚「为什
  么是这条」。
- **每条指标都有明确的 A/B/C 判定**,判 B 或手填的都写了「查过什么才这么判」。
- 每条走脚本的指标,脚本在这次会话里**真跑过一次**,输出是合法 JSON;跑不通的如实
  标注,不假装接上了。
- 每条手填指标都有一条「能不能写成脚本」的当次结论(能/暂时不能缺什么/永远不能)。
- 首次起草时 `docs/metrics.md` 存在且含:6 项判据打分、≥2 个坏候选记录、北极星与引
  领指标各自的反指标、质量门实得分(≥24)。
- 增量校准时,已定北极星的名称/定义未被改动过。
- 仍然没数的指标,每条都有诚实说明:为什么采不到、最便宜的下一步是什么。

## 常见坑

- **想当然地判 B**。「这个接口只给当前值」——查过了吗?GitHub star 数就是活例子
  (第一节),看起来只有当前值,其实带一个 Accept 头就能拿到每个 star 的时间戳,是
  A 类。判 B 之前必须真的找过一遍。
- **写 `.bw/connectors.toml`**。V4 没有这个文件、没有「连接器」这一层。一条指标直
  接指向一个脚本。
- **脚本把结果写进一个文件,而不是打到标准输出**。V4 只认**标准输出**的 JSON,写文
  件不算数——V3 恰恰相反,别照老经验写。
- **脚本里硬编码时间范围**。窗口是 buddy 传进来的,硬编码会让走势图长期对不上还没
  人发现。
- **采不到就写 0**。0 是一个真实数值,「没采到」不是——写 0 会让一条断掉的采集看起
  来像一条真实的坏消息。
- **把工程活动量塞进北极星**——每次起草前重读虚荣指标黑名单 + 自动化免疫检验。
- **把供给当价值**——「每天出一份摘要」这类供给动作太像成果,容易被直接当北极星,
  而不去追问有没有人真的打开、读完、因此变好。
- **顺手把「采不到」的指标改成另一条采得到的指标**——这是伪装成绑数据的找指标退
  化,回头交给第三步「引导出本周」的对话重新评估,不在本技能里代劳。
- **每周替人抄一次手填的数,却从不问能不能写成脚本**——那是把 agent 当抄写员用。
- **增量校准时手痒把北极星也重推了一遍**——没有人在第三步明确要求,别碰已定的北
  极星。
