# 规格即测试 (spec-to-tests)

## 何时用

构建段从 SPEC 落到实现之前(先翻译验收标准,再写代码);以及评审阶段
逐条核对验收标准时。

## 步骤

1. SPEC 里每条验收标准编号(AC-1, AC-2, …);写实现前先把它翻译成测试名(如 `ac1_reports_dead_relative_link`)。
2. 无法翻译成测试的验收标准是坏标准——回头改写它,而不是跳过。
3. 实现只做到让测试通过为止,不做规格外功能。
4. 提交前 `cargo test` 全绿是硬门禁;失败输出原样留档,不美化。

## 反例

「系统应当足够健壮」——翻译不成任何测试名,说明它不是验收标准而是感想,
回去改写成可判定的那一条。

## 在 Claude CLI 会话里如何协作

你在一段可见的 Claude 会话里完成这件活,需要多个视角时自己调 SubAgent。

**主 Agent 负责什么**:推进规格 → 任务分解 → 实现 → 评审合入全链;产出落为 docs/SPEC.md(含编号验收标准 AC-1/AC-2…)、docs/TASKS.md、docs/REVIEW.md 和真实代码。

**哪些环节调独立 SubAgent**:
- 独立评审:实现完成后,调一个只拿 docs/SPEC.md 的验收标准和代码 diff 的 SubAgent 做评审——它不看你的实现过程,只对照验收标准逐条判通过/未通过 + 依据。这是本阶段的关键分工:写实现的人和评审的人不是同一视角。

**交接什么产物**:评审 SubAgent 交回 docs/REVIEW.md(每条验收标准:通过/未通过 + 依据),附真实跑的 cargo fmt/clippy/test 输出。主 Agent 据此修 bug 再提交。

**何时回用户确认**:SPEC.md 写完后、动手实现前,给用户看一眼规格——这是你要做的东西吗。评审结论出来后报告用户,有未通过项就修完再走。

**失败或证据不足停哪**:验收标准翻译不成测试名就回头改写标准(那是坏标准,不是跳过的理由);测试红就停下修,不美化输出;评审未通过的项不假装通过。

**完成标准**:docs/SPEC.md 每条验收标准有对应测试且全绿;docs/REVIEW.md 含真实 CI 输出;有一次 git commit 含实现与测试。
