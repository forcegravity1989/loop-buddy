# 新用户漏斗走查 (fresh-eyes-funnel)

## 何时用

运营推广段诊断「发现 → 安装 → 首次使用 → 再次使用」漏斗时;以及上线
改动后做前后对照验证时。

## 步骤

1. 以从未见过本项目的人的视角,真实执行漏斗每一步,不跳步、不脑补。
2. 只记录你真实遇到的摩擦(命令报错、文档缺失、参数不明),不臆想用户。
3. 一次实验只改一个变量,改动前后用同一条真实命令对照。
4. 没有真实流量就如实做「前后对照」,不假装有 A/B 分流。

## 反例

「新用户大概会觉得 README 不够清楚」——你没真走一遍,这是臆想的用户。
去真的跑一次安装,把报错原样贴回来。

## 在 Claude CLI 会话里如何协作

你在一段可见的 Claude 会话里完成本阶段工作,需要多角色时自己调 SubAgent,buddy 不再逐阶段脚本驱动。

**主 Agent 负责什么**:推进漏斗诊断 → 实验设计 → 上线改动 → 放大或废弃全链;产出落为 docs/funnel.md、docs/growth-experiment.md、docs/growth-verdict.md 和真实改动。

**哪些环节调独立 SubAgent**:
- 新用户走查:调一个**不拿**项目上下文的 SubAgent(这是关键——它就是新用户),只给它安装说明和一条「走一遍发现→安装→首用」的指令。它遇到的摩擦就是真实摩擦,因为它真的没见过这个项目。产回每一步的报错和卡点。

**交接什么产物**:走查 SubAgent 交回 docs/funnel.md(每步真实摩擦,含报错原样)。主 Agent 据此设计最小改动实验并实施。

**何时回用户确认**:摩擦清单出来后给用户看——先治哪个。实验设计写完后确认再动手。结论(放大/保留/废弃)出来后报告用户。

**失败或证据不足停哪**:没有真实流量就如实做前后对照,不假装有 A/B 分流;走查没遇到摩擦就如实写「未发现明显摩擦」,不编造;改动后重走仍有摩擦就如实报,不粉饰。

**完成标准**:docs/growth-verdict.md 存在并含前后对照的真实输出摘录;有一次 git commit 含改动。
